# Delta Lake

오브젝트 스토리지의 [[Apache Parquet]] 파일 위에 **트랜잭션 로그**를 얹어, 데이터 레이크에 ACID 트랜잭션·스키마 관리·
Time Travel을 주는 오픈 테이블 포맷. [[데이터 레이크하우스]]를 구현하는 수단으로 Part 1에서 유일하게 다뤄진다.

## 무엇을 해결하나

| 레이크의 문제 | Delta Lake의 답 |
|---|---|
| 한 줄 수정에도 1GB 파일 재작성 | 바뀐 파일만 새로 쓰고 로그에 교체를 기록 |
| 쓰는 중에 읽으면 깨진 데이터 | 커밋되기 전 파일은 로그에 없으니 읽는 쪽에 보이지 않는다 |
| 작은 파일 폭증 | 작은 파일 병합(compaction), Z-Ordering |
| 스키마 강제 없음 → 늪 | 스키마 강제(enforcement) + 명시적 진화(evolution) |
| 실수로 지우면 복구 불가 | Time Travel로 과거 버전 조회·복구 |

## 트랜잭션 로그

| 항목 | 내용 |
|---|---|
| 위치 | 테이블 루트 아래 `_delta_log/` |
| 커밋 파일 | 버전마다 JSON 하나. 이름은 버전을 **20자리로 0-패딩** — `00000000000000000000.json`, `00000000000000000001.json`, … |
| 내용 | 메타데이터 변경, 파일 추가(add)·제거(remove) |
| 현재 상태 | 로그를 순서대로 재생해 **현재 유효한 파일 목록**을 얻는다 |
| 체크포인트 | 로그를 요약한 스냅샷. 매번 처음부터 재생하지 않게 한다. 참조 구현의 기본 주기는 10커밋 |
| 동시성 | 낙관적 동시성 제어 — 충돌을 감지하면 재시도 |

[Delta Lake PROTOCOL.md https://github.com/delta-io/delta/blob/master/PROTOCOL.md ; 기본 체크포인트 간격
`checkpointInterval = 10`은 참조 구현의 설정값. 2026-09-14 확인]

## 설계의 요점

**데이터 파일은 불변으로 두고, "지금 테이블을 이루는 파일이 무엇인가"만 로그로 관리한다.** *(위키의 정리)*

- **원자성** = 로그에 커밋 파일 하나가 생기느냐 마느냐.
- **Time Travel** = 로그를 과거 버전까지만 재생.
- 그래서 학습 시점의 데이터 스냅샷을 **복사 없이** 고정할 수 있다. → [[데이터와 모델 버전 관리]]

## ACID

| 성질 | 은행 송금으로 |
|---|---|
| 원자성 | 출금만 되고 입금이 실패하면 전체 취소 |
| 일관성 | 잔액 0원 이상, 없는 계좌로 송금 불가 |
| 고립성 | 송금이 끝나기 전 조회는 송금 전 잔액 |
| 내구성 | "송금 완료" 직후 전원이 꺼져도 내역 보존 |

## 5가지 기둥 (강의)

트랜잭션 로그 · 스냅샷과 체크포인트 · 스키마 관리 · 데이터 최적화 · 오픈 스토리지(Parquet, 벤더 비종속)

## 주의

- ⚠️ 강의의 "데이터 최적화: Compaction(압축)" — compaction은 작은 파일 **병합**이지 압축(compression)이 아니다.
- 오래된 데이터 파일을 정리하면 Time Travel로 돌아갈 수 있는 과거가 짧아진다 — 운영상의 한계는 Part 1에서 다루지 않는다.
- 같은 문제를 푸는 다른 오픈 테이블 포맷(Apache Iceberg·Apache Hudi)은 Part 1에 이름이 나오지 않는다. Iceberg는 Netflix
  사례의 싱크로만 한 번 등장한다([[AI DE 강의 1-16 AI 파이프라인 구축 사례]]).
