# 레퍼런스 카운팅과 마크 앤 스윕

「GC 알고리즘을 레퍼런스 카운팅과 마크 앤 스윕 기준으로 설명해 달라」는 질의에서 나온 비교. [[가비지 컬렉션]]의 두 계열 표를
풀어 쓰고, 실제 런타임이 두 방식을 어떻게 섞는지 1차 자료로 확인했다.

## 한 문장씩

- **레퍼런스 카운팅(RC)** — 객체마다 「나를 가리키는 참조가 몇 개인가」를 세고, 0이 되는 순간 해제한다. 묻는 것은 **몇 명이 잡고 있나**.
- **마크 앤 스윕** — 가끔 멈추고 GC Root에서 참조를 따라가며 닿는 객체에 표시(mark)한 뒤, 표시 없는 것을 전부 회수(sweep)한다.
  묻는 것은 **Root에서 닿나**. 넓게는 tracing 계열의 한 방식이다.

비유: 메모리는 장난감 방, 객체는 풍선, 참조는 끈이다. RC는 풍선마다 끈 수를 달아 두고 0이 되면 바로 치운다. 마크 앤 스윕은
청소 시간에 아이들 손(Root)에서 끈을 따라가며 스티커를 붙이고, 스티커 없는 풍선을 쓸어 담는다. *(위키의 설명)*

## 비교

| | 레퍼런스 카운팅 | 마크 앤 스윕 |
|---|---|---|
| 판단 기준 | 참조 수 = 0 | Root에서 도달 불가 |
| 언제 회수 | 마지막 참조가 사라지는 즉시 | GC 사이클에 한꺼번에 |
| 순환 참조 | **회수 못 함** → 누수 | 회수함 (Root에서 안 닿으므로) |
| 비용이 드는 곳 | 참조가 바뀔 때마다 카운트 갱신. 멀티스레드면 원자적 연산이 필요 | 산 객체 순회(mark) + 힙 전체 훑기(sweep) |
| 멈춤 | 짧고 흩어져 있다. 단, 큰 객체 그래프가 한꺼번에 0이 되면 연쇄 해제가 길어질 수 있다 *(통념, 1차 출처 미확인)* | 전통적으로 Stop-The-World. 동시 마킹으로 줄인다 |
| 해제 시점 | 예측 가능 (소멸자·자원 정리에 유리) | GC가 돌 때까지 알 수 없다 |
| 객체 이동 | 없음 | mark-sweep 자체는 없음 → 단편화. 그래서 compact·복사와 섞는다 |

**둘은 대립이 아니라 쌍대다.** Bacon 등은 tracing이 **산 객체(matter)** 를, RC가 **죽은 객체(anti-matter)** 를 다루는 쌍대 관계라고
보이고, 고성능 수집기(지연 RC, 세대별 GC 등)는 모두 둘의 **혼합**이라고 정리했다. [David F. Bacon, Perry Cheng, V.T. Rajan,
「A Unified Theory of Garbage Collection」, OOPSLA 2004, pp.50–68, https://dl.acm.org/doi/10.1145/1028976.1028982 , 2026-09-27 확인]

## 실제 런타임은 섞어 쓴다

| 런타임 | 기본 방식 | 순환 참조 처리 | 근거 |
|---|---|---|---|
| **CPython** | RC | 세대별 **순환 GC**가 RC를 보완한다 (세대 3개) | ① |
| **CPython 3.14.0–3.14.4** | RC | 순환 GC가 **점진적(incremental)** 으로 바뀌었다가, 운영 환경 메모리 압박 보고로 **3.14.5에서 3.13의 세대별 GC로 되돌렸다** | ② |
| **CPython free-threaded** | biased RC — 소유 스레드는 비원자적 지역 카운트, 다른 스레드는 원자적 공유 카운트 | 순환 GC | ③ |
| **Swift** | ARC (컴파일러가 넣는 RC) | **수집기가 없다** — 프로그래머가 `weak`·`unowned`로 순환을 끊는다 | ④ |
| **JVM (HotSpot)** | tracing | 해당 없음 | Young은 복사, Old는 mark-compact — [[가비지 컬렉션]] · [[가비지 컬렉터]] |
| **V8** | tracing | 해당 없음 | Young은 semi-space 복사(scavenger), Major GC는 mark → sweep(free-list) → 선택적 compact, 동시 마킹 ⑤ |
| **Go** | tracing | 해당 없음 | **동시·비이동 mark-sweep**. 문서에 세대 구분 언급 없음 ⑥ |

- ① Python 3.14.7 문서, 「gc — Garbage Collector interface」: "Since the collector supplements the reference counting already used in
  Python, you can disable the collector if you are sure your program does not create reference cycles."
  https://docs.python.org/3/library/gc.html , 2026-09-27 확인
- ② 「What's New In Python 3.14」, https://docs.python.org/3/whatsnew/3.14.html , 2026-09-27 확인
- ③ PEP 703 「Making the Global Interpreter Lock Optional in CPython」(Final), https://peps.python.org/pep-0703/ , 2026-09-27 확인
- ④ 「The Swift Programming Language」, Automatic Reference Counting 장: 두 인스턴스가 서로를 강하게 참조하면 "never gets to a point
  where it has zero strong references", 해결은 "weak or unowned references".
  https://docs.swift.org/swift-book/documentation/the-swift-programming-language/automaticreferencecounting/ , 2026-09-27 확인
- ⑤ Peter Marshall, 「Trash talk: the Orinoco garbage collector」, V8 블로그, 2019-01-03, https://v8.dev/blog/trash-talk , 2026-09-27 확인
- ⑥ 「A Guide to the Go Garbage Collector」: "Go's GC uses the mark-sweep technique", "Go has a non-moving GC", "does most of its work
  concurrently with the application". https://go.dev/doc/gc-guide , 2026-09-27 확인

**읽는 법:** 「Java는 마크 앤 스윕」처럼 말하면 틀린다([[Java 면접 3 GC]] 정정 참고). 순수 mark-sweep을 기본으로 쓰는 쪽은 이 표에서
Go이고, V8은 Old 영역에서 sweep을 쓰되 compact를 섞으며, HotSpot은 sweep 대신 compact·복사를 쓴다.

## 언제 무엇이 맞나

- **RC** — 해제 시점이 결정적이어야 할 때(파일·소켓 같은 자원을 스코프 끝에서 닫기), 멈춤이 흩어져야 할 때(UI·모바일). 대가는 모든
  참조 대입에 붙는 카운트 비용과 순환 참조를 사람 또는 보조 수집기가 처리해야 한다는 것.
- **tracing(마크 앤 스윕 계열)** — 할당이 많고 수명이 짧은 객체가 쏟아질 때. 대부분 죽는 Young 영역은 산 객체만 따라가면 되니 싸다.
  대가는 멈춤(→ [[지연 시간과 처리량]])과 회수 시점을 모른다는 것.

DE 연결: 스트리밍 적재의 **참조 카운트 기반 파일 정리**(스냅샷이 참조하는 데이터 파일 수를 세서 0이면 삭제)와 **만료 스냅샷 기준으로
도달 불가 파일을 찾는 orphan 정리**는 같은 두 발상이다. 뒤쪽이 실패한 커밋처럼 「순환」 대신 「아무도 기록하지 않은」 파일까지 잡는다는
점도 닮았다. *(위키의 연결, 특정 테이블 포맷의 구현으로 확인하지 않음)*
