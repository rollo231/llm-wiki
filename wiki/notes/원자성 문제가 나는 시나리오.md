# 원자성 문제가 나는 시나리오

질문: "원자성 문제는 어떤 상황에서 생기나?" [[가시성 문제는 지금도 생기나]]에 이어 직접 재현해 봤다.

짧게 답하면, 읽고 판단·계산하고 쓰는 사이에 다른 스레드가 끼어들 수 있으면 생긴다. 코드가 한 줄인지는 상관없다. 위키가 분류해 보면 모양은 네 가지다.

## 실험 (2026-09-27, OpenJDK 25.0.2, macOS arm64)

스레드 둘이 각각 1,000만 번씩 더한다. 기대값은 20,000,000이다.

| 방식 | 결과 (2회 실행) |
|---|---|
| `int` 필드 `++` | 10,658,163 · 9,989,143 |
| `volatile int` 필드 `++` | 11,090,749 · 10,613,017 |
| `synchronized` 블록 안에서 `++` | 20,000,000 |
| `AtomicInteger.incrementAndGet()` | 20,000,000 |

- 절반 가까이 사라졌다. 두 번째 실행의 `int++`는 한 스레드 몫(1,000만)보다도 적다. JIT가 루프 안의 읽기·쓰기를 묶어 버리면 한쪽 스레드가 한동안 더한 값을 통째로 덮어쓸 수 있다. 기계어는 보지 않았으므로 이 설명은 추론이다.
- `volatile`은 원자성을 주지 않는다. 매번 읽고 매번 쓸 뿐, 그 사이에 끼어드는 것은 막지 않는다. 가시성과 원자성이 다른 문제라는 것을 이 줄이 보여 준다([[동시성 문제]]).

두 번째 실험: 두 스레드가 동시에 "`containsKey`로 없는지 보고, 없으면 `put`"을 한다(2,000회 반복). 맵은 `ConcurrentHashMap`이다.

| 방식 | 초기화가 두 번 일어난 횟수 |
|---|---|
| `if (!m.containsKey(k)) m.put(k, v)` | 187 / 2000 |
| `m.computeIfAbsent(k, ...)` | 0 / 2000 |

스레드 안전한 컬렉션을 써도 난다. 메서드 하나하나는 원자적이지만 두 호출을 이은 것은 원자적이지 않다.

## 네 가지 모양

| 모양 | 예 | 끼어드는 틈 | 고치는 법 |
|---|---|---|---|
| 읽고-고치고-쓰기 (read-modify-write) | `count++`, `total += x`, 조회수·재고 카운터 | 읽은 뒤 쓰기 전 | `AtomicInteger`·`LongAdder`, `synchronized` |
| 확인 후 행동 (check-then-act) | 없으면 넣기, 지연 초기화(싱글턴), 잔액 확인 후 출금, 파일 없으면 만들기 | 확인한 뒤 행동하기 전 | 확인과 행동을 한 연산으로: `computeIfAbsent`·`putIfAbsent`, 락으로 둘을 감싸기 |
| 여러 값을 함께 바꾸기 (불변식) | 계좌 A에서 빼고 B에 더하기, `lower`·`upper` 범위의 두 필드 | 첫 쓰기와 둘째 쓰기 사이. 다른 스레드가 중간 상태를 본다 | 같은 락으로 쓰기와 읽기를 모두 감싸기, 또는 불변 객체 하나로 묶어 참조를 한 번에 바꾸기 |
| 64비트 값 하나 쓰기 | `volatile` 없는 `long`·`double` 필드 | 32비트 두 조각 사이 | `volatile`, 또는 `AtomicLong` |

- 셋째 줄은 각 쓰기가 원자적이어도 난다. 깨지는 것은 필드 사이의 약속이다. 위 실험에서 재현하지는 않았다.
- 넷째 줄은 명세만의 이야기에 가깝다. JLS §17.7: "a single write to a non-volatile `long` or `double` value is treated as two separate writes: one to each 32-bit half." 다만 쪼갤지는 구현이 정하고("implementation-specific"), 명세도 피하라고 권한다. 참조 쓰기는 언제나 원자적이다. 64비트 HotSpot에서 실제로 쪼개지는지는 확인하지 않았다. [Oracle, 「The Java Language Specification」 Java SE 21 §17.7, https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.7 , 2026-09-27 확인]

## DE·백엔드에서 같은 모양

이 절의 연결은 위키가 지은 것이다. 첫째 줄은 DB의 lost update(`SELECT` 뒤 `UPDATE`)와 같다([[동시성 문제]]). 둘째 줄도 DB에 그대로 있다. "없으면 `INSERT`"를 두 요청이 동시에 하면 중복 행이 생기고, 고치는 법도 같은 모양이다. 유니크 제약과 `INSERT ... ON CONFLICT`처럼 확인과 행동을 한 문장으로 합친다. 파이프라인의 멱등성 문제도 여기서 나온다([[멱등성]]).

## 면접에서

"`count++`는 읽기·더하기·쓰기 세 단계라서"까지는 누구나 말한다. 그다음에 덧붙일 것:

1. `volatile`로는 안 된다는 것을 먼저 말한다. 가시성과 원자성을 가르는 질문이 거의 꼭 온다.
2. check-then-act를 예로 든다: "`ConcurrentHashMap`을 써도 `containsKey` 다음 `put`은 경쟁한다. `computeIfAbsent`를 쓴다."
3. 고치는 법을 비관적(락)과 낙관적(CAS) 둘로 나눈다([[동기화 기법]]).
