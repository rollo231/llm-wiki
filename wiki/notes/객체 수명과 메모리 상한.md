# 객체 수명과 메모리 상한

「Old 영역이 꽉 차면 설계부터 잘못된 것인가」라는 질의에서 나온 분석. GC가 보여 주는 증상에서 출발해 객체를 어떻게 설계해야 하는지까지 이어 본다. GC의 동작 자체는 [[가비지 컬렉션]]에 있다.

## Old가 찬다는 것의 의미

Old가 차는 것은 정상이다. JVM은 힙을 채워 쓰다가 모자랄 때 치우므로 Old 사용량은 원래 **톱니 모양**이다. G1은 아예 다 차기 전에 움직인다. Old 점유(힙 대비 비율)가 IHOP(시작값 45%, Adaptive IHOP가 조절)를 넘으면 동시 마킹을 시작하고 Mixed GC로 미리 치운다(→ [[가비지 컬렉터]], JDK 25 `-XX:+PrintFlagsFinal` 기본값으로 확인).

봐야 할 것은 **GC 후의 바닥선(live set)**이다.

| 모양 | 뜻 | 무엇을 고치나 |
|---|---|---|
| 톱니, 바닥이 **일정** | 정상 | 없음 |
| 톱니, 바닥이 **계속 오름** | **누수**. 다 쓴 객체를 누군가 참조하고 있다 | 코드 버그. 아래 안티패턴 |
| 바닥은 일정한데 **너무 빨리 참** | **조기 승격**. 금방 죽을 객체가 Survivor를 넘쳐 Old로 간다 | 튜닝. Young·Survivor 크기, 할당량 |
| 바닥 자체가 **힙에 가까움** | 정말로 필요한 데이터가 힙보다 크다 | **설계**. 데이터를 메모리에 올리는 방식 |

조기 승격의 근거: "If survivor spaces are too small, then the copying collection overflows directly into the old generation." [Oracle, 「HotSpot Virtual Machine Garbage Collection Tuning Guide」 JDK 21, Factors Affecting Garbage Collection Performance, https://docs.oracle.com/en/java/javase/21/gctuning/factors-affecting-garbage-collection-performance.html , 2026-09-27 확인] 네 모양으로 나눈 것 자체는 운영 경험에서 나온 정리다. *(위키의 종합)*

구분하는 법: GC 로그(`-Xlog:gc*`)에서 **GC 후** 힙 사용량의 추세를 보고, `jstat -gcutil <pid> 1s`로 Old(O 열)가 어디까지 내려가는지와 Full GC 횟수(FGC)를 본다. 바닥이 오르면 힙 덤프를 떠서 Eclipse MAT의 Dominator Tree와 Path to GC Roots로 누가 붙잡고 있는지 찾는다(→ [[가비지 컬렉션]] 모니터링과 OOM 대응).

## 설계 원칙

> 객체는 **목적에 맞는 수명**을 갖게 하고, 메모리 사용량은 **입력 크기와 무관하게 상한이 있게** 설계한다.

- **오래 들고 있는 것 자체는 잘못이 아니다.** 캐시, 커넥션 풀, 스레드 풀, 설정, 싱글턴 빈은 일부러 오래 산다. 따질 것은 두 가지다. 그 객체가 왜, 언제까지 살아야 하는지 설명할 수 있는가. 크기에 상한이 있는가.
- **한 번에 올리는 것 자체도 잘못이 아니다.** 코드 테이블 몇천 건을 `Map`으로 들고 있거나, [[Apache Spark]]에서 작은 테이블을 broadcast join하는 것은 오히려 빠르다. 문제는 **데이터가 늘면 메모리도 같이 느는** 구조다.
- **Java의 해제는 「참조를 놓는 것」이다.** 지역 변수는 메서드가 끝나면 사라지니 범위를 좁게 쓰면 대부분 해결된다. 오래 사는 곳(컬렉션, 캐시, 리스너 목록)에 넣은 것만 직접 빼 준다.
- **짧게 사는 객체는 마음껏 만든다.** Minor GC 비용은 **산** 객체 수에 비례하므로(→ [[가비지 컬렉션]] 세대별 GC) 금방 죽는 객체는 거의 공짜로 치워진다.
- **메모리가 아닌 자원은 GC에 맡기지 않는다.** 파일, 소켓, DB 커넥션은 `try-with-resources`로 명시적으로 닫는다.

## 하지 말아야 할 것 (안티패턴)

| 안티패턴 | 왜 문제인가 | 대신 | 근거 |
|---|---|---|---|
| **상한 없는 캐시** (`static Map`에 넣기만) | GC Root인 static에서 계속 닿아 영원히 못 치운다 | 크기 상한 + 만료 정책(LRU, TTL). 키 수명에 맞출 수 있으면 `WeakHashMap` | ① |
| **등록만 하고 해제하지 않는 리스너·콜백** | 등록 목록이 객체를 붙잡아 계속 쌓인다 | 해제 API를 짝으로 두고 호출한다. 약한 참조로 보관한다 | ① |
| **스레드 풀에서 `ThreadLocal`을 `remove()` 없이 쓰기** | 값은 스레드가 살아 있는 동안 남는데, 풀의 스레드는 죽지 않는다 | 작업이 끝나면 `finally`에서 `remove()` | ② |
| **입력에 비례해 한 번에 올리기** (전체 조회를 `List`로, Spark `collect()`) | 데이터가 커지는 날 OOM | 스트리밍, 페이징, 청크 처리. Spark는 `take(n)`이나 분산 쓰기 | ③ |
| **가벼운 객체를 풀로 재사용** | 오래 사는 객체가 늘어 Old를 채우고, 동시성 병목도 생긴다 | 그냥 `new`. 풀은 커넥션처럼 만들기 비싼 것만 | ④ |
| **다 쓴 변수를 습관적으로 `null`** | 코드만 지저분해지고 효과가 없다 | 범위를 좁힌다. `null`은 스스로 메모리를 관리하는 클래스(스택·풀 구현)에서만 | ① |
| **`System.gc()` 호출** | 필요 없는 Full GC를 강제할 수 있다 | 호출하지 않는다. `-XX:+DisableExplicitGC`로 영향을 잰다 | ⑤ |
| **`finalize()`로 자원 정리** | 언제 도는지, 돌기는 하는지 보장이 없다 | `try-with-resources`, `Cleaner` | ⑥ |
| **증상마다 `-Xmx`만 올리기** | 누수는 늦게 터질 뿐이고 Full GC는 더 길어진다 | 위 표로 원인부터 구분한다 | [[가비지 컬렉션]] |

- ① Joshua Bloch, 『Effective Java』 3판, Item 7 「Eliminate obsolete object references」. 캐시, 리스너·콜백, 스스로 메모리를 관리하는 클래스를 누수의 세 원천으로 들고, "Nulling out object references should be the exception rather than the norm"이라고 쓴다. 원서는 확인하지 못했고, 강의 자료(EPFL CS-108, https://cs108.epfl.ch/archive/21/c/i/EffectiveJava_Item07.pdf)와 요약본으로 확인했다(2026-09-27).
- ② `java.lang.ThreadLocal` Javadoc JDK 25: "Each thread holds an implicit reference to its copy of a thread-local variable as long as the thread is alive … after a thread goes away, all of its copies … are subject to garbage collection." https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ThreadLocal.html , 2026-09-27 확인. 풀과의 조합이 누수가 된다는 것은 이 문장에서 나온 추론이다. *(위키의 연결)*
- ③ Apache Spark 4.2.0 「RDD Programming Guide」: "This can cause the driver to run out of memory, though, because `collect()` fetches the entire RDD to a single machine". https://spark.apache.org/docs/latest/rdd-programming-guide.html , 2026-09-27 확인
- ④ Brian Goetz, 「Java theory and practice: Urban performance legends, revisited」, IBM developerWorks, 2005-09-27: "Object pooling is now a serious performance loss for all but the most heavyweight of objects, and even then it is tricky to get right without introducing concurrency bottlenecks." (Wayback Machine 사본으로 확인, 2026-09-27). 2005년 글이지만 이후 JVM의 할당은 더 싸졌다.
- ⑤ Oracle GC Tuning Guide JDK 21, Other Considerations: `System.gc()` "can force a major collection to be done when it may not be necessary … and so in general should be avoided." https://docs.oracle.com/en/java/javase/21/gctuning/other-considerations.html , 2026-09-27 확인
- ⑥ JEP 421 「Deprecate Finalization for Removal」(JDK 18, Delivered): 예측할 수 없는 지연, 실행되지 않을 수도 있음, 객체 부활. 대안은 try-with-resources와 `Cleaner`. https://openjdk.org/jeps/421 , 2026-09-27 확인

## DE 연결

Spark·Kafka·Flink가 모두 JVM 위에서 도니 같은 원칙이 그대로 적용된다. 드라이버의 `collect()`와 executor의 큰 파티션 하나는 「입력에 비례해 한 번에 올리기」의 분산판이다. 이때 해법은 힙 증설이 아니라 파티션 재분할이나 분산 쓰기다(→ [[가비지 컬렉션]]). Flink의 상태를 TTL 없이 키마다 쌓는 것은 「상한 없는 캐시」와 같은 모양이다. *(위키의 연결)*

## 면접에서

「Old가 차는 건 정상입니다. 봐야 할 건 GC 후 Old 사용량의 추세입니다. 계속 오르면 누수이고, 흔한 원인은 상한 없는 캐시, 해제하지 않은 리스너, 풀 스레드의 ThreadLocal입니다. 너무 빨리 차면 조기 승격이라 Young 크기를 봅니다. 바닥 자체가 힙에 가까우면 데이터를 한 번에 올리는 설계를 의심합니다. 힙 증설은 원인을 찾은 뒤의 선택입니다.」
