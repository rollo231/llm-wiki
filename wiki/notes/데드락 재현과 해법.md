# 데드락 재현과 해법

질문: "데드락이 나는 시나리오를 재현해서 보여 달라." [[동기화 기법]]의 「synchronized의 문제점」 표에 있는 "데드락에서 못 빠져나온다"를 직접 확인했다.

## 시나리오 — 반대 방향 계좌 이체

```java
static void transfer(Account from, Account to, int amt) {
    synchronized (from) {
        sleep(50);                         // 두 스레드가 첫 락을 다 잡을 시간
        synchronized (to) { from.balance -= amt; to.balance += amt; }
    }
}
// T1: transfer(A, B, 10)   → A를 잡고 B를 기다린다
// T2: transfer(B, A, 20)   → B를 잡고 A를 기다린다
```

코드에는 잘못이 없어 보인다. 두 계좌를 잠그고 옮길 뿐이다. 문제는 잡는 순서가 호출하는 쪽의 인자 순서를 따른다는 데 있다. `sleep`은 재현을 확실하게 하려고 넣었다. 운영에서는 이 틈이 드물게 맞아떨어져서 가끔 멈추는 서버로 나타난다. 이 마지막 문장은 위키의 관찰이다.

## 실험 (2026-09-27, OpenJDK 25.0.2, macOS arm64)

| 방식 | 2초 뒤 스레드 상태 | `findDeadlockedThreads` | 잔액 (A, B) |
|---|---|---|---|
| `synchronized`, 반대 순서 | T1 · T2 모두 BLOCKED | 2개 | 100, 100 (둘 다 못 옮김) |
| `synchronized`, 순서 고정(이름순) | 끝남 | 없음 | 110, 90 |
| `ReentrantLock.tryLock(10ms)` + 무작위 물러서기 | 끝남 (재시도 T1 2번 · T2 1번) | 없음 | 110, 90 |

반대 순서일 때 JVM이 스스로 찾은 결과(`ThreadMXBean.findDeadlockedThreads()`):

```
T1: A->B waits for Dead$Account@5451c3a8 held by T2: B->A
T2: B->A waits for Dead$Account@2626b418 held by T1: A->B
```

`jstack <pid>`는 같은 것을 더 자세히 보여 준다:

```
Found one Java-level deadlock:
"T1: A->B":
  waiting to lock monitor 0x0000000c0ecc6840 (object 0x000000035fc1a830, a Dead$Account),
  which is held by "T2: B->A"
"T2: B->A":
  waiting to lock monitor 0x0000000c0ecc6920 (object 0x000000035fc1a7e8, a Dead$Account),
  which is held by "T1: A->B"
...
"T1: A->B":
	at Dead.transfer(Dead.java:16)
	- waiting to lock <0x000000035fc1a830> (a Dead$Account)
	- locked <0x000000035fc1a7e8> (a Dead$Account)
Found 1 deadlock.
```

- "waiting to lock monitor"는 경합이 생겨 두 락 모두 `ObjectMonitor`로 inflate된 뒤라는 뜻이다([[동기화 기법]]의 경량 락 절).
- `- locked` / `- waiting to lock` 두 줄이 스레드마다 엇갈려 있는 것이 데드락의 모양이다. 줄 번호(`Dead.java:16`)가 안쪽 `synchronized`를 가리킨다.
- `synchronized`로 걸린 데드락은 밖에서 풀 방법이 없다. 인터럽트해도 BLOCKED 스레드는 깨어나지 않고, 결국 프로세스를 재시작해야 한다. 위키가 정리하자면, 그래서 운영에서는 멈춘 서버의 스레드 덤프부터 뜬다.

## 락이 안 보이는 데드락: 클래스 초기화

`synchronized`를 한 줄도 쓰지 않아도 데드락이 난다. 두 클래스의 static 초기화가 서로를 부르고, 두 스레드가 각각 한쪽을 먼저 건드리면 된다. [[클래스 로딩]]의 초기화 락(JLS §12.4.2)끼리 엉키는 것이다.

```java
static class A { static final int X; static { sleep(100); X = B.Y + 1; } }
static class B { static final int Y; static { sleep(100); Y = A.X + 1; } }
// T1: A.X 를 읽는다 → A 초기화 중, B를 기다린다
// T2: B.Y 를 읽는다 → B 초기화 중, A를 기다린다
```

같은 JDK 25.0.2에서 돌린 결과는 앞의 모니터 데드락과 전혀 다르게 보였다(2026-09-27).

| 확인한 것 | 모니터 데드락(위 실험) | 클래스 초기화 데드락 |
|---|---|---|
| `Thread.getState()` | BLOCKED | RUNNABLE |
| `findDeadlockedThreads()` · `findMonitorDeadlockedThreads()` | 스레드 2개 | 둘 다 `null` |
| `ThreadInfo.getLockName()` | 락 객체가 나온다 | `null` |
| `jstack`의 "Found one Java-level deadlock" | 나온다 | 나오지 않는다 |
| 인터럽트 | 깨어나지 않는다 | 깨어나지 않는다(RUNNABLE 그대로) |

`jstack -l`에는 이렇게만 남는다.

```
"T1: init A" #25 ... cpu=0.22ms elapsed=3.23s ... in Object.wait()
   java.lang.Thread.State: RUNNABLE
	at ClinitDead$A.<clinit>(ClinitDead.java:4)
	- waiting on the Class initialization monitor for ClinitDead$B
"T2: init B" #26 ... cpu=0.20ms elapsed=3.23s ... in Object.wait()
   java.lang.Thread.State: RUNNABLE
	at ClinitDead$B.<clinit>(ClinitDead.java:5)
	- waiting on the Class initialization monitor for ClinitDead$A
```

상태는 RUNNABLE인데 CPU 시간이 0.2ms에서 늘지 않는다. 자동 탐지가 잡아 주지 않으니 사람이 스택을 읽어야 한다. 단서는 스택 맨 위의 `<clinit>`과 "waiting on the Class initialization monitor for" 줄이다. 스레드 둘이 서로의 클래스를 가리키고 있으면 이 데드락이다. RUNNABLE 스레드 수나 CPU로 멈춤을 감시하는 모니터링에도 걸리지 않는다. 이 부분은 실험에서 끌어낸 추론이고 모니터링 도구로 확인하지는 않았다.

스레드 하나로 같은 코드를 돌리면 멈추지 않는다. 대신 틀린 값이 나온다. A를 초기화하던 스레드가 B의 초기화 중에 다시 A를 요청하면 JLS 절차상 그냥 돌아가므로, B는 `final` 필드 `A.X`를 기본값 0으로 읽는다. 결과는 `A.X=2 B.Y=1`이었다.

해법은 순환을 없애는 것이다. static 초기화에서 다른 클래스의 static 상태를 부르지 않고, 상호 의존이 필요하면 지연 초기화([[동기화 기법]]의 holder 관용구)로 초기화 시점을 한쪽으로 몰아 둔다. 흔한 모양은 상위 클래스의 static 필드가 하위 클래스 인스턴스를 만드는 경우인데, 하위 클래스 초기화가 상위 클래스 초기화를 먼저 요구하기 때문이다. 이 흔한 모양은 널리 알려진 사례로 적었고 이번에 재현하지는 않았다.

## 왜 생기나 — 네 조건

데드락은 아래 넷이 동시에 성립할 때 생긴다. Coffman 외(1971)의 네 조건으로, 운영체제 교과서의 표준 설명이다. 이번에 원 논문은 열지 않았다.

| 조건 | 이 실험에서 | 깨는 방법 |
|---|---|---|
| 상호 배제: 한 번에 하나만 쥔다 | `synchronized` | 공유 자체를 없앤다(불변 객체, 스레드별 사본) |
| 쥐고 기다리기: 하나를 쥔 채 다른 것을 기다린다 | A를 쥐고 B를 기다림 | 필요한 락을 한 번에 다 잡거나, 못 잡으면 쥔 것도 놓는다(tryLock + 물러서기) |
| 빼앗을 수 없음: 남이 쥔 것을 뺏지 못한다 | 모니터는 뺏을 수 없다 | 타임아웃으로 스스로 놓게 한다(`tryLock(timeout)`) |
| 순환 대기: A → B → A | T1은 A → B, T2는 B → A | 락 순서를 전역으로 고정한다 |

실무에서 가장 흔한 해법은 넷째 조건을 깨는 락 순서 고정이다. 비용이 없고 규칙 하나만 지키면 된다. 고정할 기준은 계좌 ID처럼 변하지 않는 값이면 된다. `System.identityHashCode`도 쓸 수 있지만 두 객체가 같은 값을 가질 수 있어 그때를 위한 세 번째 락이 필요하다. Java Concurrency in Practice 10.1.2에 나오는 것으로 알려진 기법이며, 이번에 원문은 확인하지 않았다.

## 해법 비교

| 해법 | 장점 | 대가 |
|---|---|---|
| 락 순서 고정 | 공짜, `synchronized` 그대로 | 모든 코드가 규칙을 지켜야 한다. 순서를 정할 키가 필요하다 |
| `tryLock(timeout)` + 무작위 물러서기 | 순서를 몰라도 된다 | 코드가 길다. 둘이 같은 박자로 물러서면 계속 서로 양보만 하는 livelock이 생길 수 있어 무작위 대기를 넣는다 |
| 락을 하나로 합치기 | 데드락이 원천적으로 없다 | 병렬성을 잃는다 |
| 락 안에서 외부 코드(콜백·리스너) 부르지 않기 | 모르는 락과 엉키지 않는다 | 설계로 지켜야 한다 |

## DB에서도 같다

두 트랜잭션이 행 A · B를 반대 순서로 `UPDATE`하면 똑같이 걸린다. 차이는 DB가 감지해서 한쪽을 강제로 롤백한다는 것이다(PostgreSQL `deadlock detected`, MySQL InnoDB `Deadlock found when trying to get lock`). JVM의 `synchronized`는 감지만 하고(`jstack`) 풀어 주지는 않는다. 해법도 같아서, 여러 행을 갱신할 때는 기본키 순서로 잠근다([[동시성 문제]]). 이 비교는 위키가 이은 것이고, DB 메시지는 널리 알려진 문구로 적었을 뿐 이번에 재현하지는 않았다.

## 면접에서

1. 시나리오: "반대 방향 이체처럼, 두 스레드가 두 락을 서로 반대 순서로 잡을 때."
2. 조건: 네 조건을 말하고, "이 중 하나만 깨면 된다"로 잇는다.
3. 해법: "보통 락 순서를 고정합니다. 순서를 정할 수 없으면 `tryLock` 타임아웃으로 물러서게 합니다."
4. 진단: "`jstack`이나 `ThreadMXBean.findDeadlockedThreads()`가 `Found one Java-level deadlock`으로 알려 줍니다."
