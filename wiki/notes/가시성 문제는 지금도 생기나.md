# 가시성 문제는 지금도 생기나

질문: "CPU 캐시는 코히런트하다([[동시성 문제]])고 하니, 가시성 문제는 현실적으로 이제 잘 안 생긴다고 봐도 되나?"

답: **아니다. 지금도 생긴다.** 코히런시로 사라진 것은 "캐시가 서로 안 맞아서"라는 **설명**이다. 가시성 문제는 그대로다. 범인은
캐시가 아니라 최적화다. 아래 실험에서 JIT가 값을 한 번만 읽고 다시 읽지 않았다.

## 실험 (2026-09-27, OpenJDK 25.0.2, macOS arm64)

```java
public class Vis {
    static boolean running = true;          // volatile 없음
    static volatile boolean vrunning = true;
    public static void main(String[] a) throws Exception {
        boolean useVolatile = a.length > 0;
        Thread b = new Thread(() -> {
            long n = 0;
            if (useVolatile) { while (vrunning) n++; }
            else { while (running) n++; }
            System.out.println("B stopped, n=" + n);
        });
        b.setDaemon(true);
        b.start();
        Thread.sleep(1000);                 // B의 루프가 JIT 컴파일될 시간
        running = false; vrunning = false;
        b.join(3000);
        System.out.println(b.isAlive() ? "B still running" : "B stopped");
    }
}
```

| 실행 | 결과 |
|---|---|
| `java Vis` — `volatile` 없음 | A가 `false`를 쓰고 3초 뒤에도 **B가 돈다** |
| `java Vis v` — `volatile` | B가 곧 멈춘다 |
| `java -Xint Vis` — `volatile` 없음, JIT 끔 | B가 멈춘다 |

같은 하드웨어에서 `-Xint`만 바꿨는데 결과가 갈렸다. 그래서 원인은 캐시가 아니라 **JIT 컴파일**이다. 루프가 컴파일되면서
`running` 읽기가 루프 밖으로 끌어올려진 것으로 보인다(hoisting). 생성된 기계어는 보지 않았으므로 *(추론)* 이다. JMM은
happens-before가 없는 읽기에 이렇게 옛 값을 계속 주는 것을 허용한다. → [[동시성 문제]] · [[JIT 컴파일]]

## 지금도 남아 있는 원인

- **컴파일러(JIT)** — 읽기를 끌어올리거나 명령 순서를 바꾼다. 위 실험이 이쪽이다.
- **CPU** — store buffer 때문에 쓰기가 늦게, 다른 순서로 보일 수 있다. ARM(Apple Silicon, AWS Graviton)은 x86보다 순서를 더
  자유롭게 바꾸는 약한 메모리 모델이라, x86에서 우연히 되던 코드가 ARM에서 깨지기도 한다. *(일반적으로 알려진 사실이다. 이번에
  1차 자료로 재현하지는 않았다)*

## 왜 테스트에서는 안 보이나

처음에는 인터프리터로 돌고, 루프가 뜨거워진 뒤에야 컴파일된다(→ [[JIT 컴파일]]). 그래서 짧은 테스트는 통과하고, 오래 도는
운영 서버에서만 멈추지 않는 식으로 드러난다. 위 실험의 `-Xint` 결과가 곧 "컴파일 전"의 모습이다. 루프 안에 로그 출력 같은
호출을 넣으면 우연히 멈추는 일도 흔하다. 이것은 보장이 아니라 최적화가 방해받았을 뿐이다. *(위키의 관찰)*

## 그런데 실무에서 덜 마주치는 이유

흔히 쓰는 도구가 이미 happens-before를 만든다. `java.util.concurrent` 패키지 문서의 Memory Consistency Properties 절:

- "Actions in a thread prior to placing an object into any concurrent collection *happen-before* actions subsequent to the access
  or removal of that element from the collection in another thread."
- "Actions in a thread prior to the submission of a `Runnable` to an `Executor` *happen-before* its execution begins."
- "Actions taken by the asynchronous computation represented by a `Future` *happen-before* actions subsequent to the retrieval of
  the result via `Future.get()` in another thread."

[Oracle, Java SE 25 API, `java.util.concurrent` — Memory Consistency Properties,
https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/package-summary.html#MemoryVisibility ,
2026-09-27 확인] 여기에 `synchronized`·`Lock`(→ [[동기화 기법]])까지 쓰면 대부분의 코드는 가시성을 따로 신경 쓰지 않아도 된다.

그래서 문제가 나는 곳은 **공유 변수를 날것으로 직접 다루는 코드**다 *(위키의 정리)*:

- 종료 플래그 (위 실험)
- 직접 만든 지연 초기화, 특히 `volatile` 없는 double-checked locking
- 락 없이 여러 스레드가 읽고 쓰는 캐시·설정 필드

## 면접에서

"요즘 CPU는 캐시가 코히런트해서 가시성 문제가 없지 않나요?"라는 역질문에는 이렇게 답한다. "캐시는 맞춰지지만 JIT가 읽기를
끌어올리거나 순서를 바꿉니다. 실제로 `volatile` 없는 종료 플래그 루프는 JIT 컴파일 뒤에 멈추지 않고, `-Xint`로 JIT를 끄면
멈춥니다. 그래서 기준은 캐시가 아니라 JMM의 happens-before입니다."
