# 상속을 쓰는 이유

「조합이 결합도가 더 낮은데 상속을 쓰는 이유는?」 질의에서 나온 답을 정리했다. 자료([[Java 면접 5 객체지향 프로그래밍]])가 직접 주는 답은 한 줄이고, 나머지는 위키가 『Effective Java』와 JDK 소스로 보충했다.

## 자료의 답

is-a 관계가 명확하고 향후 변화가 거의 없을 때 상속을 쓴다(p85, p91). 자료는 상속의 주목적을 다형성으로 보므로, 진짜 하위 타입 관계라면 상속이 자연스럽다는 입장이다([[상속과 조합]]).

## 상속의 단점은 언제 생기나

[[상속과 조합]]의 두 단점(깨지기 쉬운 기반 클래스, 캡슐화 파괴)은 확장을 고려하지 않고 만든 구체 클래스를, 그 클래스를 통제하지 않는 쪽에서 상속할 때 생긴다. 그 페이지의 `CountingSet` 예에서 `HashSet`의 `addAll`이 안에서 `add`를 부른다는 사실은 `HashSet`이 약속한 계약이 아니었다. 그래서 하위 클래스가 그 사실에 기대면 틀리고, 기대지 않아도 틀린다.

거꾸로 말하면, 이 조건이 없는 곳에서는 상속의 비용이 작다. 아래 이유들은 모두 그 경우다.

## 상속을 쓸 만한 경우

### 1. 조합에는 위임 코드라는 비용이 있다

인터페이스와 조합으로도 다형성과 재사용을 얻는다. 그러나 Java에는 위임 문법이 없어서 감싼 객체의 메서드를 하나씩 넘겨 주는 코드를 직접 써야 한다.

```java
class CountingSet<E> implements Set<E> {
    private final Set<E> s;
    public int size() { return s.size(); }
    public boolean isEmpty() { return s.isEmpty(); }
    public boolean contains(Object o) { return s.contains(o); }
    // ... Set의 나머지 메서드 전부
}
```

상속은 이 코드 없이 구현을 물려준다. Kotlin은 `class CountingSet<E>(s: MutableSet<E>) : MutableSet<E> by s`로 위임을 언어가 대신 써 주므로, 조합의 비용 상당 부분은 언어 문법의 사정이다. 『Effective Java』 3판 Item 18은 이 전달 메서드들을 재사용 가능한 전달 클래스(`ForwardingSet`) 하나로 모아 두는 방법을 권한다.

### 2. 확장용으로 설계하고 문서화한 클래스

어디를 오버라이드하라고 정하고 그 계약을 문서화한 클래스라면, 하위 클래스가 기대는 것은 구현이 아니라 계약이다.

- 템플릿 메서드와 골격 구현: `AbstractList`의 javadoc은 읽기 전용 리스트를 만들려면 `get(int)`와 `size()`만 구현하면 된다고 적는다. 반복자, `contains`, `indexOf` 같은 나머지는 상위 클래스가 이 둘로 만든다. 인터페이스(`List`)로 타입을 정의하고 추상 클래스(`AbstractList`)로 골격을 주는 조합은 [[인터페이스와 추상 클래스]]에도 있다.
- 프레임워크 확장점: `HttpServlet`의 `doGet`, Airflow의 `BaseOperator`가 그렇다. 커스텀 오퍼레이터는 `BaseOperator`를 상속해 `execute()`를 구현하고, 재시도·템플릿 렌더링·로깅은 상위 클래스가 맡는다. 프레임워크가 정한 계약이라서 상속이 맞는 도구다.

『Effective Java』 3판 Item 19(「Design and document for inheritance or else prohibit it」)는 반대 방향도 말한다. 상속용으로 설계하지 않은 클래스는 `final`로 막거나 생성자를 숨겨 상속을 금지하라는 것이다.

### 3. 같은 사람이 양쪽을 통제한다

상위와 하위가 같은 패키지에 있고 같은 사람이 관리하면, 상위를 고칠 때 하위도 함께 고칠 수 있다. 강한 결합이 비용이 되는 것은 결합이 팀이나 라이브러리의 경계를 넘을 때다. Item 18이 상속이 안전한 경우로 드는 두 가지가 이것과 2번이다.

### 4. 상태와 생성자까지 공유한다

인터페이스에는 인스턴스 필드와 생성자가 없다. 하위 타입들이 공통 필드와 그 초기화 로직을 함께 써야 하면 추상 클래스 상속이 필요하다. 자료가 추상 클래스를 쓰는 경우로 든 조건과 같다(p103, [[인터페이스와 추상 클래스]]).

### 5. 닫힌 타입 집합을 표현한다

`sealed` 계층(JEP 409, JDK 17)은 하위 타입을 정해진 몇 개로 묶는 데 상속을 쓴다. 컴파일러가 switch 패턴 매칭이 빠짐없는지 검사한다([[다형성]]).

## 정리

기준은 결합도의 크기보다 그 결합을 누가 통제하느냐다. 상위 클래스가 확장용으로 설계됐거나, 같은 사람이 양쪽을 관리하거나, is-a가 분명하고 안정적이면 상속을 쓴다. 남이 만든 구체 클래스의 기능만 빌리고 싶으면 조합을 쓴다.

## 면접에서

「기본은 조합입니다. 다만 확장용으로 설계된 추상 클래스나 프레임워크 확장점, 그리고 같은 팀이 관리하는 진짜 is-a 관계에서는 상속이 위임 코드 없이 재사용과 다형성을 함께 줍니다. 상속의 문제는 확장을 고려하지 않은 구체 클래스를 경계 너머에서 상속할 때 생깁니다.」

## 근거

- JDK 25.0.2 `src.zip`(2026-09-27 확인): `HashSet`은 `addAll`을 오버라이드하지 않고, 물려받은 `AbstractCollection.addAll`이 원소마다 `add(e)`를 부른다. `AbstractList` javadoc: "To implement an unmodifiable list, the programmer needs only to extend this class and provide implementations for the get(int) and size() methods."
- 로컬 재현(OpenJDK 25.0.2): `CountingSet extends HashSet`에 `addAll(List.of(1, 2, 3))` → `addCount=6 size=3`.
- Joshua Bloch, 『Effective Java』 3판(Addison-Wesley, 2018), Item 18 「Favor composition over inheritance」, Item 19 「Design and document for inheritance or else prohibit it」. 원서는 확인하지 못했고 널리 인용되는 내용으로 적었다(2차 자료).
