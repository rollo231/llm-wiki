# 클래스 로딩

[[JVM]]이 `.class`의 바이트를 받아 실행할 수 있는 클래스로 만드는 과정이다. JVMS 5장은 이 과정을 **로딩 → 링크(검증 · 준비 · 해석) → 초기화**로 나눈다. 이 세 단계는 **클래스의 수명 단계이지 클래스 로더의 단계가 아니다.**

[Oracle, 「The Java Virtual Machine Specification」 Java SE 25 §5 Loading, Linking, and Initializing, https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-5.html , 2026-09-26 확인]

## 누가 무엇을 하나

| 단계 | 하는 일 | 주체 |
|---|---|---|
| **로딩** | 이름으로 클래스 파일의 바이트를 찾아 `defineClass`에 넘긴다. JVM은 그 바이트로 클래스를 도출·생성해 메서드 영역에 둔다 | 클래스 로더 + JVM의 협업 |
| **링크 — 검증** | 바이트코드가 구조적으로 올바른지 검사한다 | JVM |
| **링크 — 준비** | static 필드를 **만들고 기본값(0 · null · false)으로** 둔다. 코드는 실행하지 않는다 | JVM |
| **링크 — 해석** | 런타임 상수 풀의 심볼릭 참조(이름)를 실제 참조로 바꾼다 | JVM |
| **초기화** | `ConstantValue` 속성 값을 대입하고, static 초기화 블록과 필드 초기화 식을 모은 `<clinit>`을 실행한다 | JVM |

"준비"에서 static 필드에 **설정된 값**이 들어가는 것이 아니다. `static int x = 5;`는 준비 단계 뒤에 0이고, 초기화 단계에서 5가 된다. HotSpot 문서는 준비 단계에서 메서드 테이블도 할당한다고 적는다. [JVMS §5.3.2 · §5.4.2 · §5.5 ; OpenJDK, 「HotSpot Runtime Overview」 VM Class Loading, https://openjdk.org/groups/hotspot/docs/RuntimeOverview.html , 2026-09-26 확인]

⚠️ [[Java 면접 2 빈출 질문]] Q3은 "클래스 로더는 로딩 · 링크 · 초기화 단계로 나뉜다"고 적는다. HotSpot 문서는 이렇게 쓴다. "The VM performs constant pool resolution, linking and initialization … The loading phase is a cooperative effort between the VM and specific class loaders." 곧 클래스 로더의 몫은 로딩뿐이다.

## 언제 일어나나

- **초기화 시점은 엄격하다.** JVMS §5.5는 초기화가 일어나는 경우를 다음으로만 정한다. `new` · `getstatic` · `putstatic` ·`invokestatic` 명령의 실행, 해당 종류 `MethodHandle`의 첫 호출, 일부 리플렉션, 하위 클래스의 초기화(상위 클래스가 먼저 초기화된다), default 메서드를 가진 인터페이스를 구현한 클래스의 초기화, main 클래스.
- **로딩 · 링크 시점은 구현 재량이다.** 해석은 lazy(명령을 처음 실행할 때)로도 eager로도 할 수 있다. HotSpot은 lazy이고, 로딩 · 링크를 대개 초기화 직전까지 미룬다. 다만 검증에 필요한 클래스는 먼저 로드한다. [JVMS §5.4 ; HotSpot Runtime Overview]
- 그래서 "클래스는 처음 필요할 때 로드된다"는 말은 HotSpot의 동작으로는 맞지만 명세가 보장하는 것은 아니다. 명세가 보장하는 것은 초기화 시점이다.

*(위키의 연결)* 배포 직후 첫 요청이 느린 원인에는 JIT가 차가운 것 말고도 이 지연 로딩 · 초기화 비용이 있다. → [[JIT 컴파일]]의 「콜드 스타트와 워밍업」 절

## 내장 클래스 로더 (JDK 9 이후)

| 로더 | 로드하는 것 | API에서 |
|---|---|---|
| 부트스트랩 | 핵심 모듈(`java.base` 등) | `null` |
| 플랫폼 | 일부 Java SE · JDK 모듈. JDK 8까지의 확장(extension) 로더를 대신한다 | `ClassLoader.getPlatformClassLoader()` |
| 시스템(애플리케이션) | 클래스패스 · 모듈 패스의 애플리케이션 클래스 | `ClassLoader.getSystemClassLoader()` |

**부모 위임 모델** — 기본 `loadClass`는 이미 로드했는지 확인하고(`findLoadedClass`), 없으면 부모에게 맡기고, 부모도 못 찾을 때만 스스로 찾는다(`findClass`). 같은 이름의 핵심 클래스를 애플리케이션이 바꿔치기하지 못하게 막는 장치 가운데 하나다(이름이 `java.`로 시작하는 클래스는 플랫폼 로더와 그 조상이 아니면 `defineClass`가 `SecurityException`으로 거부한다).

단서: JDK 9부터 내장 로더는 엄격한 부모 우선이 아니다. 요청된 패키지가 어느 내장 로더의 이름 있는 모듈에 속하면 그 로더에 바로 맡긴다. 그래서 플랫폼 로더가 애플리케이션 로더에 위임하는 일도 생긴다.

[Oracle, `java.lang.ClassLoader` Javadoc JDK 25 「Run-time Built-in Class Loaders」, https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ClassLoader.html ; OpenJDK JEP 261 「Module System」 Class loaders 절, https://openjdk.org/jeps/261 , 2026-09-26 확인]

## 면접에서

- "클래스 로더가 링크와 초기화까지 한다"고 답하면, "그럼 `ClassLoader`를 직접 구현할 때 어떤 메서드를 오버라이드하나"(`findClass`) 같은 꼬리 질문에서 막힌다. 로더의 일은 **바이트를 구해 오는 것**까지라고 선을 긋는다. *(위키의 관찰)*
- 준비와 초기화의 차이는 "static 필드가 언제 0이고 언제 제 값인가"라는 질문으로 나온다.
