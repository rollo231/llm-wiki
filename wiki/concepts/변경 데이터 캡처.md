# 변경 데이터 캡처

DB의 변경(Insert·Update·Delete)을 **트랜잭션 로그 수준에서** 실시간으로 포착해 다른 시스템으로 흘려보내는 기술.

## 왜 로그를 읽나

| | 폴링(배치 추출) | 로그 기반 CDC |
|---|---|---|
| 방식 | 정해진 시간에 `SELECT`로 변경을 찾는다 | DB가 이미 쓰고 있는 트랜잭션 로그를 읽는다 |
| 소스 부하 | 반복 조회로 DB 성능 저하 | 쿼리 엔진을 거의 쓰지 않는다 |
| 신선도 | "어제 데이터" | 초 단위 |
| 전송량 | 전체 또는 대량 | 변경분만 |
| 삭제 | 지워진 행은 조회로 알기 어렵다 | Delete 이벤트가 남는다 |

[[AI DE 강의 1-07 배치 처리와 ETL·ELT]]의 추출 원칙 "소스 시스템에 절대 부하를 주지 말라"의 고급 해법이다.
(삭제 행에 대한 비교는 위키가 더한 것이다.)

| DB | 로그 |
|---|---|
| MySQL·MariaDB | Binlog |
| PostgreSQL | WAL (logical decoding) |
| Oracle | Redo Log (LogMiner) |
| MongoDB | Oplog |

## 3단계 파이프라인

**Capture → Transport → Apply** ([[AI DE 강의 1-08 CDC]])

1. **Capture** — 복제 프로토콜로 자신을 replica로 등록해 로그 스트림을 받고, 바이너리 로그를 JSON·Avro 이벤트로
   번역한다. 도구: [[Debezium]].
2. **Transport** — [[Apache Kafka]]에 담는다. 버퍼링·배압으로 타깃을 보호하고, 디스크 영속으로 유실을 막는다.
   **Kafka가 없으면 타깃 DB 장애가 CDC 전체를 멈춘다.** 가능하면 1 테이블 = 1 토픽.
3. **Apply** — 타깃 특성에 맞춰 반영한다.

## 정합성 — 세 장치가 한 세트

CDC의 품질은 연결이 아니라 **유실·순서 뒤바뀜·중복을 막는 데서** 결정된다.

| 위험 | 장치 | 예 |
|---|---|---|
| 순서 뒤바뀜 | **키 기반 파티셔닝** — Kafka는 파티션 안에서만 순서를 보장하므로 같은 Row ID는 같은 파티션으로 | 입금 +100만 뒤 출금 -50만이 뒤바뀌면 잔액 부족 에러 |
| 중복 | **멱등성** — at-least-once 전달에서 같은 이벤트가 두 번 와도 결과가 같게(upsert) | 재처리 시 같은 변경을 다시 부어도 안전 |
| 늦게 온 변경 | **이벤트 시간 기준 반영** — 더 최신 변경이 이미 반영됐으면 무시 | 순서가 뒤바뀌어도 최종 상태가 맞음 |

## 타깃 반영 전략

| 전략 | 방식 | 맞는 타깃 |
|---|---|---|
| Append-only | 변경·삭제도 새 행으로 쌓는다(이력 보존) | DW, 감사 로그 |
| Mirroring / Sync | 소스 상태를 그대로 복제(최신 상태) | 검색 엔진, 캐시 |
| Soft Delete | `deleted=true` 플래그만 갱신 | 물리 삭제가 어렵거나 비싼 HDFS·S3 |

## 스트림과 테이블

Kafka의 **로그 컴팩션**은 키별 최신 값만 남겨, 변경 이벤트 토픽을 "DB의 현재 스냅샷"으로 만든다
([[AI DE 강의 1-11 EDA와 Kafka]]). 같은 데이터를 **변경의 흐름**(Append-only)으로도, **현재 상태**(Mirroring·
컴팩션)로도 볼 수 있다.

## 쓰임새

- **OLTP → 분석 저장소 동기화** — 설계 5단계의 하이브리드 단계([[AI DE 강의 1-04 저장소의 진화 DW에서 Lakehouse까지]]).
- **MSA 데이터 동기화** — 주문 서비스는 DB에 저장만 하고, CDC가 배송 서비스로 전달한다. → [[이벤트 기반 아키텍처]]
- **검색·캐시 갱신** — 가격 변경을 Elasticsearch 인덱스에 반영하고 Redis 캐시를 무효화한다.
- **스튜디오 데이터 이동(Netflix)** — CDC 소스 커넥터 → 보강 → 스키마 진화 관리 → Iceberg 싱크
  ([[AI DE 강의 1-16 AI 파이프라인 구축 사례]]).

## 운영에서 주의할 것

- **스키마 변경** — 운영 DB 스키마가 하류 전체와의 계약이 된다. → [[스키마 진화]]
  ⚠️ [[AI DE 강의 1-08 CDC]]는 호환성 모드 정의를 뒤바꿔 설명한다.
- **로그 보존** — CDC가 오래 멈췄을 때의 결과는 DB마다 반대다. PostgreSQL은 replication slot이 WAL을 계속 붙잡아
  디스크가 찰 수 있고(`max_slot_wal_keep_size`로 상한, 기본은 무제한), MySQL은 binlog가 만료·삭제돼 커넥터가 읽던
  위치를 잃고 재스냅샷해야 한다. Part 1에는 없는 내용이다. *(위키 메모)*
  [PostgreSQL 문서 — "If max_slot_wal_keep_size is -1 (the default), replication slots may retain an unlimited amount
  of WAL files." https://www.postgresql.org/docs/current/runtime-config-replication.html · MySQL 문서 — "if a replica
  is not connected and you happen to purge one of the log files it has yet to read, the replica cannot replicate after
  it reconnects." https://dev.mysql.com/doc/refman/8.4/en/purge-binary-logs.html , 2026-09-14 확인]
