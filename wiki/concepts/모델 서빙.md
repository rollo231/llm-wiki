# 모델 서빙

학습된 모델을 **서비스가 쓸 수 있는 예측으로 내보내는 일.** [[AI DE 강의 2-05 서빙 파이프라인 설계]]의 정의로는 "추론
요청을 처리하는 실행 경로"다 — 요청을 받아 피처를 조회·계산하고, 추론하고, 응답을 돌려주는 과정이 요청마다 반복된다.
[[MLOps]] 라이프사이클의 4단계(Deployment)에 해당한다.

## 서빙 방식은 요구사항에서 정해진다

- [[AI DE 강의 2-02 MLOps와 ML 생애주기]] — "온라인 추론인지, 배치 예측인지"는 **1단계 Project Scoping**에서 정한다.
- [[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]] — "서빙 방식은 모델 문제가 아니라 시스템 선택". 같은 모델도 배치로
  서빙하면 전혀 다른 시스템이고, 이 선택이 인프라·데이터 파이프라인·운영 비용을 동시에 결정한다.

## 배치 vs 온라인

| | 배치 서빙 (비동기) | 온라인 서빙 (동기) |
|---|---|---|
| 언제 예측하나 | 주기적으로(예: 4시간마다) | 요청이 들어오는 즉시 |
| 결과 | 테이블·파일·캐시에 미리 저장 | 응답으로 바로 반환(수~수십 ms) |
| 사용 사례 | 추천 점수 사전 계산, 세그먼트, 신용 점수, 마케팅 타겟 | 사기 탐지, 광고 입찰, 개인화 추천, 이상 탐지 |
| 최적화 목표 | 높은 처리량 | 낮은 지연 시간 |
| 장점 | 비용(Spot·예약 리소스), 재시도·백필, 재현성 | 최신 입력과 사용자 행동에 즉시 반응 |
| 대가 | 예측이 낡을 수 있다 | 모델 실패 = 서비스 실패, 피처 조회 지연(강의는 "대부분"이라 하나 수치·출처 없음 → [[AI DE 강의 2-05 서빙 파이프라인 설계]]) |

이 표의 틀은 Chip Huyen의 batch vs online prediction 표에서 왔다([[Designing Machine Learning Systems]]; 강의는 출처를
밝히지 않는다 — 검증은 [[AI DE 강의 2-05 서빙 파이프라인 설계]]). 마지막 행이 곧 [[지연 시간과 처리량]]의 시소다.

## 서빙 파이프라인의 요구사항

[[AI DE 강의 2-05 서빙 파이프라인 설계]]:

- **입력은 불완전하거나 늦게 온다** — 실시간 이벤트·API 요청·사용자 컨텍스트를 전제로 설계한다.
- **지연 예산(Latency Budget)** — 백엔드 요청 경로의 일부이므로 백엔드 팀과 함께 정한다.
- **실패율이 곧 서비스 장애**, 트래픽 변동에 따른 자동 확장, 요청 단위의 안정성.

## 온라인 서빙의 구성 요소

[[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]:

```
Client → Load Balancer → Prediction Service(replica)
  → Online Feature Store / Cache 조회 → 전처리 → 추론(CPU/GPU) → 후처리·응답
  (모델 파일은 Model Artifact Storage·Registry, 요청·피처·예측은 Logging/Metrics 파이프라인으로)
```

운영 요소: p95/p99 Latency SLO, 피처 조회 실패 시 timeout·fallback, 일부 피처 스토어 장애 허용, 요청 단위 로그와 피처·예측
분포 모니터링.

## 서빙 경로의 피처

온라인 서빙에서 어려운 것은 모델보다 **피처 접근**이다.

- **접근 방식** — 실시간 계산, 사전 계산, 캐시, 외부 스토어 조회.
- **조회 비용** — 네트워크 호출, 스토리지 응답 지연, 캐시 미스, 일부 피처 누락.
- **캐싱 전략** — 변경 주기가 긴 피처는 사전 계산, 요청 단위 계산은 최소, 반복 요청은 캐시, 캐시 실패에는 fallback.

⚠️ 캐시 값·fallback 기본값이 학습 때 본 값과 다르면 스큐가 된다. *(위키의 연결)* → [[학습-서빙 스큐]]

## 배치 서빙 도구

[[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]의 평가(강의의 주장):

| 도구 | 한 줄 |
|---|---|
| Apache Airflow | DAG = 예측 파이프라인. DE 친화적, 기존 ETL과 통합, 재시도·백필 강력. ML 개념(모델 버전·실험 추적) 지원은 약함 |
| Kubeflow Pipelines | Kubernetes 기반 ML 워크플로. 학습–배포–배치 추론을 한 흐름으로, GPU 제어 용이. 순수 배치 서빙에는 과할 수 있음 |
| Flyte | 타입화된 워크플로, 재현성·캐싱 기본 제공. 러닝 커브, 생태계는 작음 |

⚠️ Flyte는 강의 이후 Flyte 2(재작성판)가 2026-08 GA가 됐다 — 상세는 [[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]의
주의·결함.

## 서빙 플랫폼의 층

강의는 네 플랫폼을 한 비교표(추상화 수준·성능·GPU·운영 난이도·확장성)에 나란히 놓지만, 이들은 **같은 종류의 물건이 아니다.**
층으로 보면 겹쳐 쓸 수 있다. *(위키의 정리)*

| 층 | 하는 일 | 예 |
|---|---|---|
| 웹 프레임워크 | 요청 수신·검증·비즈니스 로직, 서빙 로직은 직접 구현 | [[FastAPI]] |
| 모델 서버 | 모델 로딩·버전·워커 관리, 스케줄링·배칭, 배포 단위 패키지 | [[TorchServe]] · [[BentoML]] · [[Triton Inference Server]] |
| 추론 런타임·엔진 | 그래프 최적화·커널 실행 | [[ONNX]] Runtime · TensorRT · OpenVINO |

Triton은 모델 서버로서 ONNX Runtime·TensorRT 같은 런타임을 **백엔드**로 끼워 돌린다 — 아래 층과 경쟁하지 않고 그 위에 선다.
[NVIDIA Triton 문서 — "Triton Inference Server is an open source inference serving software that streamlines AI
inferencing." https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/index.html · onnxruntime_backend —
"The Triton backend for the ONNX Runtime." https://github.com/triton-inference-server/onnxruntime_backend , 2026-09-14 확인]

⚠️ 위키 정정 (2026-09-14 린트): 이 표는 처음에 Triton을 ONNX Runtime과 같은 "추론 런타임·엔진" 층에 두어, 아래 "세 모델
서버" 문장과 어긋났다.

세 모델 서버에 공통된 설계는 **I/O 중심의 요청 접수와 연산 중심의 추론을 분리**해 따로 확장하고, 모델이 죽어도 입구는
살아 있게 하는 것이다. → [[AI DE 강의 2-08 서빙 플랫폼 FastAPI·TorchServe·BentoML·Triton]]

⚠️ 강의가 소개한 상태와 현재가 다르다 — TorchServe는 2025-08-07 저장소가 보관(archived)됐고, BentoML의 API Server + Runner
구조와 Yatai는 레거시·보관 상태다. 상세와 근거는 각 엔티티 페이지.

## CPU와 GPU

[[AI DE 강의 2-05 서빙 파이프라인 설계]]는 CPU(낮은 비용·빠른 스케일)와 GPU(높은 처리량·초기 로딩 비용)를 트래픽 패턴으로
고르라고 하고, [[AI DE 강의 2-09 서빙의 CPU·GPU 가속]]은 순서를 준다 — **병목을 먼저 분해하고, CPU 최적화를 끝낸 뒤, 배치가
가능할 때 GPU.** → [[추론 최적화]]

## 모델 버전과 배포

서빙 환경에는 현재 운영 모델·신규 배포 모델·롤백 대상 모델이 **항상 공존**한다. 필요한 제어는 트래픽 분할, 단계적 배포,
즉시 롤백. 배포 단위 패키지(.mar, Bento, Triton의 버전 디렉터리)와 학습 때의 스케일링 파라미터도 모델과 함께 버전으로
묶인다. → [[데이터와 모델 버전 관리]]

- **배포 전략의 기준** — 카나리·A/B 테스트·섀도우 배포를 언제 쓰고 어떤 지표로 승격·롤백하는지 Part 2는 이름만 든다.

- **배치와 온라인의 중간 지대** — 온라인 예측이지만 피처는 배치로 미리 계산하는 경우와 스트리밍으로 갱신하는 경우의 차이를
  다루지 않는다. 강의는 둘의 이분법으로 제시한다.
- **LLM 서빙** — 토큰 스트리밍, KV 캐시 같은 LLM 특유의 서빙 문제는 Part 2에 없다(Part 5 범위).
