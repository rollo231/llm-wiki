# 멱등성

같은 작업을 여러 번 적용해도 한 번 적용한 것과 결과가 같은 성질. 수식으로는 f(f(x)) = f(x)이고, 데이터 시스템에서는 같은 이벤트·요청·배치를 다시 실행해도 최종 상태가 같다는 뜻으로 쓴다.

강의는 이 말을 여러 곳에서 쓰지만 따로 정의하지 않는다. 이 페이지는 흩어진 언급을 위키가 모아 정리한 것이다.

## 왜 데이터 엔지니어링의 핵심인가

재시도와 재실행은 피할 수 없다. 그래서 한 번만 실행되게 만드는 것보다 몇 번 실행돼도 같게 만드는 편이 현실적이다.

| 어디서 | 무엇이 반복되나 | 멱등성이 주는 것 | 출처 |
|---|---|---|---|
| 배치 | 실패한 날짜 구간의 재실행·백필 | 재실행 범위만 정하면 안전하게 다시 돌릴 수 있다 | [[AI DE 강의 1-07 배치 처리와 ETL·ELT]] · [[배치 처리]] |
| CDC · 메시징 | at-least-once 전달의 중복 이벤트 | 같은 변경을 두 번 부어도 결과가 같다(upsert) | [[AI DE 강의 1-08 CDC]] · [[변경 데이터 캡처]] · [[이벤트 기반 아키텍처]] |
| 수집 | 크롤러·API 호출의 재시도 | 중복 수집 방지 | [[AI DE 강의 1-09 비정형 데이터 수집과 전처리]] |
| 스트림 처리 | 체크포인트 복구 뒤의 재처리 | 엔진 상태의 exactly-once를 출력까지 넓힌다 | [[AI DE 강의 1-12 실시간 처리 엔진]] · [[스트림 처리]] |
| 분산 저장소 쓰기 | 일관성을 완화한 NoSQL에서의 재시도 | 재시도·중복 처리·순서 꼬임을 애플리케이션이 떠안는다(p40) | [[AI DE 강의 3-02 RDBMS의 한계와 NoSQL]] · [[NoSQL]] |

end-to-end exactly-once에는 조건이 있다. 스트림 엔진의 체크포인트가 보장하는 것은 각 레코드가 엔진 상태에 한 번 반영된다는 것까지다. 출력까지 한 번이려면 재생 가능한 소스와 트랜잭션 또는 멱등 싱크가 더 필요하다. Flink·Spark 문서가 모두 이렇게 쓴다(근거 인용은 [[스트림 처리]]). 그래서 "exactly-once 전달"은 대개 at-least-once 전달에 멱등 반영을 더해 만든다.

## 만드는 방법

| 수단 | 원리 | 예 |
|---|---|---|
| 키 기반 upsert | 같은 키면 덮어쓴다. 두 번 와도 행은 하나 | CDC 타깃 반영, PK 기준 `MERGE` |
| 파티션 덮어쓰기 | 재실행이 그 파티션 전체를 새로 쓴다(append가 아니다) | 날짜 파티션 `INSERT OVERWRITE` |
| 이벤트 ID 중복 제거 | 처리한 ID를 기억해 두 번째를 버린다 | 수집 중복 방지 |
| 이벤트 시간 기준 반영 | 이미 더 최신 변경이 반영됐으면 무시한다 | CDC의 늦게 온 변경 |

[[변경 데이터 캡처]]는 키 기반 파티셔닝(순서), 멱등 upsert(중복), 이벤트 시간 기준 반영(늦은 변경)을 한 세트로 본다. 멱등 upsert 하나만으로는 순서가 뒤바뀐 두 변경 가운데 옛것이 이길 수 있기 때문이다.

## 헷갈리기 쉬운 것들

아래 두 구분은 위키가 정리한 것이다.

- 순수 함수(결정성)와 다르다. 순수 함수는 같은 입력에 같은 출력을 낸다([[함수형 프로그래밍]]). 결정적인 변환이라도 결과를 append하는 싱크에 쓰면, 재실행할 때마다 같은 행이 한 벌씩 더 쌓인다. 재실행이 안전하려면 결정적 변환과 멱등 싱크가 함께 필요하다.
- 원자성과도 다른 축이다. `count++`는 멱등하지 않고(두 번 하면 2가 오른다) `count = 5`는 멱등하다. 원자성은 동시에 실행될 때 끼어듦이 없느냐의 문제이고([[동시성 문제]]), 멱등성은 반복 실행의 문제다. at-least-once 소비자가 "잔액 += 금액"을 하면 원자적이어도 중복 이벤트에서 틀린다.

"중복 방지"라는 말도 두 뜻으로 쓰인다. [[AI DE 강의 1-08 CDC]]는 p7에서 CDC가 "중복 데이터 처리를 방지"한다고 하고, p11에서는 at-least-once에서 중복이 생기니 멱등성으로 막으라고 한다. 앞의 말은 바뀐 것만 보낸다는 뜻이고, 전달 보장 관점에서는 뒤의 말이 맞다.
