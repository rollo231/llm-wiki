# Schema-centric data modeling

**스키마가 데이터의 형식과 연결을 미리 못박고, 그 위에서 질의하는 설계 방식.** 관계형
모델(RDBMS)이 대표이고, 지난 수십 년 데이터 설계의 기본값이었다.

이 페이지는 **왜 강했고 어디서 무너지는가**를 다룬다. 무너지는 지점이 [[NoSQL]]과
[[Data semantics]]가 등장한 자리다.

## 관계형이 뜻하는 것은 표가 아니라 관계

> **"관계형이 의미하는 것은 표가 아니라 관계다."**

- **PK(Primary Key)** — 엔터티를 유일하게 식별
- **FK(Foreign Key)** — 테이블 간 관계를 **강제**

관계를 강제하면 세 가지가 따라온다: 데이터 중복 감소 · 참조 무결성 확보 · 조인 기반의 일관된 조회.

## 스키마는 선언이 아니라 규칙

스키마가 하는 일은 두 가지다 — **무엇이 들어올 수 있는지 제한**하고, **어떻게 연결되는지 명시**한다.

| 제약 | 막는 것 |
|---|---|
| `NOT NULL` | 필수 값 누락 |
| `UNIQUE` | 중복 데이터 |
| `CHECK` | 값 범위·형식 위반 |
| `FK` | 존재하지 않는 참조 |

> **핵심: 제약은 버그를 저장 단계에서 방어한다.** 애플리케이션 버그를 DB가 1차로 막는다.
> 스키마를 "타입 선언"으로만 보면 이 방어 기능이 안 보인다.

## 트랜잭션과 ACID

트랜잭션 = 여러 DB 작업을 **하나의 논리적 단위**로 묶는 것. 목표는 **중간 상태가 외부에 보이지 않게**
하고, 성공하거나 실패하면 원래대로 돌리는 것. `BEGIN → 작업 → COMMIT | ROLLBACK`.

주문/결제 예시가 이걸 다 설명한다 — 주문 생성 · 결제 기록 · 재고 차감 **셋은 항상 함께 성공해야
한다.**

| | | 깨지면 |
|---|---|---|
| **A**tomicity | 부분 성공 없음 (all-or-nothing) | 주문은 됐는데 결제 기록이 없다 |
| **C**onsistency | 미리 정의된 규칙(제약) 안에서만 상태 전이 | 재고가 -1이 된다 |
| **I**solation | 동시 트랜잭션이 서로를 망가뜨리지 않음 (락·MVCC·격리 수준) | 재고 1개를 2명이 산다 |
| **D**urability | 커밋된 결과는 장애가 나도 사라지지 않음 (로그·저장 장치) | 결제 완료 응답 후 서버가 죽어 기록이 증발 |

**결론: RDBMS는 OLTP(주문·결제·정산)에 최적이다.** → [[Analytical data storage tiers]]의 OLTP/OLAP
구분과 같은 축. 레이크하우스가 ACID를 되찾으려 한 이야기는 [[Table formats]].

## ⭐ 정규화의 목적은 중복 제거가 아니다

> **"정규화는 중복 제거가 아니라 업데이트 안정성이다."**

중복이 많을수록 **업데이트 이상(anomaly)** 이 늘어난다 — 고객 이름 하나 바꾸는데 주문 행을 전부
고쳐야 하나? 정규화는 엔터티를 분해하고 관계로 표현해서 **쓰기(write) 무결성**을 지킨다.

**이게 방향을 정한다.** 정규화는 읽기 최적화가 아니라 쓰기 최적화다. 그래서 분석계로 오면
반대로 비정규화하는 [[Dimensional modeling]]이 등장한다 — 두 설계는 같은 데이터에 대해 **반대
방향으로 옳다.**

## 조인 — 표현력이자 비용

조인은 **분산된 데이터를 질의 시점에 '의미 있는 정보'로 변환**하는 관계형 모델의 핵심이다. 동시에:

- 조인할 테이블이 N개면 **조인 순서의 가짓수가 기하급수적으로** 증가 → 실행 플랜 복잡도 상승
- 네스티드 루프 / 해시 조인 선택에 따라 **성능 편차가 크다**
- **규모가 커지면 조인은 표현력에서 병목이 된다**

## 스키마 중심 설계의 약점

### 1. 변경 비용

**스키마 변경 = 마이그레이션.** 컬럼 추가·타입 변경·제약 변경 모두 테이블 락 또는 장시간 백필을
부르고, 마이그레이션 도구·롤백 설계가 필요하다. 대형 테이블일수록 시간이 길고 위험이 크다.

> ⭐ **"규모가 커지면 '스키마 합의'가 병목이 된다."**
> 하나의 스키마를 여러 서비스·팀이 공유하기 시작하면 **변경은 기술 문제가 아니라 조직 합의의
> 비용**이 된다 — 이 컬럼은 누가 소유하나? 어떤 서비스가 영향받나? 배포 순서와 호환성은?

### 2. 비정형·다양성

현대 데이터는 스키마만으로 의미를 담기 어렵다.

| 데이터 | 문제 |
|---|---|
| 이벤트 로그 | 키/값이 자주 바뀜 |
| 문서·텍스트 | 컬럼으로 표현이 비효율 |
| 그래프·복잡한 관계 | **조인 폭발** |
| 임베딩·벡터 | RDBMS 질의 모델과 다름 |

> **"스키마는 형식을 잡지만, '의미'는 별도 계층이 필요하다."**
> → 이 문장이 [[Data semantics]]로 가는 문이다.

### 3. 확장(scale)의 한계

전통 RDBMS는 단일 노드(또는 단일 primary) 중심 설계가 많다. 강한 일관성 + 트랜잭션 처리 비용이
커질수록 한 노드가 감당할 작업량이 폭증하고, scale-up은 언젠가 물리적·비용적 한계에 닿는다.
읽기는 read replica로 늘려도 **쓰기가 병목이면 효과가 제한적**이다.

증상 순서: QPS 증가 → DB CPU 90% 고정 → p95/p99 급등 → 인덱스·조인 최적화로 버티다 한계점.

### 4. 분산 환경에서 강한 일관성은 비싸다

노드가 1개면 트랜잭션이 내부에서 끝난다. 여러 개면 트랜잭션이 **네트워크를 건넌다** — 동기 복제,
분산 락, 2PC 같은 조정(coordination). 네트워크는 느리고 부분 장애가 필연적이다.

→ 이 지점이 [[NoSQL]]의 출발점이다.
