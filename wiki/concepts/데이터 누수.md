# 데이터 누수

학습이나 평가에 예측 시점에는 알 수 없었던 정보가 섞여서, 오프라인 지표가 실제보다 좋게 나오는 현상.

강의에는 누수를 다루는 절이 따로 없다. [[AI DE 강의 2-04 ML 데이터 파이프라인]]의 분할 슬라이드("사용자/그룹 단위 누수를 피해야 한다")에 한 번 나오고, [[AI DE 강의 2-10 Feature Store 기본 개념]]의 `as_of_t` 재정의가 같은 문제의 다른 쪽을 건드린다. 이 페이지는 두 곳을 이어서 위키가 종합한 것이다.

## 두 얼굴

### 1. 분할 누수 — 나누는 방식이 미래를 섞는다

[[AI DE 강의 2-04 ML 데이터 파이프라인]]은 이렇게 권한다. 시간 기반 분할이 필요한 경우가 많다. 사용자/그룹 단위 누수를 피한다. 테스트는 미래의 입력 분포를 가정한다. 분할 전략 자체가 성능을 과대·과소평가할 수 있다.

이 목록의 1차 자료는 Chip Huyen의 강의 자료인 CS 329S Lecture 5 "Causes of data leakage"다.

| 원인 | 원문 |
|---|---|
| 시간 상관 데이터를 무작위로 분할 | "Splitting time-correlated data randomly instead of by time" (예: 주가 예측, 곡 추천). "Solution: split data by time" |
| 분할 전에 전처리 | "Data processing before splitting" |
| 중복 처리 미흡 | "Poor handling of data duplication before splitting" |
| 그룹 누수 | "A group of examples have strongly correlated labels but are divided into different splits. Example: CT scans of the same patient a week apart" |
| 데이터 생성·수집 과정 | "Leakage from data generation & collection process" |

[https://docs.google.com/presentation/d/1X_w55MfBhXGQbZkT_fbW9wdNrOs4sOuydRGPUI_yYCo , 2026-09-14 확인]

책 요약(5장 Feature Engineering)에도 같은 말이 있다: "Split data by time into train/valid/test splits instead of doing it randomly.", "Scale and normalize your data after splitting to avoid data leakage." [https://github.com/chiphuyen/dmls-book/blob/main/summary.md , 2026-09-14 확인] 책은 [[Designing Machine Learning Systems]]에 정리했다.

강의의 "사용자/그룹 단위"는 Huyen의 환자 단위 예를 일반화한 표현이다.

### 2. 피처 시점 누수 — 붙이는 값이 미래에서 온다

분할을 시간으로 해도, 각 학습 행에 라벨 시점 이후에 계산된 피처 값이 붙으면 누수다. 이것을 막는 장치를 시점 정합성(point-in-time correctness)이라고 한다.

- [[AI DE 강의 2-10 Feature Store 기본 개념]]은 피처를 "계산 규칙 + 시점 + 스키마"로 정의하고 `total_order_count_last_30_days_as_of_t`를 예로 든다. 이름에 시점이 들어가야 한다는 요구다.
- Feast는 이것을 조인으로 강제한다: "This timestamp acts as the **upper bound (inclusive)** for which feature values are allowed to be retrieved for each entity row. Feast performs a point-in-time join (also called a "last known good value" temporal join)", "This ensures point-in-time correctness, which is critical to prevent data leakage during model training. Without this constraint, features generated *after* the prediction time could leak into training data—effectively letting the model "see the future"". [https://docs.feast.dev/getting-started/concepts/feature-retrieval , 2026-09-14 확인]

피처 스토어 쪽 이야기는 [[피처 스토어]]에 있다.

## 스케일링 통계 — 두 강의를 합치면

- [[AI DE 강의 2-06 Training-Serving Skew 예방]]은 global stats(mean·std·min·max)를 아티팩트로 고정해 모델과 함께 배포하라고 한다(스큐 방지).
- Huyen은 스케일링·정규화를 분할한 뒤에 하라고 한다(누수 방지).

두 규칙을 합치면 하나가 된다. 통계는 학습 분할에서만 계산하고, 그 값을 버전 붙은 아티팩트로 서빙까지 가져간다. 검증·테스트 데이터는 그 통계를 받아 쓰기만 한다. 이 연결은 강의에 없고 위키가 붙였다. 버전 관리 쪽은 [[데이터와 모델 버전 관리]]를 본다.

## 스큐와 증상이 같다

"오프라인 평가 지표는 높은데 프로덕션 성능은 낮다"는 [[AI DE 강의 2-06 Training-Serving Skew 예방]]이 드는 [[학습-서빙 스큐]]의 증상이면서 누수의 증상이기도 하다. 둘을 가르는 질문은 오프라인 숫자가 진짜였느냐다.

| | 데이터 누수 | 학습-서빙 스큐 |
|---|---|---|
| 오프라인 지표 | 처음부터 가짜(미래 정보 덕분) | 진짜였다 |
| 무엇이 다른가 | 평가 방식이 예측 시점을 흉내 내지 못함 | 서빙 입력이 학습 입력과 다름 |
| 고치는 곳 | 분할·피처 시점 조인 | 피처 생성 규칙·공용 변환 로직 |

그래서 프로덕션 성능이 떨어졌을 때 스큐만 의심하면, 원래 없던 성능을 찾아 서빙 파이프라인을 뒤지게 된다. 위키의 관찰이다.

## 빈칸

- 라벨·타깃 누수: 정답과 사실상 같은 정보가 피처에 들어가는 경우(예: 결과가 확정된 뒤에만 채워지는 컬럼)는 강의에 없다.
- 감지 방법: 누수를 어떻게 찾는지(비정상적으로 높은 피처 중요도, 시간 역전 검사 등)는 다루지 않는다.
- 슬라이드의 70/15/15 분할 그림은 비율만 보여 줄 뿐, 시간 기반 분할에서 검증·테스트 구간을 어떻게 잡는지는 없다.
