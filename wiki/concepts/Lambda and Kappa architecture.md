# Lambda and Kappa architecture

**배치의 정확성과 스트림의 저지연을 어떻게 함께 얻을 것인가 — 두 세대의 답.**

> ⭐ **"람다의 가장 큰 공헌은 재처리를 아키텍처 수준의 요구사항으로 끌어올린 점이다."**

## 람다 아키텍처

**네이선 마즈(Nathan Marz)** 제안. 세 계층으로 정확성과 지연을 분업한다.

| 레이어 | 목표 | 역할 |
|---|---|---|
| **배치 레이어** | **Accuracy** | 마스터 데이터셋 관리, 정교하고 정확한 분석 결과 산출 |
| **스피드 레이어** | **Latency** | 최근 데이터의 지연을 최소화하여 즉각적 결과 제공 |
| **서빙 레이어** | **Unified View** | 두 계층의 결과를 통합해 완전한 뷰 제공 |

**출발점의 긴장:** 정확한 결과는 전체 데이터를 다시 계산해야 하고, 빠른 결과는 부분 데이터와 점진
계산에 의존한다.

### ⭐ 람다가 남긴 유산

> 람다가 강조한 좋은 문제의식:
> - **원본 데이터 보존**
> - **재처리 가능성**
> - 코드 변경 시 과거 결과 재계산 필요
> - 실시간 계층 오류를 배치 계층이 결국 수정

> ⭐ **"배치 계층이 속도 계층의 일시적 오류를 결국 덮어쓴다"** 는 사고가 람다의 핵심 기여다.
> 카파가 람다를 대체해도 **이 요구사항은 남는다.**

## 람다의 한계 — 계산 비용이 아니라 인지 비용

> ⭐ **"람다의 가장 큰 비용은 계산 비용보다 인지 비용과 유지보수 비용이다."**

**구조적 한계:**

- 두 개의 코드베이스를 유지하고 **동기화**
- 같은 변환 로직을 배치 계층과 속도 계층에 **각각 구현**
- 같은 의미의 결과를 서로 다른 시스템에서 맞춰야 함
- **프레임워크가 다르면 코드 스타일·상태 처리·오류 처리도 달라짐**

**운영·개발 부담:** 두 프레임워크 운영 · 두 결과 저장소 · 결과 병합 로직 ·
장애 원인 추적 경로 증가 · **성능 병목 지점 두 배** · **결과 동치성 검증** ·
**추상화 프레임워크를 도입해도 누수 발생**

### ⭐ 람다는 틀린 답이 아니라 당시 도구의 산물

**2010년대 초반의 도구 지형:**

| 도구 | 문제 |
|---|---|
| **Hadoop** (배치) | 계산은 정확하지만 결과까지 **몇 시간, 며칠** |
| **Storm** (초기 스트림) | 1초 만에 결과를 보여주지만 **중복·유실**, 100% 정확하지 않음 |

> **"비즈니스를 위해서는 결과가 빨리 나와야 하면서도, 돈이 오가는 문제니 결국엔 100% 정확해야 한다."**

**정리:** 람다는 중요한 문제를 정확히 짚었다 · 다만 해결 방식이 구조적으로 무거웠다 ·
당시 도구를 묶어 만든 현실적 해법이다 · **도구가 성숙할수록 단일 처리 경로에 대한 요구가 증가했다.**

> ⭐ **아키텍처 패턴을 "당시 제약의 함수"로 읽으면, 제약이 바뀔 때 무엇이 바뀌는지 예측할 수 있다.**
> 정답/오답으로 배우면 왜 폐기됐는지 알 수 없다.

## 카파 아키텍처

**Jay Kreps** 제안.

> **핵심: 배치 경로와 속도 경로를 따로 두지 않고, 하나의 스트림 처리 경로로 실시간 처리와 재처리를
> 모두 수행한다.**
>
> **전제 조건: 과거 데이터를 다시 읽을 수 있는 로그 보존 — 불변 이벤트 로그.**

**핵심 구조 3요소:** 장기 보관 가능한 입력 로그 · 동일한 스트림 처리 로직 ·
결과 저장소 또는 Materialized View.

### ⭐ 재처리 흐름 5단계 — 데이터의 블루/그린 배포

1. 충분히 긴 기간 동안 입력 로그 보관
2. 코드 변경 시 **새 버전의 스트림 작업 기동**
3. 과거 오프셋부터(Earliest) 다시 읽어 **새 결과 테이블 계산**
4. 새 작업이 현재 시점까지 따라잡으면 **결과 전환**
5. 이전 버전 작업 종료

> ⭐ **"재처리를 별도 배치 파이프라인이 아니라 같은 스트림 파이프라인의 빠른 재생으로 해석한다.
> 복잡도의 초점이 '두 개의 코드 경로'에서 '재생 가능한 로그'로 이동한다."**

### 장점과 전제

| 장점 | 전제 |
|---|---|
| **단순성** — 단일 처리 경로 | 충분한 **로그 보존 기간** |
| **일관성** — 단일 코드베이스 | **빠른 재생이 가능한 처리 엔진** |
| **생산성** — 개발·테스트·디버깅 단순화 | 결과 저장소 전환 또는 갱신 전략 |
| 재처리 방식 명확화 | ⭐ **같은 입력을 다시 읽어도 의미를 유지하는 시간 기준과 상태 설계** |

> ⭐⭐ **마지막 전제가 결정적이다 — 카파는 event time을 요구한다.**
> 처리 시각 기준으로 계산하면 로그를 다시 읽었을 때 원래 결과가 나오지 않는다. 어제 사건이 오늘
> 시간 구간으로 들어간다. **[[Stream processing semantics]]의 event time·워터마크가 카파의
> 필수 조건이지 선택 사항이 아니다.**

### 카파의 도전과제 3가지

| 과제 | 내용 |
|---|---|
| **저장 비용** | **수년치 원본 데이터를 모두 보관**하는 스토리지 부담 |
| **상태 관리** | **매우 긴 윈도우**(최근 1년 사용자 행동)에서 메모리 사용량 급증 |
| **기술 장벽** | Watermark·State Store를 완벽히 다루기 위한 **높은 숙련도** |

> ⚠️ **첫 번째 과제의 현대적 대응이 강의에 없다.** 실무는 "수년치를 Kafka에"가 아니라
> **핫 구간은 Kafka, 콜드는 객체 스토리지/테이블 포맷**으로 계층화한다
> (Kafka tiered storage, Iceberg 위의 이벤트 아카이브). **강의는 카파를 2014년 형태 그대로
> 소개한다.**

## ⭐ 현대 — 하나의 정답이 아니라 5개 축

> ⭐ **"람다 다음에 하나의 정답이 등장한 구조가 아니다. 저장·처리·조직·연결·신뢰가 각각 다른
> 방향으로 진화했다. 현대 아키텍처는 한 가지 이름보다 여러 축의 조합으로 이해하는 편이 정확하다."**

| 축 | 이름 | 내용 | 이 위키의 연결 |
|---|---|---|---|
| **저장·관리 플랫폼** | **Lakehouse** | 레이크의 유연성 + 웨어하우스의 성능. 개방형 테이블 포맷(Iceberg·Delta·Hudi), ACID·스키마 강제·타임 트래블 | [[Analytical data storage tiers]] · [[Table formats]] |
| **batch/stream 통합 처리** | **Unified Path** | 배치와 스트림을 다른 계산 세계로 보지 않음. 같은 엔진·같은 API로 둘 다. **이중 코드 경로 축소** | ⭐ **카파의 계승자.** [[Apache Flink]]의 bounded/unbounded 통합, [[Apache Spark]] Structured Streaming |
| **도메인 ownership** | **Data Mesh** | 중앙집중형 IT 병목 제거, 데이터를 도메인별 제품으로. **Domain Ownership** + **Self-Serve Platform** | 이 위키에 별도 페이지 없음 (근거가 슬라이드 2장뿐) |
| **메타데이터·자동화** | **Data Fabric** | 물리적으로 모으지 말고 메타데이터와 AI로 엮기. **Active Metadata** + **Knowledge Graph** | ⭐ [[Knowledge graph]] · [[DataHub]] · [[Data catalog and semantic layer]] |
| **경계 규약** | **Data Contract** | ⚠️ **강의에 이름만 있고 설명이 없다** | [[AI DE Course - Part3 Ch3 SHACL and graph data contracts]]가 그래프용 버전 |

> ⭐ **Data Fabric 축이 Part 3 전체와 직결된다.** *Knowledge Graph로 의미론적 검색*은
> [[Knowledge graph]]·[[GraphRAG]]의 요약이고, *Active Metadata*는 [[DataHub]] 같은 메타데이터
> 그래프의 지향점이다. **강의가 Part 3를 인용하지 않지만 같은 이야기다.**

## 세 세대를 한 줄로

| | 문제 | 답 | 대가 |
|---|---|---|---|
| **람다** | 정확성 vs 지연 | **두 경로를 나란히** | 이중 코드베이스, 인지 비용 |
| **카파** | 이중 코드베이스 | **재생 가능한 로그 하나** | 저장 비용, 긴 윈도우 상태, 숙련도 |
| **Unified Path** | 재생만으로는 배치 워크로드를 다 못 담음 | **같은 API로 배치와 스트림** | 엔진 종속, 여전히 event time 설계 필요 |

**세 세대 모두 "재처리 가능성"이라는 람다의 요구사항을 유지한다.** 방식만 바뀐다.
