# 시맨틱 계층

데이터가 비즈니스에서 무엇을 의미하는지를 정의해 데이터 위에 얹는 계층이다. 강의의 정의는 "비즈니스 의미를 데이터 위로 올리는 레이어"([[AI DE 강의 3-02 RDBMS의 한계와 NoSQL]] p48)이고, 한 줄로는 "시멘틱은 데이터 해석의 계약(contract)"([[AI DE 강의 3-03 시맨틱]] p51)이다. Part 3 전체가 이 계층을 어떻게 만드느냐(그래프, 온톨로지, 지식 그래프, GraphRAG)를 다룬다.

## 스키마와 무엇이 다른가

| | 스키마 | 시맨틱 |
|---|---|---|
| 정의하는 것 | 형식: 컬럼, 타입, NULL 허용, PK/FK | 의미: 이 값이 무엇을 나타내고 어떻게 계산됐나 |
| 답하는 질문 | 어떤 테이블에, 어떤 타입으로, 어떤 키로 조인하나 | 어떤 개체인가, 어떤 관계인가, 다른 시스템의 어떤 개념과 같은가, 어떤 문맥에서 읽나 |
| 강한 곳 | 저장 최적화 | 연결, 탐색, 재사용, 해석 |

표는 [[AI DE 강의 3-03 시맨틱]] p52·p57을 정리한 것이다. 스키마가 답하지 못하는 예로 강의는 `user_id`와 `member_id`가 같은 개념인지, `created_at`이 가입 시각인지 주문 시각인지, `status`가 결제 상태인지 배송 상태인지를 든다.

## 구성 요소

Entity(독립된 대상), Attribute(속성), Relationship(개체 사이 연결), Context(해석 조건: 시간, 채널, 지역, 정책 버전, 실험군, 모델 버전). 강의가 특히 강조하는 것은 Context다. `active_user`가 최근 7일 로그인인지 30일 유효 행동인지 유료 사용자만인지, `Revenue`가 총 결제액인지 순매출인지는 맥락 없이 정해지지 않는다(3-03 p54).

이 네 요소는 뒤에서 모양을 바꿔 다시 나온다. 그래프의 노드·엣지·속성([[그래프 데이터 모델]]), 온톨로지의 클래스·관계·속성·제약([[온톨로지]]). Context는 그래프 모델에서 관계에 붙는 속성이나 별도 개체로 표현된다. 이 대응은 위키의 정리다.

## 없으면 생기는 일

- 같은 KPI가 여러 개가 된다. 정의가 SQL에 흩어지고 팀마다 제외 조건이 달라서, 같은 회사에서 매출 숫자가 셋 이상 나오고 "숫자 맞추기 회의"가 열린다. 강의의 표현으로 "지표가 계약이 아니라 쿼리가 됨"(3-02 p46).
- SQL이 비즈니스 로직이 된다. 지표 정의가 코드로만 있어 재사용할 수 없고 변경 영향을 추적할 수 없다. KPI가 바뀌면 대시보드를 전면 수정한다(3-02 p47).
- 같은 고객이 `user_id`·`member_id`·`customer_id`·`account_id`로 흩어지고, 잘못된 조인과 잘못된 결론이 나오고, RAG·추천·QA 품질이 떨어진다(3-03 p55).

## AI에서 왜 더 중요한가

전통적 BI는 정해진 집계와 리포트가 중심이지만, AI·LLM 시스템은 "이 문서와 관련된 정책·제품·팀은?", "이 장애와 비슷한 과거 이슈는?", "이 피처가 어떤 모델·데이터셋과 연결되나?" 같은 질문을 받는다(3-03 p56). 필요한 것은 의미 기반 검색, 개체 간 연결 탐색, 이질적 소스 통합, 문맥 기반 해석, 동일 개념 정규화다.

## 용어 사전에서 그래프까지

| 단계 | 형태 | 위키의 해당 페이지 |
|---|---|---|
| 가장 약한 형태 | 공통 용어 정의, 지표 사전, 데이터 카탈로그, 컬럼 설명 | [[데이터 거버넌스와 카탈로그]] |
| 더 구조화된 형태 | 공통 엔티티 모델, 표준 식별자 체계, 도메인 간 관계 정의 | [[AI DE 강의 3-10 지식 그래프 파이프라인]]의 식별자 설계 |
| 더 발전한 형태 | 온톨로지, 지식 그래프, semantic layer, context-aware retrieval | [[온톨로지]] · [[지식 그래프]] · [[GraphRAG]] |

스펙트럼은 강의(3-03 p58)를 따랐고, 오른쪽 열은 위키가 이어 붙였다.

## 계약으로서의 시맨틱

위키의 종합이다. Part 1은 스키마를 생산자와 소비자의 계약으로 봤다([[스키마 진화]]의 「스키마는 계약이다」). 시맨틱은 그 계약을 형식에서 뜻으로 넓힌다. 호환성 검사는 `double`이 `double`인 채로 cm에서 m로 단위가 바뀌는 변경을 통과시키는데, 이것이 시맨틱 계약이 없어서 새는 자리다. [[데이터 SLA]]의 데이터 계약(스키마·윈도우 크기·예외 처리 규칙을 문서로 명시)도 같은 쪽에 있다. Part 3 Ch3은 이 계약을 기계가 검사할 수 있는 형태(SHACL shape)로 만든다([[AI DE 강의 3-11 SHACL 검증]]).

## 용어 주의

강의는 "semantic layer"를 두 뜻으로 쓴다. 시맨틱 전반을 가리킬 때(3-02 p48)와, 스펙트럼에서 온톨로지·지식 그래프와 나란한 한 형태로 쓸 때(3-03 p58)다. 업계에서 semantic layer는 흔히 지표 정의를 한곳에 두고 여러 BI 도구가 공유하는 계층(dbt Semantic Layer, Looker의 LookML 같은)을 가리킨다. 강의의 "같은 KPI가 여러 개" 문제에 가장 직접적인 해법이 이쪽인데 강의는 이름만 들고 설명하지 않는다. dbt 문서는 dbt Semantic Layer를 "By centralizing metric definitions, data teams can ensure consistent self-service access to these metrics in downstream data tools and applications"로 설명하고, 지표 정의를 BI 계층에서 모델링 계층으로 옮긴다고 쓴다. Looker 문서는 LookML을 "the language that is used in Looker to create semantic data models"로 소개한다. [https://docs.getdbt.com/docs/use-dbt-semantic-layer/dbt-sl · https://cloud.google.com/looker/docs/what-is-lookml , 2026-09-28 확인] 이 업계 용법은 위키의 보충이다.
