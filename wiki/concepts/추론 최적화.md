# 추론 최적화

학습이 끝난 모델을 **서빙 경로에서 더 싸고 빠르게 돌리는 기법의 묶음** — 병목 측정, 모델 경량화, 추론 전용 런타임, 배칭,
그리고 마지막으로 GPU. [[AI DE 강의 2-09 서빙의 CPU·GPU 가속]]이 이 순서로 설명한다.

## 먼저 병목을 찾는다

```
Total Latency = 네트워크 + 직렬화 + 전/후처리 + 모델 추론 + 스케줄링
```

- **모델 추론이 병목이 아닌 경우가 매우 많다** — 작은 모델, 낮은 QPS, I/O 중심 서비스. 이때 GPU는 효과가 미미하다.
- 온라인 서빙에서는 **피처 조회가 전체 지연의 대부분**을 차지하기도 한다([[AI DE 강의 2-05 서빙 파이프라인 설계]]) — 그
  경우 처방은 모델이 아니라 캐싱·사전 계산이다. → [[모델 서빙]]
- 흔한 오해 "CPU = 느림, GPU = 빠름". GPU는 비싸고, 운영이 어렵고, 작은 요청에는 오히려 불리하다.

## 모델 수준

| 기법 | 무엇을 하나 | 강의가 드는 효과 |
|---|---|---|
| **양자화(Quantization)** | FP32 → INT8 / FP16 | 연산량 감소, 캐시 효율 증가 |
| **가지치기(Pruning)** | 영향이 적은 weight 제거 | 모델 크기·메모리 접근 감소, 실시간 서빙에 효과적 |
| **지식 증류(Knowledge Distillation)** | 큰 모델의 지식을 작은 모델로 이전 | "서빙용 모델"을 따로 만든다. 정확도 손실 대비 latency 이득이 크다 |

⚠️ 강의는 양자화가 "CPU에서도 큰 효과"라고 하지만, ONNX Runtime 기준으로 **FP16은 GPU 쪽** 최적화이고 **INT8의 CPU 이득은
하드웨어에 달려 있다**(VNNI가 있으면 유리, 오래된 장치에서는 느려질 수 있음). 검증과 출처는
[[AI DE 강의 2-09 서빙의 CPU·GPU 가속]].

⚠️ 가지치기의 "실시간 서빙에 효과적"도 단서가 필요하다 — weight를 0으로 만드는 **비구조적 가지치기는 dense 커널에서 그대로는
크기도 지연도 줄지 않는다.** 속도 이득은 구조적 가지치기(채널 제거)나 하드웨어가 지원하는 2:4 희소성(NVIDIA Ampere 이상)에서
나온다. [PyTorch 튜토리얼 「semi-structured (2:4) sparsity」 — "Zeroing out parameters doesn't affect the latency / memory
overhead of our model out of the box." https://docs.pytorch.org/tutorials/advanced/semi_structured_sparse.html ·
Mishra et al., arXiv:2104.08378 — "Sparse Tensor Cores, which exploit a 2:4 (50%) sparsity pattern that leads to twice the
math throughput of dense matrix units." https://arxiv.org/abs/2104.08378 , 2026-09-14 확인]

세 기법 모두 **서빙되는 아티팩트를 학습된 모델과 다르게 만든다** — 경량화된 모델로 오프라인 평가를 다시 하고, 무엇을
배포했는지 따로 버전으로 추적해야 한다. 강의는 이 의무를 말하지 않는다. *(위키의 관찰)* → [[데이터와 모델 버전 관리]]

## 런타임 수준

프레임워크 기본 실행(PyTorch eager 등)은 연산을 하나씩 처리한다. 추론 전용 런타임은 그래프를 미리 분석해 바꾼다.

- **그래프 최적화** — 학습용 연산(Dropout 등)과 불필요한 노드 제거, **연산 결합(operator fusion)**.
- **하드웨어 친화 실행** — SIMD 명령어(AVX2·AVX-512), 스레드 병렬.
- 예: [[ONNX]] Runtime, OpenVINO. [[Triton Inference Server]]는 C++ 코어 위에서 TensorRT·ONNX 등 여러 백엔드를 돌린다.

## 배칭 — GPU의 전제

**GPU는 빠른 단일 추론기가 아니라 병렬 연산 장치다. 배치 없이는 GPU 이점이 거의 사라진다.**
([[AI DE 강의 2-09 서빙의 CPU·GPU 가속]])

사용자 요청은 하나씩 오므로, 서버가 요청을 **잠깐 모아 한 번에** 추론하는 장치가 필요하다. 서빙 플랫폼마다 이름이 다르다
([[AI DE 강의 2-08 서빙 플랫폼 FastAPI·TorchServe·BentoML·Triton]]).

| 플랫폼 | 장치 |
|---|---|
| [[Triton Inference Server]] | **Dynamic Batching** — 모델별 스케줄러 큐에서 여러 클라이언트의 요청을 묶는다. 상태가 필요한 모델에는 순서를 보장하는 Sequence Batching |
| [[BentoML]] | **Adaptive Batching** — 여러 요청을 런타임에서 자동으로 배치 연산으로 전환 |
| [[TorchServe]] | **Optional Request Batching** — 프론트엔드가 개별 요청을 모아 모델에 전달 |

이것은 [[지연 시간과 처리량]]의 시소 그대로다 — 모이기를 기다리는 약간의 지연을 내고 처리량을 산다. 동적 배칭은 그
절충점을 서버가 대신 고르는 장치다. *(위키의 연결)*

## CPU에서 GPU로 — 전환 판단

**체크리스트** — CPU 최적화는 끝났나? 추론 연산이 전체 latency의 대부분인가? 배치 처리가 가능한가? GPU 비용 대비 효과가
명확한가?

**CPU로 충분한 경우** — 모델이 작다(수 MB~수십 MB), 단건 latency가 중요, QPS가 낮거나 중간, 트리·선형·작은 NN
(추천 후보 생성, 이상치 탐지, 피처 기반 분류, 룰 + ML 혼합).

**GPU를 고려할 경우** — Transformer·LLM·대형 CV처럼 모델이 크다, CPU 최적화 후에도 단일 추론이 SLA를 못 맞춘다, QPS가
높아 CPU 수평 확장 비용이 GPU보다 커진다, 대량 행렬 연산이 지배적이다.

**GPU를 쓰면 바뀌는 것**

| 아키텍처 | 운영 | 비용 |
|---|---|---|
| CUDA·드라이버 의존성 | 메모리 관리·OOM | 인스턴스 단가 급증 |
| GPU 스케줄링, Kubernetes GPU 리소스 관리 | GPU utilization 모니터링, 멀티 모델 로딩 전략 | idle GPU 비용, autoscaling 전략 |

## 빈칸

- **수치가 없다** — 어떤 기법이 얼마나 빨라지는지, 양자화로 정확도가 얼마나 떨어지는지 벤치마크가 하나도 없다.
- 양자화의 정확도 손실을 **어떻게 측정하고 허용 기준을 정하는지**(보정 데이터셋, 경량 모델 재평가)는 다루지 않는다.
- **LLM 전용 서빙 최적화**(KV 캐시, continuous batching, 투기적 디코딩 등)는 Part 2에는 없다. LLM은 Part 5에서 다룬다.
- GPU 공유(MIG, 한 GPU에 여러 모델 인스턴스)는 Triton의 동시 실행으로만 짧게 나온다.
