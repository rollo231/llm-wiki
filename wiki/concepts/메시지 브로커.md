# 메시지 브로커

생산자와 소비자 사이에서 메시지의 수신, 저장, 라우팅, 전달, 확인 응답, 재전달, 부하 분산을 맡는 중간 시스템이다([[AI DE 강의 4-06 메시지 브로커의 종류와 전달 보장]] p141). 실시간 파이프라인에서는 데이터가 처리되기 전에 거치는 완충 지점이자 재전달 지점이다.

## 왜 필요한가

생산자와 소비자를 직접 연결하면 규모가 커질수록 네 문제가 생긴다(p137–138).

| 문제 | 무엇이 일어나나 |
|---|---|
| 속도 불일치 | 생산자는 초당 수만 건, 소비자는 수천 건. 버퍼가 없으면 소비자 지연이 생산자 장애로 번진다 |
| 장애 전파 | 소비자가 죽으면 생산자가 재시도·임시 저장·중복 전송·복구를 떠안는다 |
| fan-out 복잡도 | 한 이벤트를 피처 스토어·모니터링·알림·DW·재학습이 함께 쓰면 producer가 downstream을 모두 알아야 한다 |
| 재처리 불가능성 | 소비자가 잘못 처리했거나 새 downstream이 생겼을 때 과거 이벤트를 다시 읽을 수 없다 |

[[AI DE 강의 1-11 EDA와 Kafka]]는 앞의 세 문제를 허브 앤 스포크(N×M 연결 → 1:N)로 설명했다([[이벤트 기반 아키텍처]]). Part 4는 넷째 문제를 더한다. 두 강의를 이은 것은 위키다.

## 소비 의미론으로 나누기

[[AI DE 강의 4-06 메시지 브로커의 종류와 전달 보장]]은 제품명이 아니라 소비 의미론으로 분류하자고 한다(p142). 축은 여섯이다.

- 메시지가 소비 후 삭제되는가, retention 동안 남는가
- 소비 상태를 ack/delete로 관리하는가, offset/cursor로 관리하는가
- 한 메시지를 한 consumer만 처리하는가, 여러 subscriber가 독립적으로 처리하는가
- 과거 메시지를 다시 읽을 수 있는가
- 순서 보장이 전체 단위인가, partition·key·message group 단위인가
- 목적이 task distribution인가, event history 보존인가

이 축으로 보면 세 모델이 갈린다.

| 모델 | 핵심 질문 | 소비 후 | 대표 | 쓰임 |
|---|---|---|---|---|
| Queue | 이 작업을 어떤 worker가 처리할 것인가 | 성공하면 삭제·완료 | RabbitMQ, Amazon SQS | 이미지 리사이징, 비동기 메일, 추론 후처리, 재시도 가능한 task dispatch |
| Pub/Sub | 이 이벤트를 누가 각자 받을 것인가 | subscription마다 독립 | Google Cloud Pub/Sub | 추론 로그 한 건을 모니터링·경보·적재가 각각 수신 |
| Retained log | 얼마나 오래 보관하고, 어떤 group이 어느 offset부터 읽을 것인가 | 보관 기간 동안 남음 | [[Apache Kafka]] | CDC, 클릭 로그, 새 downstream의 과거 재적재, 잘못된 집계의 재처리 |

Apache Pulsar는 subscription type(exclusive·shared·failover·key_shared)으로 fan-out과 queueing 의미론을 한 시스템에서 고르게 하고, 소비 위치를 durable cursor로 관리한다(p149. Pulsar 문서 "There are four subscription types in Pulsar: exclusive, shared, failover, key_shared", https://pulsar.apache.org/docs/next/concepts-messaging/ , 2026-09-28 확인).

선택 기준은 task dispatch인가 event fact 보존인가, replay·backfill이 필요한가, 여러 downstream이 독립 소비하는가, 순서가 어디까지 필요한가, 자체 운영인가 managed service인가다(p149).

## 전달 보장

| 수준 | 뜻 | 대가 |
|---|---|---|
| At-most-once | 많아야 한 번. 중복은 없지만 장애 때 유실 | 데이터 손실 |
| At-least-once | 적어도 한 번. 유실은 막지만 중복 가능 | 소비자가 중복을 견뎌야 한다 |
| Exactly-once | 한 번만 처리 | 특정 경계·싱크·트랜잭션 프로토콜 안에서만 성립 |

강의는 exactly-once를 "외부 세계 전체에서 한 번"으로 받아들이면 위험하다고 경고한다(p150). 스트림 엔진의 exactly-once가 엔진 상태에 한 번 반영된다는 뜻이고 출력까지는 재생 가능한 소스와 트랜잭션·멱등 싱크가 더 필요하다는 것은 Flink·Spark 문서로 [[스트림 처리]]에 적어 두었다.

그래서 실무 설계의 기본은 at-least-once를 전제로 한 idempotent consumer다(p151). 강의가 드는 수단은 idempotency key, deduplication table, upsert sink, transactional write, retry count, dead-letter queue, poison message 격리다. 앞의 넷은 중복을 무해하게 만들고([[멱등성]]), 뒤의 셋은 계속 실패하는 메시지가 파이프라인 전체를 막지 않게 한다. 이 둘로 나눈 것은 위키의 정리다.

SQS FIFO의 "exactly-once processing"은 이름과 달리 5분 중복 제거 창 안에서 전송 중복을 막는 것이다("within the 5-minute deduplication interval", https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/FIFO-queues-exactly-once-processing.html , 2026-09-28 확인). 소비 쪽의 처리 완료는 visibility timeout과 소비자 코드에 달려 있어서, 소비자는 여전히 멱등해야 한다. 이 결론은 위키의 정리다.

## 브로커와 스트림 처리 엔진

[[AI DE 강의 4-07 메시지 브로커와 스트림 처리 엔진]]은 둘을 질문으로 가른다(p154). 브로커는 "이벤트를 어떻게 안전하게 흘리고 보관할 것인가", 엔진은 "계속 들어오는 이벤트를 어떤 시간 기준과 상태 기준으로 계산할 것인가"를 묻는다. 브로커만 두고 실시간 집계가 끝났다고 여기거나, 엔진만 붙이면 메시징 계층이 필요 없다고 여기는 것이 둘을 섞을 때 생기는 착각이다. 엔진 쪽은 [[스트림 처리]]에 있다.

Kafka는 이 경계에 걸친다. 브로커이면서 Kafka Streams라는 처리 라이브러리를 함께 제공하고, 그 상태 저장소를 다시 Kafka 토픽(changelog)으로 복구한다([[Apache Kafka]]).
