# 데이터 레이크하우스

**데이터 웨어하우스(DW)의 관리 기능(ACID·스키마·거버넌스)과 데이터 레이크의 유연성·저비용을 하나의
플랫폼에 합친 저장 아키텍처.** 정형 분석(BI)과 비정형·ML 학습(AI)을 같은 데이터 위에서 돌리는 것이 목표다.

## DW → 레이크 → 레이크하우스

| | 데이터 웨어하우스 | 데이터 레이크 | 레이크하우스 |
|---|---|---|---|
| 담는 것 | ETL로 정제된 정형 데이터 | 모든 원시 데이터 | 원시 + 정제, 정형 + 비정형 |
| 스키마 | schema-on-write | schema-on-read | 스키마 강제와 진화를 테이블 계층이 관리 |
| 저장 | 전용 시스템 | 오브젝트 스토리지(S3·HDFS) | 오브젝트 스토리지 + 트랜잭션 로그 |
| 강점 | 고성능 SQL, 품질 | 유연성, 저비용 | 둘 다 |
| 약점 | 비정형 불가, 비용 | 데이터 늪, 품질 관리 약화 | 복잡성 |

출처: [[AI DE 강의 1-04 저장소의 진화 DW에서 Lakehouse까지]]

## 레이크는 왜 늪이 되는가

같은 "데이터 늪"을 세 강의가 서로 다른 원인으로 설명한다. *(위키의 대조)*

| 강의 | 원인 |
|---|---|
| [[AI DE 강의 1-02 AI DE 마인드셋 Latency와 Versioning]] | 쌓기만 하고 처리 방식·버전 관리가 없다 |
| [[AI DE 강의 1-06 Delta Lake와 ACID]] | **기술적 원인** — 파일 시스템이라 한 줄 수정에도 파일 전체 재작성, 격리가 없어 쓰는 중에 읽으면 깨진 데이터, 스트리밍이 만든 작은 파일, 스키마 강제 없음, 실수로 지운 데이터를 되돌릴 수 없음 |
| [[AI DE 강의 1-15 데이터 거버넌스와 카탈로그]] | **조직적 원인** — 위치·소유자 불명, 모호한 정의, 계보가 없어 품질을 믿을 수 없음 |

레이크하우스의 테이블 포맷([[Delta Lake]])은 첫 번째 원인을, 카탈로그는 두 번째 원인을 해결한다.
**둘 중 하나만으로는 늪을 벗어나지 못한다.**

## 데이터 레이크의 4요소

[[AI DE 강의 1-04 저장소의 진화 DW에서 Lakehouse까지]]: 확장성(오브젝트 스토리지), 접근성(메타데이터
카탈로그 + schema-on-read), 보안(IAM·암호화), 비용 관리(수명주기 정책으로 콜드 데이터를 저렴한 계층으로).

## AI와의 관계

학습 데이터는 비정형이 많고 대량 순차 읽기를 한다([[행 기반과 열 기반 저장]]). DW만으로는 비정형을 못 담고,
레이크만으로는 학습 데이터의 스냅샷·일관성을 보장하지 못한다. 레이크하우스는 **학습에 쓸 데이터의 특정 시점을
고정**할 수 있게 한다([[데이터와 모델 버전 관리]]).
