# 실행 계획

옵티마이저가 쿼리를 어떤 순서로, 어떤 인덱스와 어떤 조인 방식으로 실행할지 정한 계획이다. MySQL과 PostgreSQL 모두 `EXPLAIN`으로 본다. [[DB 면접 7 운영]]은 느린 쿼리를 찾는 슬로우 쿼리 로그와 원인을 찾는 EXPLAIN을 한 흐름으로 묻는다. 이 페이지는 MySQL을 기준으로 적는다.

## 슬로우 쿼리 로그

- MySQL은 실행 시간이 `long_query_time`초를 넘는 쿼리를 슬로우 쿼리 로그에 남긴다. 기본값은 10초다. [MySQL 8.4 Reference Manual, Server System Variables, https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_long_query_time : "Default Value 10", 2026-09-28 확인]
- 조건이 하나 더 있다. 검사한 행 수가 `min_examined_row_limit`보다 적으면 기록하지 않는다("Queries that examine fewer than this number of rows are not logged to the slow query log"). 기본값이 0이라 평소에는 조건이 없는 것과 같다. [같은 문서 #sysvar_min_examined_row_limit, 2026-09-28 확인]
- 로그는 기본으로 꺼져 있어(`slow_query_log` 기본값 OFF) 켜야 쓸 수 있다. 자료(p110)가 "활성화하여"라고 쓴 것이 이 뜻이다. [같은 문서 #sysvar_slow_query_log, 2026-09-28 확인]

## EXPLAIN에서 볼 것

[[DB 면접 7 운영]] Q1-1(p113)의 Gold 답이 드는 네 컬럼이다. 판정은 외부 검증에서 맞음이었다.

| 컬럼 | 보는 것 | 경고 신호 |
|---|---|---|
| `type` | 접근 방식 | `ALL`(풀스캔). `ref`·`range`는 인덱스를 쓴다 |
| `rows` | 옵티마이저가 추정한 검사 행 수 | 결과 행 수에 비해 지나치게 크다 |
| `key` | 실제로 고른 인덱스 | `NULL`이거나 기대와 다른 인덱스 |
| `Extra` | 추가 작업 | `Using filesort`(인덱스로 정렬하지 못함), `Using temporary`(임시 테이블) |

- `rows`는 추정치다. 실제로 몇 행을 읽고 얼마나 걸렸는지는 `EXPLAIN ANALYZE`가 쿼리를 실제로 실행해 보여 준다. MySQL 8.0.18에 들어왔다. 도입 버전은 외부 검증 보고가 MySQL 8.0 매뉴얼에서 요약 도구로 확인한 것이다. 자료에는 `EXPLAIN ANALYZE`가 나오지 않는다.
- PostgreSQL에도 `EXPLAIN`과 `EXPLAIN ANALYZE`가 있지만 출력 형식이 다르다(노드 트리와 cost). 위의 컬럼 표는 MySQL 전용이다.

## 옵티마이저는 비용으로 고른다

인덱스를 쓸지 풀스캔을 할지는 고정 비율이 아니라 비용 추정으로 정해진다. MySQL 매뉴얼은 예전의 30% 규칙이 없어졌다고 적는다: "At one time, a scan was used based on whether the best index spanned more than 30% of the table, but a fixed percentage no longer determines the choice between using an index or a scan." [MySQL 8.4 Reference Manual, 10.2.1.1 WHERE Clause Optimization, https://dev.mysql.com/doc/refman/8.4/en/where-optimization.html , 2026-09-28 확인]

그래서 [[DB 면접 4 인덱스]] Q2-1(p65)의 "전체의 20~30% 이상을 읽으면 풀스캔이 낫다"는 경험칙으로만 쓸 수 있다. 같은 Gold 답이 "EXPLAIN으로 실제 실행 계획을 확인해서 근거를 마련하겠다"로 끝나는 것이 이 페이지와 이어지는 부분이다. Bool 인덱스의 정정 전문은 [[데이터베이스 인덱스]]에 있다.

## 느린 쿼리 대응 순서

자료의 두 Gold 답(p110 슬로우 쿼리, p116 데이터 증가)을 위키가 한 사다리로 이었다.

1. 찾기: 슬로우 쿼리 로그로 문제 쿼리를 식별한다.
2. 분석: EXPLAIN(가능하면 EXPLAIN ANALYZE)으로 풀스캔, 비효율 조인, filesort·임시 테이블을 찾는다.
3. 쿼리 수준 조치: 인덱스 추가·조정([[데이터베이스 인덱스]]), 쿼리 리팩토링(조인·서브쿼리).
4. 구조 조치: 테이블 구조 변경, 캐싱, 파티셔닝·아카이빙, Replication, 마지막으로 [[샤딩]].

[[DB 면접 7 운영]] Q4(p131)의 장애 대응 순서는 원인을 쿼리·락·리소스 세 칸으로 나누는데, 이 사다리는 그중 쿼리 칸의 절차다. 락 칸은 [[데이터베이스 락]]과 [[데드락 재현과 해법]], 리소스 칸은 [[커넥션 풀]]로 이어진다.

## 자료의 서술과 정정

| 자료의 서술 (쪽) | 판정 | 정정 |
|---|---|---|
| 슬로우 쿼리 로그(`long_query_time`)를 켜서 문제 쿼리 식별(p110) | 맞음 | 기본 10초, `min_examined_row_limit` 조건도 있다 |
| EXPLAIN의 type·rows·key·Extra를 본다(p113) | 맞음 | `rows`는 추정치. 실제 값은 EXPLAIN ANALYZE(8.0.18+) |
| 20~30% 이상 읽으면 풀스캔이 효율적(p65) | 단서 필요 | 고정 비율 규칙은 폐기됐고 옵티마이저는 비용으로 고른다([[데이터베이스 인덱스]]) |
| 데이터 증가 시 쿼리 수준 → 파티셔닝·아카이빙·캐싱·Replication → 샤딩(p116) | 맞음 | 없음 |

## 면접에서

1. 순서로 답한다: "슬로우 쿼리 로그로 찾고, EXPLAIN으로 보고, 인덱스와 쿼리를 고치고, 그래도 안 되면 구조를 바꿉니다."
2. EXPLAIN은 네 컬럼을 각각 무엇을 경고하는지와 함께 말한다(`type` ALL, `rows` 과다, `key` NULL, `Extra`의 filesort·temporary).
3. 덧붙일 것: "`rows`는 추정치라, 실제 시간은 EXPLAIN ANALYZE로 확인합니다." 자료의 Gold 답에는 없는 내용이다.
