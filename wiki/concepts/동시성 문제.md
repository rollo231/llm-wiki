# 동시성 문제

여러 스레드가 같은 변수(공유 자원)를 읽고 쓸 때 생기는 문제. Java 면접에서는 **가시성**과 **원자성** 두 가지로 나눠 묻는다
([[Java 면접 4 동시성 이슈]] p52–60). 해결 수단은 [[동기화 기법]]에 있다.

| | 가시성 (visibility) | 원자성 (atomicity) |
|---|---|---|
| 증상 | 한 스레드가 쓴 값을 다른 스레드가 **계속 못 본다** | 두 스레드의 쓰기가 섞여 **한쪽 결과가 사라진다** |
| 대표 예 | 종료 플래그 `running = false`를 바꿨는데 루프가 안 끝남 | 공유 카운터 `count++` |
| 원인 | 컴파일러·JIT 최적화, CPU의 store buffer — 아래 참고 | 한 줄짜리 연산이 사실 여러 단계 |
| 대표 해결 | `volatile` | `synchronized`, lock, atomic(CAS) |

## 원자성 — count++는 세 단계다

`count++`는 **읽기 → 1 더하기 → 쓰기**다. 스레드 A와 B가 둘 다 0을 읽고, 둘 다 1을 쓰면 두 번 더했는데 결과는 1이다. 이렇게
실행 순서(타이밍)에 따라 결과가 달라지는 상태를 **경쟁 조건**(race condition)이라 한다.

DE·백엔드 쪽 말로 옮기면 **lost update**다 — 재고 차감을 `SELECT` 후 애플리케이션에서 빼고 `UPDATE` 하면 같은 일이 DB에서
일어난다. 해법도 같은 모양이다: 한 번에 하나만 들이거나(비관적 락 ↔ `synchronized`), 읽은 값이 그대로일 때만 쓴다(낙관적
락·버전 컬럼 ↔ CAS). *(위키의 연결)*

## 가시성 — 원인은 "캐시 불일치"가 아니다

면접 자료(p54·p57)는 가시성을 "코어마다 캐시가 따로 있어서, 코어 1 캐시만 갱신되고 코어 2 캐시는 옛 값을 유지한다"로
설명한다. 직관적이지만 **틀린 모형**이다.

- **하드웨어 캐시는 이미 일관성이 유지된다.** 현대 CPU(x86·ARM)는 MESI 같은 코히런시 프로토콜로, 한 코어가 캐시 라인에 쓰면
  다른 코어의 같은 라인을 무효화한다. "캐시에 옛 값이 영원히 남는" 일은 없다.
- **실제 원인은 세 가지다.**
  1. **컴파일러·JIT 재정렬** — 단일 스레드 의미가 같다면 명령 순서를 바꿔도 된다.
  2. **레지스터 hoisting** — 루프 안에서 바뀌지 않는 것처럼 보이는 필드를 레지스터에 한 번 읽어 두고 루프 밖으로 끌어낸다.
     `while (running) {}`가 영원히 도는 고전적 사례의 주범이 이것이다.
  3. **store buffer·invalidation queue** — 코어가 쓰기를 캐시에 반영하기 전에 잠시 버퍼에 담아 둔다. 그 사이 다른 코어는 옛 값을
     읽을 수 있고, 쓰기 순서가 다른 코어에 뒤바뀌어 보일 수 있다.
- **정식 기준은 자바 메모리 모델(JMM)이다.** JLS §17.4는 어떤 쓰기를 어떤 읽기가 반드시 보는지를 **happens-before** 관계로
  정의한다. volatile 쓰기 → 같은 변수의 volatile 읽기, 모니터 해제 → 같은 모니터 획득, `Thread.start()`·`join()` 등이
  happens-before를 만든다. 이 관계가 없으면 JVM은 다른 스레드가 새 값을 볼 것을 **보장하지 않는다** — 그게 가시성 문제의
  정확한 정의다.

> "most of the interesting things are happening on the micro-scale of cache coherency, not the 'actual' main memory."
> — Aleksey Shipilëv, 「Close Encounters of The Java Memory Model Kind」 §2.4 (2016)

그래서 `volatile`도 "캐시를 우회해 RAM에 직접 간다"가 아니다. 그 변수 주변의 컴파일러 최적화를 막고 필요한 메모리 배리어를
넣어 happens-before를 만들 뿐이며, 읽기·쓰기는 여전히 L1 캐시를 거친다. 자세한 도구 설명은 [[동기화 기법]].

## 면접에서

자료의 Gold 답을 이렇게 고치면 역질문에 버틴다.

1. **두 문제를 구분한다** — 가시성(쓴 값이 안 보임)과 원자성(여러 단계 연산 사이에 끼어듦). 여기까지는 자료와 같다.
2. **가시성의 원인** — "CPU 캐시 때문"이라고 뭉뚱그리지 말고 "JIT가 값을 레지스터에 올려 두거나 명령을 재정렬하고, CPU도 store
   buffer 때문에 쓰기가 늦게·다른 순서로 보일 수 있다"고 말한다. 그리고 "그래서 JMM이 happens-before로 무엇이 보이는지를
   보장한다"로 닫는다.
3. **원자성의 원인** — `count++`의 읽기-수정-쓰기 3단계. 여기까지는 자료와 같다.
4. 역질문 "그럼 캐시를 끄면 되나요?"가 나오면 — 하드웨어 캐시는 코히런트하고, 문제는 최적화와 버퍼링을 **언제 막을지**를
   언어가 정해 주는 것이라고 답한다.

## 자료의 서술과 정정

| 자료 (쪽) | 판정 | 정정 |
|---|---|---|
| 가시성 = 코어 캐시와 RAM의 불일치 (p54·p57) | 틀림 | 캐시는 코히런트하다. 원인은 JIT 재정렬·레지스터 hoisting·store buffer, 기준은 JMM happens-before |
| volatile = CPU 캐시를 우회해 RAM에 직접 접근 (p63) | 틀림 | 최적화 금지 + 메모리 배리어로 happens-before를 보장. 캐시를 우회하지 않는다 |
| count++ = 읽기·더하기·쓰기 3단계 (p60) | 맞음 | — |
