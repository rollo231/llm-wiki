# 스레드 풀

작업을 처리할 스레드를 **정해진 수만큼 미리 만들어 두고**, 들어오는 작업을 **작업 큐**에 쌓았다가 놀고 있는 스레드가 하나씩
맡아 처리하는 기법([[Java 면접 4 동시성 이슈]] p70–72). Java에서는 `ExecutorService`(`ThreadPoolExecutor`)가 표준 구현이다.

## 왜 쓰나

1. **생성·삭제 비용** — Java의 플랫폼 스레드는 OS 스레드와 1:1이라 만들 때 시스템 콜과 스택 메모리가 든다. 재사용하면 이
   비용을 한 번만 낸다.
2. **폭증 방지(배압)** — 요청이 몰려도 스레드 수는 상한에서 멈추고 나머지는 큐에서 기다린다. 요청마다 스레드를 만들면 스레드
   수가 폭증해 메모리와 전환 비용으로 시스템 전체가 무너진다.

DE 쪽 말로 하면 **워커 수가 고정된 소비자 그룹 + 큐**다 — Kafka 컨슈머 그룹이나 Spark executor 슬롯처럼 동시성의 상한을 정해
두고 나머지는 대기시키는 구조와 같다. *(위키의 연결)* → [[Apache Kafka]] · [[Apache Spark]]

## 스레드는 몇 개가 적당한가 — Spring MVC가 수백 개를 쓰는 이유

면접 자료의 꼬리 질문(p73–75): "컨텍스트 스위칭 비용이 있는데 Spring MVC는 왜 스레드를 수백 개 두나?"

- 웹 요청 처리는 대부분 **Blocking I/O**(DB 조회, 외부 API, 파일)를 기다리는 시간이다. 기다리는 스레드는 CPU를 쓰지 않는다.
- 스레드가 코어 수만큼만 있으면 I/O 대기 중에 코어가 논다. 그래서 스레드를 늘려, 일부가 막혀 있어도 다른 스레드가 CPU를 쓰게
  한다. **전환 비용보다 CPU 가동률 이득이 크다.**
- Spring MVC가 올라타는 Tomcat의 기본값은 `maxThreads=200`(동시 처리 스레드), `acceptCount=100`(스레드가 다 찼을 때 대기할 연결
  수)이다.
- 반대로 **CPU 바운드** 작업(계산·압축·직렬화)은 스레드를 코어 수 근처로 둔다 — 늘려 봐야 전환 비용만 는다.

이것은 [[지연 시간과 처리량]]의 맞교환과 같은 축이다 — 스레드를 늘리면 CPU 가동률(처리량)은 오르지만 전환·캐시 오염 비용이
생기고, 어느 지점부터는 요청당 지연이 늘어난다. *(위키의 연결)*

## 가상 스레드 — 수백 개의 다음

면접 자료에는 없지만 이 질문의 다음 역질문은 거의 확실히 이것이다. *(위키의 관찰)*

- **가상 스레드**(Virtual thread, JDK 21, JEP 444) — JVM이 관리하는 가벼운 스레드. 수백만 개를 만들 수 있고, Blocking I/O를 만나면
  캐리어(플랫폼) 스레드에서 내려와 다른 가상 스레드에게 자리를 내준다. **"blocking 코드를 그대로 쓰면서 스레드를 수백 개가 아니라
  요청 수만큼"** 둘 수 있게 된다.
- 가상 스레드는 **풀링하지 않는다** — 생성이 싸므로 작업마다 새로 만든다(`Executors.newVirtualThreadPerTaskExecutor()`). 동시성
  상한이 필요하면 풀 크기가 아니라 `Semaphore` 같은 것으로 건다.
- Spring Boot 3.2+는 `spring.threads.virtual.enabled=true` 한 줄로 Tomcat 요청 처리를 가상 스레드로 바꾼다.
- 초기의 함정 — `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 묶이는 **pinning**이 있었다. JDK 24(JEP 491)에서 해결.
  → [[동기화 기법]]
- CPU 바운드 작업은 빨라지지 않는다. 가상 스레드가 푸는 것은 "I/O 대기 중인 스레드가 비싸다"는 문제뿐이다.

## 면접에서

- **Q3(스레드 풀이란)** — 자료의 Gold 답(작업 큐 + 생성 비용 절약 + 폭증 방지)으로 충분하다.
- **Q3-1(Spring MVC 수백 개)** — 자료의 Gold 답(Blocking I/O 동안 CPU가 놀지 않게)에 두 가지를 덧붙인다: ① Tomcat 기본
  `maxThreads=200`, CPU 바운드면 코어 수 근처라는 대비 ② 대안으로 가상 스레드(JDK 21)와 Spring Boot 3.2의 설정, 그리고 WebFlux 같은
  논블로킹 모델과의 차이 — 가상 스레드는 코드 모양을 바꾸지 않는다.
