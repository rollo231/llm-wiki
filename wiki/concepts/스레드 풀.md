# 스레드 풀

작업을 처리할 스레드를 **정해진 수만큼 미리 만들어 두고**, 들어오는 작업을 **작업 큐**에 쌓았다가 놀고 있는 스레드가 하나씩
맡아 처리하는 기법([[Java 면접 4 동시성 이슈]] p70–72). Java에서는 `ExecutorService`(`ThreadPoolExecutor`)가 표준 구현이다.

## 왜 쓰나

1. **생성·삭제 비용** — Java의 플랫폼 스레드는 OS 스레드와 1:1이라 만들 때 시스템 콜과 스택 메모리가 든다. 재사용하면 이
   비용을 한 번만 낸다.
2. **폭증 방지(배압)** — 요청이 몰려도 스레드 수는 상한에서 멈추고 나머지는 큐에서 기다린다. 요청마다 스레드를 만들면 스레드
   수가 폭증해 메모리와 전환 비용으로 시스템 전체가 무너진다.

DE 쪽 말로 하면 **워커 수가 고정된 소비자 그룹 + 큐**다 — Kafka 컨슈머 그룹이나 Spark executor 슬롯처럼 동시성의 상한을 정해
두고 나머지는 대기시키는 구조와 같다. *(위키의 연결)* → [[Apache Kafka]] · [[Apache Spark]]

## ThreadPoolExecutor는 어떤 순서로 늘리나

`ThreadPoolExecutor(core, max, keepAlive, unit, queue)`의 규칙은 직관과 반대다. **core까지 스레드 → 큐 → 큐가 차면 max까지 스레드 →
거절** 순이다. 로컬 JDK 25에서 core=2, max=4로 0.5초짜리 작업 10개를 넣었다(2026-09-27).

| 큐 | 결과 |
|---|---|
| `LinkedBlockingQueue()` (무제한) | 스레드는 **끝까지 2개**. 나머지 8개는 큐에 쌓인다 — max=4는 한 번도 쓰이지 않는다 |
| `ArrayBlockingQueue(3)` | 2개 → 큐 3개가 찬 뒤에야 3 · 4개 → 8번째 작업에서 `RejectedExecutionException` |

- 그래서 **무제한 큐를 주면 max는 의미가 없다.** `Executors.newFixedThreadPool(n)`이 core = max = n에 무제한 큐인 이유이고,
  동시에 큐가 끝없이 자라 메모리를 먹을 수 있다는 뜻이다 → [[객체 수명과 메모리 상한]]
- **Tomcat은 이 순서를 뒤집는다.** Tomcat의 `TaskQueue.offer()`는 놀고 있는 스레드가 없고 스레드 수가 max보다 적으면 `false`를 돌려준다
  ("if we have less threads than maximum force creation of a new thread"). 큐에 넣기를 거부당한 `ThreadPoolExecutor`가 스레드를 새로
  만든다. 결과적으로 **스레드를 max(200)까지 먼저 늘리고, 그다음에 큐에 쌓는다.** 요청을 기다리게 하기보다 바로 처리하는 쪽을
  고른 것이다. [Apache Tomcat 소스 `java/org/apache/tomcat/util/threads/TaskQueue.java`, 10.1.x, https://github.com/apache/tomcat , 2026-09-27 확인]

## 스레드는 몇 개가 적당한가 — Spring MVC가 수백 개를 쓰는 이유

면접 자료의 꼬리 질문(p73–75): "컨텍스트 스위칭 비용이 있는데 Spring MVC는 왜 스레드를 수백 개 두나?"

- 웹 요청 처리는 대부분 **Blocking I/O**(DB 조회, 외부 API, 파일)를 기다리는 시간이다. 기다리는 스레드는 CPU를 쓰지 않는다.
- 스레드가 코어 수만큼만 있으면 I/O 대기 중에 코어가 논다. 그래서 스레드를 늘려, 일부가 막혀 있어도 다른 스레드가 CPU를 쓰게
  한다. **전환 비용보다 CPU 가동률 이득이 크다.**
- **몇 개가 필요한지는 계산할 수 있다.** 동시에 처리 중인 요청 수 = 초당 요청 수 × 요청 하나의 처리 시간(리틀의 법칙, L = λW).
  초당 1,000건이 각각 100ms 걸리면 늘 100건이 처리 중이다. 요청 하나가 스레드 하나를 쥐는 Spring MVC에서는 그대로 **스레드 100개**다.
  CPU 쪽에서 보면 필요한 스레드 ≈ 코어 수 × (1 + 대기 시간 / 계산 시간)이다. 10코어에서 요청이 계산 10ms + DB 대기 90ms면 10 × (1 + 9) = 100.
  *(두 식 모두 널리 쓰이는 공식이다 — 뒤의 것은 Java Concurrency in Practice 8.2의 것으로 알려져 있으나 원문은 확인하지 않았다)*
- Spring MVC가 올라타는 Tomcat의 기본값(Tomcat 10.1 문서, Spring Boot `server.tomcat.*`도 같다):

  | 설정 | 기본값 | 뜻 |
  |---|---|---|
  | `maxThreads` | 200 | 요청을 처리하는 스레드 수의 상한 = 동시에 처리할 수 있는 요청 수 |
  | `minSpareThreads` | 10 | 놀 때도 남겨 두는 스레드 |
  | `maxConnections` | 8192 (NIO) | 받아 둘 수 있는 연결 수. **스레드가 다 차도 연결은 여기까지 받는다** — "Connections are queued inside the server socket created by the Connector until a thread becomes available" |
  | `acceptCount` | 100 | `maxConnections`까지 찬 뒤에 **OS가** 쌓아 두는 연결 대기열. 이것도 차면 연결이 거절되거나 시간 초과된다 |

  그래서 요청이 몰릴 때의 순서는 **스레드 200 → 연결 8192까지 받아 두고 기다림 → OS 대기열 100 → 거절**이다.
  ⚠️ 위키 정정(2026-09-27): 처음에 `acceptCount`를 "스레드가 다 찼을 때 대기할 연결 수"로 적었다. Spring Boot의 속성 설명("when all
  possible request processing threads are in use")이 그렇게 적지만, Tomcat 문서는 "when `maxConnections` has been reached"라고 한다.
  위키는 Tomcat 문서를 따른다. [Apache Tomcat 10.1 HTTP Connector, https://tomcat.apache.org/tomcat-10.1-doc/config/http.html ;
  Spring Boot 소스 `TomcatServerProperties.java`(main), https://github.com/spring-projects/spring-boot , 2026-09-27 확인]
- **스레드를 늘려도 DB 커넥션 풀이 병목이 된다.** Spring Boot 기본 커넥션 풀인 HikariCP의 기본 크기는 10이다(`DEFAULT_POOL_SIZE = 10`).
  요청 스레드 200개가 모두 DB를 쓰면 190개는 커넥션을 기다린다. 스레드 수는 그 뒤에 있는 자원(커넥션 풀, 외부 API의 한도)과 함께
  정해야 한다. [HikariCP 소스 `HikariConfig.java`, https://github.com/brettwooldridge/HikariCP , 2026-09-27 확인] *(위키의 연결)*
- 반대로 **CPU 바운드** 작업(계산·압축·직렬화)은 스레드를 코어 수 근처로 둔다 — 늘려 봐야 전환 비용만 는다.

이것은 [[지연 시간과 처리량]]의 맞교환과 같은 축이다 — 스레드를 늘리면 CPU 가동률(처리량)은 오르지만 전환·캐시 오염 비용이
생기고, 어느 지점부터는 요청당 지연이 늘어난다. *(위키의 연결)*

## 가상 스레드 — 수백 개의 다음

면접 자료에는 없지만 이 질문의 다음 역질문은 거의 확실히 이것이다. *(위키의 관찰)*

- **가상 스레드**(Virtual thread, JDK 21, JEP 444) — JVM이 관리하는 가벼운 스레드. 수백만 개를 만들 수 있고, Blocking I/O를 만나면
  캐리어(플랫폼) 스레드에서 내려와 다른 가상 스레드에게 자리를 내준다. **"blocking 코드를 그대로 쓰면서 스레드를 수백 개가 아니라
  요청 수만큼"** 둘 수 있게 된다. 가벼운 이유 하나는 스택을 OS 스레드 스택이 아니라 힙에 두기 때문이다 → [[JVM 메모리 구조]] 가상 스레드의 스택.
- 가상 스레드는 **풀링하지 않는다** — 생성이 싸므로 작업마다 새로 만든다(`Executors.newVirtualThreadPerTaskExecutor()`). 동시성
  상한이 필요하면 풀 크기가 아니라 `Semaphore` 같은 것으로 건다.
- 반대로 플랫폼 스레드 풀의 스레드는 죽지 않으므로, `ThreadLocal`을 `remove()` 없이 쓰면 값이 남는다 → [[객체 수명과 메모리 상한]] 안티패턴.
- Spring Boot 3.2+는 `spring.threads.virtual.enabled=true` 한 줄로 Tomcat 요청 처리를 가상 스레드로 바꾼다.
- 초기의 함정 — `synchronized` 블록 안에서 블로킹하면 캐리어 스레드에 묶이는 **pinning**이 있었다. JDK 24(JEP 491)에서 해결.
  → [[동기화 기법]]
- CPU 바운드 작업은 빨라지지 않는다. 가상 스레드가 푸는 것은 "I/O 대기 중인 스레드가 비싸다"는 문제뿐이다.

## 면접에서

- **Q3(스레드 풀이란)** — 자료의 Gold 답(작업 큐 + 생성 비용 절약 + 폭증 방지)으로 충분하다.
- **Q3-1(Spring MVC 수백 개)** — 자료의 Gold 답(Blocking I/O 동안 CPU가 놀지 않게)에 세 가지를 덧붙인다: ① Tomcat 기본
  `maxThreads=200`, CPU 바운드면 코어 수 근처라는 대비, 그리고 "초당 요청 × 처리 시간"으로 필요한 수를 계산해 보이기
  ② 스레드를 늘려도 커넥션 풀(Hikari 기본 10)이 병목이 될 수 있다는 것 ③ 대안으로 가상 스레드(JDK 21)와 Spring Boot 3.2의 설정, 그리고 WebFlux 같은
  논블로킹 모델과의 차이 — 가상 스레드는 코드 모양을 바꾸지 않는다.
