# Data semantics

**스키마가 형식을 정의한다면, 시멘틱은 의미를 정의한다.** Part 3 전체의 축이자, 그래프·온톨로지·
GraphRAG가 왜 필요한지를 설명하는 전제다.

> **"시멘틱은 데이터 해석의 계약(contract)이다."**

## 스키마가 못 하는 일

스키마는 컬럼/타입/제약을 통해 **저장 구조**를 보장한다. 하지만 알지 못하는 것:

- 이 값이 **어떤 기준으로 계산됐는지**
- 어떤 조건을 **포함/제외하는지**
- 어떤 **기간/타임존/시점**을 기준으로 하는지

구체적으로, 스키마만으로는 이런 걸 설명할 수 없다:

- `user_id`와 `member_id`가 **같은 개념인가**
- `created_at`이 **생성** 시각인가 **가입** 시각인가 **주문** 시각인가
- `status` 값이 **업무** 상태인가 **결제** 상태인가 **배송** 상태인가
- 두 테이블의 연결이 **식별 관계**인가 **이벤트 관계**인가 **집계 관계**인가

## ⭐ 시멘틱이 없으면 생기는 일

### 같은 KPI가 여러 개가 된다

> **한 회사에서 매출 숫자가 3개 이상 나오는 이유:**
> 정의가 SQL에 흩어지고 · 팀마다 제외 조건이 다르고 · **지표가 계약이 아니라 쿼리가 된다.**
>
> 결과: 숫자 맞추기 회의, 분석 신뢰도 하락.

### SQL이 비즈니스 로직이 된다

지표 정의가 **코드로만 존재**하면 재사용이 안 되고 변경 영향을 추적할 수 없다.
KPI 하나 바꾸면 대시보드를 전면 수정해야 하고, 실험/리포트 결과가 일관되지 않는다.

### 같은 대상을 시스템마다 다른 이름으로 관리한다

`user_id`, `member_id`, `customer_id`, `account_id` — 그리고 `active user`, `conversion`,
`retention`, `revenue`가 팀마다 다르게 정의된다. 문서·로그·테이블·메타데이터가 분리되어 존재하니
**사람이 직접 맥락을 추론해야 질의가 가능하다.**

귀결: 데이터 통합 비용 증가 · 지표 해석 충돌 · **잘못된 조인과 잘못된 결론** · 검색은 되지만 정확한
연결이 약함 · RAG·추천·QA 품질 저하.

## 시멘틱을 구성하는 네 요소

| | 정의 | 예 |
|---|---|---|
| **Entity** | 의미적으로 독립된 대상 | 사용자, 주문, 상품, 콘텐츠, 세션, 모델, 피처 |
| **Attribute** | 개체가 가진 속성 | 사용자 나이, 상품 카테고리, 주문 금액, 콘텐츠 장르 |
| **Relationship** | 개체와 개체 사이의 연결 | 사용자가 주문을 생성, 상품이 카테고리에 속함 |
| **Context** | 데이터가 해석되는 조건과 배경 | 시간, 채널, 지역, 정책 버전, 실험군, 모델 버전 |

### Context가 왜 별도 요소인가

**같은 데이터도 맥락이 달라지면 의미가 달라지기 때문**이다. 같은 용어라도 조직과 시스템에 따라
의미가 다를 수 있다.

- `active_user` — 최근 7일 로그인? 최근 30일 유효 행동? 유료 사용자만?
- `Revenue` — 총 결제 금액? 취소 제외 순매출? 세전/세후?

> 이 관찰은 [[Feature store]]의 Feature 재정의(`total_order_count` ❌ →
> `total_order_count_last_30_days_as_of_t` ⭕)와 **같은 이야기다.** Feature 이름에 window와 기준
> 시점을 박는 것이 곧 Context를 이름에 넣는 것이다.

## 스키마 중심 사고 vs 시멘틱 중심 사고

| 스키마 중심이 묻는 것 | 시멘틱 중심이 묻는 것 |
|---|---|
| 어떤 테이블에 저장할 것인가 | 이 데이터는 **어떤 개체**를 표현하는가 |
| 어떤 컬럼 타입을 가질 것인가 | 어떤 **속성과 관계**를 가지는가 |
| 어떤 키로 조인할 것인가 | 다른 시스템의 **어떤 개념과 연결**되는가 |
| | 어떤 **문맥**에서 해석해야 하는가 |

**스키마 중심은 저장 최적화에 강하고, 시멘틱 중심은 연결·탐색·재사용·해석에 강하다.**
강의의 결론: **AI 시대 데이터 엔지니어는 두 관점을 함께 다뤄야 한다.**

## AI가 시멘틱을 더 요구한다

전통적 BI는 정해진 집계와 리포트 중심이다. AI/LLM 기반 시스템은 더 복잡한 질문을 다룬다:

- 이 사용자와 비슷한 성향의 고객은 누구인가
- 이 문서와 관련된 정책·제품·팀은 무엇인가
- 이 장애와 과거 유사한 이슈는 무엇인가
- 이 피처가 어떤 모델·데이터셋·서비스와 연결되는가

AI가 자주 요구하는 것: 의미 기반 검색 · 개체 간 연결 탐색 · 이질적 소스 통합 · 문맥 기반 해석 ·
동일 개념 정규화.

## 시멘틱의 실무 스펙트럼

**용어 사전에서 그래프까지 이어지는 연속선**이고, 어디까지 갈지가 설계 결정이다.

| 강도 | 형태 |
|---|---|
| 가장 약한 형태 | 공통 용어 정의 · 지표 사전 · **데이터 카탈로그** · 컬럼 설명 |
| 더 구조화된 형태 | 공통 엔터티 모델 · **표준 식별자 체계** · 도메인 간 관계 정의 |
| 더 발전한 형태 | **[[Ontology|온톨로지]]** · **[[Knowledge graph|지식 그래프]]** · semantic layer · context-aware retrieval |

> ⭐ **이 스펙트럼이 Part 3의 뼈대다.** Ch1은 왼쪽 끝(왜 필요한가), Ch2~Ch3은 오른쪽 끝
> (그래프·온톨로지), Ch4는 그 위의 활용(GraphRAG)이다.
> 그리고 **[[Data catalog and semantic layer]]가 이미 왼쪽~가운데를 다루고 있다** — 두 페이지는
> 같은 스펙트럼의 다른 구간이다.

## 요약

> **"RDBMS는 구조를 잘 다루고, NoSQL은 유연성과 확장을 잘 다룬다.
> 하지만 둘 다 데이터의 의미를 자동으로 설명하지는 못한다.
> 시멘틱은 개념·관계·문맥을 해석 가능하게 만드는 계층이다."**
