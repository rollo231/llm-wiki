# 서비스 수준 목표

서비스가 얼마나 잘 동작해야 하는지를 측정 가능한 숫자로 정한 목표(SLO)와, 그 목표를 받치는 지표(SLI)·외부 계약(SLA)·실패 여유분(Error Budget)의 묶음이다. Google SRE 책이 정리한 틀이고, [[AI DE 강의 4-15 AI 시스템 지표와 SLA]]가 이 틀을 AI 시스템의 여러 경로에 적용한다.

## 네 단계

| 단계 | 뜻 | 강의 예시(p9) |
|---|---|---|
| SLI (Service Level Indicator) | 실제로 측정하는 지표 | 최근 30일 동안 정상 응답한 추론 요청 비율 |
| SLO (Service Level Objective) | SLI에 대한 내부 목표 | 정상 응답 비율 99.9% 이상 |
| SLA (Service Level Agreement) | 고객·조직과 공식적으로 맺은 약속. 미달 시 보상 같은 결과가 붙는다 | 고객에게 월간 99.5% 이상 가용성 |
| Error Budget | SLO가 허용하는 실패 여유분 | 99.9% SLO라면 30일 동안 0.1% 실패 허용 |

- SLA는 SLO보다 느슨하게 둔다. 내부 목표를 외부 약속보다 빡빡하게 두어야 사용자가 알아채기 전에 대응할 여유가 생긴다. SRE 책의 표현은 "Using a tighter internal SLO than the SLO advertised to users gives you room to respond to chronic problems before they become visible externally."다. [https://sre.google/sre-book/service-level-objectives/ , 2026-09-28 확인] 강의 p9의 예(SLO 99.9%, SLA 99.5%)는 이 원칙과 맞지만, p10 표의 예시는 SLA와 SLO를 같은 99.9%로 둔다([[AI DE 강의 4-15 AI 시스템 지표와 SLA]]의 주의·결함).
- Error Budget을 시간으로 환산하면 99.9%는 30일에 약 43분(43.2분)이다. 위키의 계산이다. 요청 비율로 정의한 SLI라면 허용 실패도 요청 수로 센다.
- Error Budget은 운영 판단에 쓰인다. 예산이 남으면 배포·실험을 계속하고, 소진되면 안정화에 집중한다는 식이다. 강의는 정의만 주고 이 쓰임은 다루지 않는다. 이 문장은 SRE의 일반적 용법을 위키가 요약한 것이다.

## [[데이터 SLA]]와의 관계

Part 1의 [[데이터 SLA]]는 "SLA"를 생산자와 소비자 사이의 데이터 품질 약속 전반을 가리키는 넓은 말로 쓴다. 신선도 p95·p99, 08:00 데드라인 같은 목표값은 이 페이지의 구분으로는 SLO에 해당하고, 이를 어기면 보상이 따르는 대외 계약일 때만 엄밀한 의미의 SLA다. 두 페이지를 잇는 이 구분은 위키가 한 것이다. Part 4는 데이터 SLA를 AI 시스템 SLA의 한 층위로 둔다(p11).

## AI 시스템의 다섯 층위

[[AI DE 강의 4-15 AI 시스템 지표와 SLA]] p11은 AI 시스템의 SLA/SLO를 다섯 층으로 나눈다. 같은 다섯 층이 모니터링 지표의 계층으로 다시 나온다([[AI 시스템 모니터링]]).

| 층 | 무엇을 거나 |
|---|---|
| 서비스 | 요청 성공률, 응답 지연, 가용성 |
| 데이터 | freshness, completeness, schema 안정성 ([[데이터 SLA]]) |
| 모델 품질 | 정확도, drift, score distribution, segment별 성능 ([[데이터 드리프트]]) |
| 인프라 | GPU availability, GPU memory headroom, queue length, node readiness ([[GPU 할당과 스케줄링]]) |
| 비용 | cost per inference, idle GPU cost, batch job 비용 한도 |

## 워크로드별 SLI와 SLO

AI 시스템은 온라인 추론·배치 추론·학습·모니터링 네 경로가 동시에 움직이고, 경로마다 목표가 다르다(p4–5). 강의가 워크로드마다 든 예시를 모았다. 수치는 모두 자료의 예시이고 권장값이 아니다.

| 워크로드 | 목표 | 대표 SLI | SLO 예시 | 쪽 |
|---|---|---|---|---|
| 온라인 추론 | 요청한 순간 빠르고 안정적으로 응답 | 정상 응답 비율, p95·p99 latency, timeout·model unavailable·feature lookup 실패율, queueing delay, TTFT, tokens per second | 30일 정상 응답률 99.9%, p95 300ms, p99 1s, feature lookup 실패율 0.1%, LLM 첫 토큰 p95 1s | p17 |
| 배치 추론 | 정해진 시간 안에 대량 예측을 만들어 downstream이 쓰게 함 | job success rate, deadline miss count, prediction table freshness, processed row count, failed partition, retry, output completeness, cost per run | 매일 07:00 KST 전 생성, 대상 user 99.5% scoring, 실패 partition 0.5%, 재시도 후 성공률 99%, 월 예산 이하 | p18 |
| 피처 스토어 | 학습·추론에 일관된 feature, 온라인 조회는 빠르게 | online lookup latency, feature availability·freshness, missing feature ratio, offline-online skew, schema violation, pipeline success rate | online lookup p99 50ms, 주요 feature freshness 5분, missing 0.1%, offline-online mismatch 0.1%, pipeline 성공률 99% | p19 |
| 학습 파이프라인 | 정확한 데이터셋, 재현성, 완료 시각 | dataset generation success rate, completeness, validation failure count, training job success rate, experiment runtime, registry 등록 성공 | 학습 데이터셋 매일 09:00 전 생성, 데이터 검증 실패 시 학습 job 시작 금지 | p20–21 |
| 모델 모니터링 | 버전별 품질 변화와 분포 변화 감지 | serving log ingestion delay, prediction-label join delay, drift·quality metric freshness, alert evaluation delay, segment별 metric completeness | serving log 10분 내 반영, label 도착 후 1시간 내 join, drift metric 매일 1회 이상 | p20–21 |

- 온라인 추론은 지연, 배치 추론은 마감 시각, 학습은 완료 시각과 검증 게이트, 모니터링은 반영 지연을 SLO로 건다. 가용성 숫자 하나로 AI 시스템을 설명하지 못하는 이유다.
- 피처 스토어의 offline-online mismatch SLO는 [[학습-서빙 스큐]]를 운영 목표로 바꾼 것이고([[피처 스토어]]), 학습의 "검증 실패 시 시작 금지"는 [[데이터 관측성]]의 서킷 브레이커와 같은 생각이다. 두 연결은 위키의 관찰이다.

## LLM 서비스 지표

강의 p12가 드는 LLM 전용 서비스 지표는 time to first token(첫 토큰까지의 시간), time per output token(토큰 생성 속도), tokens per second(전체 생성 처리량), prompt·output 길이에 따른 latency 변화다. 비용 쪽에는 cost per 1M tokens가 있다(p16). 첫 토큰 지연은 사용자가 체감하는 응답성이고 토큰 속도는 긴 답변의 체감 속도라서 둘을 따로 건다는 해석은 위키의 것이다.

## 좋은 지표의 조건

강의 p7–8의 기준은 SLI를 고를 때도 그대로 쓸 수 있다. 사용자 경험과 연결되고, 운영자가 행동할 수 있고, 측정 방법·시간 범위·소유자가 정해져 있고, 알람 기준으로 바꿀 수 있어야 한다. 평균만 보는 지표(tail latency를 놓침), GPU 사용률만 보는 지표, 정확도만 보는 지표(freshness 문제를 숨김), 「200 OK」만 보는 지표는 나쁜 예다. 꼬리 지연을 보는 이유는 [[지연 시간과 처리량]]에 있다.
