# 피처 스토어

모델이 쓰는 피처를 **한 번 정의해, 학습용(대량 이력)과 서빙용(실시간 최신값)으로 같은 결과를 제공하는 저장소.**
Part 1에서 [[학습-서빙 스큐]]의 해결책으로 소개되고, Part 2의 [[AI DE 강의 2-10 Feature Store 기본 개념]]이 따로 한
덱을 쓴다. 강의의 한 줄: "성능 향상 도구가 아니라 **ML 시스템의 안정성을 위한 인프라**."

## 피처란 무엇인가 — 계산 규칙 + 시점 + 스키마

[[AI DE 강의 2-10 Feature Store 기본 개념]]의 재정의: 피처는 컬럼도 원천 데이터도 아니고, **특정 시점 기준으로 계산된
의미 있는 값**이다. `total_order_count`가 아니라 `total_order_count_last_30_days_as_of_t`. 그래서 피처는 "계산 규칙 +
시점 + 스키마의 묶음"이고, 피처 스토어는 피처를 **데이터가 아니라 운영 대상 자산**으로 관리하는 시스템이다.

## 구조

[[AI DE 강의 1-13 Skew와 Drift]]:

```
배치 소스(DW·레이크) ─┐
                     ├→ 피처 변환(하나의 로직) ─┬→ 오프라인 스토어 → 학습   get_historical_features()
스트림 소스(Kafka) ───┘                         └→ 온라인 스토어  → 서빙   get_online_features()
                          피처 레지스트리·메타데이터
```

| | 오프라인 스토어 | 온라인 스토어 |
|---|---|---|
| 담는 것 | 대용량 이력 | 키별 최신값 |
| 용도 | 학습 데이터셋 생성, **과거 시점 피처 재현** | 실시간 추론 시 조회 |
| 저장소 예 | S3, BigQuery, Snowflake, Parquet·Hive | Redis, DynamoDB, Cassandra |
| 요구 | 처리량, **시간 기준 조회**, 대량 조인·집계 | 지연 시간(밀리초), 높은 가용성 |
| 제약 | — | **모든 피처를 온라인에 둘 수는 없다** |

([[AI DE 강의 2-10 Feature Store 기본 개념]]이 더한 칸은 굵게)

도구: Feast, Tecton, Hopsworks, Vertex AI Feature Store.

## 피처 스토어 없이 운영할 때

[[AI DE 강의 2-10 Feature Store 기본 개념]]이 그리는 "없는 구조": 오프라인은 Spark/SQL로 피처를 만들어 CSV·Parquet로
저장하고, 온라인은 API 서버가 직접 재계산하거나 Redis·DB를 ad-hoc 조회한다. 피처가 늘면서 생기는 일:

- 같은 피처를 팀마다 다시 구현한다.
- 학습용 SQL과 서빙용 코드가 갈라진다 → [[학습-서빙 스큐]]
- 변경 이력이 없어 **어떤 모델이 어떤 피처를 쓰는지 모른다** → 실험을 재현할 수 없고, 장애 원인 추적이 느리거나 불가능하다.
  → [[데이터 거버넌스와 카탈로그]]

## 무엇을 해결하나

강의가 드는 등장 배경 네 가지는 피처 정의의 단일화, 학습/서빙 일관성, 재사용, 운영 자동화다.

- **스큐 제거** — 학습과 서빙이 같은 변환 로직을 거친 값을 읽는다. "Write Once, Compute Anywhere."
- **실시간 조회** — 이상 거래 탐지에서 결제 요청이 오면 최근 위치 같은 피처를 Redis 피처 스토어에서 꺼내 모델 점수를
  낸다([[AI DE 강의 1-10 배치 vs 스트리밍]]).
- **재사용** — 데이터 준비 시간의 병목을 피처 추출 로직의 재사용으로 줄인다([[AI DE 강의 1-16 AI 파이프라인 구축 사례]]).

## 서빙 경로에서

[[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]의 온라인 서빙에서 Online Feature Store/Cache(Redis·DynamoDB·Feast
Online Store)는 요청 경로 한가운데 있다 — Feature Key 추출 → 조회 → 결합·전처리 → 추론. 운영 요소로 "Feature 조회 실패
시 기본값"과 "일부 Feature Store 장애 허용"을 든다. 이 기본값이 학습 쪽 결측 처리와 다르면 스큐가 된다.
→ [[학습-서빙 스큐]] · [[모델 서빙]]

## 언제 필요 없나

[[AI DE 강의 2-10 Feature Store 기본 개념]]: "항상 필요한 기본 인프라가 아니다."

| 생각해 볼 조건 | 불필요한 경우 |
|---|---|
| 피처가 실시간·서빙에 반드시 필요한가 | 클라이언트가 값을 이미 안다 |
| 계산 비용이 높아 중복 실행을 피해야 하나 | 데이터 웨어하우스에 이미 있다 |
| 여러 모델·팀이 공유해야 하나 | 시간 의존성이 없다 |
| | 배치 서빙만 필요하다 |
| | 계산 비용이 낮다 |

출처는 Lak Lakshmanan의 글이다 — "tldr: Use a feature store if you need to inject features server-side, especially if
the method of computing these features will keep improving. Otherwise, it is overkill." 필자는 당시 Google Cloud
소속이었다. [Lak Lakshmanan, "Do You Really Need a Feature Store?", *Towards Data Science*, 2022-02-02,
https://medium.com/data-science/do-you-really-need-a-feature-store-e59e3cc666d3 , 2026-09-14 확인]

## 거버넌스

[[AI DE 강의 1-13 Skew와 Drift]]가 데이터 엔지니어의 새 책임으로 드는 것: 피처 재사용성·표준화, 피처의 데이터 계보

## 빈칸

- **시점 정합성(point-in-time correctness)** — 학습 데이터를 만들 때 각 레이블 시점에 **그때 알 수 있었던** 피처 값만
  붙여야 미래 정보가 새지 않는다. Part 1은 설명하지 않았고, **Part 2는 시간 차원에 이름을 붙였다**(`as_of_t`, 오프라인
  스토어의 "과거 시점 재현·시간 기준 조회"). 그러나 그것을 보장하는 **조인**은 여전히 보여 주지 않는다. 1차 자료의 설명:
  Feast의 `get_historical_features()`는 엔티티 행의 `event_timestamp`를 "upper bound (inclusive)"로 삼아 "a
  point-in-time join (also called a "last known good value" temporal join)"을 수행하고, 이것이 "critical to prevent
  data leakage during model training"이라고 한다.
  [https://docs.feast.dev/getting-started/concepts/feature-retrieval , 2026-09-14 확인] → [[데이터 누수]]
- 오프라인·온라인 스토어를 어떻게 동기화하는지(배치 적재 vs 스트리밍 쓰기), 둘의 불일치를 어떻게 측정하는지는
  Part 2에서도 다루지 않는다. 덱 제목의 "운영"이 비어 있다.
- Ch1 p23 그림의 출처(Simba Khadder, Featureform, 2022-11-30 — 현재 redis.io로 이전)는 피처 스토어 아키텍처를 literal·
  physical·virtual 세 가지로 나누는데, 강의는 이 구분을 설명하지 않는다.
