# 피처 스토어

모델이 쓰는 피처를 **한 번 정의해, 학습용(대량 이력)과 서빙용(실시간 최신값)으로 같은 결과를 제공하는 저장소.**
Part 1에서 [[학습-서빙 스큐]]의 해결책으로 소개된다.

## 구조

[[AI DE 강의 1-13 Skew와 Drift]]:

```
배치 소스(DW·레이크) ─┐
                     ├→ 피처 변환(하나의 로직) ─┬→ 오프라인 스토어 → 학습   get_historical_features()
스트림 소스(Kafka) ───┘                         └→ 온라인 스토어  → 서빙   get_online_features()
                          피처 레지스트리·메타데이터
```

| | 오프라인 스토어 | 온라인 스토어 |
|---|---|---|
| 담는 것 | 대용량 이력 | 키별 최신값 |
| 용도 | 학습 데이터셋 생성 | 실시간 추론 시 조회 |
| 저장소 예 | S3, BigQuery, Snowflake | Redis, DynamoDB, Cassandra |
| 요구 | 처리량 | 지연 시간(밀리초) |

도구: Feast, Tecton, Hopsworks, Vertex AI Feature Store.

## 무엇을 해결하나

- **스큐 제거** — 학습과 서빙이 같은 변환 로직을 거친 값을 읽는다. "Write Once, Compute Anywhere."
- **실시간 조회** — 이상 거래 탐지에서 결제 요청이 오면 최근 위치 같은 피처를 Redis 피처 스토어에서 꺼내 모델 점수를
  낸다([[AI DE 강의 1-10 배치 vs 스트리밍]]).
- **재사용** — 데이터 준비 시간의 병목을 피처 추출 로직의 재사용으로 줄인다([[AI DE 강의 1-16 AI 파이프라인 구축 사례]]).

## 거버넌스

[[AI DE 강의 1-13 Skew와 Drift]]가 데이터 엔지니어의 새 책임으로 드는 것: 피처 재사용성·표준화, 피처의 데이터 계보
추적, 정답 라벨(ground truth) 피드백 연결. 피처도 스키마·윈도우 크기·예외 처리 규칙을 담은 **계약**으로 관리한다.
→ [[데이터 거버넌스와 카탈로그]]

## 빈칸

- **시점 정합성(point-in-time correctness)** — 학습 데이터를 만들 때 각 레이블 시점에 **그때 알 수 있었던** 피처 값만
  붙여야 미래 정보가 새지 않는다. `get_historical_features()`의 핵심 기능인데 Part 1은 설명하지 않는다.
- 오프라인·온라인 스토어를 어떻게 동기화하는지(배치 적재 vs 스트리밍 쓰기), 둘의 불일치를 어떻게 측정하는지는
  다루지 않는다.
