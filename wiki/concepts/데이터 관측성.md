# 데이터 관측성

파이프라인 내부의 **데이터 상태(볼륨·신선도·스키마·분포)를 시스템이 자동으로 수집·감시해, 문제가 하류로
번지기 전에 발견하고 막는 능력.** [[데이터 SLA]]가 "무엇을 약속하나"라면 관측성은 "그 약속을 어떻게 지키나"다.

## 수동 확인에서 자동 감시로

| 수동 확인 | 데이터 관측성 |
|---|---|
| 수천 개 파이프라인과 TB급 데이터를 사람이 볼 수 없다 | 볼륨·신선도·스키마 변경·값 분포를 24시간 자동 수집 |
| 지연·누락을 뒤늦게 알아 골든타임을 놓친다 | 과거 정상 패턴을 학습한 이상 탐지로 먼저 잡는다 |
| 피로로 인한 실수 | 하류로 번지기 전에 차단 |

## 알림 설계 — 경고 피로 방지

- **비즈니스 임팩트로 거른다** — 모든 오류가 응급은 아니다. 핵심 SLA 위반만 울린다.
- **동적 임계치** — 고정값 대신 시간대·계절성을 반영한다.
- **채널을 나눈다** — 경미한 이슈는 대시보드, 심각한 장애만 온콜 전화.

## 장애 대응

감지 → 격리 → 완화 → 원인 규명 → 복구. 소비 팀에 "문제를 인지했고 복구 예정"을 즉시 알리는 것이 신뢰 유지의
첫걸음이다. 원인 규명은 근본 원인 분석(RCA)과 재발 방지 대책(CAPA)으로 끝낸다. 원인을 역추적할 때는 데이터
계보가 쓰인다([[데이터 거버넌스와 카탈로그]]).

## 서킷 브레이커 — "멈춤이 최선의 품질"

데이터가 이동하는 단계 사이(소스 → 게이트 → 모델)에 품질 게이트를 둔다. 사전 정의한 규칙을 위반하면
(예: Null 비율 1% → 50%) **스위치를 내려 하류 전파를 막고 안전 모드로 전환한다**(예: 어제 데이터 사용).
"망가진 데이터로 모델을 망칠 바에는 멈추는 것이 낫다."

드리프트 쪽의 대응은 반대로 **자동 재학습**이다. 두 자동화는 방향이 반대라서 쿨다운 기간과 사람 승인 같은
안전장치가 함께 나온다([[AI DE 강의 1-13 Skew와 Drift]]). *(위키의 대조)*

## 빈칸

- 관측성 도구와 이상 탐지 방법은 Part 1에 구체적으로 나오지 않는다.
- 서킷 브레이커가 열렸을 때 "어제 데이터"로 버티는 시간의 한도, 복구 후 밀린 데이터를 처리하는 방법은
  다루지 않는다.
