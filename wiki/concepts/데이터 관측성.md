# 데이터 관측성

파이프라인 내부의 데이터 상태(볼륨·신선도·스키마·분포)를 시스템이 자동으로 수집·감시해, 문제가 하류로 번지기 전에 발견하고 막는 능력. [[데이터 SLA]]가 "무엇을 약속하나"라면 관측성은 "그 약속을 어떻게 지키나"다.

## 수동 확인에서 자동 감시로

| 수동 확인 | 데이터 관측성 |
|---|---|
| 수천 개 파이프라인과 TB급 데이터를 사람이 볼 수 없다 | 볼륨·신선도·스키마 변경·값 분포를 24시간 자동 수집 |
| 지연·누락을 뒤늦게 알아 골든타임을 놓친다 | 과거 정상 패턴을 학습한 이상 탐지로 먼저 잡는다 |
| 피로로 인한 실수 | 하류로 번지기 전에 차단 |

## 알림 설계 — 경고 피로 방지

- 비즈니스 임팩트로 거른다. 모든 오류가 응급은 아니다. 중요한 SLA 위반만 울린다.
- 동적 임계치: 고정값 대신 시간대·계절성을 반영한다.
- 채널을 나눈다. 경미한 이슈는 대시보드, 심각한 장애만 온콜 전화.

Part 4의 [[AI DE 강의 4-16 모니터링 대시보드와 알람]]은 같은 문제를 조건식 수준으로 구체화한다. 알람은 사용자 영향과 직결된 증상(freshness SLO 위반, prediction table 미생성)에 걸고, 원인(feature pipeline 실패, schema validation failure)은 대시보드로 좁힌다(p42). 피로 대책으로 지속 시간·최소 트래픽 조건, 모델 버전 단위 grouping, maintenance window 반영, page/ticket/info 구분, 알람마다 runbook 연결, 장애 뒤 알람 품질 리뷰를 든다(p46–47). 서비스·모델·인프라·비용까지 포함한 AI 시스템 전체의 알람 설계는 [[AI 시스템 모니터링]]에 모았다.

## 장애 대응

감지 → 격리 → 완화 → 원인 규명 → 복구. 소비 팀에 "문제를 인지했고 복구 예정"을 즉시 알리는 것이 신뢰 유지의 첫걸음이다. 원인 규명은 근본 원인 분석(RCA)과 재발 방지 대책(CAPA)으로 끝낸다. 원인을 역추적할 때는 데이터 계보가 쓰인다([[데이터 거버넌스와 카탈로그]]).

## 서킷 브레이커 — "멈춤이 최선의 품질"

데이터가 이동하는 단계 사이(소스 → 게이트 → 모델)에 품질 게이트를 둔다. 사전 정의한 규칙을 위반하면(예: Null 비율 1% → 50%) 스위치를 내려 하류 전파를 막고 안전 모드로 전환한다(예: 어제 데이터 사용). "망가진 데이터로 모델을 망칠 바에는 멈추는 것이 낫다."

[[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]는 같은 이름을 요청 경로의 패턴으로 쓴다. 장애 난 의존성(피처 스토어 등)을 끊고 fallback으로 응답한다. 이름은 같지만 쓰이는 층이 다르다([[모델 서빙]]).

드리프트 쪽의 대응은 반대로 자동 재학습이다. 두 자동화는 방향이 반대라서 쿨다운 기간과 사람 승인 같은 안전장치가 함께 나온다([[AI DE 강의 1-13 Skew와 Drift]]). 이 대조는 위키가 한 것이다.

## 빈칸

- 관측성 도구와 이상 탐지 방법은 Part 1에 구체적으로 나오지 않는다. Part 4도 지표·대시보드·알람의 설계만 주고 도구(Prometheus, Grafana 등)는 이름으로 설명하지 않는다. Part 2는 Prometheus를 서빙 로그·지표를 보내는 곳으로 이름만 들고([[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]] 덱 `04` p13, [[AI DE 강의 2-08 서빙 플랫폼 FastAPI·TorchServe·BentoML·Triton]] p56), 도구 로고 슬라이드(2-07 p16)에 Grafana·Datadog를 함께 싣는다.
- 서킷 브레이커가 열렸을 때 "어제 데이터"로 버티는 시간의 한도, 복구 후 밀린 데이터를 처리하는 방법은 다루지 않는다.
