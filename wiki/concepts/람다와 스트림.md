# 람다와 스트림

> **동음이의 주의** — 이 페이지의 "스트림"은 Java 8의 **Stream API**(컬렉션을 선언적으로 처리하는 라이브러리)다. Kafka·Flink로 끝없는 이벤트 흐름을 처리하는 [[스트림 처리]]와는 다른 것이다. Java Stream은 한 번만 소비되고, 무한할 수도 있지만(`Stream.iterate`·`generate` + `limit`) 이벤트 시간·워터마크 같은 개념이 없다. ⚠️ 위키 정정(2026-09-26 린트): 처음엔 "유한한 컬렉션을 한 번 훑고 끝난다"고 적었다. 패키지 문서 원문은 "Possibly unbounded. While collections have a finite size, streams need not."

- **람다** — 메서드를 하나의 식으로 쓴 익명 함수. 함수형 인터페이스(추상 메서드가 하나인 인터페이스, `Function`·`Predicate` 등)의 구현체를 간결하게 만든다.
- **스트림** — 컬렉션의 요소를 람다로 처리하게 해 주는 **내부 반복자**. 반복문을 호출자가 쓰지 않고 라이브러리가 돈다([[Java 면접 6 람다와 스트림]] p107).

## 왜 "내부 반복"이 핵심인가

`for` 루프(외부 반복)는 호출자가 순서와 방법을 쥐고 있어서 라이브러리가 끼어들 틈이 없다. 반복을 라이브러리에 넘기면 라이브러리가 **언제(지연 연산), 어떻게(병렬화·연산 합치기)** 돌릴지 정할 수 있다. 람다는 "각 요소에 할 일"을 라이브러리에 넘기는 가벼운 수단이다. 자료가 나란히 든 세 도입 이유(병렬·부수 효과 최소화·선언적)는 이 한 가지에서 나온다. *(위키의 관찰)*

## 지연 연산

중간 연산(`filter`·`map`)은 호출해도 실행되지 않고 파이프라인에 쌓이기만 한다. 최종 연산(`collect`·`forEach`)이 호출되어야 실제로 돈다(p116–117). 효과는 두 가지다.

1. **short-circuit** — `.filter(...).limit(5)`는 5개를 찾는 순간 멈춘다. 나머지 요소는 보지도 않는다.
2. **fusion** — filter·map·sum이 요소마다 한 번에 적용되어 **한 번의 순회**로 끝난다. 중간 컬렉션이 만들어지지 않는다.

단서: **stateful** 중간 연산은 전체 입력을 처리해야 할 수 있다(문서 원문 "may need to process the entire input"). 대표가 `sorted`다 — 모든 요소를 받아야 첫 결과를 낼 수 있어 그 지점에서 fusion과 short-circuit이 끊긴다. 순차 스트림의 `distinct`는 처음 본 요소를 바로 흘려보내므로 `limit`과의 short-circuit이 유지된다(병렬 ordered `distinct`는 비싸다). ⚠️ 위키 정정(2026-09-26 린트): 처음엔 `distinct`도 `sorted`와 같다고 적었다.

**[[Apache Spark]]와 같은 생각이다** — Spark의 transformation(`map`·`filter`)은 계획(DAG)만 쌓고 action(`count`·`collect`)이 호출되어야 실행되며, 좁은 변환은 한 stage로 합쳐진다. 규모(한 JVM 안 vs 클러스터)만 다르고 "계획을 쌓았다가 결과가 필요할 때 한 번에 최적화해 실행"이라는 구조가 같다. `sorted`가 fusion을 끊는 것도 Spark에서 넓은 변환이 셔플과 stage 경계를 만드는 것과 닮았다. *(위키의 연결)*

## 도입 배경 — Java 8 (JSR 335)

Brian Goetz의 설계 문서 「State of the Lambda」는 멀티코어를 핵심 동기로 든다 — 코어는 늘지만 코어가 빨라지지는 않는데, 직렬 반복 API는 그 하드웨어를 쓰지 못한다. 동시에 콜백과 "코드를 데이터처럼 넘기기"를 가볍게 만드는 것, 내부 반복, default 메서드로 기존 컬렉션 라이브러리를 진화시키는 것을 함께 든다. [Brian Goetz, 「State of the Lambda」 final edition, JSR 335 / Java SE 8, https://cr.openjdk.org/~briangoetz/lambda/lambda-state-final.html , 2026-09-26 확인]

## 면접에서

- 정의: 람다 = 함수형 인터페이스의 간결한 구현체, 스트림 = **내부 반복자**. 이 한 단어가 뒤의 모든 꼬리 질문의 열쇠다.
- 도입 이유: "내부 반복으로 반복의 제어권이 라이브러리로 넘어가서 ① 병렬화 ② 지연 연산 ③ 선언적 코드가 가능해졌다"로 **하나로 묶어** 답하면 자료의 Gold(세 가지 나열)보다 낫다.
- **"람다는 순수 함수라 안전하다"고 말하지 않는다.** "Java는 순수성을 강제하지 않는다. 캡처하는 지역 변수가 effectively final이어야 할 뿐이고, 부수 효과 없는 람다를 쓰는 것은 개발자의 책임이다. 특히 parallelStream에서는 공유 상태를 건드리면 안 된다"가 정확한 답이다.
- `parallelStream`은 "쉽게 병렬화"의 예로만 들고, 공용 ForkJoinPool을 공유하고 작은 데이터·I/O 작업에서는 오히려 느릴 수 있어 실무에서는 제한적으로 쓴다는 단서를 붙인다. *(위키의 보충)*
- 지연 연산은 short-circuit + fusion 두 효과를 말하고, stateful 연산의 예외까지 말하면 완결이다.

## 자료의 서술과 정정

- ⚠️ **"람다와 스트림은 순수 함수 기반으로 동작하므로 외부 상태를 변경하지 않아 멀티스레드 환경에서도 안전"(p110)은 틀리다.** Java가 강제하는 것은 람다가 캡처하는 지역 변수가 effectively final이어야 한다는 것뿐이고, 필드나 외부 컬렉션은 얼마든지 바꿀 수 있다. Stream 패키지 문서는 동작 파라미터에 non-interference와 stateless를 **요구**하면서, 부수 효과가 있으면 "there are no guarantees as to: the visibility of those side-effects to other threads; …"라고 경고한다. 자료 스스로도 p114 코드 슬라이드에서 외부 `log`를 건드리는 메서드를 "순수 함수 위반"의 예로 든다. [java.util.stream 패키지 문서, Java SE 25 — "Non-interference", "Stateless behaviors", "Side-effects", https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/stream/package-summary.html , 2026-09-26 확인]
- **"가장 핵심적인 이유" 셋 중 첫째가 멀티코어(p110)** — Goetz 문서가 멀티코어를 핵심 동기로 드는 것은 맞지만 순위는 없다. 단서 필요.
- 지연 연산 설명(p117)은 패키지 문서와 일치한다(중간 연산은 lazy, "fused into a single pass", `limit`은 short-circuiting 중간 연산). 빠진 것은 stateful 연산의 예외뿐이다.
