# 분산 시스템

데이터와 계산을 여러 노드에 나누고, 네트워크로 조정해 "하나의 시스템"처럼 동작하게 만드는 방식이다. [[AI DE 강의 4-01 분산 처리의 등장과 도입 판단]]은 이것을 "여러 대의 서버를 쓰는 것"과 구분한다(p20). 나뉘는 것은 서버 수가 아니라 데이터 저장 위치, 계산 실행 위치, 상태 보관 위치, 장애 때의 대체 경로다.

## 역사: GFS에서 Spark까지

| 해 | 시스템 | 무엇을 풀었나 |
|---|---|---|
| 2003 | GFS | 큰 파일을 64MB 청크로 쪼개 저가 서버 수천 대에 나눠 저장하고, 청크마다 기본 3벌 복제. 하드웨어는 언제든 고장 난다는 전제로 신뢰성을 소프트웨어가 보장한다 |
| 2004 | MapReduce | 데이터를 계산기로 가져오지 않고 계산을 데이터가 있는 곳으로 보낸다. Map → Shuffle → Reduce. 개발자는 함수 두 개만 쓴다 |
| 2006 | BigTable | 대규모 분산 데이터베이스 |
| 2006 | Hadoop | HDFS(GFS 구현)와 Hadoop MapReduce. 단계마다 결과를 디스크에 썼다가 다시 읽는 것이 한계 |
| 2010 | Spark | 데이터를 메모리에 두고 전체 작업 경로를 DAG로 그려 한 번에 최적화(lazy execution). 반복 알고리즘과 대화형 분석에 맞다 |

표는 강의(p5–14)를 따랐다. GFS의 64MB·3복제는 원 논문과 맞다("By default, we store three replicas", "chosen 64 MB", https://static.googleusercontent.com/media/research.google.com/en//archive/gfs-sosp2003.pdf , 2026-09-28 확인).

두 가지를 보충한다.

- Hadoop은 Doug Cutting 혼자 만든 것이 아니다. Cutting과 Mike Cafarella가 웹 크롤러 Nutch 안에서 NDFS(2004)와 MapReduce(2005)를 먼저 구현했고, 2006년에 이것을 Hadoop으로 떼어 냈다. HADOOP-1 이슈(2006-02-01 생성)의 제목이 "initial import of code from Nutch"다. NDFS·MapReduce의 연도는 2차 자료다. [https://issues.apache.org/jira/browse/HADOOP-1 , 2026-09-28 확인]
- "Hadoop보다 최대 100배 빠르다"는 Spark 옛 홈페이지의 문구다("Run programs up to 100x faster than Hadoop MapReduce in memory, or 10x faster on disk", 2016 Wayback). 조건은 인메모리이고 비교 대상은 MapReduce였다. 지금 홈페이지에는 이 문구가 없다. [https://spark.apache.org/ , 2026-09-28 확인] Spark 자체는 [[Apache Spark]]에 있다.

## 분산은 꼭 필요한가

[[AI DE 강의 4-01 분산 처리의 등장과 도입 판단]]의 출발점은 "분산이 멋져 보이는가가 아니라 단일 서버로도 충분한가"다(p17).

- 단일 서버는 더 이상 작지 않다. AWS U7i 계열은 최대 32 TiB 메모리를, I4i는 최대 30 TB 로컬 NVMe를 준다(p18). 1,920 vCPU는 U7i의 변형인 `u7inh-32tb.480xlarge`의 값이다. [https://aws.amazon.com/ec2/instance-types/u7i/ , 2026-09-28 확인]
- 그래도 남는 한계는 CPU·메모리 숫자가 아니다(p19). 장애 도메인이 하나이고, 메모리만 필요해도 CPU·스토리지를 함께 사야 하고, 병렬성에 상한이 있고, 서버가 거대할수록 재기동·상태 재적재·캐시 warm-up이 무거워진다.

### 도입 판단

강의는 세 축이 동시에 맞을 때만 분산이 정당화된다고 한다(p24). 요구사항(처리량·지연·가용성·정합성 중 무엇이 핵심인가), 실제 병목(CPU·메모리·디스크·네트워크·동시성·상태 크기), 운영 비용(장애 분석·재처리·재배치·복제·상태 복구 부담)이다.

여기에 숨은 변수 셋을 더한다(p25–28).

| 변수 | 질문 |
|---|---|
| 데이터 응집도 | 조인이 노드 간 셔플을 부르는가, [[샤딩]] 키에 hotspot이 생기는가, 2PC 없이 무결성을 지킬 수 있는가. 데이터를 독립 silo로 가를 수 있으면 분산 적합도가 높다 |
| 선형 확장성 | 서버를 2배로 해도 처리량은 2배가 안 된다. 순차 구간(1-p)과 복제·합의·직렬화 오버헤드를 잰다(암달의 법칙) |
| 엔지니어링 복잡도 | 분산 추적, 부분 장애 격리(bulkhead), 노드 교체·리밸런싱 자동화가 되는가. 모니터링 없이 분산을 들이면 "운영 재앙"이다 |

지표로는 CPU 포화, 메모리 OOM·spill·GC, 디스크 I/O wait·temp usage, 네트워크 shuffle·remote fetch 비중을 본다(p29).

## 분산의 대상

| 대상 | 예 |
|---|---|
| 데이터 | Kafka 토픽 파티션, HDFS 블록, 샤딩된 테이블 |
| 계산 | Spark executor의 task 병렬 실행 |
| 상태 | 집계·세션·윈도우·캐시를 노드에 나눠 보관(Flink stateful processing) |
| 장애 허용 | 복제본과 재실행 경로(Kafka replication, PostgreSQL standby) |

강의 p23의 구분이다. 네 번째는 [[복제]]와 [[합의 알고리즘]]에서, 세 번째는 [[스트림 처리]]에서 다룬다.

## 근본적 한계

[[AI DE 강의 4-02 CAP 정리와 분산 시스템의 한계]]는 분산이 어려운 것이 구현 난이도 때문만이 아니라고 한다(p34). 아무리 잘 만들어도 동시에 완전히 만족시킬 수 없는 성질이 있다.

- 부분 실패. 단일 서버의 실패는 단순하다(프로세스·머신·디스크가 죽는다). 분산 시스템에서는 어떤 노드는 살고 어떤 노드는 죽고, 일부 링크만 느려지고, 관찰자마다 누가 죽었는지 다르게 본다(p47).
- 전역 시계의 부재. Lamport(1978)가 보였듯 두 사건 중 무엇이 먼저인지 말하는 것이 때로 불가능하다. 먼저 쓴 값, 로그 정렬, 복제 순서, 외부 일관성을 정하기 어렵다(p48).
- FLP 불가능성. Fischer·Lynch·Paterson(1985)은 완전 비동기 모델에서 프로세스 하나만 멈출 수 있어도 항상 결정을 내리는 결정론적 합의 프로토콜이 없음을 보였다(p49).
- 실무의 타협. 실제 시스템은 FLP를 무시하지 않고 완전 비동기 가정을 버린다. timeout을 두고, leader를 뽑고, 언젠가 네트워크가 안정된다고 기대한다(부분 동기성, p50). Raft가 이 타협 위에 있다([[합의 알고리즘]]).
- 분할이 났을 때의 선택은 [[CAP 정리]]에서 다룬다.

## 실용적 분산

강의의 결론은 "모든 것을 분산하지 말고 필요한 축만 분산하라"다(p30–31). 읽기 확장은 replica, 비동기 분리는 [[메시지 브로커]], 대규모 배치는 분산 컴퓨트, 스트리밍 정합성은 stateful 스트림 엔진에 맡기고 나머지는 단순하게 둔다. 최근 흐름도 분산이 사라진 것이 아니라 강한 단일 서버, 저장과 컴퓨트 분리, 관리형 분석 엔진으로 복잡성을 사용자가 떠안지 않는 쪽으로 간다.

[[AI DE 강의 3-02 RDBMS의 한계와 NoSQL]]이 "NoSQL은 확장성을 자동 제공하지 않는다"(p37)고 한 것과 같은 방향이다. 두 소단원을 잇는 것은 위키의 관찰이다.
