# 데이터 SLA

데이터 생산자(엔지니어)와 소비자(모델·데이터 사이언티스트) 사이에 **데이터의 시간·양·질을 약속하는 계약.**
서버가 켜져 있음(가동률)이 아니라 **데이터가 쓸 만한 상태임**을 보장한다.

## 왜 필요한가 — 침묵의 실패

파이프라인이 exit code 0으로 끝나고 에러 로그도 없고 스케줄러가 초록불인데, 결과 테이블이 0건이거나 결제
금액이 Null일 수 있다. 가동률 99.9% SLA로는 절대 잡지 못한다([[AI DE 강의 1-14 데이터 SLA와 모니터링]]).
AI에서는 이것이 **잘못된 재학습 → 틀린 추천 → 고객 이탈**로 이어진다.

같은 모양의 실패가 [[학습-서빙 스큐]](에러 없이 틀린 피처 값)와 [[데이터 드리프트]](코드는 완벽한데 세상이
바뀜)에서도 나온다. 셋 다 **로그가 조용하다.**

## 세 가지 핵심 지표

| 지표 | 질문 | 측정 예 | 대응 예 |
|---|---|---|---|
| 신선도(Timeliness) | 약속한 시간에 도착했나? | `Now() - Event_Timestamp`의 p95·p99 | 08:00 데드라인, 08:30 초과 시 호출 |
| 완전성(Completeness) | 100% 도착했나? | 소스·타깃 건수·해시 대사, PK 중복 검사 | 누락 시 백필 자동 트리거 |
| 정확성·유효성(Accuracy) | 규칙을 만족하나? | 스키마·타입·도메인·범위 검사, 통과율 | 실패 레코드 격리 → 알림 → 재처리 |

| 완전성 | ✅ | ✅ (품질/완전성으로 합침) | ✅ |
| 정확성·유효성 | ✅ | ✅ (결측·이상치·타입·스키마) | ✅ |

| 일관성 | — | ✅ (학습·서빙 전처리 로직 동일성) | ✅ (소스·시간대별 형식 통일) |

읽는 법: 3대 지표는 **어떤 파이프라인에나** 적용되는 기본이고, 4대 축의 분포 안정성·피처 일관성은 **소비자가
모델일 때** 추가되는 축이다. 5대 기둥의 "일관성"은 4대 축의 "피처 일관성"과 이름은 같지만 뜻이 다르다
(형식 통일 vs 학습·서빙 동일성).

## 계약에서 시스템으로

- **데이터 계약(Data Contract)** — 스키마·윈도우 크기·예외 처리 규칙 같은 데이터 정의를 문서로 명시한다
  ([[AI DE 강의 1-13 Skew와 Drift]]의 "피처 계약").
- **테스트** — 배포 전 스키마·도메인 규칙 테스트를 CI/CD에 넣는다.
- **감시와 차단** — 자동 수집·동적 임계치·서킷 브레이커. → [[데이터 관측성]]
- "SLA는 시스템으로 지켜질 때 비로소 진짜 약속이 된다."

## 빈칸

- 데이터 품질 검사·관측 도구는 Part 1에 이름이 나오지 않는다.
- SLA 목표값을 어떻게 정하는지(소비자와 협상, 비용과의 균형)는 다루지 않는다.
