# 가비지 컬렉션

더 이상 쓰이지 않는 객체의 메모리를 런타임이 자동으로 회수하는 것. [[JVM]]의 장점(메모리 휴먼 에러 예방)이자, 애플리케이션을
멈추게 하는 비용의 원천이다. 구현체별 차이는 [[가비지 컬렉터]]에 있다.

## 무엇이 쓰레기인가 — 두 계열

| 계열 | 방식 | 약점 |
|---|---|---|
| Reference Counting | 객체마다 참조 수를 세고 0이 되면 즉시 해제 | 서로 참조하는 순환 구조는 영원히 0이 안 돼 누수 |
| **Tracing** | **GC Root**에서 참조 그래프를 따라가 도달 가능한 객체만 산 것으로 본다 | 순회하는 동안 참조가 바뀌면 안 된다 → STW 또는 barrier가 필요 |

두 계열의 비용·멈춤·해제 시점 비교와 CPython·Swift·V8·Go가 둘을 어떻게 섞는지는 [[레퍼런스 카운팅과 마크 앤 스윕]]에 있다.

HotSpot은 tracing 계열이다. 단, **죽은 객체를 어떻게 치우느냐**는 영역마다 다르다.

| 치우는 방식 | 어디서 |
|---|---|
| 복사(copying, scavenge) — 산 객체만 다른 공간으로 옮기고 원래 공간을 통째로 비운다 | Young 영역 전부. G1의 evacuation도 복사 |
| mark-compact — 산 객체를 한쪽으로 모아 단편화를 없앤다 | Serial·Parallel의 Old/Full GC, G1 Full GC |
| mark-sweep — 죽은 자리를 빈 칸 목록에 올린다(이동 없음) | 제거된 CMS의 Old 영역 |
| 동시 compaction | ZGC, Shenandoah |

[Oracle, 「HotSpot Virtual Machine Garbage Collection Tuning Guide」 JDK 21, https://docs.oracle.com/en/java/javase/21/gctuning/ ,
2026-09-26 확인]

**GC Root**에는 스레드 스택의 지역 변수, 클래스의 static 필드 말고도 JNI 지역·전역 참조, 살아 있는 Thread 객체, synchronized로
잡혀 있는 모니터 객체, 시스템 클래스로더가 로드한 클래스, finalizer 대기 객체 등이 있다. static 필드는 JDK 7부터 PermGen(자료가 말하는 "메서드
영역", → [[JVM 메모리 구조]])이 아니라 Class 미러 객체와 함께 힙에 있다. JDK 8에서 바뀐 것은 PermGen이 Metaspace로 대체된 일이다. [Eclipse MAT 도움말,
「Garbage Collection Roots」, https://help.eclipse.org/latest/topic/org.eclipse.mat.ui.help/concepts/gcroots.html ;
OpenJDK JDK-7017732 「move static fields into Class to prepare for perm gen removal」(hs21 = JDK 7),
https://bugs.openjdk.org/browse/JDK-7017732 , 2026-09-26 확인] ⚠️ 위키 정정(2026-09-26 린트): 처음에 "JDK 8부터"로 적었다.
예외: **가상 스레드의 스택은 GC Root가 아니다.** 힙에 stack chunk 객체로 있어 다른 객체처럼 동시에 훑는다(JEP 444, → [[JVM 메모리 구조]]).

**Young만 치울 때는 Old → Young 참조도 루트다.** Old를 훑지 않으므로, Old 객체가 가리키는 Young 객체를 놓치지 않도록 세대 사이
포인터를 **remembered set**에 기록해 두고 루트처럼 스캔한다. Serial·Parallel은 그 한 종류인 **card table**을 쓰고, 참조를 대입할
때마다 도는 **write barrier**가 이를 갱신한다. G1은 Region마다 「이 Region을 가리킬 수 있는 바깥 위치」의 remembered set을 두고(512바이트
card 단위), Young Region 것은 매 수거에 쓰므로 항상 유지한다. [OpenJDK 「HotSpot Glossary of Terms」,
https://openjdk.org/groups/hotspot/docs/HotSpotGlossary.html ; Oracle, 「Garbage-First (G1) Garbage Collector」 GC Tuning Guide JDK 21,
https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html , 2026-09-27 확인]

## 세대별 GC

**약한 세대 가설(weak generational hypothesis)** — 대부분의 객체는 만들어지자마자 죽는다. 그래서 힙을 나눈다.

- **Young** = Eden + Survivor 두 칸. 새 객체는 Eden에 생긴다. Eden이 차면 **Minor(Young) GC**가 산 객체를 Survivor로 복사하고
  Eden을 비운다. 여러 번 살아남은 객체는 Old로 **승격(promotion)**된다.
- **Old** — 오래 산 객체. 여기까지 치우는 수거는 비싸다.
- 용어: JVM 로그의 공식 구분은 Young GC · (G1의) Mixed GC · Full GC(힙 전체)다. "Major GC"는 흔히 쓰지만 공식 용어가 아니다.

DE 비유: 스트리밍 적재에서 **최근 파티션은 자주 compaction하고, 오래된 파티션은 드물게 크게 정리**하는 것과 같은 발상이다.
대부분의 변경이 최근 데이터에 몰린다는 가정 위에 서 있다. *(위키의 연결)*

## Stop-The-World

GC가 애플리케이션 스레드를 전부 멈추는 구간. 전통적으로 두 이유로 필요했다.

1. 순회하는 동안 참조 관계가 바뀌면 산 객체를 죽었다고 오판할 수 있다. 예: GC가 이미 훑은 A가 C를 새로 가리키고, 아직 안 훑은
   B가 C를 놓으면 C는 살아 있는데 표시되지 않아 회수된다. 쓰레기를 살려 두는 오판은 다음 GC가 치우면 되지만, 이 반대 오판은
   치명적이다. *(위키의 설명)*
2. compaction이나 복사로 객체 주소가 바뀌면, 그 객체를 가리키는 모든 참조를 고쳐야 한다.

### 컴팩션이 STW를 부른다

mark-sweep만 하면 죽은 자리가 구멍으로 남는다(**단편화**). 빈 칸의 합은 충분한데 연속된 자리가 없어 큰 객체 할당에 실패한다.
compaction은 "live objects occupying a dense portion of the virtual address space, and available space in another portion"으로 만드는
기법이다. 빈 공간이 한 덩어리면 할당은 포인터를 미는 것으로 끝난다(bump pointer). HotSpot은 스레드마다 **TLAB**("Thread-local
allocation buffer. Used to allocate heap space quickly without synchronization")을 주고, 그 안의 할당은 `top`이 `end`까지 남은
공간을 확인한 뒤 `top += size` 하는 것이 전부다. 대가는 객체가 **움직인다**는 것이고, 그래서 위 2번 이유로 STW가 필요해진다.
제거된 CMS는 compaction을 빼서 멈춤을 줄였지만, 단편화가 쌓이면 긴 STW Full GC로 떨어졌다(→ [[가비지 컬렉터]]).
[OpenJDK 「HotSpot Glossary of Terms」, https://openjdk.org/groups/hotspot/docs/HotSpotGlossary.html ; HotSpot 소스
`src/hotspot/share/gc/shared/threadLocalAllocBuffer.inline.hpp`의 `ThreadLocalAllocBuffer::allocate`, https://github.com/openjdk/jdk ,
2026-09-27 확인]

### 어떻게 멈추나 — safepoint

JVM은 스레드를 아무 데서나 세우지 않는다. **safepoint**는 "A point during program execution at which all GC roots are known and all
heap object contents are consistent"다. JVM이 safepoint를 요청(arm)하면 스레드는 상태별로 다르게 멈춘다.

- **인터프리터로 실행 중** — 분기·반환 바이트코드를 실행할 때 poll을 확인하고 멈춘다.
- **컴파일된 코드 실행 중** — 컴파일러가 넣어 둔 지점에서 스레드별 polling page를 읽는다. safepoint가 요청되면 이 읽기가 fault를
  내 스레드가 멈춘다. C2는 긴 counted loop에도 poll이 들어가도록 루프를 쪼갠다(loop strip mining).
- **native 코드 실행 중** — VM은 이 스레드를 **기다리지 않는다**. 스레드가 native에서 Java로 돌아오려 할 때 멈춘다. 그래서 JNI 코드는
  STW 동안에도 계속 돈다.
- **이미 블록돼 있음** — safepoint 작업이 끝날 때까지 풀려나지 못한다.

그래서 **STW 시간 = safepoint 도달 대기 + GC 작업**이다. poll이 드문 코드를 도는 스레드 하나가 늦으면 나머지 스레드가 모두 기다린다.

`src/hotspot/share/opto/loopnode.cpp`의 strip mining, https://github.com/openjdk/jdk , 2026-09-27 확인]

### 멈추지 않는 방법 — barrier

동시 컬렉터는 멈추는 대신 애플리케이션 코드에 barrier를 끼워 비용을 CPU로 나눠 낸다.

- **1번 문제 → G1의 SATB(Snapshot-At-The-Beginning)** — 동시 마킹을 시작하는 pause 시점의 가상 스냅샷을 기준으로, 그때 살아 있던
  객체는 마킹이 끝날 때까지 산 것으로 본다. 대가: 마킹 도중 죽은 객체는 이번에 못 치우고 다음 마킹에서 치운다. 그 대신 Remark
  pause가 짧다. [Oracle G1 GC Tuning Guide JDK 21, https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html ,
  2026-09-27 확인]
- **2번 문제 → ZGC·Shenandoah** — 아래처럼 재배치까지 동시에 한다.
- G1은 그 중간이다. 마킹은 동시지만 **복사(evacuation)는 STW**다. 문서도 G1을 "mostly concurrent, stop-the-world, and evacuating"
  컬렉터라 부르고, 복사하면서 compaction이 함께 된다.

**그러나 STW가 본질적인 것은 아니다.** ZGC(colored pointer + load barrier)와 Shenandoah(forwarding pointer + barrier)는 마킹과
재배치를 애플리케이션과 **동시에** 한다. STW는 루트 스캔 같은 짧은 구간(대략 ms 이하)에만 남는다.
[JEP 377 ZGC, https://openjdk.org/jeps/377 ; JEP 379 Shenandoah, https://openjdk.org/jeps/379 ; 2026-09-26 확인]

STW 시간은 서비스의 꼬리 지연에 그대로 더해진다 → [[지연 시간과 처리량]]. *(위키의 연결)*

## 모니터링과 OOM 대응

- **무엇을 보나** — GC 빈도, 1회 소요 시간(특히 Full GC), GC 후 힙 사용률의 추세. 사용률이 GC 후에도 계속 오르면 누수를 의심한다.
  바닥선의 네 모양(정상·누수·조기 승격·live set 과대)과 누수 안티패턴은 [[객체 수명과 메모리 상한]]에 있다.
  도구는 GC 로그(`-Xlog:gc*`), VisualVM, Prometheus + Grafana. 소요 시간 감각(Young 수 ms~수십 ms, Full 수백 ms~수 초)은 힙
  크기와 컬렉터에 따라 크게 다른 경험치다.
- **왜 보나** — GC 문제는 조용히 쌓이다 한 번에 터진다. 누수는 GC 후 바닥선이 며칠에 걸쳐 오르다 OOM으로 끝나고, 긴 멈춤은
  에러 없이 꼬리 지연만 올린다. 평소 추세가 있어야 「원래 이랬나, 최근에 변했나」를 가린다. *(위키의 설명)*
- **OOM 메시지로 영역부터 가린다** — `OutOfMemoryError` 뒤의 detail message가 어디가 찼는지 말한다.

  | 메시지 | 영역 | 첫 대응 |
  |---|---|---|
  | `Java heap space` | 힙 | 힙 덤프 분석 — 누수인가, 데이터가 정말 큰가 |
  | `GC overhead limit exceeded` | 힙이 거의 찬 채 GC만 돈다 | 위와 같다. 힙 부족의 조기 경보 |
  | `Requested array size exceeds VM limit` | 배열 하나가 VM 한계 초과 | 힙 크기와 무관. 그 배열을 만드는 코드를 고친다 |
  | `Metaspace` · `Compressed class space` | 클래스 메타데이터(힙 밖) | 클래스 생성·클래스로더 누수 (→ [[JVM 메모리 구조]]) |
  | `request <size> bytes for <reason>. Out of swap space?` | 네이티브 메모리 | 힙이 아니라 OS·네이티브 쪽 |
  | `<reason> <stack trace> (Native method)` | 네이티브 메서드 안의 할당 실패 | JNI·네이티브 라이브러리 |

  `GC overhead limit exceeded`의 기준: GC 뒤 애플리케이션 시간의 **약 98% 이상**을 GC에 쓰고 힙을 **2% 미만** 회수하는 일이 **연속
  5번**(컴파일 시 상수) 이어지면 던진다. JDK 25 기본값 `GCTimeLimit=98` · `GCHeapFreeLimit=2` · `UseGCOverheadLimit=true`와 맞는다.
  [Oracle, 「Troubleshooting Guide」 JDK 25, Troubleshoot Memory Leaks — Understand the OutOfMemoryError Exception,
  https://docs.oracle.com/en/java/javase/25/troubleshoot/troubleshooting-memory-leaks.html ; JDK 25 `-XX:+PrintFlagsFinal`, 2026-09-27 확인]
- **OOM 대응 순서**([[Java 면접 3 GC]] Q2-3, 1차 자료와 맞음):
  1. `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=<경로>`로 OOM 때 힙 덤프를 자동으로 남긴다(JDK 25 플래그로 확인, manageable
     플래그라 런타임에도 바꿀 수 있다).
  2. Eclipse MAT이나 VisualVM으로 덤프를 열어 가장 큰 객체와 참조 체인을 본다. MAT의 Leak Suspects 리포트가 출발점이다.
  3. 근본 원인을 고친다 — 무한히 쌓이는 컬렉션, 캐시 정책, 메모리 효율 나쁜 라이브러리.
  4. 힙 증설(`-Xmx`)은 **마지막의 임시 조치**다.
  - 덤프 옆에 둘 것: `-Xlog:gc*:file=<경로>`로 GC 로그를 파일로 남긴다. `-XX:+ExitOnOutOfMemoryError`는 "JVM exits on the first
    occurrence of an out-of-memory error thrown from JVM"(기본 꺼짐), `-XX:+CrashOnOutOfMemoryError`는 에러 로그와 core dump를 남기고
    abort한다. [HotSpot 소스 `src/hotspot/share/runtime/globals.hpp`, https://github.com/openjdk/jdk , 2026-09-27 확인] OOM 뒤의 JVM은 반쯤
    망가진 채 돌 수 있으니, 재시작해 주는 오케스트레이터가 있으면 끝내는 쪽이 낫다는 것이 흔한 운영 판단이다. *(통념)*
- **컨테이너에서는 OOM이 두 종류다.**

  | | JVM의 `OutOfMemoryError` | 컨테이너의 `OOMKilled` |
  |---|---|---|
  | 누가 | JVM이 던진다 | 커널이 프로세스를 죽인다 |
  | 언제 | 힙·Metaspace 등이 **JVM 한도**를 넘을 때 | **프로세스 전체 메모리**가 컨테이너 limit을 넘을 때 |
  | 흔적 | 스택 트레이스, 힙 덤프 | 없다. 파드 상태에 `OOMKilled` |

  Kubernetes: "If a Container allocates more memory than its limit, the Container becomes a candidate for termination."
  [Kubernetes, 「Assign Memory Resources to Containers and Pods」, https://kubernetes.io/docs/tasks/configure-pod-container/assign-memory-resource/ ,
  2026-09-27 확인] JVM은 힙 밖에도 Metaspace · 스레드 스택 · 코드 캐시 · 다이렉트 버퍼를 쓰므로(→ [[JVM 메모리 구조]]), 힙을 limit에
  딱 맞추면 JVM OOM보다 먼저 OOMKilled가 난다. 기본 최대 힙은 `MaxRAMPercentage`(기본 **25%**, `java` 매뉴얼 JDK 25)로 정해지며,
  컨테이너 지원이 켜져 있으면 기준이 컨테이너 limit이다. 25%라는 값이 힙 밖 여유를 위한 것이라는 설명은 매뉴얼에 없다. *(통념)*
  [Oracle, `java` 명령 매뉴얼 JDK 25, https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html , 2026-09-27 확인]

DE 쪽에서 가장 흔한 OOM은 [[Apache Spark]] executor다. 큰 파티션 하나, broadcast join의 큰 테이블, `collect()`가 원인일 때가 많아
"힙 증설"보다 파티션 재분할이 근본 원인 수정이다. *(위키의 연결)*

자료의 Gold 답([[Java 면접 3 GC]])보다 나은 뼈대:

- **Q. Java는 어떤 GC 알고리즘을 쓰나** — "도달 가능성으로 판단하는 tracing GC입니다. 치우는 방식은 영역마다 달라서, Young은 산
  객체만 복사하고 Old는 mark-compact로 모읍니다. Reference Counting은 순환 참조를 못 치워서 쓰지 않습니다."
- **Q. Minor GC 동작** — "Eden이 차면 Root에서 도달 가능한 객체만 Survivor로 복사하고 Eden은 통째로 비웁니다. 산 객체 수에만
  비례하니 대부분 죽는 Young에서 싸게 끝납니다."
- **Q. STW는 왜** — 위 두 이유를 말한 뒤 "ZGC·Shenandoah는 barrier로 재배치까지 동시에 해서 STW를 ms 이하로 줄입니다"를 덧붙인다.

## 자료의 서술과 정정

| 자료 | 판정 | 정정 |
|---|---|---|
| Java는 Mark and Sweep을 쓴다 (p26) | 틀림(과단순화) | tracing이지만 Young은 복사, Old는 mark-compact. 순수 mark-sweep은 제거된 CMS 정도 |
| Minor GC도 M&S로 Survivor로 옮긴다 (p29) | 틀림 | 복사(evacuate)이고 sweep 단계가 없다. "Major GC"는 공식 용어가 아니다 |
| Root = 스택 지역 변수 + 메서드 영역 static (p32) | 단서 필요 | JNI 참조·스레드·모니터 등도 루트. static은 JDK 7부터 힙(JDK-7017732) |
| STW가 필요한 이유 둘 (p38) | 단서 필요 | 전통적 GC에만 맞다. ZGC·Shenandoah는 동시 compaction |
| Young/Old로 나누는 이유 (p35) | 맞음 | 약한 세대 가설이라는 이름을 붙이면 더 좋다 |
| 모니터링·OOM 4단계 (p50) | 맞음 | p50 원문은 `+` 뒤에 공백이 있는 오타. 소요 시간은 경험치 |
