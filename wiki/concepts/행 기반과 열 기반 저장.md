# 행 기반과 열 기반 저장

데이터를 디스크에 **행 단위로 이어 쓰느냐, 열 단위로 모아 쓰느냐**의 차이. 워크로드(OLTP vs OLAP)가
어느 쪽이 맞는지를 정한다.

## 비교

| | 행 기반 | 열 기반 |
|---|---|---|
| 디스크 배치 | 한 레코드의 모든 필드가 붙어 있다 | 같은 컬럼의 값끼리 모여 있다 |
| 맞는 워크로드 | OLTP — 단건 조회·쓰기(CRUD). "백만 건 중 한 건" | OLAP·학습 — 대량 집계, 일부 컬럼만. "백만 건의 매출 합계" |
| 읽기 | 나이 하나를 읽으려 해도 이름·주소까지 읽는다 | 필요한 컬럼만 읽는다(column pruning) |
| 압축 | 타입이 섞여 있어 낮다 | 같은 타입이 연속돼 높다(RLE, 딕셔너리 인코딩) |
| 쓰기 | 도착 즉시 끝에 붙이기 쉽다 | 컬럼으로 분해·압축하느라 CPU를 쓴다 |
| 대표 | RDBMS, CSV, [[Apache Avro]] | DW, [[Apache Parquet]], ORC |

## AI 학습 워크로드가 열 기반에 맞는 이유

[[AI DE 강의 1-05 열 기반 저장 Parquet와 Avro]] (덱 06):

- **대량 읽기(heavy read)** — TB~PB 데이터를 반복해서 메모리로 불러온다. 쓰기보다 읽기가 압도적이다.
- **선택적 열 접근** — 수백 개 속성 중 학습에 쓸 피처만 뽑는다.
- **순차적 고처리량** — 랜덤 접근보다 순차 대량 읽기. GPU가 쉬지 않도록 데이터 대역폭을 키워야 한다.

행 기반 저장소에서는 필요한 데이터가 10%여도 100%를 읽고, **디스크가 헛일하는 동안 GPU가 대기한다.**
열 기반은 여기에 **벡터화 실행**(컬럼을 통째로 CPU 캐시에 올려 배열 연산)을 더한다.

## 둘을 함께 쓰는 설계

- **OLTP + CDC + OLAP** — 고객 요청은 행 기반 OLTP가 받고, CDC로 열 기반 분석 저장소에 동기화한다
  ([[AI DE 강의 1-04 저장소의 진화 DW에서 Lakehouse까지]]의 설계 5단계). → [[변경 데이터 캡처]]
- **Avro로 받고 Parquet로 합친다(compaction)** — 유입 시점엔 행 기반으로 빠르게 쓰고, 배치로 큰 열 기반
  파일로 변환한다. 열 기반의 약점(쓰기 지연, 작은 파일)을 피하는 패턴이다. → [[지연 시간과 처리량]]
