# 스트림 처리

끝이 정해지지 않은 데이터(unbounded)를 발생하는 대로 처리하는 방식이다. 이벤트가 생기자마자 반응하므로 데이터가 가장 신선할 때 가치를 만든다.

> Java의 Stream API(컬렉션을 선언적으로 처리하는 라이브러리)와는 이름만 같다. Stream API는 [[람다와 스트림]]에서 다룬다.

## 세 가지 난관과 세 가지 장치

[[AI DE 강의 1-12 실시간 처리 엔진]]의 세 난관에 강의가 소개하는 장치를 짝지으면 하나씩 맞아떨어진다. 이 짝짓기는 강의에 없고 위키가 정리한 것이다.

| 난관 | 무엇이 어려운가 | 장치 |
|---|---|---|
| 무한성 | 끝이 없으니 "다 모아서" 처리할 수 없다 | 윈도우: 끝을 만든다 |
| 비동기성 | 생성 순서와 도착 순서가 다르다 | 이벤트 시간과 워터마크: 순서를 복원한다 |
| 상태 보존 | 멈추면 안 되는데 중간 계산값은 메모리에 있다 | 체크포인트: 멈춰도 이어 간다 |

Part 4는 같은 장치를 역할로 다시 나눈다([[AI DE 강의 4-09 워터마크와 윈도우 연산]] p200). 윈도우는 "이 이벤트를 어느 계산 구간에 넣을 것인가", 워터마크는 "이 구간을 언제 닫을 것인가", 출력 규칙은 "중간 결과를 낼 것인가, 최종만 낼 것인가, 늦은 데이터가 오면 다시 낼 것인가"를 맡는다. 운반은 이 목록에 없다. 이벤트를 안전하게 흘리고 보관하는 일은 [[메시지 브로커]]의 몫이고, 엔진은 그 위에서 시간과 상태를 계산한다([[AI DE 강의 4-07 메시지 브로커와 스트림 처리 엔진]] p154).

## 윈도우

| 종류 | 모양 | 용도 | 주의 |
|---|---|---|---|
| Tumbling | 겹치지 않는 고정 크기 | 분·시간 단위 집계. 가장 저렴 | 경계에 걸친 패턴이 두 윈도우로 쪼개진다 |
| Sliding | 크기 + 이동 간격, 겹친다 | 이동평균, "최근 5분 에러율" 경보 | 한 데이터가 여러 윈도우에 속한다 |
| Session | 활동이 끊기는 간격(gap)으로 구분 | 체류 시간, 이탈 직전 행동 | 크기를 예측할 수 없다 |

Part 4는 고르는 질문을 준다(p205–206). 결과가 끊어진 구간이어야 하면 Tumbling(5분마다 결제 건수), 최근 흐름을 계속 갱신해야 하면 Sliding(최근 10분 평균 지연을 1분마다), 활동 묶음 자체가 분석 단위면 Session이다. 한 이벤트가 여러 결과에 들어가도 되는지도 따진다. 크기는 지표의 시간 단위·보고 빈도·상태 비용으로, 세션 간격은 도메인의 평균 행동 간격과 과분할·과병합의 균형으로 정한다(p214–215).

## 이벤트 시간과 늦은 데이터

[[AI DE 강의 4-08 Processing Time과 Event Time]]은 시각을 셋으로 나눈다(p180).

| 시각 | 뜻 | 예 |
|---|---|---|
| 발생 시각(이벤트 시간) | 이벤트가 실제로 일어난 순간 | 사용자가 결제 버튼을 누른 순간 |
| 수집 시각 | 브로커나 시스템이 받아 기록한 순간 | Kafka 브로커가 로그에 쓴 순간 |
| 처리 시각(처리 시간) | 엔진 연산자가 실제로 계산한 순간 | Flink 연산자가 집계한 순간 |

Kafka 레코드의 타임스탬프는 토픽 설정 `message.timestamp.type`에 따라 생산자가 넣은 시각(CreateTime)이 되기도 하고 브로커가 붙인 시각(LogAppendTime)이 되기도 한다. 발생 시각과 수집 시각 가운데 어느 것을 들고 있는지 확인해야 한다는 뜻이다. 강의에는 없는 위키의 보충이다.

같은 데이터가 기준에 따라 다른 결과를 낸다(p191–193).

| 이벤트 | 발생 | 도착 |
|---|---|---|
| 결제 A | 10:02 | 10:02 |
| 결제 B | 10:04 | 10:12 |
| 결제 C | 10:07 | 10:07 |

"10:00~10:10 결제 건수"는 처리 시각 기준이면 A·C 2건이고(그 10분 동안 시스템이 본 데이터), 발생 시각 기준이면 A·B·C 3건이다(그 10분 동안 실제로 일어난 데이터).

| | 처리 시각 기준 | 발생 시각 기준 |
|---|---|---|
| 장점 | 구현 단순, 결과가 빠름, 지연 낮음 | 비즈니스 의미 보존, 재처리해도 같은 구간 |
| 약점 | 늦은 데이터가 원래 구간에 못 들어감, 재처리하면 결과가 바뀜 | 늦은 데이터 처리 규칙(워터마크)이 필요 |
| 맞는 지표 | 초당 처리량, 오류율, 적체량, 지연 경보, 운영 대시보드 | 시간대별 결제·클릭, 정산, 센서 집계, 학습용 로그 재구성 |

강의의 설계 순서는 시간 기준 → 늦은 데이터 처리 → 구간 결과를 언제 확정할지다(p181). 처리 시각 기준 결과는 재생할 때마다 달라지므로, 로그 재생으로 재처리하는 [[람다 아키텍처와 카파 아키텍처|카파 아키텍처]]는 발생 시각 기준 계산을 전제로 한다.

### 워터마크와 허용 지연

- 워터마크: 발생 시각 기준으로 "여기까지는 대부분 도착했다"고 보는 기준선이다. 구간을 닫을 기준, 늦은 데이터 판단 기준, 오래된 상태를 정리할 기준이 된다(p207).
- 늦은 데이터: 워터마크가 이미 지나간 구간에 속하는 이벤트다.
- 허용 지연: 늦은 데이터를 추가로 받아 줄 시간 범위다. 길수록 더 많이 반영하지만 상태를 오래 들고 결과 확정도 늦어진다(p208).

강의는 워터마크를 "정답 시계가 아니라 절충 기준", 정확성·지연·상태 비용 사이에서 운영 가능한 마감선을 만드는 장치라고 정리한다(p209). Spark 문서의 보장이 이 성격을 보여 준다. "any data less than 2 hours behind… is guaranteed to be aggregated… Data delayed by more than 2 hours is not guaranteed to be dropped; it may or may not get aggregated." [https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html , 2026-09-28 확인] 워터마크 지연보다 덜 늦은 데이터만 반영이 보장된다.

엔진마다 두 개념을 다루는 방식이 다르다. Flink는 워터마크 전략과 별도로 윈도우에 `allowedLateness`를 두고, Spark Structured Streaming은 워터마크 지연 하나로 둘을 겸한다. 이 대비는 위키의 보충이다.

늦게 온 데이터를 어떻게 할지는 정확성, 비용, 복잡도 사이에서 고르는 문제다.

| 전략 | 방식 | 대가 | 사용처 |
|---|---|---|---|
| Drop | 허용 지연을 넘으면 버린다 | 유실 | 실시간 대시보드 |
| Update | 이미 낸 결과를 다시 계산해 갱신 | 싱크가 upsert를 지원해야 | 정산, 리포트 |
| Side Output | 따로 모아 나중에 보정 | 별도 배치 보정 파이프라인 | 로그 아카이빙, 재처리 |

Part 4의 선택지도 같다(바로 버림, 일정 시간까지 반영, 별도 경로로 분리, 수정 결과를 다시 출력, p208). 강의는 "늦게 온 데이터는 버리면 된다"가 운영 지표에는 가능해도 정산·분석·학습 데이터에서는 큰 왜곡이 된다고 경고한다(p188).

### 결과를 어떻게 내보내나

늦은 데이터가 이미 낸 결과를 바꾸면 그 수정을 싱크에 어떻게 반영할지 정해야 한다. 결제 예시로는 첫 결과 2건 뒤에 3건이 오면 새 행으로 추가할지, 2건을 3건으로 갱신할지, 둘 다 이벤트로 남길지다(p211–212).

⚠️ 강의는 출력 방식을 Append·Upsert·Update로 나누는데(p213), Spark Structured Streaming의 출력 모드는 Append·Complete·Update다("Append mode (default)… Complete mode… Update mode", 같은 가이드, 2026-09-28 확인). 위키가 정리하면 다음과 같다.

| 모드(Spark) | 내보내는 것 | 맞는 싱크 |
|---|---|---|
| Append | 확정된(더는 안 바뀌는) 결과 행만. 워터마크가 구간을 닫은 뒤에 나온다 | 파일, 로그성 테이블 |
| Update | 이번 트리거에 바뀐 결과 행만 | 키로 덮어쓸 수 있는 싱크 |
| Complete | 결과 표 전체를 매번 | 작은 집계 결과 |

Upsert는 출력 모드가 아니라 싱크 쪽 반영 방식이다. Update 모드의 변경 행을 키 기반으로 덮어쓰는 싱크(`MERGE`, Flink의 upsert-kafka 같은 changelog 싱크)에 쓸 때 "같은 키 결과를 덮어쓰기"가 된다. 덮어쓰기가 멱등하므로 재처리에도 안전하다([[멱등성]]). Flink의 changelog 의미는 위키가 문서로 대조하지 않았다.

### 시간 기준이 갈리면 스큐가 된다

[[AI DE 강의 2-06 Training-Serving Skew 예방]]은 이 구분을 모델 쪽에서 다시 쓴다. "최근 10분" 피처를 학습에서는 배치로 이벤트 시간 기준으로 쉽게 집계한다. 서빙은 실시간이라 처리 시간 기준이 되기 쉽고, 늦거나 빠진 이벤트 때문에 집계에 들어가는 이벤트 집합 자체가 달라진다. 강의의 처방은 두 시간 가운데 하나로 고정해 양쪽에 똑같이 적용하고, 늦은 이벤트를 워터마크로 얼마나 허용할지 정책으로 정하는 것이다. 스큐 전반은 [[학습-서빙 스큐]]에 있다.

## 상태와 exactly-once

- Stateless 연산(필터·맵·파싱)은 확장이 쉽고, Stateful 연산(윈도우·조인·집계)은 과거를 기억해야 한다. Part 4는 stateless 처리는 브로커에 붙인 단순 consumer 앱으로도 되지만, "최근 5분간 로그인 실패 5회 이상 계정 차단"처럼 실무 요구 대부분이 상태를 필요로 해서 엔진이 필요하다고 설명한다([[AI DE 강의 4-07 메시지 브로커와 스트림 처리 엔진]] p159–161).
- 상태는 레코드마다 외부 DB에 가지 않고 계산 노드 로컬에 둔다(p162). 메모리 기반(Flink의 HashMapStateBackend, 가장 빠르지만 메모리 크기가 한계)과 임베디드 RocksDB 기반(로컬 SSD에 LSM-Tree, TB급 상태)이 있다. Flink 2.0(2025-03-24)은 원격 저장소에 상태를 두는 ForSt 백엔드(disaggregated state)를 도입했지만, 현재 문서는 "still in the experimental stage and is not fully available for production"이라고 적는다. [https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/state_backends/ , 2026-09-28 확인]
- 상태는 키별(Keyed)로 나뉘어 병렬 처리되고, 연산자 단위(Operator) 상태에는 Kafka 오프셋 같은 입력 위치가 들어간다.
- 체크포인트: 주기적으로 상태를 일관된 스냅샷으로 떠서 HDFS·S3에 저장하고, 장애가 나면 그 시점부터 다시 처리한다. 상태와 입력 오프셋을 함께 찍기 때문에, 복구할 때 상태를 되돌린 만큼 입력도 되감는다. 그래서 각 레코드는 엔진 상태에 한 번만 반영된다. 출력까지 exactly-once(end-to-end)가 되려면 재생 가능한 소스와 트랜잭션 싱크나 [[멱등성|멱등]] 싱크가 더 필요하다. [Flink 문서 "Fault Tolerance": "this does *not* mean that every event will be processed exactly once. Instead, it means that _every event will affect the state being managed by Flink exactly once_." · "To achieve exactly once end-to-end… 1. your sources must be replayable, and 2. your sinks must be transactional (or idempotent)" https://nightlies.apache.org/flink/flink-docs-stable/docs/learn-flink/fault_tolerance/ · Spark 문서: "using replayable sources and idempotent sinks, Structured Streaming can ensure end-to-end exactly-once semantics under any failure." https://spark.apache.org/docs/latest/streaming/getting-started.html , 2026-09-14 확인] 오프셋은 [[Apache Kafka]]에서 설명한다.

| 배포 | 별도 클러스터 | Spark 클러스터 | 별도 클러스터 없음. Java·Scala 앱 안에서 실행 |

| 상태 복구 | 체크포인트(상태 + 입력 위치) | 체크포인트 + WAL + 재생 가능한 소스 + 멱등 싱크 | 상태 저장소의 변경 이력 토픽(changelog)에서 복원 |

마이크로 배치는 [[지연 시간과 처리량]] 사이의 절충점이다. 0.5초~수 초를 모아 처리해서, 1~5초 지연으로 배치에 가까운 효율을 낸다.

⚠️ Part 4(2026-05 작성)도 Spark를 마이크로 배치 엔진으로만 설명하지만, Spark 4.1.0(2025-12-16)이 Real-Time Mode를 넣었다. 릴리스 노트는 "First official support for Structured Streaming queries running in real-time mode… single-digit milliseconds"라고 적고, 4.2.0(2026-07-14)이 PySpark 지원을 더했다. [https://spark.apache.org/releases/spark-release-4.1.0.html , 2026-09-28 확인] 실험적 기능인 Continuous Processing은 2.3부터 있었다. "Flink는 밀리초, Spark는 초"라는 대비는 이제 기본 설정에 대한 설명으로만 맞다.

## 언제 스트리밍을 쓰나

[[AI DE 강의 1-10 배치 vs 스트리밍]]은 두 조건을 든다. 데이터 가치가 초 단위로 사라지고(이상 거래 탐지·실시간 추천·경보), 24x7 운영 역량이 있을 때다. 나머지 경우는 [[배치 처리]]가 기본이다. 스트리밍을 쓰면 건별 오버헤드, 순서·유실 대응, 상태 관리의 복잡성을 떠안는다.
