# 가비지 컬렉터

[[가비지 컬렉션]]을 실제로 수행하는 HotSpot [[JVM]]의 구현체들. 원리는 같고, **무엇을 희생해 무엇을 얻느냐**가 다르다.

## 고르는 축 — 처리량 vs 지연

- **처리량(throughput)** — 전체 CPU 시간 중 애플리케이션이 쓴 비율. 가끔 길게 멈춰도 총량이 크면 좋다. 배치에 맞다.
- **지연(pause)** — STW 한 번의 길이와 그 예측 가능성. 요청-응답 서비스의 p99에 맞다.
- **대가** — 지연을 줄이는 컬렉터는 barrier와 동시 작업에 CPU·메모리를 더 쓴다.

이것은 [[지연 시간과 처리량]]의 맞교환이 GC에서 나타난 모습이다. *(위키의 연결)*

## 컬렉터들

| 컬렉터 | 방식 | 고른 쪽 | 상태 |
|---|---|---|---|
| **Serial** | 단일 스레드, STW, Young은 복사 · Old는 mark-compact | 작은 힙·단일 CPU | 현역. 작은 환경의 기본이었다 |
| **Parallel** | Serial을 멀티 스레드로. 여전히 전부 STW | **처리량** | 현역. JDK 8 기본 |
| **CMS** | Old를 대부분 동시에 mark-sweep. compaction이 기본으로 없어 단편화가 심하면 Full GC로 떨어진다 | 지연 | JDK 9 deprecated(JEP 291), **JDK 14 제거**(JEP 363) |
| **G1** | 힙을 Region으로 나누고 garbage 많은 Region부터 복사로 수거. 목표 pause를 준다 | **지연과 처리량의 균형** | JDK 9부터 기본 |
| **ZGC** | colored pointer + load barrier로 마킹·재배치까지 동시. pause가 힙 크기와 거의 무관 | **초저지연**, 대형 힙 | JDK 11 실험(JEP 333) → JDK 15 정식(JEP 377) → JDK 21 Generational(JEP 439) → JDK 23부터 generational이 기본 모드(JEP 474) |
| **Shenandoah** | forwarding pointer + barrier로 동시 compaction | 초저지연 | JDK 15 정식(JEP 379) |

[JEP 363, https://openjdk.org/jeps/363 ; JEP 377, https://openjdk.org/jeps/377 ; JEP 474, https://openjdk.org/jeps/474 ;
JEP 379, https://openjdk.org/jeps/379 ; 2026-09-26 확인]

## 기본 GC의 변천

| 시점 | 기본 | 비고 |
|---|---|---|
| JDK 8 | Parallel | server-class 머신 기준 |
| **JDK 9** | **G1** | JEP 248. 단 **server-class 머신**(CPU 2개 이상 · 메모리 1792MB 이상)에서만. 못 미치면 Serial |
| JDK 11 (LTS) | G1 | JDK 9 결정을 이어받은 첫 LTS |
| **JDK 27** | **모든 환경에서 G1** | JEP 523 「Make G1 the Default Garbage Collector in All Environments」 (Delivered, Release 27) |

[JEP 248, https://openjdk.org/jeps/248 ; JEP 523, https://openjdk.org/jeps/523 ; 2026-09-26 확인]

**컨테이너 함정.** CPU 1개나 메모리 1792MB 미만으로 제한한 파드는 JDK 26까지 조용히 Serial GC로 뜬다. 로그를 보고 놀라는 일이
흔하다. `-XX:+UseG1GC`를 명시하거나 JDK 27로 올린다. *(위키의 관찰)*

## G1의 구조와 사이클

- **Region** — 힙을 고정 크기 Region으로 나눈다. 크기는 ergonomics가 정하고(1~32MB, JDK 18부터 최대 512MB), `-XX:G1HeapRegionSize`로
  조정한다. Region마다 Eden · Survivor · Old 역할이 **동적으로** 붙고, 같은 세대의 Region이 물리적으로 연속일 필요가 없다.
- **Humongous** — Region 크기의 절반 이상인 객체는 연속된 Humongous Region에 바로 들어간다.
- **사이클**
  1. **Young-only** — Young GC(STW, 복사)를 반복한다.
  2. **Concurrent Start** — Old 점유가 IHOP(기본은 Adaptive IHOP)을 넘으면 Young GC와 함께 동시 마킹을 시작해 Region별 생존량을 잰다.
  3. **Remark · Cleanup** — 짧은 STW로 마킹을 마무리한다.
  4. **Space-reclamation** — **Mixed GC**가 Young과 함께 garbage 많은 Old Region을 골라 수거한다("Garbage First"). 회수할 가치가
     줄면 다시 Young-only로.
- 동시 마킹은 애플리케이션과 함께 돌지만, Young GC와 Mixed GC 자체는 STW다.
- `-XX:MaxGCPauseMillis` — 목표 pause(기본 200ms). 보장이 아니라 목표다. G1은 이 목표에 맞춰 한 번에 수거할 Region 수를 고른다.

[Oracle, 「Garbage-First (G1) Garbage Collector」, GC Tuning Guide JDK 21,
https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html ; JDK 25 플래그, 2026-09-26 확인]

## DE가 신경 쓰는 이유

[[Apache Spark]] executor, [[Apache Kafka]] 브로커, [[Apache Flink]] TaskManager가 모두 JVM 위에서 돈다. 큰 힙에서 긴 Full GC가
나서 그 멈춤이 heartbeat 한계(`spark.network.timeout`, 기본 120s)를 넘으면 Spark는 executor를 잃은 것으로 보고 태스크를
재스케줄하고, Flink는 체크포인트가 늦어진다. 그래서 대형 힙 JVM 워크로드에서는
G1 튜닝이나 ZGC 검토가 흔한 운영 작업이다. *(위키의 연결)*

## 면접에서

자료의 Gold 답([[Java 면접 3 GC]] Q2·Q2-1)보다 나은 뼈대:

- **Q. GC 종류** — 처리량 vs 지연 축을 먼저 세운다. "Serial·Parallel은 처리량 쪽이고 전부 STW, CMS는 지연을 줄이려던 시도였지만
  단편화 문제로 JDK 14에서 제거됐습니다. G1은 Region 단위로 목표 pause를 맞추는 균형형이고, ZGC·Shenandoah는 재배치까지 동시에 해
  pause를 ms 이하로 줄입니다."
- **Q. 기본 GC가 왜 바뀌었나** — "JDK 9에서 G1이 기본이 됐습니다. 힙이 커지면서 Parallel의 Full GC pause가 힙 크기에 비례해
  길어지는 게 문제였고, G1은 Region을 골라 수거해 pause를 목표치 안에 둡니다. 다만 JDK 26까지는 작은 머신에서 Serial이 골라져서,
  컨테이너에서는 명시하는 게 안전합니다."

## 자료의 서술과 정정

| 자료 | 판정 | 정정 |
|---|---|---|
| 주요 GC = Serial·Parallel·CMS·G1 (p41), "G1은 최신 GC"(Silver p40) | 단서 필요 | CMS는 JDK 14에서 제거. ZGC·Shenandoah가 빠졌다. G1은 기본이지 최신이 아니다 |
| CMS는 Compaction이 기본으로 없다 (p41) | 맞음 | 단편화가 심하면 Full GC로 떨어졌다 |
| Java 8 기본 Parallel, Java 11 기본 G1 (p44) | 단서 필요 | G1 기본은 JDK 9부터, 그것도 server-class 머신에서만. JDK 27부터 모든 환경 |
| G1 Region·Humongous·Young-only → Concurrent Marking → Mixed GC (p47) | 맞음 | Region 크기 범위와 Adaptive IHOP을 덧붙이면 좋다 |
| `-XX:MaxGCPauseMillis` (p44) | 맞음 | 기본 200ms, 목표이지 보장이 아니다 |
