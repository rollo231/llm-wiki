# 가비지 컬렉터

[[가비지 컬렉션]]을 실제로 수행하는 HotSpot [[JVM]]의 구현체들. 원리는 같고, 무엇을 희생해 무엇을 얻느냐가 다르다.

## 고르는 축 — 처리량 vs 지연

- 처리량(throughput): 전체 CPU 시간 중 애플리케이션이 쓴 비율. 가끔 길게 멈춰도 총량이 크면 좋다. 배치에 맞다.
- 지연(pause): STW 한 번의 길이와 그 예측 가능성. 요청-응답 서비스의 p99에 맞다.
- 대가: 지연을 줄이는 컬렉터는 barrier와 동시 작업에 CPU·메모리를 더 쓴다.

이것은 [[지연 시간과 처리량]]의 맞교환이 GC에서 나타난 모습이다. 이 연결은 위키가 붙였다.

## 컬렉터들

| 컬렉터 | 방식 | 고른 쪽 | 상태 |
|---|---|---|---|
| Serial | 단일 스레드, STW, Young은 복사 · Old는 mark-compact | 작은 힙·단일 CPU | 현역. 작은 환경의 기본이었다 |
| Parallel | Serial을 멀티 스레드로. 여전히 전부 STW | 처리량 | 현역. JDK 8 기본 |
| CMS | Old를 대부분 동시에 mark-sweep. compaction이 기본으로 없어 단편화가 심하면 Full GC로 떨어진다 | 지연 | JDK 9 deprecated(JEP 291), JDK 14 제거(JEP 363) |
| G1 | 힙을 Region으로 나누고 garbage 많은 Region부터 복사로 수거. 목표 pause를 준다 | 지연과 처리량의 균형 | JDK 9부터 기본 |
| ZGC | colored pointer + load barrier로 마킹·재배치까지 동시. pause가 힙 크기와 거의 무관 | 초저지연, 대형 힙 | JDK 11 실험(JEP 333) → JDK 15 정식(JEP 377) → JDK 21 Generational(JEP 439) → JDK 23부터 ZGC의 기본 모드가 generational(JEP 474) → JDK 24에서 비세대 모드 제거(JEP 490). ZGC 자체가 JVM 기본 GC인 적은 없다(기본은 G1) ↓ |
| Shenandoah | forwarding pointer + barrier로 동시 compaction | 초저지연 | JDK 15 정식(JEP 379) → JDK 24 세대별 모드 실험(JEP 404) → JDK 25 세대별 모드 정식(JEP 521, 기본은 여전히 단일 세대). Oracle 빌드에는 없다 ↓ |
| Epsilon | 할당만 하고 회수하지 않는다. 힙이 다 차면 JVM이 종료된다 | 성능 측정 기준선, 아주 짧은 작업 | JDK 11 실험(JEP 318). 지금도 `-XX:+UnlockExperimentalVMOptions`가 필요하다(JDK 25 확인) |

[JEP 363, https://openjdk.org/jeps/363 ; JEP 377, https://openjdk.org/jeps/377 ; JEP 474, https://openjdk.org/jeps/474 ; JEP 379, https://openjdk.org/jeps/379 ; 2026-09-26 확인 · JEP 318, https://openjdk.org/jeps/318 ; JEP 490, https://openjdk.org/jeps/490 ; JEP 404, https://openjdk.org/jeps/404 ; JEP 521, https://openjdk.org/jeps/521 ; 2026-09-27 확인]

켜는 옵션: `-XX:+UseSerialGC` · `-XX:+UseParallelGC` · `-XX:+UseG1GC` · `-XX:+UseZGC` · `-XX:+UseShenandoahGC` ·`-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC`.

Shenandoah는 배포판에 따라 없다. Oracle은 Shenandoah를 빌드하지 않는다. jdk.java.net의 Oracle OpenJDK 25.0.2 빌드에서 `-XX:+UseShenandoahGC`는 `Option -XX:+UseShenandoahGC not supported`로 실패한다(2026-09-27 로컬 확인). Red Hat 계열 등 다른 배포판에는 들어 있다. [Red Hat Developer, 「Not all OpenJDK 12 builds include Shenandoah: Here's why」, 2019-04-19, https://developers.redhat.com/blog/2019/04/19/not-all-openjdk-12-builds-include-shenandoah-heres-why , 2026-09-27 확인] 어느 배포판에 들어 있는지는 배포판마다 확인한다.

흐름: 저지연 GC도 세대별로 간다. ZGC는 비세대 모드를 없앴고 Shenandoah는 세대별 모드를 정식으로 만들었다. [[가비지 컬렉션]]의 약한 세대 가설이 동시 컬렉터에도 들어온 것이다. 이 흐름은 위키가 종합한 것이고, JEP 439가 밝힌 동기와 맞는다. 비세대 ZGC는 "stores all objects together, regardless of age, so it must collect all objects every time it runs"였고, 그래서 메모리와 CPU가 넉넉해 애플리케이션의 할당보다 빨리 회수할 수 있을 때만 잘 동작했다. 세대 가설에 따라 어린 객체를 더 자주 수거하면 성능이 좋아진다. [JEP 439 「Generational ZGC」(JDK 21), https://openjdk.org/jeps/439 , 2026-09-27 확인]

「기본」 두 가지를 섞지 않는다. 「JVM의 기본 GC」는 JDK 9부터 G1이고, JDK 27부터는 모든 환경에서 G1이다(JEP 523). 「ZGC의 기본 모드」는 ZGC를 직접 켰을 때(`-XX:+UseZGC`) 어느 모드로 도느냐로, JDK 23부터 generational이다(JEP 474 「ZGC: Generational Mode by Default」). JEP 439도 G1을 "the default garbage collector"라고 부르며 ZGC와 비교한다. 로컬 JDK 25.0.2는 옵션 없이 `Using G1`을 찍고, `-XX:-ZGenerational`에는 "support was removed in 24.0"라고 경고한다(2026-09-27 확인).

## 기본 GC의 변천

| 시점 | 기본 | 비고 |
|---|---|---|
| JDK 8 | Parallel | server-class 머신 기준 |
| JDK 9 | G1 | JEP 248. 단 server-class 머신(CPU 2개 이상 · 메모리 1792MB 이상)에서만. 못 미치면 Serial |
| JDK 11 (LTS) | G1 | JDK 9 결정을 이어받은 첫 LTS |
| JDK 27 | 모든 환경에서 G1 | JEP 523 「Make G1 the Default Garbage Collector in All Environments」 (Delivered, Release 27) |

[JEP 248, https://openjdk.org/jeps/248 ; JEP 523, https://openjdk.org/jeps/523 ; 2026-09-26 확인]

컨테이너 함정. CPU 1개나 메모리 1792MB 미만으로 제한한 파드는 JDK 26까지 조용히 Serial GC로 뜬다. 로그를 보고 놀라는 일이 흔하다. `-XX:+UseG1GC`를 명시하거나 JDK 27로 올린다. 위키가 관찰한 것이다.

Java 8의 G1(단일 스레드 Full GC)과 8 → 11 전환 논리는 [[Java 8에서 11로 가는 GC 관점의 이유]]에 있다.

## G1의 구조와 사이클

- Region: 힙을 고정 크기 Region으로 나눈다. 크기는 ergonomics가 정하고(1~32MB, JDK 18부터 최대 512MB), `-XX:G1HeapRegionSize`로 조정한다. Region마다 Eden · Survivor · Old 역할이 동적으로 붙고, 같은 세대의 Region이 물리적으로 연속일 필요가 없다.
  - 자동으로 정하는 규칙: `최대 힙 ÷ 2048`(목표 Region 수 `TARGET_REGION_NUMBER = 2048`)을 1MB~32MB로 자른 뒤 2의 거듭제곱으로 올린다. 직접 지정한 값도 2의 거듭제곱으로 올리고 1MB~512MB(`MAX_REGION_SIZE`)로 자른다. 그래서 힙이 64GB를 넘으면 Region은 32MB에 머물고 개수가 2048을 넘는다. [OpenJDK 소스 `src/hotspot/share/gc/g1/g1HeapRegionBounds.hpp` ·`g1HeapRegion.cpp`의 `G1HeapRegion::setup_heap_region_size`, https://github.com/openjdk/jdk , 2026-09-27 확인]
  - 실측(JDK 25.0.2, `-XX:+PrintFlagsFinal`, 2026-09-27): `-Xmx` 512m·2g → 1MB, 8g → 4MB, 16g → 8MB, 32g → 16MB, 64g → 32MB. `-XX:G1HeapRegionSize=3m` → 4MB, `64m` → 64MB, `512m` → 512MB. 기본 최대 힙은 RAM의 1/4(RAM 32GB 맥에서 8GB)이었다.
- Humongous: Region 크기의 절반 이상인 객체는 연속된 Humongous Region에 바로 들어간다(소스의 `humongous_threshold_for` = `region_size / 2`). 힙 8GB면 Region이 4MB이므로 2MB 이상의 배열 하나가 Humongous다. 많아지면 연속된 빈 Region을 찾기 어렵고, 할당 실패(`Humongous Allocation Failure`)는 Full GC로 이어질 수 있다. 큰 객체가 흔한 앱은 Region을 키워 Humongous를 피하기도 한다. 이 마지막 문장은 운영 통념이다.
  - 왜 문제인가: Oracle 문서가 드는 특별 취급 다섯 가지:
    1. Eden을 건너뛴다. "directly allocated as belonging to the old generation". 연속된 Old Region에 바로 놓이므로 금방 죽어도 Young GC가 싸게 치우지 못한다.
    2. 회수가 늦다. 보통은 마킹이 끝나는 pause나 Full GC에서만 회수된다. 예외: 원시 타입 배열(bool·정수·부동소수)은 참조하는 객체가 적으면 어느 GC pause에서든 회수를 시도한다(eager reclaim, 기본 켜짐, `-XX:-G1EagerReclaimHumongousObjects`로 끔).
    3. GC를 앞당긴다. 할당할 때마다 IHOP를 확인해, 넘었고 마킹 중이 아니면 Concurrent Start를 즉시 건다.
    4. 거의 옮기지 않는다. 같은 pause 안의 첫 Full GC로도 연속 공간이 모자랄 때, 두 번째 Full GC에서야 옮긴다.
    5. 끝 Region의 남는 자리: 객체 끝이 걸친 Region의 나머지는 할당에 쓸 수 없어, 그 때문에 OOM으로 끝날 수 있다. 예: Region 4MB에 5MB 객체면 8MB를 차지하고 3MB가 남는다. 이 예시 계산은 위키가 한 것이다.
  - 회수 시점은 JDK 11부터 Remark다. 문서만 JDK 21까지 Cleanup이라 적었다. 2번의 「마킹이 끝나는 pause」를 튜닝 가이드는 JDK 17 · 21판에서 Cleanup, JDK 22판부터 Remark로 적는다(17·21·22·23·24·25판 대조). 그러나 동작은 이미 JDK 11에서 바뀌었다. JDK-8154528 「Reclaim regions emptied by marking in Remark pause」(Fixed in 11, 2018-04-18)의 설명: "Currently we reclaim dead humongous objects (and in general completely empty regions) after the Cleanup pause. It may take a while from Remark to Cleanup." 그래서 JDK 17·21판도 같은 문서의 Remark 설명에는 이미 "reclaims completely empty regions"라고 적어, 한 문서 안에서 서로 어긋나 있었다. JDK 22판에서 고쳐진 것은 문서 갱신 이슈 JDK-8319794 「GC Tuning Guide: G1 Updates for JDK 22」("Updates and corrections")에서다. 단, 이 이슈 설명에 이 문장이 따로 적혀 있지는 않아 연결은 추론이다. [JDK-8154528, https://bugs.openjdk.org/browse/JDK-8154528 ; JDK-8319794, https://bugs.openjdk.org/browse/JDK-8319794 ; 2026-09-27 확인] [Oracle, 「Garbage-First (G1) Garbage Collector」 Humongous Objects 절, GC Tuning Guide JDK 17 · 21 · 22 · 23 · 24 · 25, https://docs.oracle.com/en/java/javase/25/gctuning/garbage-first-g1-garbage-collector1.html (버전 번호만 바꿔 대조), 2026-09-27 확인]
- 사이클
  1. Young-only: Young GC(STW, 복사)를 반복한다.
  2. Concurrent Start: Old 점유가 IHOP(기본은 Adaptive IHOP)을 넘으면 Young GC와 함께 동시 마킹을 시작해 Region별 생존량을 잰다.
  3. Remark · Cleanup: 짧은 STW 둘로 마킹을 마무리한다. Remark는 마킹을 끝내고 참조 처리·클래스 언로딩을 하며, 완전히 빈 Region은 이 자리에서 바로 회수한다. Cleanup은 Space-reclamation 단계로 갈지 정한다. 간다면 Young-only는 Prepare Mixed Young GC 한 번으로 끝난다.
  4. Space-reclamation: Mixed GC가 Young과 함께 garbage 많은 Old Region을 골라 수거한다("Garbage First"). 회수할 가치가 줄면 다시 Young-only로.
- 동시 마킹은 애플리케이션과 함께 돌지만, Young GC와 Mixed GC 자체는 STW다.
- `-XX:MaxGCPauseMillis`: 목표 pause(기본 200ms). 보장하지는 않는 목표값이다. G1은 이 목표에 맞춰 한 번에 수거할 Region 수를 고른다.

[Oracle, 「Garbage-First (G1) Garbage Collector」, GC Tuning Guide JDK 21, https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html ; JDK 25 플래그, 2026-09-26 확인]

## DE가 신경 쓰는 이유

[[Apache Spark]] executor, [[Apache Kafka]] 브로커, [[Apache Flink]] TaskManager가 모두 JVM 위에서 돈다. 큰 힙에서 긴 Full GC가 나서 그 멈춤이 heartbeat 한계(`spark.network.timeout`, 기본 120s)를 넘으면 Spark는 executor를 잃은 것으로 보고 태스크를 재스케줄하고, Flink는 체크포인트가 늦어진다. 그래서 대형 힙 JVM 워크로드에서는 G1 튜닝이나 ZGC 검토가 흔한 운영 작업이다. 이 연결은 위키가 붙였다.

## 면접에서

자료의 Gold 답([[Java 면접 3 GC]] Q2·Q2-1)보다 나은 뼈대:

- Q. GC 종류: 처리량 vs 지연 축을 먼저 세운다. "Serial·Parallel은 처리량 쪽이고 전부 STW, CMS는 지연을 줄이려던 시도였지만 단편화 문제로 JDK 14에서 제거됐습니다. G1은 Region 단위로 목표 pause를 맞추는 균형형이고, ZGC·Shenandoah는 재배치까지 동시에 해 pause를 ms 이하로 줄입니다."
- Q. 기본 GC가 왜 바뀌었나: "JDK 9에서 G1이 기본이 됐습니다. 힙이 커지면서 Parallel의 Full GC pause가 힙 크기에 비례해 길어지는 게 문제였고, G1은 Region을 골라 수거해 pause를 목표치 안에 둡니다. 다만 JDK 26까지는 작은 머신에서 Serial이 골라져서, 컨테이너에서는 명시하는 게 안전합니다."

## 자료의 서술과 정정

| 자료 | 판정 | 정정 |
|---|---|---|
| 주요 GC = Serial·Parallel·CMS·G1 (p41), "G1은 최신 GC"(Silver p40) | 단서 필요 | CMS는 JDK 14에서 제거. ZGC·Shenandoah가 빠졌다. G1은 기본이지 최신이 아니다 |
| CMS는 Compaction이 기본으로 없다 (p41) | 맞음 | 단편화가 심하면 Full GC로 떨어졌다 |
| Java 8 기본 Parallel, Java 11 기본 G1 (p44) | 단서 필요 | G1 기본은 JDK 9부터, 그것도 server-class 머신에서만. JDK 27부터 모든 환경 |
| G1 Region·Humongous·Young-only → Concurrent Marking → Mixed GC (p47) | 맞음 | Region 크기 범위와 Adaptive IHOP을 덧붙이면 좋다 |
| `-XX:MaxGCPauseMillis` (p44) | 맞음 | 기본 200ms, 목표이지 보장이 아니다 |
