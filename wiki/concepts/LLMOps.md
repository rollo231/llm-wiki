# LLMOps

**LLM 기반 시스템을 운영 가능하게 만드는 체계**([[AI DE 강의 2-03 LLMOps]]). [[MLOps]]가 모델(학습·배포·모니터링)을
중심에 뒀다면, LLMOps의 중심은 **생성 시스템 전체** — 프롬프트·컨텍스트·검색·가드레일 — 이다. 핵심 자산은 모델보다
프롬프트, 컨텍스트 파이프라인, 지식 베이스(RAG)이고, 핵심 문제는 품질 평가·통제, 토큰 비용, 안전, 지식 최신성이다.

"LLM은 엔진이고, 서비스는 파이프라인."

## MLOps와의 차이

| 구분 | MLOps | LLMOps |
|---|---|---|
| 입력 | 정형 피처 | 자연어 |
| 출력 | 숫자 예측 | 텍스트 생성 |
| 핵심 자산 | 모델 | 프롬프트 + 컨텍스트 |
| 외부 지식 | 제한적 | 필수 |
| 비용 구조 | 비교적 안정 | 호출 기반 변동 |

강의는 둘 사이에 **AI Engineering**(제품 중심 — 모델 + 데이터 파이프라인 + 서빙 + 관측·평가 + 비용)을 둔다.

## 기본 구조

```
Query 입력 → Retrieval(검색) → Context 구성 → LLM 생성 → 후처리/필터링
```

LLM 단독으로는 최신 정보·사내 데이터·근거가 부족하므로 검색으로 보완한다. 검색 쪽 부품(임베딩·벡터 DB·청킹)은
[[비정형 데이터 파이프라인]]에 있다. [[AI DE 강의 2-01 데이터 파이프라인의 진화와 데이터 엔지니어]]의 LLMOps 그림은
사내·공개 데이터 → 처리 파이프라인 → 임베딩(벡터 스토어)과 사전학습 LLM → 파인튜닝 → LLM API → 앱, 그리고 RLHF 피드백
루프와 모델 버전 관리·캐싱·모니터링을 한 판에 놓는다.

## 관리 대상 — 변경 지점

모델 가중치를 건드리지 않고 출력을 바꿀 수 있는 지점이 많고, 그래서 운영 체계가 필요하다.

| 변경 지점 | 예 |
|---|---|
| 프롬프트 | 템플릿 버전 |
| 검색 | top-k, rerank |
| 인덱싱 | 청킹 전략, 임베딩 모델 버전, 벡터 DB 인덱스·스키마 |
| 안전 | 정책 필터(guardrail) |
| 평가 | 평가셋(질문·정답·근거) |

재현성(같은 질문 → 같은 답)을 확보하려면 이 전부를 한 시점의 스냅샷으로 기록해야 한다 — MLOps보다 버전 표면이 넓다.
*(위키의 관찰)* → [[데이터와 모델 버전 관리]]

## 컨텍스트 엔지니어링

기존 ML에서 피처가 성능을 좌우했다면 LLM에서는 컨텍스트가 좌우한다. 설계 변수 네 가지:

| 질문 | 변수 |
|---|---|
| 무엇을 넣나 | source 선택 |
| 얼마나 넣나 | top-k, token budget |
| 어떤 순서로 넣나 | ranking |
| 얼마나 압축하나 | summarization |

**피처 엔지니어링의 교훈이 그대로 이어진다.** 인덱싱 때의 청킹·임베딩 모델과 질의 때의 임베딩 모델이 어긋나면 에러 없이
검색 품질만 떨어진다 — [[학습-서빙 스큐]]와 같은 모양이다. 검색 설정은 "피처 로직"이므로 버전으로 묶는다. *(위키의 연결)*

## 새 위험과 대응

| 위험 | 강의의 정의 | 대응 |
|---|---|---|
| 환각(Hallucination) | 근거 없이 그럴듯한 내용 생성 | 근거 문서 링크·ID·스니펫 강제, 근거 부족 시 "답할 수 없음" 폴백, retrieval 품질 게이트(유사도·재랭킹 점수 임계치), 출처-응답 정합성(entailment) 점검 |
| Context Drift ⚠️ | 검색·컨텍스트 품질 저하로 답변 품질 변동 | retrieval 품질·드리프트 모니터링 |
| Prompt Drift ⚠️ | 프롬프트 수정·누적으로 동작이 의도에서 벗어남 | 프롬프트 템플릿 버전 관리, 평가셋 |
| 응답 일관성 | 같은 질문에도 편차가 큼 | 로깅, 평가 |
| 개인정보 유출 | 민감 정보가 출력에 섞임 | PII 탐지·마스킹(정규식 + 탐지 모델) |
| 프롬프트 인젝션 | 지시를 우회해 정책을 깨거나 정보 탈취 | 정책 우회 패턴 탐지, 프롬프트 분리, 컨텍스트 정화 |

필수 요소: 로깅 · 평가 · 가드레일 · Human-in-the-loop.

- ⚠️ Context Drift·Prompt Drift는 **표준 용어가 아니다** — 벤더마다 정의가 다르고(예: Kore.ai는 Prompt Drift를 모델이
  바뀌어 같은 프롬프트의 응답이 달라지는 현상으로 정의), 강의의 정의는 강의 안의 작업 정의다. 근거는
  [[AI DE 강의 2-03 LLMOps]]의 주의·결함.
- 프롬프트 인젝션은 OWASP Top 10 for LLM Applications 2025의 **LLM01**이다.

**가드레일** — 출력 필터링 레이어(금지 카테고리, 규칙 + 분류기), PII 마스킹, 정책 우회 탐지("ignore previous
instructions"), 차단 시 사유를 과하게 드러내지 않는 정책 템플릿 응답.

## 보안 원칙 — 모델이 아니라 데이터 경로에서 막는다

1. **권한 기반 retrieval** — 사용자 권한에 따라 검색 대상 문서를 제한한다. 검색 결과에 비밀이 섞이면 모델이 유출하므로
   모델보다 retrieval 계층에서 막는다. → [[데이터 거버넌스와 카탈로그]]의 "권한 관리가 검색 계층으로 옮겨 간다"
2. **시스템·사용자·툴 프롬프트 분리** — 사용자 입력은 지시가 아니라 데이터로 취급한다. 단 모델 안에서는 이 구분을 강제할
   수 없어 완화책일 뿐이다(아래).
3. **툴 호출 allowlist** — 도구 목록 제한, 입력 스키마 검증, 민감 API 차단.
4. **컨텍스트 정화** — 가져온 문서에 숨은 지시문을 걸러 정보만 전달한다.

넷 중 셋이 모델 밖의 데이터 경로에서 일어난다 — LLM 보안의 상당 부분이 데이터 엔지니어의 일이다. *(위키의 관찰)*

겉보기엔 SQL 인젝션 방어(입력을 코드가 아니라 데이터로 취급)와 닮았지만 **구조가 다르다.** 파라미터화 쿼리는 입력이 명령으로
해석될 수 없게 보장하는데, LLM 안에는 데이터와 지시의 구분이 없다. 그래서 프롬프트 분리는 완화책일 뿐이고, 방어의 중심은
인젝션이 성공해도 피해를 줄이는 쪽(권한 기반 retrieval·툴 allowlist)이다.
[NCSC, "Prompt injection is not SQL injection (it may be worse)" (2025-12-08) — "Under the hood of an LLM, there's no
distinction made between 'data' or 'instructions'; there is only ever 'next token'."
https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection · OWASP LLM01:2025 — "it is unclear if there are
fool-proof methods of prevention for prompt injection." https://genai.owasp.org/llmrisk/llm01-prompt-injection/ ,
2026-09-14 확인]

⚠️ 위키 정정 (2026-09-14 린트): 이 절은 처음에 "구조가 SQL 인젝션 방어와 같다"고 썼다.

## 비용 통제

| 수단 | 방법 | 맞바꾸는 것 *(위키의 정리)* |
|---|---|---|
| 토큰 예산 | 요청별 최대 입력·출력 토큰 제한 | 긴 컨텍스트의 품질 |
| 캐싱 | retrieval 결과 캐시, 응답 캐시 | 지식 최신성 |
| 모델 라우팅 | 간단한 질의는 작은 모델, 고난도만 큰 모델 | 라우팅 오판의 품질 손실 |
| 컨텍스트 압축 | top-k 줄이기, 요약, rerank | 근거 누락 |

[[지연 시간과 처리량]]의 맞교환에 **토큰 비용이라는 세 번째 축**이 붙는다. 모델 라우팅은 서빙 쪽의 "CPU로 충분하면 GPU를
쓰지 않는다"([[추론 최적화]])와 같은 판단이다. *(위키의 연결)*

## 데이터 엔지니어의 역할

**"지식 파이프라인과 운영 가능한 컨텍스트를 책임진다."**

- 지식 소스 수집·정제 파이프라인
- 청킹·임베딩 파이프라인 운영
- 벡터 DB·인덱스 운영(성능·비용·정합성)
- retrieval 품질·드리프트 모니터링
- 보안·거버넌스
- 제품·운영 관점의 시스템 설계

## 빈칸

- **평가 방법론** — 평가셋(질문·정답·근거)이 이름만 나온다. 지표, 오프라인·온라인 평가, LLM을 채점자로 쓰는 방식 같은
  것은 없다.
- **파인튜닝 파이프라인** — 2-01 그림에 "Fine-Tuning / Few-Shot Learning"과 RLHF가 있지만 설명이 없다.
- **에이전트** — 툴 호출은 allowlist 한 줄로만 다룬다.
- **RAG 세부**(청킹 방법, 하이브리드 검색, 리랭킹)는 Part 5의 전용 강의로 미룬다 — 아직 인제스트하지 않았다.
