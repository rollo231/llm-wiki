# 람다 아키텍처와 카파 아키텍처

배치의 정확성과 스트리밍의 저지연을 함께 얻으려는 두 데이터 처리 구조다. 람다는 두 경로(배치·속도)를 병렬로 두고 결과를 합치고, 카파는 재생 가능한 로그 위의 스트림 경로 하나로 실시간 처리와 재처리를 모두 한다. Java의 람다식과는 이름만 같다([[람다와 스트림]]).

## 람다 아키텍처

Nathan Marz가 제안했다. Marz의 2011-10-13 블로그 글 「How to beat the CAP theorem」이 구조를 설명하지만 「Lambda Architecture」라는 이름은 그 글에 없고, 이후 Manning 책 『Big Data』(Marz·Warren)에서 붙었다. 책은 위키가 직접 확인하지 않았다. [http://nathanmarz.com/blog/how-to-beat-the-cap-theorem.html , 2026-09-28 확인]

| 계층 | 맡는 것 | 강의의 키워드 |
|---|---|---|
| 배치 레이어 | 불변 마스터 데이터셋을 주기적으로 전체 재계산 | Accuracy |
| 스피드 레이어 | 최근 데이터를 증분 처리해 즉시 결과 | Latency |
| 서빙 레이어 | 두 결과를 합친 뷰로 질의에 답함 | Unified View |

[[AI DE 강의 4-10 람다·카파와 현대 아키텍처]]의 사례는 이상 결제 탐지다. 스피드 레이어가 결제 즉시 블랙리스트 대조와 차단을 하고, 배치 레이어가 수개월 결제를 전수 조사해 새 사기 패턴을 학습한다(p223).

### 남긴 것

강의는 람다를 "잘못된 답이 아니라 당시 도구 한계의 산물"로 본다(p226). 2010년대 초 Hadoop은 정확하지만 느렸고, 초기 스트림 시스템은 빨랐지만 결과를 믿기 어려웠다. 그 사이에서 나온 현실적 해법이다.

가장 큰 유산은 재처리를 아키텍처 수준의 요구사항으로 끌어올린 것이다(p222). 원본 데이터를 보존하고, 코드가 바뀌면 과거 결과를 다시 계산하고, 실시간 계층의 일시적 오류를 배치 계층이 결국 덮어쓴다. 이 생각은 카파에도 그대로 이어진다.

⚠️ 강의는 당시 Storm이 "데이터가 중복되거나 유실되어 100% 정확하지 않다"고 쓴다. Storm은 ack를 쓰면 at-least-once(중복은 나도 유실은 없다)이고, 유실은 acker를 끄거나 anchor 없이 튜플을 보낼 때 생기며, exactly-once는 Trident가 준다("best effort, at least once, and exactly once through Trident", https://storm.apache.org/releases/current/Guaranteeing-message-processing.html , 2026-09-28 확인). 정확히는 "설정에 따라 중복이 나거나, 드물게 유실될 수 있었다"다.

### 한계

같은 변환 로직을 배치와 속도 계층에 두 번 구현한다(p224). 프레임워크가 다르면 코드 스타일, 상태 처리, 오류 처리가 달라지고, 결과가 같은지 검증하고 테스트하고 디버깅하기가 급격히 어려워진다. 강의는 람다의 가장 큰 비용이 계산 비용이 아니라 인지 비용과 유지보수 비용이라고 한다. 운영 쪽으로는 프레임워크 둘, 결과 저장소 둘, 병합 로직, 두 배의 장애 추적 경로가 생긴다(p225).

이중 구현 문제는 [[학습-서빙 스큐]]의 원인(학습 Python과 서빙 Java가 같은 피처를 따로 구현)과 같은 구조다. 이 연결은 Part 1 인제스트 때 위키가 [[배치 처리]]에 붙였다.

## 카파 아키텍처

Jay Kreps가 「Questioning the Lambda Architecture」(O'Reilly Radar, 2014-07-02)에서 제안했다. 배치 경로를 없애고, 재처리를 "같은 스트림 파이프라인의 빠른 재생"으로 바꾼다.

재처리 흐름(p228). 원문은 네 단계이고, 강의는 원문의 둘째 단계(두 번째 작업을 보관된 로그의 처음부터 돌려 새 테이블에 쓴다)를 아래 2·3으로 나눠 다섯 단계로 적었다. 내용은 원문과 맞다.

1. 입력 로그를 충분히 오래 보관한다(예: Kafka retention).
2. 코드가 바뀌면 새 버전의 스트림 작업을 띄운다.
3. 새 작업이 보관된 로그의 처음부터 다시 읽어 새 결과 테이블을 만든다.
4. 새 작업이 현재까지 따라잡으면 애플리케이션이 새 테이블을 읽도록 전환한다.
5. 옛 작업을 멈추고 옛 결과 테이블을 지운다.

[원문: "start a second instance… from the beginning of the retained data", "new output table", "switch the application", "Stop the old version of the job, and delete the old output table." https://www.oreilly.com/radar/questioning-the-lambda-architecture/ , 2026-09-28 확인]

강의의 표현으로는 복잡도의 초점이 "두 개의 코드 경로"에서 "재생 가능한 로그"로 옮겨 간다.

### 전제와 도전

| 전제(p229) | 도전(p231) |
|---|---|
| 충분한 로그 보존 기간 | 수년치 원본을 로그에 두는 저장 비용 |
| 빠른 재생이 가능한 처리 엔진 | 매우 긴 윈도우(최근 1년 행동)의 상태 크기 |
| 결과 저장소 전환 또는 갱신 전략 | 워터마크·상태 저장소를 다루는 높은 숙련도 |
| 다시 읽어도 의미가 유지되는 시간 기준과 상태 설계 | |

넷째 전제는 [[AI DE 강의 4-08 Processing Time과 Event Time]]의 결론과 같다. 처리 시각 기준으로 집계하면 재생할 때마다 결과가 달라지므로, 카파는 이벤트 발생 시각 기준 계산을 전제로 한다([[스트림 처리]]). 두 소단원을 이은 것은 위키다.

저장 비용 문제는 로그의 오래된 구간을 오브젝트 스토리지로 내리는 계층형 저장소나, 로그를 레이크하우스 테이블로 떨어뜨려 재생 원천으로 쓰는 방식으로 완화하는 것이 일반적이다. 강의에는 없는 위키의 보충이고, 개별 제품 기능은 이번에 확인하지 않았다.

⚠️ 강의의 카파 사례는 "늦게 도착한 데이터도 워터마크를 통해 별도의 배치 처리 없이 스트리밍 계층에서만 정확히 집계"한다고 쓴다(p232). 같은 챕터가 워터마크 지연보다 더 늦은 데이터는 반영이 보장되지 않는다고 했으므로(p209) 모순이다. 너무 늦은 데이터를 결국 반영하는 것은 워터마크가 아니라 재생(재처리)이다.

## 람다 다음

강의는 람다 다음에 정답 하나가 온 것이 아니라 여러 축이 각자 진화했다고 본다(p233).

| 축 | 무엇을 푸나 | 위키의 페이지 |
|---|---|---|
| Lakehouse | 저장·관리. 오픈 테이블 포맷 위의 ACID·스키마·타임 트래블 | [[데이터 레이크하우스]] |
| Unified Path | 처리. 같은 엔진·API로 batch와 stream을 처리해 이중 코드 경로를 줄임 | [[스트림 처리]] |
| Data Mesh | 조직. 도메인 팀이 데이터를 제품으로 소유 | 이 페이지 |
| Data Fabric | 연결. 메타데이터와 AI로 흩어진 데이터를 엮음(Active Metadata, Knowledge Graph) | [[지식 그래프]] · [[데이터 거버넌스와 카탈로그]] |
| Data Contract | 신뢰. 경계에서의 규약 | [[데이터 계약]] |

Unified Path는 카파의 발상을 엔진 쪽에서 실현한 것이다. 배치를 bounded stream으로 보는 Flink나, 배치와 스트림에 같은 DataFrame API를 쓰는 Spark Structured Streaming이 예다. 이 대응은 위키가 붙였다.

Data Mesh의 원칙은 넷이다. Dehghani의 원문은 "Domain-oriented decentralized data ownership and architecture", "Data as a product", "Self-serve data infrastructure as a platform", "Federated computational governance"다. [https://martinfowler.com/articles/data-mesh-principles.html , 2020-12-03, 2026-09-28 확인] ⚠️ 강의는 불릿으로 둘(Domain Ownership, Self-Serve Platform)만 적고, 데이터 제품은 본문 한 줄에, 연합 거버넌스는 그림에만 둔다(p237–238).
