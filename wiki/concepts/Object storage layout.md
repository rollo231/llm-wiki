# Object storage layout

**오브젝트 스토리지에서 "디렉토리 규칙"을 정하는 일이 유독 어렵게 느껴지는 데는 구체적인 원인이
있다 — 디렉토리가 없기 때문이다.**

S3·MinIO의 키는 **평평한 문자열**이고 `/`는 콘솔이 트리처럼 그려주는 표시 규약일 뿐이다.
그런데 우리는 파일시스템 직관(**계층 = 정리**)을 들고 간다. 실제로 prefix가 하는 일은 넷뿐이다:

1. **권한 경계** — IAM 정책이 prefix로 매칭된다
2. **열거 단위** — `list-objects` + delimiter
3. **생애주기 단위** — lifecycle/ILM 규칙이 prefix로 매칭된다
4. 분산 배치 — 내부 해싱·샤딩

**분류 체계(taxonomy)도 아니고 질의 인덱스도 아니다.** 경로에 의미 분류를 넣는 순간
*질의할 수 없는 곳에 질의하고 싶은 정보를 넣은* 상태가 된다 — prefix scan 말고는 물어볼 방법이
없다. 설계가 계속 어긋나는 느낌의 정체가 이것이다.

> **규칙 한 줄: 경로는 "누가 접근할 수 있고 언제 지워도 되는가"만 답한다.
> 나머지는 전부 카탈로그가 답한다.**

## 세그먼트를 추가하기 전에 물을 세 가지

```
1. 이 값이 바뀔 수 있나?               → 바뀌면 넣지 않는다 (이관 비용)
2. 이걸로 권한이나 생애주기를 가르나?    → 아니면 넣지 않는다
3. 이걸로 "찾으려는" 건가?              → 그럼 카탈로그 컬럼이다
```

셋 다 아니면 그 세그먼트는 **장식**이다.

## 흔한 실패 5종

### ① 의미를 경로에 넣으면 그 의미가 바뀔 때 이관이다

`bucket/lung-cancer/xenium/S0142/` — 프로젝트명이 바뀌거나, 대상이 두 분류에 걸치거나, 재분류되면?
**오브젝트 스토리지에 rename은 없다. 복사 + 삭제다.** 수백 TB에서 그건 rename이 아니라
마이그레이션이다.

→ 경로에는 **불변인 것만**: 테넌트, 불변 ID, 버전. 변하는 건 전부 카탈로그 컬럼.

### ② 경로로 찾으려는 시도

prefix list는 수백만 객체 페이지네이션에 필터는 prefix 하나, 정렬은 키 순서뿐이다.
**"이 속성을 앞 세그먼트에 둘까 뒤에 둘까"가 답이 안 나오는 이유가 이것** — 시스템이 못 하는
질의를 위해 prefix 순서를 최적화하려니 답이 없다. **질문이 틀린 것이다.**

### ③ 사람이 브라우징하게 만들려는 욕심

콘솔에서 클릭해 돌아다니고 싶은 마음. 그런데 규모가 커지면 브라우징은 도구가 아니고,
사람이 읽기 좋은 경로는 대개 **변하는 것**을 담아서 ①을 부른다.
browsability는 카탈로그 위의 UI가 줘야 한다.

### ④ 날짜 파티셔닝을 습관적으로 넣기

`year=/month=/day=`는 **Parquet 스캔 엔진을 위한 규약**(Hive-style)이지 blob을 위한 게 아니다.
개체 단위 접근은 항상 ID로 하고 시간 질의는 카탈로그가 답한다.
**Hive 파티셔닝이 의미 있는 곳은 쿼리 엔진이 읽는 테이블 층뿐이다.**

### ⑤ 한 prefix 아래 객체가 수백만 개

청크 배열([[SpatialData|Zarr]])이나 스트리밍 산출물에서 흔하다. **이건 경로 설계로 못 고친다** —
객체 크기로 고친다. 하지만 결과로 **목록을 `list-objects`로 얻는 게 실용적으로 불가능**해지고,
GC·정합성 검사·용량 집계가 전부 여기서 막힌다.

→ 산출물 안에 **매니페스트(객체 목록·바이트·체크섬)** 를 함께 쓴다. 목록을 리스팅이 아니라
매니페스트에서 얻는다.

## 무엇을 버킷으로, 무엇을 prefix로

버킷이 통제하는 것은 **정책**이다 — 버저닝 · 생애주기(ILM) · 보존 · quota · 복제.

> **정책이 다르면 버킷을 나눈다. 그 외에는 prefix로 충분하다.**

정책이 실제로 갈리는 축은 대개 **생애주기 단계**([[Medallion architecture]]의 층)다:
원본(불변·장기보존·버저닝) / 작업중(짧은 TTL·자동삭제) / 정제본(불변·백업) /
**파생물(재생성 가능 → 백업 제외)** / 테이블 층(갱신됨).

⭐ **파생물을 정제본과 같은 버킷에 두지 않는 것**이 실무에서 가장 큰 차이를 만든다.
정제본은 지켜야 하고 파생물은 정의상 언제든 버려도 된다. 섞으면 **백업 비용이 파생물 배수만큼
곱해진다.**

테넌트는 보통 prefix가 맞다 — 정책은 층마다 갈리지 테넌트마다 갈리지 않고, 테넌트 수는 계속
늘어나는데 층 수는 고정이기 때문이다. 정책을 테넌트마다 복제하면 drift가 생긴다.
**뒤집는 조건은 하나: 테넌트별 용량 quota가 필요하면** quota가 버킷 단위이므로 테넌트 = 버킷.

## 카탈로그 행보다 먼저 도착하는 데이터

경로에서 의미를 다 빼면 한 가지가 걸린다 — **카탈로그 행이 생기기 전에 파일이 도착하는 구간**은
어떻게 하나. 원본 수집 층이 그렇다: 파일이 먼저 떨어지고, 무엇으로 읽을지가 그 시점에 결정된다.

> **원칙: 카탈로그 행이 존재하기 *전에* 도착하는 데이터만 경로가 자기설명적이어야 한다.**

그 구간에서만 최소한의 기능적 정보(소스 종류 등)를 경로에 남기고, 정제 이후 층은 카탈로그가
항상 먼저 있으므로 경로에서 뺀다.

## 파일 모델인가 오브젝트 모델인가 — 온프레미스의 갈림길

이 페이지의 전제는 *"오브젝트 스토리지엔 디렉토리가 없다"* 인데, **온프레미스에서는 그 전제를 고를 수
있다.**

| | 모델 | 성격 |
|---|---|---|
| 🔸 **HDFS** | 파일 · 디렉터리 · **블록** | 전통 배치·분석 클러스터의 기본 저장 계층 → [[Apache Hadoop]] |
| 🔸 **Apache Ozone** | **볼륨 → 버킷 → 키** | 클라우드 API 방식. **대량의 작은 파일과 대규모 네임스페이스**에 유리하게 설계 |

⭐ *"저장 계층을 고를 때는 **파일 모델이 필요한지, 오브젝트 모델이 필요한지**를 먼저 따져 보면 선택이
쉬워진다."* Ozone은 HDFS의 아이디어를 오브젝트 스토리지에 맞게 확장한 것이고, 동기는 HDFS의 한계
(**작은 파일 · 네임스페이스 규모**)다.

⚠️ **이미 클라우드 오브젝트 스토리지(또는 MinIO 같은 S3 호환 저장소)를 쓰고 있다면 Ozone을 중복으로 둘
이유가 적다.** 검토 대상은 **Hadoop 기반 플랫폼을 오래 운영하며 HDFS의 한계를 느끼는 조직**이다.
→ [[Apache Map - Ch2 Distributed foundations]]

## Hive는 경로를 구속했고 Iceberg는 해방했다

이 문제의 역사가 [[Table formats]]에 그대로 있다.

| | 경로의 위치 | 결과 |
|---|---|---|
| **Hive** | **디렉토리 레이아웃 = 데이터 모델.** 파티션 = `key=value` 하위 디렉토리 | 규약을 줬지만 **구속**이다. 스킴을 바꾸면 재작성, 사용자가 물리 레이아웃을 알아야 함 |
| **Iceberg** | **매니페스트가 파일 목록을 정의.** 경로는 불투명 | *hidden partitioning* — 경로에 파티션 값이 없어도 된다. **질문 자체를 없앴다** |

**그런데 둘 다 [[Table formats|테이블 포맷]]이다** — 관리 대상이 쿼리 엔진이 행으로 읽는 데이터
파일이다. **불투명한 blob 트리(청크 배열·이미지·모델 아티팩트)에는 둘 다 오지 않는다.**

그 경우 Iceberg가 한 일을 **손으로 다시 만드는 것**이 답이다: 경로를 불투명하게 두고,
별도 카탈로그 테이블이 *어느 객체가 유효한가*와 *열기 전에 걸러낼 통계*를 들고 있게 한다.
Iceberg는 도입할 도구가 아니라 **레퍼런스 설계**로 읽는다.
