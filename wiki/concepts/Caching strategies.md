# Caching strategies

**원본 저장소 앞에 두어 반복 조회를 흡수하는 계층과, 그 계층을 언제 어떻게 채우고 비울지의 규칙.**

> ⭐ **"캐시는 원본 저장소를 완전히 대체하는 계층이 아니라 보호하는 계층이다."**
> 원본이 **Source of Truth**, 캐시는 보조 계층.

## 캐싱 레이어의 역할과 위험

| 역할 | 위험 |
|---|---|
| **응답 시간 단축** | 오래된 데이터 반환 |
| **원본 저장소 부하 감소** — DB QPS·connection 사용량 감소 | 캐시와 원본 불일치 |
| **트래픽 급증 완충** — 이벤트·배포·캠페인에서 원본 보호 | **캐시 만료 시 원본 폭주** (thundering herd) |
| | **hot key 집중** |
| | 낮은 cache hit로 효과 부족 |

> ⭐ **"캐싱 전략은 속도만의 문제가 아니다. 성능·신선도·안정성·운영비용의 균형 문제."**

### ⭐ 캐시가 효과적인 4조건

1. 같은 데이터가 **반복 조회**된다
2. **원본 조회 비용이 크다**
3. ⭐ **약간의 지연된 데이터가 허용된다**
4. TTL 동안 재사용될 가능성이 높다

**3번이 도입의 진짜 조건이다.** 1·2번만 보고 도입했다가 정합성 문제로 되돌리는 게 흔한 실패다.

### ⭐ hit가 없으면 캐시는 "효과 없음"이 아니라 "손해"다

miss가 많을 때:

- Redis 조회 비용이 **추가된다**
- 원본 저장소도 **여전히** 조회한다
- **전체 응답 경로가 길어진다**
- DB 부하가 줄지 않는다
- 캐시 메모리만 사용하고 성능 효과는 작다

## 두 축과 다섯 전략

| 축 | 질문 | 전략 |
|---|---|---|
| **읽기** | 조회할 때 캐시를 어떻게 쓸 것인가 | Cache-Aside · Read-Through · Refresh-Ahead |
| **쓰기** | 원본이 변경될 때 캐시를 어떻게 할 것인가 | Write-Through · Write-Behind |

### Cache-Aside (Lazy Loading)

애플리케이션이 캐시를 먼저 조회 → miss면 원본 조회 후 캐시에 저장.

| 장점 | 단점 |
|---|---|
| 필요한 데이터만 캐시에 올라감 | **첫 요청은 항상 miss** |
| 구현 단순 | 배포·재시작 직후 **cold cache** |
| 읽기 많은 시스템에 적합 | **동시에 같은 key가 miss되면 원본으로 요청이 몰림** |
| **캐시 장애 시 원본으로 우회하기 쉬움** | 원본 변경 시 무효화 전략이 별도로 필요 |

> ⭐ **안티패턴 — 변경 주기가 다른 데이터를 한 key에 묶지 마라.**
> *"가격·재고·쿠폰처럼 실시간성이 높은 데이터는 상품 상세와 같은 key에 섞지 않는 편이 안전.
> 변경 주기가 다른 데이터를 하나의 캐시 객체로 묶으면 TTL 설계가 어려워진다."*
>
> 묶으면 **TTL을 가장 빨리 변하는 필드 기준으로** 잡을 수밖에 없고, 그러면 안 변하는 필드까지
> 매번 다시 조회된다.

### Read-Through

캐시 **계층**이 miss 처리와 원본 조회를 감싼다. 애플리케이션은 캐시에만 요청한다.

| | miss 처리 주체 |
|---|---|
| Cache-Aside | **애플리케이션** |
| Read-Through | **캐시 계층** |

장점: 앱 코드 단순, **적재 로직 중앙화**, 여러 서비스가 규칙 공유.
단점: 캐시 계층 구현 복잡, **장애 시 추적 경로가 길어짐**.

### Write-Through

쓰기 시점에 캐시와 원본을 **함께** 갱신.

- **장점** — 쓰기 직후 캐시가 최신, stale 가능성 감소
- **단점** — **쓰기 경로가 느려짐**, **둘 중 하나만 성공하면 보상 처리 필요**,
  자주 읽히지 않는 데이터까지 캐시됨

### Write-Behind (Write-Back)

캐시에 먼저 쓰고 빠르게 응답, 별도 worker가 원본에 비동기 반영.

- **장점** — 쓰기 응답 시간 짧음, 대량 쓰기 흡수, 여러 변경을 묶어 반영
- **단점** — ⚠️ **캐시 장애 시 미반영 데이터 유실**, 재처리 구조 필요, 일시적 불일치
- ⭐ **정산·결제·주문 같은 강한 정합성 데이터에는 위험**

### Refresh-Ahead / Prefetching

자주 사용될 데이터를 **요청 전에 미리** 적재해 miss를 줄인다. 조회 대상이 예측 가능하고 안정적인
기준 데이터·카테고리·설정값·마스터 데이터에 적합.

## ⭐ 캐시 무효화

> **"캐시 무효화는 캐싱에서 가장 어려운 부분."**

| 방식 | 동작 | 특징 |
|---|---|---|
| **삭제** | 변경 후 key 삭제 → 다음 조회에서 miss 후 재적재 | 구현 단순, 다음 조회에 miss 비용 |
| **갱신** | 변경 후 key를 새 값으로 갱신 | 쓰기 직후 읽기 최신성 좋음 |
| **짧은 TTL** | 명시적 삭제 없이 자연 만료 | 구현 단순, **stale 허용 필요** |

**선택 기준:** 최신성이 중요 → 삭제/갱신 · 약간 오래된 데이터 허용 → TTL 중심 ·
쓰기 로직 복잡 → 삭제 후 재적재 · 읽기 지연 최소화 → 갱신 또는 refresh-ahead.

> ⭐ **"캐시를 지우지 않으면 오래된 값을 줄 수 있고, 너무 자주 지우면 hit ratio가 떨어진다."**

## ⭐ TTL 설계 — 숫자와 그 근거

| 데이터 유형 | 권장 TTL | 근거 |
|---|---|---|
| **상품 가격** | 5초 ~ 30초 | 민감도 최상. 결제 직전 가격이 달라지면 안 되므로 짧게, 단 찰나의 반복 조회 부하는 막는 용도 |
| **상품 설명** | 10분 ~ 1시간 | 정적. **변경 시 강제 삭제 전략과 병행** |
| **카테고리 목록** | 1시간 ~ 24시간 | 변동성 최저. **DB 조인이 많은 무거운 쿼리라 길게 잡는 것이 유리** |
| **사용자 세션** | 30분 ~ 수 시간 | 활동성 기반. **조회할 때마다 TTL을 갱신하는 Sliding Window 필수** |
| **추천 결과** | 수초 ~ 수분 | 개인화 & 연산량. 추천 엔진 부하를 막기 위한 짧은 캐싱 |
| **랭킹 데이터** | 10초 ~ 1분 | 실시간성 체감을 주면서 집계 쿼리 폭주는 막는 선 |
| **실험 설정값** | 수 분 ~ 수십 분 | ⭐ **잘못된 설정 시 긴급 수정이 필요하므로 너무 길지 않게** |

> ⭐ **"근거" 열이 이 표를 판단 규칙으로 만든다.** 특히 마지막 항목 —
> **TTL은 "잘못된 설정이 살아 있는 최대 시간"이기도 하다.** 설정성 데이터의 TTL 상한은
> **허용 가능한 롤백 지연**으로 잡아야 한다.

| TTL이 짧을 때 | TTL이 길 때 |
|---|---|
| 신선도 ↑ | cache hit ↑ |
| miss ↑ | 원본 부하 ↓ |
| 원본 부하 ↑ | **stale 제공 가능성 ↑** |

## ⚠️ 강의가 빠뜨린 3가지 — 실무 필수

강의는 **문제를 언급하고 대응을 주지 않는다.** 아래는 이 위키가 채우는 부분이다.

| 실패 모드 | 증상 | 표준 대응 |
|---|---|---|
| **Cache stampede / thundering herd** | 인기 key의 TTL이 만료되는 순간 동시 miss가 발생해 원본으로 요청이 폭주 | **뮤텍스/single-flight**(하나만 원본을 조회하고 나머지는 대기) · **확률적 조기 갱신** · stale-while-revalidate |
| **동시 만료** | 같은 TTL로 대량 적재한 key들이 동시에 만료 | ⭐ **TTL jitter** — 만료 시각을 ±랜덤 오프셋으로 흩뜨림 |
| **Cache penetration** | 존재하지 않는 key를 반복 조회해 매번 DB를 때림 | **negative caching**(없음을 짧은 TTL로 캐싱) · Bloom filter |

**두 번째가 위 TTL 표의 실무적 함정이다** — "카테고리 목록 1시간"을 일괄 적용하면 배포 직후
적재된 key들이 한 시간 뒤 동시에 만료된다.

자료구조 매핑 표는 이를 **"무거운 연산 결과를 저장해 두었다가 즉시 서빙"** 으로 설명한다.

**강의가 이 셋을 잇지 않지만 같은 이야기다.**

## 캐시 vs 스트림 처리 상태 — 헷갈리는 지점

[[AI DE Course - Part4 Ch3 Brokers vs stream processing engines]]은 **"매 레코드 처리 시마다
외부 DB(Redis)에 접근하면 실시간성 확보 불가능"** 이라며 로컬 State Backend(RocksDB)를 권한다.
Ch2는 Redis를 상태 저장소로 권한다. **모순이 아니라 접근 빈도의 차이다:**

| | 접근 패턴 | 적합한 저장소 |
|---|---|---|
| **서빙 경로** | 요청당 수 회 조회 | **Redis (네트워크 홉 1회 감수)** |
| **스트림 연산** | 레코드당 매번 읽고 쓰기 | **로컬 embedded store (RocksDB)** |
