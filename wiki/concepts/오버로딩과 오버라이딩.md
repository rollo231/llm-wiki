# 오버로딩과 오버라이딩

- 오버로딩(overloading)은 한 클래스 안에서 이름은 같고 매개변수 목록이 다른 메서드를 여러 개 두는 것이다. 어느 것을 부를지는 컴파일러가 인자의 정적 타입으로 정한다.
- 오버라이딩(overriding)은 하위 클래스가 상위 타입의 인스턴스 메서드를 같은 시그니처로 다시 구현하는 것이다. 어느 구현을 실행할지는 런타임에 실제 객체의 클래스로 정한다.

자료([[Java 면접 5 객체지향 프로그래밍]])는 이 둘을 따로 묻지 않고, [[다형성]]의 구현 방법으로 함께 든다(p94). 그 서술의 문제는 [[다형성]]의 정정 절에 있다. 같은 섹션의 부록 Q13도 오버로딩을 다형성의 구현 방법으로 든다([[Java 면접 5 빈출 질문]]). 이 페이지의 규칙과 함정은 자료에 없고 위키가 JLS SE 25와 JDK 25 재현으로 보충했다.

## 한눈에 비교

| | 오버로딩 | 오버라이딩 |
|---|---|---|
| 어디서 | 같은 클래스(상속받은 메서드 포함) | 상위 타입과 하위 클래스 사이 |
| 시그니처 | 이름 같고 매개변수 목록이 달라야 한다 | 같아야 한다 |
| 반환 타입 | 상관없다. 반환 타입만 다르면 컴파일 오류 | 같거나 하위 타입(공변 반환) |
| 접근 제어자 | 상관없다 | 좁힐 수 없다 |
| checked 예외 | 상관없다 | 더 넓게 던질 수 없다 |
| 대상 | static·인스턴스 모두 | 인스턴스 메서드만. static은 숨김, private은 상속되지 않음, final은 금지 |
| 결정 시점 | 컴파일 타임, 인자의 정적 타입 | 런타임, 수신 객체의 실제 클래스 |
| 다형성 분류 | ad-hoc 다형성으로 분류하기도 한다 | 서브타입 다형성의 구현 수단 |

JLS의 두 문장이 표의 마지막 두 줄을 요약한다. 오버로딩은 "the same name but signatures that are not override-equivalent"(§8.4.9)이고, 호출 시에는 "the compile-time types of the arguments are used, at compile time, to determine the signature of the method that will be invoked (§15.12.2). If the method that is to be invoked is an instance method, the actual method to be invoked will be determined at run time, using dynamic method lookup (§15.12.4)"(§8.4.9)다.

즉 호출 하나에서 두 단계가 차례로 일어난다. 컴파일러가 오버로딩 후보 가운데 시그니처 하나를 고르고(정적), 런타임이 그 시그니처의 오버라이딩 구현 가운데 실제 객체의 것을 고른다(동적). Java는 수신 객체 하나로만 동적으로 고르는 단일 디스패치 언어라서, 인자의 런타임 타입으로 고르고 싶으면 방문자 패턴 같은 이중 디스패치 기법이나 패턴 매칭([[다형성]])을 쓴다.

## 오버라이딩의 규칙

컴파일러가 막는 것들이다(JDK 25 `javac` 오류 메시지).

```java
class A { protected Object m() throws Exception { return null; } }
class B1 extends A { @Override Object m() { ... } }
// m() in B1 cannot override m() in A
//   attempting to assign weaker access privileges; was protected
class B2 extends A { @Override protected Object m() throws Throwable { ... } }
// m() in B2 cannot override m() in A
//   overridden method does not throw Throwable
```

- 반환 타입은 같거나 하위 타입이면 된다(공변 반환, return-type-substitutable, §8.4.5). `Animal self()`를 `Cat self()`로 오버라이드할 수 있다.
- 접근 제어자는 "at least as much access"여야 한다(§8.4.8.3). `protected`를 `public`으로 넓히는 것은 되고 좁히는 것은 안 된다.
- checked 예외는 상위 메서드가 선언한 범위 안에서만 던질 수 있다(§8.4.8.3). 줄이거나 없애는 것은 된다.
- 이 세 규칙은 모두 하위 객체를 상위 타입 자리에 넣어도 호출하는 쪽이 깨지지 않게 하는 장치다. 리스코프 치환 원칙([[SOLID 원칙]])을 컴파일러가 강제할 수 있는 만큼 강제하는 셈이다. 이 해석은 위키의 것이다.

## 오버라이딩되지 않는 것: static 메서드와 필드

static 메서드는 오버라이드되지 않고 숨겨진다(hiding, §8.4.8.2). 필드도 숨겨질 뿐 다형적으로 동작하지 않는다(§8.3). 둘 다 컴파일 타임에 변수의 정적 타입으로 정해진다.

```java
class Animal { String name = "animal"; static String kind() { return "Animal.kind"; }
               String speak() { return "..."; } }
class Cat extends Animal { String name = "cat"; static String kind() { return "Cat.kind"; }
               @Override String speak() { return "meow"; } }

Animal an = new Cat();
an.speak();   // "meow"        오버라이딩: 실제 객체
an.name;      // "animal"      필드: 정적 타입
an.kind();    // "Animal.kind" static: 정적 타입
```

private 메서드는 상속되지 않으므로 하위에 같은 이름을 만들어도 별개의 메서드다. final 메서드는 오버라이드할 수 없다.

## 오버로딩의 함정

### 정적 타입으로 고른다

```java
static String f(Object o) { return "f(Object)"; }
static String f(String s) { return "f(String)"; }

Object o = "hello";
f(o);        // "f(Object)". 실제 객체가 String이어도 변수 타입이 Object다
```

오버라이딩에 익숙하면 여기서 `f(String)`을 기대하기 쉽다. 오버로딩은 런타임 타입을 보지 않는다.

### 후보는 세 단계로 찾는다

컴파일러는 박싱과 가변 인자를 뒤로 미룬다(§15.12.2.2–15.12.2.4). 1단계는 박싱·언박싱과 가변 인자 없이, 2단계는 박싱을 허용하고, 3단계에서야 가변 인자를 본다. 앞 단계에서 후보가 나오면 뒤 단계는 보지 않는다.

```java
static String g(long x)    { ... }
static String g(Integer x) { ... }
static String g(int... x)  { ... }
g(1);   // "g(long)". int → long 확장이 1단계에서 먼저 맞는다
```

### `List.remove(int)`와 `remove(Object)`

```java
List<Integer> list = new ArrayList<>(List.of(10, 20, 30));
list.remove(1);                    // [10, 30]. 인덱스 1을 지운다
list.remove(Integer.valueOf(10));  // [30]. 값 10을 지운다
```

`remove(1)`은 1단계에서 `remove(int)`가 맞으므로 값이 아니라 인덱스로 지운다. 값을 지우려면 `Integer`로 넘겨야 한다.

### `equals`를 오버로딩해 버리는 실수

```java
class Point {
    final int x;
    public boolean equals(Point p) { return p != null && p.x == x; }  // equals(Object)가 아니다
    public int hashCode() { return x; }
}
Set<Point> s = new HashSet<>();
s.add(new Point(1)); s.add(new Point(1));
s.size();                    // 2
s.contains(new Point(1));    // false
```

`HashSet`은 `equals(Object)`를 부르는데, 이 클래스는 그것을 오버라이드하지 않고 새 오버로딩을 추가했을 뿐이다. `@Override`를 붙이면 컴파일러가 "method does not override or implement a method from a supertype"으로 잡는다(§9.6.4.4). 오버라이드할 의도가 있으면 항상 `@Override`를 붙이는 이유다.

## 면접에서

「오버로딩은 같은 이름에 매개변수가 다른 메서드를 여럿 두는 것이고, 컴파일 타임에 인자의 정적 타입으로 결정됩니다. 오버라이딩은 하위 클래스가 상위의 인스턴스 메서드를 같은 시그니처로 다시 구현하는 것이고, 런타임에 실제 객체로 결정됩니다. 서브타입 다형성을 구현하는 것은 오버라이딩입니다. 오버라이딩은 반환 타입을 공변으로만 바꿀 수 있고, 접근 제어자를 좁히거나 checked 예외를 넓힐 수 없습니다. static 메서드와 필드는 오버라이드되지 않고 숨겨집니다.」

꼬리 질문으로는 `f(Object o = "hello")`가 무엇을 부르는지, `List<Integer>.remove(1)`, `equals(Point)` 실수와 `@Override`가 자주 나온다.
