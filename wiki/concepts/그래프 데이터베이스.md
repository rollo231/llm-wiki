# 그래프 데이터베이스

관계를 노드 사이의 연결로 저장하고, 질의할 때 그 연결을 따라가는(traversal) 데이터베이스다. [[AI DE 강의 3-14 그래프 DB의 특징]]은 RDB와의 차이를 "관계를 계산하느냐, 저장하느냐"로 요약한다. 무엇을 노드·엣지·속성으로 둘지는 [[그래프 데이터 모델]]의 몫이고, 이 페이지는 그 모델을 담는 엔진을 다룬다.

## 관계를 계산하느냐, 저장하느냐

| | [[관계형 데이터베이스]] | 그래프 DB |
|---|---|---|
| 관계의 표현 | foreign key, bridge table, join table | 저장된 relationship(edge). 타입·방향·속성을 가진다 |
| 관계가 생기는 시점 | 질의 시점에 JOIN으로 다시 연결 | 쓰기 시점에 저장 |
| 탐색 | 인덱스 lookup → JOIN → self join·recursive join | 시작 노드 → 관계 타입을 따라 hop → 패턴 매칭 |
| 질의의 사고 | 어떤 테이블을 JOIN할까 | 어떤 관계를 몇 hop 따라갈까 |

RDB로도 그래프를 저장할 수 있다. 강의가 드는 문제는 다단계 탐색(친구의 친구, 연결된 의심 계정, 테이블 변경의 downstream 영향)이 핵심이 될 때 self join과 recursive join이 쌓여 쿼리가 읽히지 않고 설계 의도가 SQL 안에 묻힌다는 점이다.

## "빠르다"의 범위

index-free adjacency는 각 노드가 이웃에 대한 참조를 직접 들고 있어서, 다음 노드로 갈 때 전역 인덱스 탐색이나 JOIN을 거치지 않는다는 설계 원칙이다. Neo4j의 설명은 "each node directly references its adjacent (neighboring) nodes, meaning that accessing relationships and related data is simply a memory pointer lookup"이다. [Neo4j 블로그 「Native vs. Non-Native Graph Database」, https://neo4j.com/blog/cypher-and-gql/native-vs-non-native-graph-technology/ , 2026-09-28 확인] 이 용어는 제품사의 설명이고 표준 정의가 따로 있지는 않다. 강의(p7)는 이것이 hop 하나의 비용을 낮출 뿐이라고 분명히 한다.

- 전체 질의가 O(1)인 것은 아니다. hop 수가 늘면 건드리는 부분 그래프가 커진다.
- high-degree node(슈퍼노드)가 많으면 path explosion이 생긴다.
- 시작점을 좁히는 선택적 조건이 약하면 그래프 DB도 느리다.

위키가 덧붙이면, 그래프 DB의 이점은 탐색 깊이가 데이터 전체 크기가 아니라 탐색 경로 주변의 크기에 비례한다는 데 있다. 반대로 "카테고리별 매출 합계"처럼 전체를 훑는 집계는 RDB나 열 기반 엔진이 더 잘한다([[행 기반과 열 기반 저장]]).

## 트랜잭션

그래프 DB는 [[NoSQL]]로 분류되지만 트랜잭션이 없는 것이 아니다. [[Neo4j]]는 ACID 트랜잭션을 주고 기본 [[트랜잭션 격리 수준|격리 수준]]은 read-committed다(운영 매뉴얼로 확인, 2026-09-28). [[Amazon Neptune]]도 문서에 "ACID support and well-defined transaction guarantees"를 명시하고, 읽기 전용 질의는 snapshot isolation, mutation 질의의 읽기는 READ COMMITTED에 non-repeatable·phantom read까지 막는 잠금을 더해 실행한다(2026-09-28 확인, 세부는 [[Amazon Neptune]]). 이 점은 [[AI DE 강의 3-02 RDBMS의 한계와 NoSQL]]의 "NoSQL은 일관성을 완화한다"는 일반화에 단서를 단다.

## 질의 언어

| 언어 | 대상 모델 | 방식 | 대표 제품 |
|---|---|---|---|
| Cypher / openCypher | property graph | 선언형 패턴 매칭 | Neo4j, Neptune |
| Gremlin | property graph | step-by-step traversal (Apache TinkerPop). 명령형·선언형·혼합 모두 쓸 수 있다 | Neptune, JanusGraph |
| SPARQL | RDF | triple pattern 매칭 | Neptune |
| AQL | 문서 + 그래프 | 문서 질의와 traversal 통합 | ArangoDB |
| GQL | property graph | ISO/IEC 39075:2024 표준 | Cypher가 적합성 쪽으로 수렴 중 |

GQL 행과 "대표 제품" 열은 강의에 없고 위키가 검증 보고로 채운 것이다.

## 언제 쓰나

[[AI DE 강의 3-14 그래프 DB의 특징]]의 기준을 옮긴다. RDB는 스키마가 안정적이고 CRUD·집계·리포팅이 중심이며 원장처럼 레코드 정확성이 핵심일 때 맞다. 그래프 DB는 질문이 "누가 누구와 어떻게 연결되는가"이고 self join·recursive join이 반복되며 fraud, recommendation, lineage, entity resolution이 중요할 때 맞다. 강의는 둘을 경쟁 관계가 아니라 질문 유형이 다른 두 엔진으로 본다.

데이터 엔지니어에게 가까운 쓰임은 메타데이터와 계보다. 계보는 본질적으로 경로 정보라서 "이 컬럼이 바뀌면 어떤 대시보드가 깨지는가"가 곧 downstream traversal이다([[데이터 거버넌스와 카탈로그]]). [[GraphRAG]]의 저장소로도 쓰인다([[지식 그래프]]).

## 제품 비교

[[AI DE 강의 3-15 그래프 DB 제품 비교]]는 저장 철학, 그래프 모델, 질의 언어, 확장 방식, 운영 방식의 다섯 축으로 네 제품을 비교한다.

| 제품 | 축에서의 자리 | 확장 방식 |
|---|---|---|
| [[Neo4j]] | native graph + Cypher | 클러스터, Infinigraph(속성 샤딩) |
| [[Amazon Neptune]] | AWS 관리형, property graph + RDF | AWS가 운영 |
| [[ArangoDB]] | 멀티모델(문서·키값·그래프) | 클러스터, SmartGraphs |
| [[JanusGraph]] | 분산 저장소 위 graph engine | 저장 백엔드(Cassandra·HBase 등)에 기댐 |

강의의 비교에는 라이선스와 비용 축이 없다. 제품을 고를 때 자주 결정적인 축이라 엔티티 페이지마다 현재 상태를 적어 두었다. 이 지적은 위키의 관찰이다.

## 빈칸

- Part 3에는 그래프 DB 실습이 없다. Ch5 덱 제목이 「실습」이지만 Cypher·Gremlin 쿼리 예제, 데이터 적재, 같은 질의의 SQL·그래프 비교가 모두 없다.
- 성능 수치가 없다. "JOIN이 길어진다"와 "인접 노드 접근이 싸다"를 벤치마크나 실행 계획으로 보여 주지 않는다.
- 그래프 분석(PageRank, 커뮤니티 탐지 같은 알고리즘)은 "graph analytics가 필요하면"으로만 나온다. 커뮤니티 탐지는 [[GraphRAG]]의 Leiden 단계에서 따로 등장한다.
