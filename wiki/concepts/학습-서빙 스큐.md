# 학습-서빙 스큐

모델을 **학습할 때 쓴 데이터·전처리 로직**과 **서비스할 때 들어오는 데이터·로직**이 달라, 에러 없이 예측
성능이 떨어지는 현상.

## 원인 — 같은 로직을 두 번 구현한다

| | 학습 | 서빙 |
|---|---|---|
| 담당 | 데이터 사이언티스트 | 백엔드·플랫폼 엔지니어 |
| 데이터 | 과거 이력(배치) | 실시간 이벤트(스트리밍) |
| 언어 | Python·Pandas | Java·Go·C++ |
| 로직 | 복잡한 집계, 고지연 허용 | 단순화, 밀리초 |

언어와 환경이 다르니 **같은 피처를 두 번 구현하고, 그 사이에서 미세한 차이가 생긴다.**
([[AI DE 강의 1-13 Skew와 Drift]])

## 예 — "최근 30일 평균 결제액"

이력: 구매 100만 원, 취소 -100만 원, 구매 2만 원.

| | 계산 | 값 | 모델이 보는 고객 |
|---|---|---|---|
| 학습 | (100만 − 100만 + 2만) ÷ 1 | 20,000원 | 소액 구매 고객 |
| 서빙(취소 예외 처리 누락) | (100만 + 100만 + 2만) ÷ 3 | 673,333원 | VIP |

위키가 검산한 비율은 33.67배로 강의의 "33배"와 맞는다. 이 예에는 차이가 **두 군데** 있다 — 취소의 부호와
**분모**(무엇을 1건으로 세나). 강의는 취소 누락만 원인으로 들지만, 집계 단위의 정의가 다른 것도 그 자체로 스큐다.

## 왜 위험한가 — "침묵의 살인자"

시스템 에러 로그는 0건이다. 모델은 정상 동작하며 엉뚱한 입력으로 엉뚱한 추천을 한다. 같은 모양의 실패가
[[데이터 SLA]]의 "침묵의 실패"(exit 0인데 결과 0건)다.

## 해결

1. **로직을 하나로** — [[피처 스토어]]에서 피처 변환을 한 번 정의하고, 학습(오프라인 스토어)과 서빙(온라인 스토어)이
   같은 결과를 읽는다. "Write Once, Compute Anywhere."
2. **피처 계약** — 스키마·윈도우 크기·예외 처리 규칙을 문서로 명시한다.
3. **공통 라이브러리** — 학습과 서빙이 같은 코드를 공유한다.
4. **감시** — 서빙 데이터의 통계 분포가 학습 데이터와 달라지는지 본다. [[AI DE 강의 1-13 Skew와 Drift]]는 이것을
   데이터 SLA의 "피처 일관성" 축으로 둔다.
5. **Training은 Serving을 따라간다** — 서빙에서 재현할 수 있는 규칙만 학습에도 쓴다
   ([[AI DE 강의 2-06 Training-Serving Skew 예방]]). 아래 절 참고.

## 네 가지 형태 — Part 2

[[AI DE 강의 2-06 Training-Serving Skew 예방]]은 스큐를 "모델 성능 문제가 아니라 **Feature 생성 규칙** 문제"로 보고,
운영에서 가장 자주 깨지는 규칙 넷을 든다. 피처는 **데이터 소스 + 집계 기준 + 시간 해석 + 전처리 규칙**의 결과라서,
학습과 서빙의 환경이 다르면 이 조합을 똑같이 구현하기 어렵다.

| 형태 | 학습 쪽 | 서빙 쪽 | 대응 |
|---|---|---|---|
| 시간 기준 | 이벤트 시간 집계가 쉽다 | 처리 시간이 되기 쉽다 | 하나로 고정해 양쪽에 적용, 늦은 이벤트 허용을 워터마크로 정책화 → [[스트림 처리]] |
| 집계 범위 | full window(예: 7일치 완전) | partial window(최신 구간 + 배치 값·캐시) | 데이터 가용성에 맞게 윈도우 설계, 안 되면 피처 재정의, long-term(배치) + short-term(실시간) 분리 |
| 결측 처리 | 0·평균으로 채우거나 drop | 조회 실패·지연도 결측으로 보인다 | "값 없음"과 "조회 실패"를 같은 0으로 두지 않는다 — `is_missing` 플래그, fallback 정책 |
| 스케일링 | 학습 전체의 global stats | 최근 window·사용자 단위 local 재계산, 또는 직접 구현한 다른 공식 | mean·std·min·max를 **아티팩트로 버전 관리해 함께 배포** → [[데이터와 모델 버전 관리]] |

**원칙은 "Training은 Serving을 따라가야 한다"**다. 학습 쪽에서 더 정확하게 만들 수 있어도 서빙에서 재현할 수 없는
정확성은 버리고, 입력이 같다는 보장을 택하는 맞교환이다. *(위키의 관찰)* 규칙을 강제하는 수단으로는 공용 변환 로직,
Feature Contract, (필요 시) [[피처 스토어]]를 든다.

- **Part 1 사례를 네 형태에 대 보면** — 위 "최근 30일 평균 결제액"에서 취소의 부호 차이는 **예외·결측 처리 규칙**의
  차이, 분모 차이는 **집계 기준**의 차이다. 한 피처에 두 형태가 겹쳐 있었다. *(위키의 연결)*
- ⚠️ **같은 코스 안의 긴장** — [[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]는 온라인 서빙 운영 요소로 "Feature 조회
  실패 시 기본값"을 권한다. 그 기본값이 학습 데이터의 결측 처리와 다르면 결측 처리형 스큐가 된다. 기본값을 쓰려면 학습
  데이터에도 같은 규칙(조회 실패 표시 방식)을 적용해야 하는데, 강의는 둘을 잇지 않는다. *(위키의 관찰)*

## 드리프트와의 구분 — 용어가 두 갈래다

Google 안에서도 "스큐"는 두 뜻으로 쓰인다.

- **(a) 성능 차이** — Zinkevich의 「Rules of Machine Learning」과 Google ML Glossary는 스큐를 학습 때와 서빙 때의 **성능
  차이**로 정의하고, 원인으로 파이프라인의 데이터 처리 불일치·**학습과 서빙 사이의 데이터 변화**·모델과 알고리즘 사이의
  피드백 루프를 든다. 이 뜻에서는 드리프트도 스큐의 원인이다. [Google for Developers, 「Rules of Machine Learning」 —
  "Training-serving skew is a difference between performance during training and performance during serving. This skew
  can be caused by: A discrepancy between how you handle data in the training and serving pipelines. A change in the
  data between when you train and when you serve. A feedback loop between your model and your algorithm."
  https://developers.google.com/machine-learning/guides/rules-of-ml , 2026-09-14 확인]
- **(b) 분포 비교** — TFDV와 Vertex AI는 스큐를 **학습 데이터 vs 서빙 데이터**의 분포 차이로, 드리프트를 **시간에 따른
  변화**(연속된 데이터 구간 사이, 운영 데이터의 시간 경과)로 쓴다. 비교 대상이 다를 뿐 원인으로 나누지 않는다.
  [Vertex AI Model Monitoring 개요 — "Training-serving skew occurs when the feature data distribution in production
  deviates from the feature data distribution used to train the model." / "Inference drift occurs when feature data
  distribution in production changes significantly over time."
  https://docs.cloud.google.com/vertex-ai/docs/model-monitoring/overview , 2026-09-14 확인 · TFDV 가이드 — "Drift
  detection is supported between consecutive spans of data (i.e., between span N and span N+1)"
  https://www.tensorflow.org/tfx/guide/tfdv , 2026-09-14 확인]

어느 쪽도 "스큐는 코드, 드리프트는 세상"으로 나누지 않는다. [[AI DE 강의 2-06 Training-Serving Skew 예방]]이 스큐의 원인에
Data Drift를 넣는 것은 (a)의 뜻에 맞는다.

그래도 **로직이 달라서 생긴 스큐**와 드리프트를 대비하는 것은 대응을 고르는 데 쓸모가 있다.

| | 로직 불일치형 스큐 | [[데이터 드리프트]] |
|---|---|---|
| 원인 | 학습·서빙의 **처리 규칙**이 다르다 | **세상**이 달라졌다 |
| 누구 탓 | 우리가 만든 불일치 | 누구의 버그도 아니다 |
| 대응 | 로직을 하나로 모아 **제거** | 감시하고 **재학습** |
| 시점 | 배포 순간부터 | 시간이 지나면서 |

⚠️ 위키 정정 (2026-09-14): 이 페이지는 처음에 스큐와 드리프트를 "원인이 반대"로 대비했다. Google 정의에 비추면 과장이라
위 표를 로직 불일치형 스큐로 좁혔다. 같은 대비를 쓴 [[AI DE 강의 1-13 Skew와 Drift]]의 핵심에도 정정을 달았다.

두 번 구현하면 두 결과가 갈라진다는 같은 교훈이다. *(위키의 연결)*
