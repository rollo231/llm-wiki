# 인터페이스와 추상 클래스

둘 다 "구현을 일부 비워 두고 하위 타입에게 맡기는" 장치다. 차이의 핵심은 **인스턴스 상태를 가질 수 있느냐**와 **몇 개를
물려받을 수 있느냐**다([[Java 면접 5 객체지향 프로그래밍]] p98–103).

## 차이 (현재 Java 기준)

| | 인터페이스 | 추상 클래스 |
|---|---|---|
| 인스턴스 상태(필드) | ❌ 없음. `public static final` 상수만 | ✅ 있음 |
| 생성자 | ❌ | ✅ (하위가 호출) |
| 다중 상속 | ✅ 여러 개 구현 | ❌ 하나만 상속 |
| 구현이 있는 메서드 | `default`·`static` (Java 8+), `private` (Java 9+) | 자유 |
| 메서드 접근 제어자 | `public` 또는 `private` (Java 9+) | 자유 |
| 관계 | "~할 수 있다"(능력, `Comparable`) | "~의 일종이다"(is-a) |

## 언제 무엇을 쓰나 — 자료의 답

- **기본은 인터페이스 + default 메서드**다. 다중 구현이 되고 상태가 없어서 결합도가 낮다(p103).
- **추상 클래스는 상태를 유의미하게 써야 할 때** — 하위 클래스들이 공통 필드를 쓰거나, 템플릿 메서드 패턴처럼 공통 로직을
  상태와 함께 공유해야 할 때.

이 답은 Java 8 이후의 표준적인 관점이다. default 메서드가 생기면서 "구현을 공유하려면 추상 클래스"라는 이유가 대부분
사라졌고, 남은 이유는 **상태**와 **생성자**다. *(위키의 관찰)*

## 면접에서

- 차이는 **상태 → 다중 구현 → 메서드 형태**의 순서로 말한다. 자료는 "상태 보유 여부"를 빠뜨린 답을 Silver로 본다.
- "모든 메서드는 public"이라고 말하지 않는다. "Java 8부터 default·static, Java 9부터 private 메서드도 가질 수 있다"는
  버전 변화를 말하면 오히려 가산점이다.
- 사용 기준은 "기본은 인터페이스, 인스턴스 상태나 생성자가 필요하면 추상 클래스"로 답하고, 흔한 조합(인터페이스로 타입을
  정의하고 추상 클래스로 골격 구현을 제공 — `List`와 `AbstractList`)을 예로 들면 좋다. *(위키의 보충)*

## 자료의 서술과 정정

- ⚠️ **"인터페이스의 모든 메서드는 public"(p100)은 Java 9부터 틀리다.** Java 9는 인터페이스에 private 메서드를 허용했다 —
  default 메서드끼리 공통 로직을 나누기 위해서다. [JEP 213 Milling Project Coin — "Support for private methods in
  interfaces", JDK 9, https://openjdk.org/jeps/213 ; JLS SE 25 §9.4 Method Declarations, 2026-09-26 확인]
- **"인터페이스는 상태를 가질 수 없다"(p100)는 단서가 필요하다** — 인스턴스 필드는 없지만, 인터페이스에 선언한 필드는 암묵적으로
  `public static final` 상수로 존재한다. 정확히는 "인스턴스 상태가 없다". [JLS SE 25 §9.3 Field (Constant) Declarations,
  https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html , 2026-09-26 확인]
- **Q4-1 Silver의 "인터페이스는 has-a, 추상 클래스는 is-a"(p102)는 이상한 구분이다.** has-a는 조합(필드로 가짐)의 관계이지
  인터페이스의 관계가 아니다 — 인터페이스 구현도 타입 관계(is-a, 또는 "can-do")다. 그런데 이유 칸은 "default 메서드·상태
  공유 상황 미언급"만 짚고, Gold는 이 구분을 말없이 버린다. 틀린 부분이 교정되지 않은 채 남는다. *(위키의 관찰)*
