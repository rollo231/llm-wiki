# 동시성 컬렉션

여러 스레드가 함께 쓰는 컬렉션을 스레드 안전하게 만드는 두 세대의 방법. 동기화 컬렉션(`Vector` · `Hashtable` · `Collections.synchronizedXxx`)은 락 하나로 전부 감싸고, 동시성 컬렉션(`java.util.concurrent`의 `ConcurrentHashMap` · `CopyOnWriteArrayList` 등)은 락을 쪼개거나 없앤다. 면접에서는 둘의 차이와 `ConcurrentHashMap`의 동작을 묻는다([[Java 면접 4 빈출 질문]] Q6~Q9).

## 한 줄기로 보면

자료에는 없고 위키가 정리한 흐름이다. 아래 단계로 읽으면 질문 네 개가 이어진다.

| 단계 | 방법 | 대표 | 비용 |
|---|---|---|---|
| 락 하나 | 모든 메서드를 같은 모니터로 감싼다 | `Vector` · `Hashtable` · `synchronizedList` | 경합이 생기면 전부 줄을 선다 |
| 락 쪼개기 | 버킷(또는 세그먼트)마다 따로 잠근다 | `ConcurrentHashMap` | 다른 버킷끼리는 안 막힌다 |
| 읽기에서 락 없애기 | volatile 읽기, 불변 스냅샷 | `ConcurrentHashMap.get`, `CopyOnWriteArrayList` | 쓰기가 비싸지거나 읽은 값이 약하게 일관된다 |
| 쓰기에서도 락 없애기 | CAS로만 연결을 바꾼다 | `ConcurrentLinkedQueue` · `ConcurrentSkipListMap` | 구현이 복잡하다 |

## 동기화 컬렉션 — 락 하나

`Collections.synchronizedList(list)`가 돌려주는 래퍼는 `final Object mutex` 필드를 두고 기본값으로 `mutex = this`를 쓴다. 모든 메서드가 `synchronized (mutex)` 안에서 원본을 부른다. `Vector`는 메서드마다 `synchronized`가 붙어 있다. 그래서 한 스레드가 락을 쥐면 다른 스레드는 어떤 메서드든 기다린다. 자료(Q6)가 지적하는 성능 문제가 이것이다. [OpenJDK master `Collections.java` · `Vector.java`, 2026-09-27 확인]

성능보다 더 큰 문제는 메서드 하나하나만 원자적이라는 점이다.

- 복합 연산은 여전히 경쟁한다. "없으면 넣기"(`contains` 다음 `add`)나 "마지막 원소 꺼내기"(`size` 다음 `get`)는 두 호출 사이에 다른 스레드가 끼어든다. [[원자성 문제가 나는 시나리오]]의 check-then-act가 동기화 컬렉션에서도 그대로 난다.
- 순회는 호출자가 잠가야 한다. javadoc은 이렇게 적는다: "It is imperative that the user manually synchronize on the returned list when traversing it." 잠그지 않고 순회하는 도중 다른 스레드가 고치면 fail-fast 이터레이터가 `ConcurrentModificationException`을 던진다. 이것도 최선 노력일 뿐 보장은 아니다.

따라서 스레드 안전한 컬렉션을 쓴다고 코드가 안전해지지는 않는다. 스레드 안전은 그 클래스가 약속한 연산 단위까지만 성립한다([[동시성 문제]]의 스레드 안전 정의).

## 동시성 컬렉션이 약속하는 것

`java.util.concurrent` package-summary는 이렇게 정의한다. "A concurrent collection is thread-safe, but not governed by a single exclusion lock." 약속은 세 가지다.

- 단일 락을 쓰지 않는다. 어떻게 쪼개거나 없애는지는 클래스마다 다르다.
- 이터레이터가 weakly consistent다. "they will never throw ConcurrentModificationException", 순회 중의 수정은 "may (but are not guaranteed to)" 반영된다. 그 대가로 `ConcurrentHashMap`의 `size` · `isEmpty`는 "typically useful only when a map is not undergoing concurrent updates".
- 메모리 일관성을 준다. 컬렉션에 넣기 전의 동작은 다른 스레드가 그 원소를 꺼낸 뒤의 동작보다 happens-before다. 그래서 동시성 컬렉션은 안전한 공개 수단이 된다([[불변 객체]]).

"읽기에는 락이 없고 쓰기만 잠근다"(자료 Q7)는 이 약속에 들어 있지 않다. 클래스마다 다르다.

| 클래스 | 읽기 | 쓰기 |
|---|---|---|
| `ConcurrentHashMap` | 락 없음 (volatile 읽기 `tabAt`) | 빈 버킷은 CAS, 아니면 버킷 첫 노드에 `synchronized` |
| `CopyOnWriteArrayList` | 락 없음 (배열 스냅샷) | 락 + 배열 전체 복사 |
| `ConcurrentLinkedQueue` · `ConcurrentSkipListMap` | 락 없음 | 락 없음. CAS만 쓴다(소스에 `ReentrantLock` · `synchronized (` 없음) |
| `LinkedBlockingQueue` | `take`는 `takeLock`을 잡는다 | `put`은 `putLock`. 락이 두 개다("two lock queue") |
| `ArrayBlockingQueue` | 잠근다. `peek` · `size`까지 | 같은 락 하나("Main lock guarding all access") |

[OpenJDK master 각 클래스 소스, `java.util.concurrent` package-summary, 2026-09-27 확인]

## CopyOnWriteArrayList

쓰기마다 배열을 통째로 복사한다. 순서는 락을 잡는다 → 지금 배열을 복사한 새 배열을 만든다 → 새 배열에 쓴다 → `setArray(newElements)`로 volatile 배열 참조를 새 배열로 바꾼다. 원본 배열은 건드리지 않으므로, 자료 Q8의 "원본 배열을 갱신"은 부정확하다. 읽는 스레드는 그 순간의 배열 참조를 한 번 읽고 끝까지 그 배열을 본다.

- 이터레이터는 스냅샷이다. 만들 때의 배열을 순회하므로 `ConcurrentModificationException`이 없고, 순회 중의 수정은 보이지 않는다. 이터레이터로 `remove` · `set` · `add`를 할 수도 없다(`UnsupportedOperationException`).
- 쓰기는 O(n)이다. javadoc: "ordinarily too costly, but may be more efficient than alternatives when traversal operations vastly outnumber mutations". 리스너 목록처럼 읽기가 압도적으로 많고 목록이 작을 때 쓴다.
- 락 구현이 바뀌었다. JDK 8은 `ReentrantLock`, JDK 9부터는 `synchronized (lock)`(내부 `Object lock`)이다. 소스 주석: "We have a mild preference for builtin monitors over ReentrantLock". 바뀐 커밋은 JDK-8134853(java.util.concurrent 일괄 통합, 2015-10)이다.

## ConcurrentHashMap

JDK 8부터의 구조다.

- 읽기(`get`)는 락이 없다. 테이블 칸을 volatile로 읽는다(`tabAt`).
- 빈 버킷에 넣을 때는 CAS를 쓴다. `casTabAt(tab, i, null, new Node<>(…))`가 성공하면 끝이고, 실패하면(다른 스레드가 먼저 넣음) 다시 돈다.
- 그 밖의 변경은 버킷의 첫 노드를 잠근다(`synchronized (f)`). 다른 버킷의 변경과는 서로 막지 않는다.
- 리사이즈는 여러 스레드가 나눠 옮긴다. 옮긴 칸에는 `ForwardingNode`를 둔다. 변경하러 온 스레드가 이 노드를 만나면 옮기기를 돕는다. 상태는 `volatile int sizeCtl`이 관리한다.
- 버킷이 길어지면 트리로 바꾼다. `TREEIFY_THRESHOLD = 8`(HashMap과 같다).
- 크기는 쪼개서 센다. `CounterCell[]`에 나눠 더하는데, 소스 주석이 직접 "The element count is maintained using a specialization of LongAdder"라고 밝힌다. `LongAdder`는 [[동기화 기법]]에 있다.

JDK 7까지는 달랐다. 테이블을 `Segment`(각각 `ReentrantLock`을 상속)로 나눠 세그먼트마다 잠갔고, 기본값은 16개(`DEFAULT_CONCURRENCY_LEVEL`)였다. 이 값은 경합 없이 동시에 갱신할 수 있는 기대치이고 상한은 아니다. javadoc: "Because placement in hash tables is essentially random, the actual concurrency will vary". 지금의 CHM도 `concurrencyLevel` 인자를 받지만 크기 힌트로만 쓴다. "버킷 단위 잠금"은 JDK 8 이후의 이야기다. [OpenJDK master · jdk7u `ConcurrentHashMap.java`, 2026-09-27 확인]

### HashMap과 비교하면

자료(Q9)는 HashMap과 비교하라는 질문에 SynchronizedMap과 비교해 답한다. HashMap과의 차이는 이렇다.

| | `HashMap` | `ConcurrentHashMap` |
|---|---|---|
| 스레드 안전 | 아니다. javadoc "not synchronized" | 그렇다 |
| null 키 · 값 | 허용 | 금지: "does not allow null to be used as a key or value" |
| 이터레이터 | fail-fast (`ConcurrentModificationException`) | weakly consistent |
| 원자적 복합 연산 | 없다 (`computeIfAbsent`는 있지만 원자성을 약속하지 않는다) | `putIfAbsent`(`ConcurrentMap` 계약) · `computeIfAbsent` · `compute` · `merge`: "The entire method invocation is performed atomically" |
| 동시 수정 시 | 데이터를 잃는 데서 그치지 않고 구조가 깨질 수 있다 | — |

null을 금지하는 이유는 흔히 이렇게 설명한다. `get`이 null을 돌려줄 때 "키가 없다"와 "값이 null이다"를 가를 수 없는데, 동시성 맵에서는 `containsKey`로 다시 확인하는 사이에 상태가 바뀌므로 애초에 null을 받지 않는다는 것이다. javadoc은 이유를 적지 않으며, 이 설명은 위키가 보충했다.

HashMap을 동기화 없이 여러 스레드가 고치면 구조가 망가질 수 있다. JDK 7 리사이즈의 무한 루프가 흔히 인용되는 사례다. 관련 버그 JDK-6423457 「High cpu usage in HashMap.get()」는 Not an Issue로 닫혔다. 동기화 없이 쓴 것이 오용이라는 판단이다. 검증은 버그 제목과 처리 상태까지만 했고, 원인 서술은 버그 본문에서 확인하지 못했다.

## 면접에서

1. Q6(동기화 컬렉션의 문제)에서는 락 하나의 경합에서 그치지 말고, 메서드 하나만 원자적이라 check-then-act와 순회는 호출자가 잠가야 한다는 것까지 말한다.
2. Q7(차이)에는 "Concurrent는 읽기에 락이 없다"고 하지 말고, 단일 락으로 다스리지 않는다고 답한다. 락을 쪼개거나(CHM) 없애고(COW 읽기, CAS 큐), 이터레이터는 weakly consistent다. `ArrayBlockingQueue` 반례를 알고 있으면 꼬리 질문에 대응할 수 있다.
3. Q8(COW)에는 참조를 바꿔치기하고, 이터레이터는 스냅샷이며, 쓰기가 O(n)이라 읽기 위주의 작은 목록에만 쓴다고 답한다.
4. Q9(CHM)에는 JDK 8 구조(락 없는 get, 빈 칸 CAS, 첫 노드 `synchronized`, 협력 리사이즈)에 JDK 7 Segment와의 대비, HashMap과의 차이(null 금지 · 원자적 `computeIfAbsent`)를 덧붙인다. 그래도 `containsKey` 뒤 `put`은 경쟁한다는 것까지 말할 수 있으면 좋다([[원자성 문제가 나는 시나리오]]).

## 자료의 서술과 정정

| 자료 | 판정 | 정정 |
|---|---|---|
| 락 하나를 공유해 모두 Blocking (Q6) | 맞음(구현) · 누락 | 복합 연산 비원자성, 순회 중 수동 동기화, fail-fast |
| Concurrent 컬렉션은 읽기에 잠금이 없다 (Q7) | 틀림 | `ArrayBlockingQueue`는 읽기도 잠근다. 약속은 "단일 락이 아님"과 weakly consistent |
| COW는 복사본에 쓴 뒤 원본 배열을 갱신 (Q8) | 단서 필요 | volatile 참조를 새 배열로 교체. 락은 JDK 9부터 `synchronized` |
| CHM은 버킷별 잠금, 빈 버킷은 CAS (Q9) | 단서 필요 | JDK 8+로는 맞음. 질문과 답이 어긋남, null 금지·락 없는 get·JDK 7 Segment 누락 |
