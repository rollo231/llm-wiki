# 다형성

하나의 타입으로 여러 구현 객체를 다룰 수 있는 성질. `Animal a = new Cat();`처럼 상위 타입(또는 인터페이스) 변수에 여러 하위 객체를 넣고, 같은 메서드 호출이 실제 객체에 따라 다르게 동작한다([[Java 면접 5 객체지향 프로그래밍]] p92–94).

## 왜 필요한가 — OCP

새 구현 클래스를 추가해도 그것을 쓰는 기존 코드는 고치지 않는다. 이것이 개방-폐쇄 원칙(OCP, Open-Closed Principle)이다. 확장에는 열려 있고 수정에는 닫혀 있다. 자료는 Silver와 Gold를 가르는 기준으로 OCP 언급을 든다.

데이터 엔지니어에게 익숙한 예로는 새 저장소를 붙일 때 파이프라인 코드를 고치지 않고 `Sink` 인터페이스의 구현체만 하나 추가하는 구조다. 이 연결은 위키가 붙였다.

## 다형성의 종류 — 오버로딩은 어디에 속하나

| 종류 | Java의 수단 | 결정 시점 |
|---|---|---|
| 서브타입 다형성 | 오버라이딩 (동적 디스패치) | 런타임 |
| ad-hoc 다형성 | 오버로딩 | 컴파일 타임 |
| 매개변수 다형성 | 제네릭 | 컴파일 타임 |

자료가 정의로 든 "하나의 타입에 여러 객체를 대입"은 서브타입 다형성이고, 이를 구현하는 것은 오버라이딩이다.

## instanceof 문제

자료(p97)는 instanceof로 타입을 확인해 분기하면 ① 다형성의 의미가 사라지고 ② 타입이 늘 때마다 분기를 고쳐야 해서 OCP를 어기고 ③ 런타임 성능 오버헤드가 있다고 한다. ①·②는 전통적인 객체지향 관점에서 맞다. ③은 아래 정정을 본다.

반대편의 관점은 패턴 매칭이다. 최신 Java는 "타입을 보고 분기"를 공식 지원한다. 패턴 매칭 instanceof(JEP 394, JDK 16), sealed 클래스(JEP 409, JDK 17), switch 패턴 매칭(JEP 441, JDK 21)이다. sealed로 하위 타입을 닫아 두면 컴파일러가 switch가 빠짐없는지 검사하므로, ②의 "분기를 빠뜨린다" 문제가 컴파일 오류가 된다. 어느 쪽이 맞는지는 무엇이 늘어나는지로 갈린다. 위키가 관찰한 것이다.

- 타입이 자주 늘어난다 → 다형성(메서드를 타입 안에 둔다). 새 타입 = 새 클래스.
- 연산이 자주 늘어나고 타입은 고정 → sealed + 패턴 매칭. 새 연산 = 새 switch 하나.

## 면접에서

- 정의 → OCP로 필요성 → 구현 수단은 오버라이딩(동적 디스패치)의 순서로 답한다. 오버로딩을 꺼내려면 "컴파일 타임 다형성으로 분류하기도 한다"고 종류를 구분해서 말한다.
- instanceof 질문에는 ①·②를 말하고, "다만 Java 17+의 sealed 타입과 패턴 매칭처럼 닫힌 타입 집합에서는 타입 분기가 권장되기도 한다"를 덧붙이면 자료의 Gold보다 한 단계 위다. 성능(③)은 근거로 쓰지 않는다.

## 자료의 서술과 정정

- ⚠️ "구현 방법으로는 오버로딩, 오버라이딩 등이 있다"(p94)는 자료 자신의 정의와 맞지 않는다. 오버로딩은 컴파일 타임에 결정되는 ad-hoc 다형성으로, "한 타입에 여러 객체 대입"과 무관하다. [Java Language Specification SE 25 §8.4.8 Overriding, §8.4.9 Overloading, §15.12 Method Invocation Expressions, https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html , 2026-09-26 확인]
- ⚠️ "상속 계층이 깊을수록 모든 부모 타입을 확인해야 하므로 성능이 저하된다"(p97)는 틀리다. HotSpot의 fast subtype check는 클래스의 상위 타입(깊이 약 8까지)을 표(primary supers display)로 들고 있다가 상수 시간에 판정한다. 인터페이스는 secondary supers 목록에서 찾는데, JDK 23부터 해시 기반 조회로 바뀌었다. [Cliff Click & John Rose, 「Fast Subtype Checking in the HotSpot JVM」, 2002; OpenJDK JDK-8180450 「secondary_super_cache does not scale well」, https://bugs.openjdk.org/browse/JDK-8180450 , JDK 23, 2026-09-26 확인]
- 패턴 매칭 근거: [JEP 394 Pattern Matching for instanceof (JDK 16), https://openjdk.org/jeps/394 ; JEP 409 Sealed Classes(JDK 17), https://openjdk.org/jeps/409 ; JEP 441 Pattern Matching for switch (JDK 21), https://openjdk.org/jeps/441 , 2026-09-26 확인]
