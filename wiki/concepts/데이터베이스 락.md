# 데이터베이스 락

여러 트랜잭션이 같은 데이터에 동시에 접근할 때 순서를 정하는 장치다. 이 페이지는 세 층을 한곳에 모은다. DB 엔진 안의 락(공유·배타, InnoDB의 레코드·갭·넥스트 키), 애플리케이션이 고르는 전략(낙관적·비관적), DB 바깥의 락(분산 락)이다. [[인프런 DB 면접 강의]]의 Section 2 Q2-4와 Section 3을 바탕으로 MySQL 매뉴얼과 JPA 명세 등을 보탰다. 읽기가 락 없이 도는 부분은 [[MVCC]]에, 락이 막는 이상 현상은 [[트랜잭션 격리 수준]]에 있다.

## 공유 락과 배타 락

| | 공유 락(S) 보유 중 | 배타 락(X) 보유 중 |
|---|---|---|
| 다른 트랜잭션의 S 요청 | 허용 | 대기 |
| 다른 트랜잭션의 X 요청 | 대기 | 대기 |

공유 락은 여럿이 함께 들 수 있고 배타 락은 혼자만 든다. InnoDB에서 S는 `SELECT ... FOR SHARE`, X는 `SELECT ... FOR UPDATE`와 UPDATE·DELETE가 건다. `FOR UPDATE`는 "가장 최근 데이터를 읽고, 읽은 행마다 배타 락을 건다". [MySQL 8.4 매뉴얼 17.7.2.4 Locking Reads, https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html , 2026-09-28 확인]

배타 락이 "읽기도 막는다"는 흔한 설명은 잠금 읽기에만 맞다. 매뉴얼은 "일관된 읽기는 read view에 있는 레코드에 걸린 락을 무시한다"고 쓴다. [같은 절, 2026-09-28 확인] InnoDB의 일반 SELECT는 [[MVCC]] 스냅숏을 읽으므로 X 락이 걸린 행도 막히지 않고 읽는다(SERIALIZABLE 제외). 위키가 MySQL 9.2.0(Innovation 릴리스)을 로컬에 띄워 확인했다. 한 세션이 UPDATE로 X 락을 쥔 동안 REPEATABLE READ 세션의 일반 SELECT는 곧바로 옛 값을 돌려주었고, SERIALIZABLE 세션의 같은 SELECT는 락을 기다리다 1205(Lock wait timeout)로 끝났다. (2026-09-28)

## InnoDB의 레코드 락, 갭 락, 넥스트 키 락

InnoDB의 행 락은 행이 아니라 인덱스 레코드에 걸린다.

- 레코드 락은 인덱스 레코드 하나를 잠근다.
- 갭 락은 인덱스 레코드 사이의 틈, 또는 첫 레코드 앞이나 마지막 레코드 뒤의 틈을 잠근다. 매뉴얼은 갭 락이 "순전히 억제용"이라서 다른 트랜잭션이 그 틈에 삽입하지 못하게 하는 것이 유일한 목적이고, 갭 락끼리는 함께 들 수 있다고 쓴다.
- 넥스트 키 락은 "인덱스 레코드의 레코드 락과, 그 인덱스 레코드 앞 갭의 갭 락을 합친 것"이다. 앞 갭 하나만 포함한다. REPEATABLE READ에서 InnoDB는 검색과 인덱스 스캔에 넥스트 키 락을 써서 팬텀 행을 막는다.

[MySQL 8.4 매뉴얼 17.7.1 InnoDB Locking, https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html , 2026-09-28 확인]

### unique 인덱스로 한 행을 찾으면 레코드 락만

자료(p22)의 예 `SELECT ... FOR UPDATE WHERE id = 5`는 id가 PK라면 id 5의 레코드 락만 건다. 매뉴얼은 "unique 인덱스로 unique한 행을 찾아 잠그는 문장에는 갭 락이 필요 없다"고 쓰고, 바로 `SELECT * FROM child WHERE id = 100`을 예로 들어 "id에 unique 인덱스가 있으면 id 100인 행에 인덱스 레코드 락만 쓰고, 다른 세션이 앞 갭에 삽입해도 상관없다. id에 인덱스가 없거나 unique가 아니면 앞 갭을 잠근다"고 설명한다. 여러 컬럼으로 된 unique 인덱스의 일부 컬럼으로만 찾으면 갭 락이 걸린다는 단서도 있다. [MySQL 8.4 매뉴얼 17.7.1, 2026-09-28 확인] 같은 규칙이 격리 수준 절에도 있다(「unique 인덱스에 unique 검색 조건이면 찾은 인덱스 레코드만 잠그고 그 앞의 갭은 잠그지 않는다」, [[트랜잭션 격리 수준]]).

갭이 잠기는 것은 unique가 아닌 인덱스로 찾을 때, 범위 조건일 때, 인덱스가 없어 스캔할 때다. 찾는 값이 없을 때도 그 자리의 갭이 잠긴다. 이 경우는 매뉴얼 문장으로는 확인하지 못했고, 위키가 MySQL 9.2.0(Innovation 릴리스)을 로컬에 띄워 재현했다. id 1·5·10이 있는 테이블에서 `performance_schema.data_locks`를 보면 `WHERE id = 5 FOR UPDATE`는 PRIMARY의 5에 `X,REC_NOT_GAP`(레코드 락만) 하나를 걸고, 그동안 다른 세션의 `INSERT ... id = 4`는 기다리지 않고 성공했다. 없는 값 `WHERE id = 7 FOR UPDATE`는 10 앞의 갭에 `X,GAP`을 걸었다. unique가 아닌 인덱스 `WHERE c = 50 FOR UPDATE`는 c=50에 넥스트 키 락(`X`)을, 다음 값 앞에 `X,GAP`을 걸었다. (2026-09-28, 기본 격리 수준 REPEATABLE READ) 그래서 면접의 "범위를 잠가 팬텀을 막는다"는 예시로는 범위 조건이나 unique가 아닌 컬럼 조건이 맞다. 매뉴얼의 갭 락 예시도 `SELECT c1 FROM t WHERE c1 BETWEEN 10 and 20 FOR UPDATE`이고, 이 문장은 범위 안에 15가 이미 있든 없든 다른 트랜잭션이 15를 넣지 못하게 한다. [MySQL 8.4 매뉴얼 17.7.1, 2026-09-28 확인]

READ COMMITTED에서는 갭 락이 외래 키 검사와 중복 키 검사에만 쓰이므로 팬텀이 생길 수 있다. [MySQL 8.4 매뉴얼 17.7.2.1, https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html , 2026-09-28 확인]

## 비관적 락과 낙관적 락

| | 비관적 락 | 낙관적 락 |
|---|---|---|
| 가정 | 충돌이 날 것이다 | 충돌은 드물다 |
| 방법 | 읽을 때 `SELECT ... FOR UPDATE`로 선점 | 선점하지 않고, 쓸 때 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`로 확인 |
| 충돌 시 | 뒤 트랜잭션이 기다린다 | 갱신된 행이 0개면 실패, 다시 읽고 재시도 |
| 비용 | 대기, 데드락 가능성 | 재시도 |
| 맞는 곳 | 충돌이 잦거나 임계 영역이 길어 재시도가 비쌀 때 | 충돌이 드물고 재시도가 쌀 때 |

낙관적 락은 Java의 CAS(compare-and-set)와 같은 생각이다. 값이 내가 읽은 그대로일 때만 쓰고, 아니면 다시 한다([[동기화 기법]]). 이 연결은 위키가 했다.

자료(p29)는 둘을 "DB 단이라 자동 롤백" 대 "애플리케이션 단이라 롤백을 직접 구현"으로 가른다. 롤백은 락 종류가 아니라 트랜잭션의 일이다. JPA의 `@Version` 낙관적 락에서 충돌이 나면 `OptimisticLockException`이 나고, 명세는 "OptimisticLockException은 언제나 트랜잭션을 롤백 대상으로 표시한다. 객체를 새 트랜잭션 맥락에서 다시 읽고 트랜잭션을 재시도하는 것이 가능한 대응이다"라고 쓴다. [Jakarta Persistence 3.1 명세 §3.4.5, https://jakarta.ee/specifications/persistence/3.1/jakarta-persistence-spec-3.1 , 2026-09-28 확인] 애플리케이션이 직접 짜야 하는 것은 롤백이 아니라 재시도다. 비관적 락도 예외가 나면 롤백되는 것은 트랜잭션 경계 덕분이지 `FOR UPDATE` 덕분이 아니다.

Lost Update를 막는 가장 간단한 길은 두 락 모두 아니고 원자적 UPDATE(`SET balance = balance + 100`)다. 이 문장은 찾은 레코드에 배타 락을 걸고 최신 값에서 계산한다([[트랜잭션 격리 수준]]).

## 분산 락

DB 행 락은 그 DB 안의 행만 잠근다. 여러 애플리케이션 인스턴스가 DB 바깥의 자원(외부 API 호출, 파일, 캐시 갱신, 여러 DB에 걸친 작업)을 두고 한 번에 하나만 들어가야 할 때, [[Redis]]나 ZooKeeper·etcd 같은 공용 저장소에 락을 두는 것이 분산 락이다.

- 락은 상호 배제만 준다. 자료(p35)의 예처럼 재고를 차감한 뒤 외부 결제를 부르는 흐름에서 결제가 실패했을 때 재고를 되돌리는 일, 캐시와 DB를 원자적으로 함께 바꾸는 일은 락이 해 주지 않는다. 그건 보상 트랜잭션이나 outbox 같은 다른 장치의 몫이다. 이 구분은 위키가 덧붙인 것이다.
- 분산 락은 만료(lease)가 있어 락을 잡은 프로세스가 GC 멈춤 등으로 오래 서 있으면 락이 풀린 줄 모르고 계속 쓸 수 있다. Kleppmann은 이를 막으려면 "저장소에 보내는 모든 쓰기 요청에 fencing token을 붙여야 한다"고 쓰고, Redis의 Redlock 알고리즘에 대해서는 효율용 락에는 무겁고 "정확성이 락에 달린 상황에는 충분히 안전하지 않다"고 결론짓는다. [Martin Kleppmann, "How to do distributed locking", 2016-02-08, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html , 2026-09-28 확인] 이 결론은 Redlock에 대한 것이고, Redis 작성자(antirez)의 반론이 있다. 위키는 반론을 읽지 않았다.
- 그래서 락의 목적을 둘로 나눠 말하는 것이 좋다. 중복 작업을 줄이는 효율용이면 단일 Redis 락으로 충분하고, 틀리면 데이터가 깨지는 정확성용이면 fencing token이나 DB의 조건부 쓰기 같은 최종 방어선이 필요하다. 이 두 갈래는 Kleppmann 글의 구분을 위키가 요약한 것이다.

## 락과 데드락

락을 서로 다른 순서로 잡으면 데드락이 된다. InnoDB는 이를 자동 감지해 한쪽을 롤백한다. 원인과 해법은 Java의 모니터 락과 같다([[데드락 재현과 해법]]). InnoDB의 감지와 설정은 [[DB 면접 7 운영]]에서 다룬다.

## 면접에서

- "공유 락과 배타 락"에는 호환 표로 답하고, "그런데 InnoDB의 일반 SELECT는 X 락이 걸린 행도 읽는다(MVCC)"를 덧붙이면 자료의 Gold보다 한 걸음 낫다.
- "넥스트 키 락"은 "레코드 락 + 그 앞 갭의 갭 락"으로 정의하고, 예시는 범위 조건으로 든다. PK 등호 조건을 예로 들면 "그건 레코드 락만 걸리지 않나"라는 역질문을 받는다.
- "낙관적 락과 비관적 락"은 충돌 빈도와 재시도 비용의 맞교환으로 답하고, 롤백이 아니라 재시도를 차이로 든다.
- "분산 락"은 필요한 이유(여러 인스턴스, DB 바깥 자원)와 한계(상호 배제일 뿐, 만료와 fencing)를 함께 말한다.

## 자료의 서술과 정정

| 쪽 | 자료 서술 | 판정 | 근거 |
|---|---|---|---|
| p22 | `FOR UPDATE WHERE id = 5`는 id 5 레코드와 5의 전후 갭을 잠근다 | 틀림 | unique 인덱스로 한 행을 찾으면 레코드 락만, 넥스트 키 락도 앞 갭 하나 |
| p22 | 넥스트 키 락 = 레코드 락 + 갭 락 | 맞음 | 매뉴얼 정의 그대로(앞 갭) |
| p26 | 배타 락은 해제될 때까지 다른 트랜잭션이 읽기도 불가 | 단서 필요 | 잠금 읽기만 막힘, 일반 SELECT는 MVCC로 읽음 |
| p29 | 비관적 락은 예외 시 자동 롤백, 낙관적 락은 롤백을 직접 구현 | 틀림 | 롤백은 트랜잭션의 일, JPA는 rollback-only 표시, 직접 짤 것은 재시도 |
| p29·p32 | 충돌이 많으면 비관적, 적으면 낙관적, 임계 영역 길이도 기준 | 맞음 | — |
| p35 | 한 DB 트랜잭션으로 묶을 수 없는 자원을 Redis 락으로 함께 제어 | 단서 필요 | 락은 상호 배제만, 원자성은 다른 장치, 정확성용이면 fencing token |
