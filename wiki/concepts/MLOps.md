# MLOps

**ML 시스템을 운영 가능한 형태로 만드는 체계** — 모델 개발과 서비스 운영을 잇고, 데이터·모델·인프라·배포를 하나의
흐름으로 관리한다([[AI DE 강의 2-02 MLOps와 ML 생애주기]]). 목표는 반복 가능한 학습 파이프라인, 안정적인 추론 서비스,
성능 저하 감지를 통한 자동 재학습이다.

## 왜 필요한가

모델 학습은 시작일 뿐이다. 서비스까지 가는 길에 수작업이 많고, 재학습·배포·모니터링이 반복되며, **모델 품질은 시간이
지나면 자연스럽게 떨어진다.** 이 반복을 사람 손으로 관리할 수 없어서 체계가 필요하다.

## DevOps와의 차이

| | DevOps | MLOps |
|---|---|---|
| 관리 대상 | 코드 | 코드 + **데이터 버전 + 모델 버전** |
| 결과물 | 빌드된 소프트웨어 | 학습된 모델 자체 |
| 성능 기준 | 코드가 같으면 동작이 같다 | 고정되지 않음 — 코드가 그대로여도 시간이 지나면 품질이 떨어진다 |

두 번째·세 번째 행이 MLOps를 어렵게 만드는 이유다. 코드가 같아도 데이터가 다르면 다른 모델이 나오고
([[데이터와 모델 버전 관리]]), 아무것도 바꾸지 않아도 세상이 바뀌면 모델이 낡는다([[데이터 드리프트]]).
*(표의 DevOps 열은 강의 문구를 대비로 정리한 위키의 표현)*

## ML 라이프사이클 6단계

출처: [[Designing Machine Learning Systems]](Chip Huyen, O'Reilly 2022) Figure 2-2 — "The process of developing an ML
system looks more like a cycle with a lot of back and forth between steps." (강의 슬라이드에 캡처된 그림 캡션. 책 본문은
위키가 직접 확인하지 못했고, 같은 그림이 저자의 CS 329S 강의 노트에 Figure 1-7로 있다)

```
        1. Project scoping
       ↗                ↘
6. Business analysis    2. Data engineering
       ↑     ⇠ ⇢ ✕ ⇠ ⇢     ↓
5. Monitoring &         3. ML model development
   continual learning
       ↖                ↙
          4. Deployment
   (점선: 2·3·5·6 사이를 오가는 되돌림)
```

| 단계 | 핵심 질문 | DE와의 접점 |
|---|---|---|
| 1. Project scoping | 어떤 비즈니스 문제인가, 성공 지표(business metric)는, 온라인인가 배치인가 | 데이터 접근 가능성, 실시간 요구 → [[모델 서빙]] |
| 2. Data engineering | 학습에 쓸 데이터를 어떻게 만들고 유지하나 | 수집·정제·피처 생성, 데이터셋 구성, [[피처 스토어]], 재현 가능한 데이터 버전 |
| 3. ML model development | 어떤 모델이 좋은가 | 모델 아티팩트·실험 메타데이터 저장 |
| 4. Deployment | 어떻게 서비스로 내보내나 | 배치 vs 온라인 서빙, GPU, 롤백, 학습/추론 정합성 → [[학습-서빙 스큐]] |
| 5. Monitoring & continual learning | 모델이 아직 괜찮은가 | 드리프트 감지, 재학습 트리거, 자동 검증 → [[데이터 드리프트]] · [[데이터 관측성]] |
| 6. Business analysis | 모델이 실제로 KPI를 움직였나 | 결과에 따라 1단계로 되돌아감 |

**요점은 순환이다.** 1단계에서 정확도가 아닌 비즈니스 지표를 정하고, 6단계가 그 지표로 문제 정의를 다시 고친다.
어느 단계에서든 앞 단계로 되돌아갈 수 있다.

## 자동화된 고리 — Part 1의 Self-Healing 파이프라인

[[AI DE 강의 1-13 Skew와 Drift]]의 Self-Healing 파이프라인 5단계(데이터 수집 → 모델 학습 → 모델 평가 → 배포 → 관측)는
위 6단계 가운데 **2~5단계를 자동으로 도는 고리**다. 안전장치로 재학습 쿨다운 기간과 고위험 모델의 사람 승인
(Human-in-the-loop)을 둔다. 사람의 판단이 필요한 양 끝(1 문제 정의, 6 비즈니스 분석)은 고리 밖에 남는다. *(위키의 대응)*

## 데이터 엔지니어의 책임

[[AI DE 강의 2-02 MLOps와 ML 생애주기]] p17이 드는 DE 책임 영역:

- 데이터 파이프라인 설계
- [[피처 스토어]] 운영
- 학습/추론 데이터 일관성 ([[학습-서빙 스큐]])
- GPU 사용 흐름 설계 ([[AI DE 강의 2-09 서빙의 CPU·GPU 가속]])
- 자동 재학습 파이프라인 구축

[[AI DE 강의 2-01 데이터 파이프라인의 진화와 데이터 엔지니어]]는 이를 "DE의 확장 영역"으로 묶는다 — 피처 스토어(스큐),
Vector DB(RAG), 모니터링(드리프트 → 재실행 트리거). 이 책임들은 라이프사이클의 **2단계 하나에 모이지 않고 2~5단계를
가로지른다** — 데이터 버전은 2단계에서 만들어 3단계 실험 재현에 쓰이고, 학습/추론 정합성은 4단계, 드리프트 감지는
5단계다. *(위키의 관찰)*

## 빈칸

- **단계 사이의 인계물** — 3단계가 4단계에 무엇을 넘기는지(모델 레지스트리, 아티팩트·메타데이터 형식), 5단계의 트리거가
  2단계에 어떤 형태로 되돌아가는지 Part 2는 설명하지 않는다. 이름만 나오는 도구(MLflow·Kubeflow)도 역할이 풀리지 않는다.
- **MLOps 성숙도** — 수동 → 파이프라인 자동화 → CI/CD 자동화 같은 단계 구분은 다루지 않는다.
- **모델 평가와 승격 규칙** — Part 1의 Champion vs Challenger 외에, 오프라인 지표를 통과한 모델을 언제 온라인으로 올리는지
  (A/B 테스트, 섀도우) 기준이 없다.
