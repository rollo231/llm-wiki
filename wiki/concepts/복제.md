# 복제

같거나 동등한 상태를 여러 노드에 유지하는 기법이다. 목적은 장애 때의 대체본, 읽기 분산·지역 분산, 데이터 손실 위험 감소 세 가지다([[AI DE 강의 4-03 고가용성·복제·합의]] p58). 가용성과 내구성을 함께 높이는 가장 기본 수단이다.

## 고가용성, 복제, 합의의 관계

강의의 틀은 "고가용성은 목표, 복제는 데이터 수단, 합의는 제어 수단"이다(p53–54). 세 개념은 서로를 대체하지 않고 층을 이룬다. 복제본이 여러 개 있어도 누가 지금 primary인지, 어느 복제본이 가장 최신인지, 분할 중 어느 쪽이 쓰기를 받아도 되는지, 장애 후 트래픽을 어디로 돌릴지는 따로 정해야 한다. 이 결정이 [[합의 알고리즘]]의 몫이다.

## 고가용성(HA)

HA는 장애가 나도 서비스가 멈추지 않거나 빨리 복구되는 상태다. 운영 목표는 두 숫자로 잡는다(p55).

| 지표 | 질문 |
|---|---|
| RTO (Recovery Time Objective) | 장애 후 서비스가 다시 살아날 때까지 얼마나 걸려도 되나 |
| RPO (Recovery Point Objective) | 장애 때 잃어도 되는 데이터가 최대 얼마인가 |

그래서 HA는 "복제본이 있다"가 아니라 "얼마나 빨리 전환되고 얼마나 적게 잃는가"까지 포함한다. HA 구성에는 최소 네 가지가 필요하다(p56, Google Cloud의 PostgreSQL HA 문서를 인용). 실패 감지, standby를 primary로 올리는 failover 절차, 요청을 새 primary로 보내는 라우팅 전환, 옛 primary를 안전하게 되돌리는 fallback 절차다.

강의가 드는 예(p57):

- PostgreSQL: primary와 standby, 필요하면 standby 승격.
- Kubernetes control plane: stacked etcd와 external etcd 토폴로지. external은 한 노드 손실의 영향을 줄이지만 서버가 더 든다.
- Vault: Raft 기반으로 모든 노드에 데이터를 복제한다.

## 동기 복제와 비동기 복제

클라이언트에게 "커밋 완료"를 돌려주는 시점을 언제로 정하느냐의 차이다(p59–60).

| | 동기 | 비동기 |
|---|---|---|
| 커밋 반환 | standby 최소 1개가 받아 디스크에 기록했다는 ACK를 받은 뒤 | primary가 로컬 WAL에 기록한 즉시 |
| RPO | 0 | 0보다 크다. 전송 전 트랜잭션이 사라질 수 있다 |
| 지연 | standby 응답만큼 늘어난다 | 낮다 |
| 위험 | standby가 죽으면 primary 쓰기까지 막힐 수 있다 | primary 크래시 때 최근 커밋 유실 |

PostgreSQL은 `synchronous_standby_names`가 비어 있으면 비동기이고, 이것이 기본값이다(p60의 서술이 맞다). 동기 모드에도 단계가 있다. `synchronous_commit = on`은 동기 standby가 커밋 기록을 durable storage까지 flush할 때까지, `remote_write`는 standby OS에 쓰는 데까지, `remote_apply`는 standby에 반영될 때까지 기다린다. [https://www.postgresql.org/docs/current/runtime-config-wal.html : "received the commit record of the transaction and flushed it to durable storage", 2026-09-28 확인] 강의의 "디스크에 기록(Flush)했음을 확인"은 `on`에 해당한다. 단계 구분은 위키가 보충한 것이다.

이 맞교환은 [[지연 시간과 처리량]]과 [[CAP 정리]]의 한 사례로 읽힌다. 동기 복제는 일관성·내구성 쪽으로, 비동기 복제는 지연·가용성 쪽으로 기운다.

## Kafka의 복제

Kafka는 토픽 파티션마다 로그를 여러 브로커에 복제해 브로커 장애 때 자동 failover를 한다(p58). 강의의 "분산 로그 패턴"은 다중 브로커, replication factor 3, `min.insync.replicas=2`, `acks=all`이다(p66). 이렇게 두면 in-sync 복제본이 2개 밑으로 떨어질 때 쓰기가 NotEnoughReplicas로 실패한다. 내구성을 높일수록 저장 비용과 쓰기 실패율이 오른다는 것이 강의 p65의 요점이다. [apache/kafka `TopicConfig.java`: "A typical scenario would be to create a topic with a replication factor of 3, set min.insync.replicas to 2, and produce with acks of \"all\"", 2026-09-28 확인]

프로듀서 기본값은 Kafka 3.0.0에서 `acks=all`과 `enable.idempotence=true`로 바뀌었다. 다만 idempotence 기본값은 설정을 명시하지 않으면 켜지지 않는 버그(KAFKA-13598)가 있어, 3.0 계열은 3.0.1, 3.1 계열은 3.1.1부터 실제로 적용됐다(영향 버전 3.0.0·3.1.0). [https://kafka.apache.org/30/documentation.html#upgrade_300_notable · https://issues.apache.org/jira/browse/KAFKA-13598 , 2026-09-28 확인] Kafka 전반은 [[Apache Kafka]]에 있다.

## MySQL의 복제

[[DB 면접 7 운영]] Q2-1(p122)은 MySQL 복제를 세 단계로 설명한다. Master에서 쓰기 트랜잭션이 Binlog에 기록되고, Slave의 IO Thread가 Master의 Binlog를 가져와 Relay log에 저장하고, Slave의 SQL Thread가 Relay log를 읽어 같은 트랜잭션을 재실행한다. 구조는 맞고, 이름과 기본값이 바뀌었다.

| 자료의 이름 | 현재 이름 | 하는 일 |
|---|---|---|
| Master | source | 변경을 binary log(Binlog)에 기록하고, 붙은 replica에 보낸다(source 쪽 Binlog Dump 스레드) |
| Slave | replica | source의 변경을 받아 다시 실행한다 |
| IO Thread | receiver 스레드 | source에 붙어 binlog 이벤트를 읽고 relay log에 쓴다 |
| SQL Thread | applier 스레드 | relay log를 읽어 트랜잭션을 실행한다 |

- 용어는 MySQL 8.0.22부터 차례로 바뀌었다. `START SLAVE` 대신 `START REPLICA`를 쓰고, 옛 문은 그 릴리스부터 deprecated다("From MySQL 8.0.22, use START REPLICA in place of START SLAVE"). [MySQL 8.0 Reference Manual, START REPLICA Statement, https://dev.mysql.com/doc/refman/8.0/en/start-replica.html , 2026-09-28 확인] 같은 문서가 `IO_THREAD` 옵션을 "replication receiver thread", `SQL_THREAD`를 "replication applier thread"로 설명한다. 변수 이름도 따로 바뀌었다. 8.0 매뉴얼의 복제 스레드 절은 8.0.26 이하에서는 `replica_parallel_workers` 대신 옛 이름 `slave_parallel_workers`를 쓰라고 적는다. [https://dev.mysql.com/doc/refman/8.0/en/replication-threads.html , 2026-09-28 확인]
- applier는 이제 기본으로 여럿이다. `replica_parallel_workers`의 기본값이 8.0.27부터 4다("Beginning with MySQL 8.0.27, the default value is 4, which means that replicas are multithreaded by default"). 이때는 코디네이터 스레드 하나가 여러 applier 워커에 트랜잭션을 나눠 준다. 그러니 "SQL Thread 하나가 재실행한다"는 8.0.26 이전 기본 설정의 그림이다. [MySQL 8.0 Reference Manual, Replica Server Options, https://dev.mysql.com/doc/refman/8.0/en/replication-options-replica.html , 2026-09-28 확인]
- 기본은 비동기다("Replication is asynchronous by default"). [MySQL 8.0 Reference Manual, Chapter 19 Replication, https://dev.mysql.com/doc/refman/8.0/en/replication.html , 2026-09-28 확인] 그래서 자료(p119)의 "데이터 동기화에 지연이 발생할 수 있다"가 기본 동작이다. 앞 절의 동기·비동기 맞교환이 여기에도 그대로 있다. 이 연결은 위키가 했다.

### Read Replica로 읽기 확장

[[DB 면접 5 NoSQL과 RDBMS 비교]] Q1-2(p78)는 RDBMS의 읽기 확장을 Read Replica로 설명한다. 쓰기는 source가 맡고 읽기를 여러 replica로 나눈다. 쓰기는 여전히 한 곳이라 쓰기 확장은 [[샤딩]]의 몫이다. 비동기 복제라 replica에서 방금 쓴 값이 안 보일 수 있다(Replication Lag). [[DB 면접 7 운영]] Q4-1(p134)이 이 지연을 모니터링 메트릭으로 든다.

## Clustering, Replication, Sharding

[[DB 면접 7 운영]] Q2(p119)의 Gold 답은 셋을 이렇게 나눈다. Clustering은 스토리지 하나를 두고 여러 DB 서버를 묶어 Active-StandBy로 가용성을 유지하며 정합성을 보장한다. Replication은 Master(쓰기)와 Slave(읽기)가 각자 스토리지를 가지고, 읽기를 나누지만 동기화 지연이 생길 수 있다. Sharding은 테이블을 나눠 여러 서버에 저장하고, 읽기·쓰기를 모두 나누지만 샤드 간 조인·트랜잭션이 복잡하다.

Replication과 Sharding의 설명은 맞다. Clustering은 벤더마다 뜻이 달라 한 문장으로 정의하기 어렵다.

| 제품 | 저장소 | 노드 역할 | 자료의 정의와 |
|---|---|---|---|
| Oracle RAC | 공유 디스크(한 DB) | 여러 인스턴스가 한 DB를 동시에 처리 | 공유 스토리지는 같고, Active-StandBy가 아니라 active-active다 |
| MySQL NDB Cluster | 노드마다 자기 메모리·디스크 | shared-nothing, 데이터 노드가 데이터를 나눠 가진다 | 공유 스토리지가 아니다 |
| MySQL InnoDB Cluster (Group Replication) | 서버마다 전체 사본 | 복제 그룹, 서버끼리 메시지를 주고받으며 맞춘다 | 공유 스토리지가 아니다. 사실상 복제 위의 클러스터다 |

- Oracle RAC 문서는 여러 인스턴스가 한 데이터베이스에 접근해 서버 하나가 단일 장애점이 되지 않게 한다고 쓴다("Having multiple instances access a single database prevents the server from being a single point of failure"). [Oracle Database 19c, Real Application Clusters Administration and Deployment Guide, Introduction to Oracle RAC, https://docs.oracle.com/en/database/oracle/oracle-database/19/racad/introduction-to-oracle-rac.html , 2026-09-28 확인]
- NDB Cluster는 "a technology that enables clustering of in-memory databases in a shared-nothing system"이다. [MySQL 8.4 Reference Manual, NDB Cluster Overview, https://dev.mysql.com/doc/refman/8.4/en/mysql-cluster-overview.html , 2026-09-28 확인]
- Group Replication은 "each of which has a complete copy of the data (a shared-nothing replication scheme)"이다. [MySQL 8.4 Reference Manual, 20.1.1.2 Group Replication, https://dev.mysql.com/doc/refman/8.4/en/group-replication-summary.html , 2026-09-28 확인]

자료의 정의는 공유 디스크 + 페일오버라는 한 형태(전통적인 HA 클러스터)에 맞는다. 면접에서는 "공유 스토리지 방식과 shared-nothing 방식이 있다"고 먼저 나누는 편이 안전하다. 이 표와 조언은 위키가 정리한 것이다.

## 세 계층의 조합

강의 p66은 HA·복제·합의를 조합한 패턴 세 개로 소단원을 닫는다.

| 패턴 | 구성 |
|---|---|
| RDBMS HA | primary-standby + 동기 복제 + Patroni(또는 pg_auto_failover) + 로드 밸런서 |
| 분산 로그 | 다중 브로커 + RF=3 + min.ISR=2 + acks=all |
| 제어-데이터 분리 | 다중 control plane 노드 + external etcd |

Patroni가 failover를 결정할 때 etcd·Consul 같은 합의 저장소에 기대는 것처럼, 세 패턴 모두 복제된 데이터 위에 합의 계층을 얹는다. 이 연결은 위키의 설명이다.
