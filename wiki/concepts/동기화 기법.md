# 동기화 기법

[[동시성 문제]](가시성·원자성)를 막는 Java의 도구들. 면접 자료는 앞의 세 가지를 문제와 짝지어 가르친다([[Java 면접 4 동시성 이슈]] p61–69). 자료에 없는 두 가지(`ReentrantLock`, 동시성 컬렉션의 복합 연산)는 위키가 더했다.

| 도구 | 막는 문제 | 방식 | 한계 |
|---|---|---|---|
| `volatile` | 가시성 (+ 재정렬) | 컴파일러 최적화 금지 + 메모리 배리어로 happens-before | 원자성은 못 준다. `volatile int count; count++`는 여전히 깨진다 |
| `synchronized` | 원자성 + 가시성 | 객체의 모니터를 잠가 임계 영역에 한 스레드만. 해제 → 획득이 happens-before | 기다리는 동안 포기·타임아웃·인터럽트가 안 된다. 경합이 심하면 BLOCKED |
| `ReentrantLock` | 원자성 + 가시성 | `synchronized`와 같은 의미 + `tryLock`·타임아웃·인터럽트·공정성·여러 `Condition` | `finally`에서 직접 `unlock`해야 한다 |
| atomic 타입 (`AtomicInteger` 등) | 원자성 + 가시성 (변수 하나) | CAS: 기대값이 그대로면 쓰고, 아니면 재시도 | 변수 하나만. 경합이 심하면 재시도가 몰린다. ABA |
| 동시성 컬렉션의 복합 연산 | 원자성 (확인 후 행동) | `putIfAbsent`·`computeIfAbsent`·`compute`·`merge`가 확인과 행동을 한 연산으로([[동시성 컬렉션]]) | 그 컬렉션 안의 연산에만 |

재현 실험은 [[가시성 문제는 지금도 생기나]](volatile)와 [[원자성 문제가 나는 시나리오]](synchronized·atomic·`computeIfAbsent`)에 있다.

## volatile

"CPU 캐시를 우회해 RAM에 직접 접근한다"는 흔한 설명은 틀렸다. 정정 전문은 [[동시성 문제]]의 가시성 절에 있다. 여기서는 결론만 적는다. volatile 쓰기와 그 뒤의 같은 변수 volatile 읽기 사이에 happens-before가 생긴다. 그래서 쓴 값이 보이고, volatile 쓰기 이전의 일반 쓰기들도 함께 보인다(플래그 하나로 초기화 완료를 알리는 패턴이 이걸로 성립한다).

volatile이 꼭 필요한 곳은 두 군데다.

- double-checked locking. 락 밖에서 한 번, 락 안에서 한 번 null을 확인하는 지연 초기화다. `volatile`이 없으면 다른 스레드가 생성이 덜 끝난 객체를 볼 수 있다. "the writes that initialize the Helper object and the write to the helper field can be done or perceived out of order." JDK 5(JSR-133)부터 "the Double-Checked Locking idiom can be made to work by declaring the helper field to be volatile." 객체의 필드가 모두 `final`인 불변 객체면 `volatile` 없이도 된다. [Bill Pugh 외, 「The "Double-Checked Locking is Broken" Declaration」, https://www.cs.umd.edu/~pugh/java/memoryModel/DoubleCheckedLocking.html , 2026-09-27 확인]
- 공유하는 `long`·`double`. `volatile`이 없으면 쓰기 하나가 32비트 두 번으로 쪼개질 수 있다. "Writes and reads of volatile `long` and `double` values are always atomic." (JLS §17.7) 재현은 [[원자성 문제가 나는 시나리오]]에 있다.

## synchronized와 모니터

- 모니터는 모든 객체가 암묵적으로 가진 동기화 장치다. 상호 배제(한 번에 한 스레드만 소유)와 조건 동기화(`wait`/`notify`)를 제공한다. 인스턴스 메서드에 붙이면 `this`의, static 메서드에 붙이면 Class 객체의, 블록이면 지정한 객체의 모니터를 잠근다.
- 가시성도 준다. "An unlock on a monitor happens-before every subsequent lock on that monitor." (JLS §17.4.5) 그래서 같은 락으로 쓰기와 읽기를 모두 감싸야 한다. 쓰기만 감싸고 읽기를 락 밖에서 하면 가시성이 보장되지 않는다.
- 재진입한다. "A thread t may lock a particular monitor multiple times; each unlock reverses the effect of one lock operation."(JLS §17.1) `synchronized` 메서드가 같은 객체의 다른 `synchronized` 메서드를 불러도 스스로 막히지 않는다.
- 블록은 `monitorenter`/`monitorexit` 명령으로, 메서드는 `ACC_SYNCHRONIZED` 플래그로 컴파일된다. 아래 「바이트코드로 보면」에서 직접 확인했다.

[Oracle, 「The Java Language Specification」 Java SE 25 17장, https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html , 2026-09-27 확인]

### 바이트코드로 보면

로컬 JDK 25에서 `synchronized (lock) { count++; }`를 컴파일해 `javap -c`로 열었다(2026-09-27).

```
 6: monitorenter          // 락 잡기
    ... count++ ...
18: monitorexit           // 정상 경로에서 풀기
19: goto 27
22: astore_2              // 예외가 나면 여기로
24: monitorexit           // 예외 경로에서도 풀기
26: athrow
Exception table:  7~19 → 22 (any),  22~25 → 22 (any)
```

- `monitorexit`가 두 번 있다. javac가 예외 경로에도 풀기를 넣어서, 블록을 어떻게 나가든 락이 풀린다. `ReentrantLock`에서 개발자가 `finally { unlock(); }`로 직접 하는 일을 컴파일러가 대신한다.
- 메서드에 붙이면 명령이 없다. `synchronized void method()`의 본문에는 `monitorenter`가 없고, 메서드에 `ACC_SYNCHRONIZED` 플래그(`0x0020`)만 붙는다. 들어가고 나올 때 JVM이 잡고 푼다.

### HotSpot은 처음부터 막지 않는다

자료(p66)는 "blocking이라 runnable → blocked 전환 비용이 든다"고 하지만, 그것은 경합이 생긴 뒤의 이야기다. 지금(JDK 23+) 기본인 lightweight locking은 이렇게 간다.

1. 경합이 없으면 객체 헤더(mark word)의 lock 비트를 CAS 한 번으로 "fast-locked"로 바꾸고, 객체를 스레드별 lock-stack(용량 8)에 push한다. OS가 개입하지 않는다. 같은 스레드가 다시 잡으면(재진입) lock-stack 맨 위가 같은 객체인지만 보고 한 번 더 쌓는다.
2. 경합이 생기면 inflate하기 전에 잠시 스핀한다("Fast-lock spinning to avoid inflating for short critical sections").
3. 그래도 안 되면 ObjectMonitor로 inflate한다. 모니터에서도 적응형으로 스핀해 보고, 끝내 못 잡으면 대기 스레드가 BLOCKED 상태로 OS에 맡겨진다.

`ObjectMonitor`는 Java 객체가 아니라 HotSpot의 C++ 객체다. 주요 필드는 다음과 같다(`src/hotspot/share/runtime/objectMonitor.hpp`, master, 2026-09-27 확인).

| 필드 | 뜻 |
|---|---|
| `_owner` | 지금 락을 가진 스레드 |
| `_recursions` | 재진입 횟수: "recursion count, 0 for first entry" |
| `_entry_list` | 락을 기다리는 스레드: "Threads blocked on entry or reentry" |
| `_wait_set` | `wait()`로 잠든 스레드: "threads waiting on the monitor - wait()" |
| `_succ` | 다음 차례로 점찍은 스레드: "used for futile wakeup throttling" |

`_owner` 주석에 `DEFLATER_MARKER`가 있어서, 한가해진 모니터를 다시 떼어내는(deflate) 과정이 있는 것으로 보인다. 이것은 추론이고 과정은 확인하지 않았다.

⚠️ 위키 정정(2026-09-27): 처음에는 "객체 헤더에 CAS 한 번으로 소유를 표시한다"고만 적었다. 이 말은 옛 방식(stack-locking)에도 지금 방식에도 맞지만, 소유를 표시하는 방법이 바뀌었다. 옛 방식은 헤더에 스레드 스택을 가리키는 포인터를 넣었다("Current stack-locking overloads object headers with pointers into the stack"). 지금 방식은 헤더에 lock 비트만 두고 소유 기록은 lock-stack에 둔다.

| 릴리스 | 일 | 이슈 |
|---|---|---|
| JDK 21 | 새 방식(`LM_LIGHTWEIGHT`) 추가. 기본은 여전히 옛 방식 | JDK-8291555 |
| JDK 23 | 기본값을 `LM_LIGHTWEIGHT`로. 재진입 지원 | JDK-8319251 · JDK-8319796 |
| JDK 24 | `LockingMode` 옵션과 옛 방식 deprecated | JDK-8334299 |
| JDK 26 | `LockingMode`를 사용자가 설정할 수 없게 하고 옛 방식 코드 제거 | JDK-8359437 외 |

로컬 OpenJDK 25.0.2의 `-XX:+PrintFlagsFinal`은 `LockingMode = 2`(lightweight, 기본값)다. [OpenJDK JBS 각 이슈(REST API로 fix version 확인), https://bugs.openjdk.org/browse/JDK-8291555 ; HotSpot 소스 `src/hotspot/share/runtime/synchronizer.cpp`(`cas_set_mark(fast_locked_mark, …)` 뒤 "Successfully fast-locked, push object to lock-stack") · `lockStack.hpp`(`CAPACITY = 8`), https://github.com/openjdk/jdk , master, 2026-09-27 확인]

- biased locking은 없어졌다. 한 스레드가 반복해서 잡는 lock을 CAS조차 없이 처리하던 최적화였는데, JDK 15에서 기본 비활성·deprecated(JEP 374), JDK 18에서 obsolete가 됐다. 옛 면접 자료에 자주 나오니 지금은 없다고 말할 수 있으면 좋다.
- JDK 21의 가상 스레드는 `synchronized` 안에서 블로킹하면 캐리어(플랫폼) 스레드에 묶이는 pinning 문제가 있어서 `ReentrantLock`을 권장했다. JDK 24(JEP 491)에서 해결됐다. 가상 스레드 이야기는 [[스레드 풀]]에 있다.

### synchronized의 문제점

기다리는 방법이 하나뿐이다. 아래 대안은 모두 `java.util.concurrent.locks`에 있다.

| 문제 | 무슨 일이 생기나 | 대안 |
|---|---|---|
| 포기할 수 없다 | 못 잡으면 무한정 기다린다. 타임아웃도, 기다리는 중의 인터럽트도 없다 | `tryLock(timeout)`, `lockInterruptibly()` |
| 데드락에서 못 빠져나온다 | A가 락1을 쥐고 락2를, B가 락2를 쥐고 락1을 기다리면 둘 다 영원히 멈춘다. 재현은 [[데드락 재현과 해법]] | 락을 잡는 순서를 고정, 또는 `tryLock`으로 물러서기 |
| 공정성이 없다 | 먼저 온 순서를 약속하지 않아 운 나쁜 스레드가 계속 밀릴 수 있다(기아) | `new ReentrantLock(true)`. 대신 처리량이 떨어진다 |
| 대기실이 하나다 | 객체당 wait set 하나. `notify()`가 깨우는 스레드는 "arbitrary"라 생산자·소비자를 골라 깨울 수 없어 `notifyAll()`로 모두 깨우게 된다 | `Condition` 여러 개 |
| 읽기·쓰기를 가리지 않는다 | 읽기만 하는 스레드끼리도 서로 막는다 | `ReadWriteLock`, `StampedLock` |

쓰는 쪽에서 나는 사고도 있다. 아래는 위키가 정리한 것이다.

- 락 범위가 넓으면 병렬이 사라진다. 메서드 전체에 걸거나 락 안에서 I/O(DB·HTTP 호출)를 하면 그 구간이 한 줄로 선다. 락 안에는 공유 상태를 건드리는 최소한만 둔다.
- 락 객체가 밖으로 드러난다. `synchronized(this)`와 `synchronized` 메서드는 외부 코드도 같은 객체로 잡을 수 있다. 그래서 `private final Object lock`을 따로 둔다. 문자열 리터럴(intern되어 공유된다)이나 박싱된 정수로 락을 잡으면 전혀 다른 코드와 락이 엉킬 수 있다. `Integer.valueOf`는 "will always cache values in the range -128 to 127".
- JVM 하나 안에서만 통한다. 서버를 두 대 띄우면 서로의 `synchronized`를 모른다. 여러 인스턴스 사이의 재고 차감 같은 문제는 DB 락·버전 컬럼, 분산 락으로 푼다([[동시성 문제]] 원자성 절).
- 성능 면에서 "느리다"는 경합이 있을 때만 맞다(위 경량 락 절). 가상 스레드 pinning은 JDK 24에서 해결됐다(위).

[Oracle, Java SE 25 API — `Object.notify()`("The choice is arbitrary and occurs at the discretion of the implementation") · `Integer.valueOf(int)`, https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Object.html , 2026-09-27 확인]

## ReentrantLock

"the same basic behavior and semantics as the implicit monitor lock accessed using `synchronized` methods and statements, but with extended capabilities." 가시성도 같다: "All `Lock` implementations must enforce the same memory synchronization semantics as provided by the built-in monitor lock". 차이는 기다리는 방법에 있다.

| | `synchronized` | `ReentrantLock` |
|---|---|---|
| 재진입 | 된다 | 된다 (hold count가 1씩 는다) |
| 못 잡으면 바로 포기 | 안 된다 | `tryLock()` |
| 기다리다 시간 초과 | 안 된다 | `tryLock(timeout, unit)` |
| 기다리다 인터럽트 | 안 된다 | `lockInterruptibly()` |
| 공정성(오래 기다린 순서) | 없다 | `new ReentrantLock(true)`. 대신 처리량이 "often much slower" |
| 조건 대기 | 객체 하나에 대기실 하나(`wait`/`notify`) | `newCondition()`으로 여러 개: "the effect of having multiple wait-sets per object" |
| 풀기 | 블록을 나가면 자동 | 직접: "always immediately call unlock as the first statement in the finally block" |

- 공정 락이어도 시간 제한 없는 `tryLock()`은 공정성을 무시한다("does not honor the fairness setting").
- 고르는 기준은 위키가 정리했다. 기본은 `synchronized`다(짧고 실수할 곳이 없다). 타임아웃·인터럽트·공정성·여러 조건 가운데 하나라도 필요하면 `ReentrantLock`을 쓴다. JDK 24부터는 가상 스레드를 쓴다는 것이 `ReentrantLock`을 고를 이유가 되지 않는다.

[Oracle, Java SE 25 API — `java.util.concurrent.locks.ReentrantLock` · `Lock` · `Condition`, https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html , 2026-09-27 확인]

## CAS와 atomic 타입

CAS(Compare-And-Swap)는 "메모리 값이 내가 읽은 값과 같으면 새 값으로 바꾸고, 다르면 실패"를 원자적으로 하는 연산이다. atomic 타입은 실패하면 다시 읽고 재시도한다. 그래서 lock 없이(non-blocking) 원자성을 얻는다.

- "CPU 명령 하나"는 x86에서만 그대로 맞다. x86은 `lock cmpxchg` 한 명령이다. AArch64는 CPU가 LSE(ARMv8.1)를 지원하면 CAS 한 명령이고, 아니면 `ldaxr`/`stlxr`(배타적 읽기·쓰기)를 실패할 때마다 되풀이하는 루프다. HotSpot은 LSE를 지원하는 CPU에서 자동으로 `UseLSE`를 켠다(로컬 Apple Silicon JDK 25: `UseLSE = true`). [HotSpot 소스 `src/hotspot/cpu/aarch64/macroAssembler_aarch64.cpp`의 `MacroAssembler::cmpxchg`, `src/hotspot/cpu/x86/x86.ad`, master, 2026-09-27 확인]
- "lock이 없으니 synchronized보다 빠르다"(자료 p63)는 경합이 낮을 때만 대체로 맞다. 경합이 높으면 재시도가 몰리고, 캐시 라인이 코어 사이를 계속 오가면서 오히려 느려질 수 있다.
- 그래서 JDK 8에 `LongAdder`가 들어왔다. 카운터를 여러 셀로 나눠 스레드마다 다른 셀을 더하고, 읽을 때 합친다. 통계·지표 카운터처럼 쓰기가 많고 읽기가 드문 곳에 맞는다.
- `updateAndGet`·`accumulateAndGet`에 넘기는 함수는 부작용이 없어야 한다: "it may be re-applied when attempted updates fail due to contention among threads." 재시도 때 함수가 다시 불리기 때문이다. 안에서 로그를 쓰거나 카운터를 올리면 여러 번 일어난다.
- DB 낙관적 락과 같은 모양이라는 연결은 [[동시성 문제]]의 원자성 절에 있다. 충돌이 드물면 싸고 잦으면 재시도 비용이 커지는 것도 같다. 이 연결은 위키가 붙였다.

### ABA 문제

CAS는 값이 같은지만 본다. 그 사이에 A → B → A로 바뀌었다 돌아와도 안 바뀌었다고 보고 성공한다. 값만 중요한 카운터에서는 상관없지만, lock-free 스택처럼 그 사이에 구조가 바뀌었는지가 중요한 곳에서는 틀린 결과를 낸다.

- 해법은 값과 함께 버전을 바꾸는 것이다. `AtomicStampedReference`는 참조와 정수 "stamp"를 함께 원자적으로 바꾼다. 패키지 문서는 이 stamp를 "version numbers corresponding to series of updates"에 쓸 수 있다고 적는다. `AtomicMarkableReference`는 boolean 하나를 붙인다("logically been deleted" 표시). DB 낙관적 락의 버전 컬럼과 같은 생각이라는 연결은 위키가 붙였다.
- javadoc에는 "ABA"라는 단어가 없다. "Java는 GC가 있어서 참조의 ABA가 C보다 드물다"(해제된 주소가 바로 재사용되지 않으므로)는 널리 쓰이는 설명이지만 1차 자료로 확인하지 못했다.

[Oracle, Java SE 25 API — `java.util.concurrent.atomic` 패키지 · `AtomicStampedReference` · `AtomicReference`, https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/package-summary.html , 2026-09-27 확인]

### 여러 값을 함께 바꿀 때

atomic 패키지는 스스로 "lock-free thread-safe programming on **single variables**"라고 밝힌다. 필드 둘을 같이 바꿔야 하면([[원자성 문제가 나는 시나리오]]의 「여러 값을 함께 바꾸기」) 두 길이 있다. 이 두 길은 위키가 정리한 것이고, javadoc이 이 패턴을 직접 권하지는 않는다.

- 같은 락으로 쓰기와 읽기를 모두 감싼다.
- 두 값을 불변 객체 하나로 묶고 `AtomicReference`로 그 참조를 한 번에 바꾼다(`updateAndGet(old -> new Range(...))`).

### 안쪽 구현

JDK 9(JEP 193)에 `VarHandle`이 들어와 `java.util.concurrent`가 `Unsafe` 대신 쓰기 시작했다(JDK-8080603). 다만 클래스마다 다르다. `AtomicReference`는 `VarHandle`을 쓰고, `AtomicInteger`·`AtomicLong`은 지금도 `jdk.internal.misc.Unsafe`를 쓴다. 소스 주석은 이렇다: "This class intended to be implemented using VarHandles, but there are unresolved cyclic startup dependencies." 면접에서는 직접 CAS를 쓸 일이 있으면 `VarHandle`을 쓴다는 것 정도만 알면 된다. [OpenJDK JEP 193, https://openjdk.org/jeps/193 ; `AtomicInteger.java` · `AtomicReference.java`, https://github.com/openjdk/jdk , master, 2026-09-27 확인]

## 싱글톤 지연 초기화

[[Java 면접 4 빈출 질문]] Q4는 "synchronized를 써 본 경험"에 싱글톤 이야기로 답한다. 지연 초기화의 선택지를 위키가 나란히 정리하면 이렇다.

| 방법 | 안전한 이유 | 비용 · 한계 |
|---|---|---|
| `synchronized getInstance()` | 모니터의 상호 배제 + 해제 → 획득 happens-before | 생성이 끝난 뒤에도 호출할 때마다 모니터를 잡는다. 경합이 없으면 경량 락이라 싸지만, 호출이 몰리면 직렬화된다 |
| double-checked locking | 위 「volatile」 절 참고. 필드가 `volatile`이어야 한다 | 코드가 길고, `volatile`을 빼면 조용히 깨진다 |
| holder 클래스 | JLS §12.4.2의 클래스 초기화 락 | 인자를 받는 초기화에는 못 쓴다. 생성자가 예외를 던지면 복구할 수 없다 |
| `enum` 싱글톤 | 초기화는 holder와 같은 원리. 리플렉션 생성과 직렬화 복제를 언어가 막는다 | 상속할 수 없다. JLS §8.9가 보장한다: "Reflective instantiation of enum classes is prohibited", 역직렬화로 "duplicate instances are never created". Effective Java Item 3이 권한다(2차 자료) |

holder 관용구는 이렇게 생겼다.

```java
public class Singleton {
    private Singleton() {}
    public static Singleton getInstance() { return Holder.instance; }
    private static class Holder {
        static final Singleton instance = new Singleton();
    }
}
```

- 지연되는 이유: 클래스는 static 필드를 처음 쓸 때 초기화된다(JLS §12.4.1 "A static field declared by T is used"). `Singleton`이 로드돼도 `Holder`는 `getInstance()`가 처음 불릴 때까지 초기화되지 않는다.
- 안전한 이유: "For each class or interface C, there is a unique initialization lock LC." 여러 스레드가 동시에 초기화를 시도해도 하나만 `<clinit>`을 실행하고 나머지는 기다린다. JVM이 이 락을 생략하는 최적화도 "all happens-before orderings that would exist if the lock were acquired, still exist"일 때만 허용된다. 자료가 말한 "원자적 특성"을 정확히 옮기면 상호 배제와 happens-before다. 초기화가 끝난 뒤의 호출은 락 없이 필드만 읽는다. 자세한 절차는 [[클래스 로딩]]의 「초기화는 한 번만, 스레드 안전하게」에 있다.
- 실패하면: 생성자가 예외를 던지면 `Holder`는 오류 상태가 되고, 이후 모든 접근이 `NoClassDefFoundError`다(§12.4.2 11~12단계). 다시 시도할 길이 없다.

[JLS SE 25 §12.4.1 · §12.4.2, https://docs.oracle.com/javase/specs/jls/se25/html/jls-12.html#jls-12.4 , 2026-09-27 확인]

## 무엇을 고르나

[[원자성 문제가 나는 시나리오]]의 네 가지 모양과 가시성에 맞춰 위키가 정리한 표다.

| 문제 | 먼저 고를 것 | 그다음 |
|---|---|---|
| 가시성만: 종료 플래그, 설정값 한 개 갱신 | `volatile` | — |
| 읽고-고치고-쓰기: 카운터 | `AtomicInteger`·`AtomicLong` | 쓰기가 몰리면 `LongAdder` |
| 확인 후 행동: 없으면 넣기, 지연 초기화 | `ConcurrentHashMap.computeIfAbsent`·`putIfAbsent` | 컬렉션 밖이면 락, 지연 초기화면 `volatile` DCL 또는 holder 클래스 |
| 여러 값을 함께 바꾸기 | `synchronized` (쓰기와 읽기 모두) | 불변 객체 + `AtomicReference` |
| 기다리는 방법이 중요: 타임아웃·인터럽트·공정성·여러 조건 | `ReentrantLock` | — |

## 면접에서

자료의 Gold 답(Q2·Q2-1·Q2-2)에 아래를 보탠다.

1. 짝짓기는 자료와 같다: volatile ↔ 가시성, synchronized·atomic ↔ 원자성. 다만 volatile은 "캐시 우회"로 설명하지 말고 happens-before를 보장한다고 설명한다. synchronized도 가시성을 준다는 것(해제 → 획득)을 덧붙인다.
2. synchronized의 비용을 "항상 blocking"이라고 하지 않는다. 경합이 없으면 CAS 한 번과 lock-stack push로 끝나는 경량 락이고, 경합이 생기면 스핀하다가 모니터로 부풀어 스레드가 BLOCKED로 가며, 그때 전환 비용이 든다고 말한다.
3. synchronized와 ReentrantLock은 의미가 같다. 차이는 `tryLock`·타임아웃·인터럽트·공정성·여러 `Condition`이고, 대가는 `finally`의 `unlock`이다. "synchronized의 문제점"을 물으면 이 차이를 문제 쪽에서 말하고(데드락에서 못 빠져나옴 등), 락 범위·락 객체 노출·JVM 하나 안에서만 통한다는 점을 덧붙인다.
4. CAS는 경합이 낮으면 lock보다 유리하고 높으면 재시도가 폭주한다. 카운터라면 `LongAdder`를 쓴다. 꼬리 질문으로 ABA가 오면, 값만 비교해서 A → B → A를 알아채지 못하므로 버전을 같이 바꾸는 `AtomicStampedReference`를 쓴다고 답한다.
5. 복합 연산: `ConcurrentHashMap`을 써도 `containsKey` 뒤 `put`은 경쟁하므로 `computeIfAbsent`를 쓴다.
6. 여유가 있으면 biased locking 제거(JEP 374), lightweight locking의 lock-stack(JDK 23 기본), 가상 스레드 pinning 해결(JEP 491)을 말한다.

## 자료의 서술과 정정

| 자료 (쪽) | 판정 | 정정 |
|---|---|---|
| volatile = 캐시 우회, RAM 직접 접근 (p63) | 틀림 | [[동시성 문제]] 참고 |
| atomic은 lock이 없어 성능이 더 좋다 (p63) | 단서 필요 | 경합이 낮을 때만. 높은 경합에서는 `LongAdder` |
| synchronized는 blocking, 상태 전환 비용 (p66) | 틀림(과단순화) | 경합 없으면 lightweight lock(CAS + lock-stack), 경합 시 스핀 → inflate 뒤에야 BLOCKED |
| synchronized 싱글톤은 동시에 생성자에 접근할 때 비효율 (부록 Q4) | 틀림 | 생성 뒤에도 호출마다 모니터를 잡는다. 경합이 없으면 싸다는 단서 |
| LazyHolder = 클래스 초기화의 원자적 특성 (부록 Q4) | 단서 필요 | 초기화 락 LC의 상호 배제 + happens-before (JLS §12.4.2). 생성자 예외 → `NoClassDefFoundError` |
