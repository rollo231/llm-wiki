# 동기화 기법

[[동시성 문제]](가시성·원자성)를 막는 Java의 도구들. 면접 자료는 세 가지를 문제와 짝지어 가르친다
([[Java 면접 4 동시성 이슈]] p61–69).

| 도구 | 막는 문제 | 방식 | 한계 |
|---|---|---|---|
| `volatile` | 가시성 (+ 재정렬) | 컴파일러 최적화 금지 + 메모리 배리어로 happens-before | 원자성은 못 준다 — `volatile int count; count++`는 여전히 깨진다 |
| `synchronized` | 원자성 + 가시성 | 객체의 모니터를 잠가 임계 영역에 한 스레드만 | 경합이 심하면 스레드가 BLOCKED로 대기 |
| atomic 타입 (`AtomicInteger` 등) | 원자성 + 가시성 (변수 하나) | CAS — 기대값이 그대로면 쓰고, 아니면 재시도 | 변수 하나만. 여러 변수를 함께 바꾸는 일은 못 한다. 경합이 심하면 재시도가 몰린다 |

## volatile

"CPU 캐시를 우회해 RAM에 직접 접근한다"는 흔한 설명은 틀렸다 — 정정 전문은 [[동시성 문제]]의 가시성 절에 있다. 요점만: volatile
쓰기와 그 뒤의 같은 변수 volatile 읽기 사이에 happens-before가 생긴다. 그래서 쓴 값이 보이고, volatile 쓰기 **이전의** 일반
쓰기들도 함께 보인다(플래그 하나로 초기화 완료를 알리는 패턴이 이걸로 성립한다).

## synchronized와 모니터

- **모니터** — 모든 객체가 암묵적으로 가진 동기화 장치. 상호 배제(한 번에 한 스레드만 소유)와 조건 동기화(`wait`/`notify`)를
  제공한다. 인스턴스 메서드에 붙이면 `this`의, static 메서드에 붙이면 Class 객체의, 블록이면 지정한 객체의 모니터를 잠근다.
- **바이트코드** — 블록은 `monitorenter`/`monitorexit` 명령, 메서드는 `ACC_SYNCHRONIZED` 플래그로 컴파일된다.
- **HotSpot은 처음부터 막지 않는다.** 자료(p66)는 "blocking이라 runnable → blocked 전환 비용이 든다"고 하지만, 그것은 경합이
  생긴 뒤의 이야기다.
  1. 경합이 없으면 **lightweight lock** — 객체 헤더에 CAS 한 번으로 소유를 표시한다. OS가 개입하지 않는다.
  2. 경합이 생기면 잠시 **스핀**하며 기다려 보고,
  3. 그래도 안 되면 **ObjectMonitor로 inflate**한다. 이때부터 대기 스레드가 BLOCKED 상태로 OS에 맡겨진다.
- **biased locking은 없어졌다** — 한 스레드가 반복해서 잡는 lock을 CAS조차 없이 처리하던 최적화였으나 JDK 15에서 기본 비활성·
  deprecated(JEP 374), JDK 18에서 obsolete가 됐다. 옛 면접 자료에 자주 나오니 "지금은 없다"고 말할 수 있으면 좋다.
- **가상 스레드와의 관계** — JDK 21의 가상 스레드는 `synchronized` 안에서 블로킹하면 캐리어(플랫폼) 스레드에 묶이는
  **pinning** 문제가 있어 `ReentrantLock`을 권장했다. JDK 24(JEP 491)에서 해결됐다. → [[스레드 풀]]

## CAS와 atomic 타입

CAS(Compare-And-Swap)는 "메모리 값이 내가 읽은 값과 같으면 새 값으로 바꾸고, 다르면 실패"를 CPU 명령 하나로 하는 연산이다.
atomic 타입은 실패하면 다시 읽고 재시도한다 — lock 없이(non-blocking) 원자성을 얻는다.

- **"lock이 없으니 synchronized보다 빠르다"(자료 p63)는 경합이 낮을 때만 대체로 맞다.** 경합이 높으면 재시도가 몰리고, 캐시
  라인이 코어 사이를 계속 오가면서 오히려 느려질 수 있다.
- 그래서 JDK 8에 **`LongAdder`**가 들어왔다 — 카운터를 여러 셀로 나눠 스레드마다 다른 셀을 더하고, 읽을 때 합친다. 통계·지표
  카운터처럼 쓰기가 많고 읽기가 드문 곳에 맞는다.
- DB의 낙관적 락(버전 컬럼 비교 후 UPDATE)과 같은 모양이다 — 충돌이 드물면 싸고, 잦으면 재시도 비용이 커진다. *(위키의 연결)*

## 면접에서

자료의 Gold 답(Q2·Q2-1·Q2-2)을 이렇게 보강한다.

1. **짝** — volatile ↔ 가시성, synchronized·atomic ↔ 원자성. 자료와 같다. 단 volatile은 "캐시 우회"가 아니라 "happens-before
   보장"으로 설명한다.
2. **synchronized의 비용** — "항상 blocking"이 아니라 "경합이 없으면 CAS 한 번짜리 경량 락, 경합이 심해지면 모니터로 부풀어
   스레드가 BLOCKED로 가고 그때 전환 비용이 든다"고 말한다.
3. **CAS의 조건** — "경합이 낮으면 lock보다 유리하고, 높으면 재시도 폭주 — 카운터라면 `LongAdder`"까지.
4. 여유가 있으면 — biased locking 제거(JEP 374), 가상 스레드 pinning 해결(JEP 491).

## 자료의 서술과 정정

| 자료 (쪽) | 판정 | 정정 |
|---|---|---|
| volatile = 캐시 우회, RAM 직접 접근 (p63) | 틀림 | [[동시성 문제]] 참고 |
| atomic은 lock이 없어 성능이 더 좋다 (p63) | 단서 필요 | 경합이 낮을 때만. 높은 경합에서는 `LongAdder` |
| synchronized는 blocking, 상태 전환 비용 (p66) | 틀림(과단순화) | 경합 없으면 lightweight lock(CAS), 경합 시 스핀 → inflate 뒤에야 BLOCKED |
| synchronized는 모니터로 구현 (p69) | 맞음 | 바이트코드 `monitorenter`/`monitorexit`, `ACC_SYNCHRONIZED`를 덧붙이면 좋다 |
