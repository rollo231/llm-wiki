# 동기화 기법

[[동시성 문제]](가시성·원자성)를 막는 Java의 도구들. 면접 자료는 앞의 세 가지를 문제와 짝지어 가르친다
([[Java 면접 4 동시성 이슈]] p61–69). 위키는 자료에 없는 두 가지(`ReentrantLock`, 동시성 컬렉션의 복합 연산)를 더했다.

| 도구 | 막는 문제 | 방식 | 한계 |
|---|---|---|---|
| `volatile` | 가시성 (+ 재정렬) | 컴파일러 최적화 금지 + 메모리 배리어로 happens-before | 원자성은 못 준다 — `volatile int count; count++`는 여전히 깨진다 |
| `synchronized` | 원자성 + 가시성 | 객체의 모니터를 잠가 임계 영역에 한 스레드만. 해제 → 획득이 happens-before | 기다리는 동안 포기·타임아웃·인터럽트가 안 된다. 경합이 심하면 BLOCKED |
| `ReentrantLock` | 원자성 + 가시성 | `synchronized`와 같은 의미 + `tryLock`·타임아웃·인터럽트·공정성·여러 `Condition` | `finally`에서 직접 `unlock`해야 한다 |
| atomic 타입 (`AtomicInteger` 등) | 원자성 + 가시성 (변수 하나) | CAS — 기대값이 그대로면 쓰고, 아니면 재시도 | 변수 하나만. 경합이 심하면 재시도가 몰린다. ABA |
| 동시성 컬렉션의 복합 연산 | 원자성 (확인 후 행동) | `computeIfAbsent`·`putIfAbsent`·`merge`가 확인과 행동을 한 연산으로 | 그 컬렉션 안의 연산에만 |

재현 실험은 [[가시성 문제는 지금도 생기나]](volatile)와 [[원자성 문제가 나는 시나리오]](synchronized·atomic·`computeIfAbsent`)에 있다.

## volatile

"CPU 캐시를 우회해 RAM에 직접 접근한다"는 흔한 설명은 틀렸다 — 정정 전문은 [[동시성 문제]]의 가시성 절에 있다. 요점만: volatile
쓰기와 그 뒤의 같은 변수 volatile 읽기 사이에 happens-before가 생긴다. 그래서 쓴 값이 보이고, volatile 쓰기 **이전의** 일반
쓰기들도 함께 보인다(플래그 하나로 초기화 완료를 알리는 패턴이 이걸로 성립한다).

**volatile이 꼭 필요한 곳 둘:**

- **double-checked locking** — 락 밖에서 한 번, 락 안에서 한 번 null을 확인하는 지연 초기화. `volatile`이 없으면 다른 스레드가
  **생성이 덜 끝난 객체**를 볼 수 있다. "the writes that initialize the Helper object and the write to the helper field can be done
  or perceived out of order." JDK 5(JSR-133)부터 "the Double-Checked Locking idiom can be made to work by declaring the helper field
  to be volatile." 객체의 필드가 모두 `final`인 불변 객체면 `volatile` 없이도 된다.
  [Bill Pugh 외, 「The "Double-Checked Locking is Broken" Declaration」, https://www.cs.umd.edu/~pugh/java/memoryModel/DoubleCheckedLocking.html ,
  2026-09-27 확인]
- **공유하는 `long`·`double`** — `volatile`이 없으면 쓰기 하나가 32비트 두 번으로 쪼개질 수 있다. "Writes and reads of volatile `long`
  and `double` values are always atomic." (JLS §17.7) → [[원자성 문제가 나는 시나리오]]

## synchronized와 모니터

- **모니터** — 모든 객체가 암묵적으로 가진 동기화 장치. 상호 배제(한 번에 한 스레드만 소유)와 조건 동기화(`wait`/`notify`)를
  제공한다. 인스턴스 메서드에 붙이면 `this`의, static 메서드에 붙이면 Class 객체의, 블록이면 지정한 객체의 모니터를 잠근다.
- **가시성도 준다** — "An unlock on a monitor happens-before every subsequent lock on that monitor." (JLS §17.4.5) 그래서 같은
  락으로 **쓰기와 읽기를 모두** 감싸야 한다. 쓰기만 감싸고 읽기를 락 밖에서 하면 가시성이 보장되지 않는다.
- **재진입한다** — "A thread t may lock a particular monitor multiple times; each unlock reverses the effect of one lock operation."
  (JLS §17.1) `synchronized` 메서드가 같은 객체의 다른 `synchronized` 메서드를 불러도 스스로 막히지 않는다.
- **바이트코드** — 블록은 `monitorenter`/`monitorexit` 명령, 메서드는 `ACC_SYNCHRONIZED` 플래그로 컴파일된다.

[Oracle, 「The Java Language Specification」 Java SE 21 17장, https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html , 2026-09-27 확인]

### HotSpot은 처음부터 막지 않는다

자료(p66)는 "blocking이라 runnable → blocked 전환 비용이 든다"고 하지만, 그것은 경합이 생긴 뒤의 이야기다. 지금(JDK 23+) 기본인
**lightweight locking**은 이렇게 간다.

1. **경합이 없으면** — 객체 헤더(mark word)의 lock 비트를 CAS 한 번으로 "fast-locked"로 바꾸고, 객체를 **스레드별 lock-stack**(용량 8)에
   push한다. OS가 개입하지 않는다. 같은 스레드가 다시 잡으면(재진입) lock-stack 맨 위가 같은 객체인지만 보고 한 번 더 쌓는다.
2. **경합이 생기면** — inflate하기 전에 잠시 스핀한다("Fast-lock spinning to avoid inflating for short critical sections").
3. **그래도 안 되면** — **ObjectMonitor로 inflate**한다. 모니터에서도 적응형으로 스핀해 보고, 끝내 못 잡으면 대기 스레드가 BLOCKED
   상태로 OS에 맡겨진다.

⚠️ 위키 정정(2026-09-27): 처음에는 "객체 헤더에 CAS 한 번으로 소유를 표시한다"고만 적었다. 이 말은 옛 방식(stack-locking)에도
지금 방식에도 맞지만, 소유를 표시하는 방법이 바뀌었다. 옛 방식은 헤더에 **스레드 스택을 가리키는 포인터**를 넣었다("Current
stack-locking overloads object headers with pointers into the stack"). 지금 방식은 헤더에 lock 비트만 두고 **소유 기록은 lock-stack에** 둔다.

| 릴리스 | 일 | 이슈 |
|---|---|---|
| JDK 21 | 새 방식(`LM_LIGHTWEIGHT`) 추가 — 기본은 여전히 옛 방식 | JDK-8291555 |
| JDK 23 | 기본값을 `LM_LIGHTWEIGHT`로. 재진입 지원 | JDK-8319251 · JDK-8319796 |
| JDK 24 | `LockingMode` 옵션과 옛 방식 deprecated | JDK-8334299 |
| JDK 26 | `LockingMode`를 사용자가 설정할 수 없게 하고 옛 방식 코드 제거 | JDK-8359437 외 |

로컬 OpenJDK 25.0.2의 `-XX:+PrintFlagsFinal`은 `LockingMode = 2`(lightweight, 기본값)다.
[OpenJDK JBS 각 이슈(REST API로 fix version 확인), https://bugs.openjdk.org/browse/JDK-8291555 ; HotSpot 소스 `src/hotspot/share/runtime/synchronizer.cpp`
(`cas_set_mark(fast_locked_mark, …)` 뒤 "Successfully fast-locked, push object to lock-stack") · `lockStack.hpp`(`CAPACITY = 8`),
https://github.com/openjdk/jdk , master, 2026-09-27 확인]

- **biased locking은 없어졌다** — 한 스레드가 반복해서 잡는 lock을 CAS조차 없이 처리하던 최적화였으나 JDK 15에서 기본 비활성·
  deprecated(JEP 374), JDK 18에서 obsolete가 됐다. 옛 면접 자료에 자주 나오니 "지금은 없다"고 말할 수 있으면 좋다.
- **가상 스레드와의 관계** — JDK 21의 가상 스레드는 `synchronized` 안에서 블로킹하면 캐리어(플랫폼) 스레드에 묶이는
  **pinning** 문제가 있어 `ReentrantLock`을 권장했다. JDK 24(JEP 491)에서 해결됐다. → [[스레드 풀]]

## ReentrantLock

"the same basic behavior and semantics as the implicit monitor lock accessed using `synchronized` methods and statements, but with
extended capabilities." 가시성도 같다 — "All `Lock` implementations must enforce the same memory synchronization semantics as provided
by the built-in monitor lock". 차이는 **기다리는 방법**에 있다.

| | `synchronized` | `ReentrantLock` |
|---|---|---|
| 재진입 | 된다 | 된다 (hold count가 1씩 는다) |
| 못 잡으면 바로 포기 | 안 된다 | `tryLock()` |
| 기다리다 시간 초과 | 안 된다 | `tryLock(timeout, unit)` |
| 기다리다 인터럽트 | 안 된다 | `lockInterruptibly()` |
| 공정성(오래 기다린 순서) | 없다 | `new ReentrantLock(true)` — 대신 처리량이 "often much slower" |
| 조건 대기 | 객체 하나에 대기실 하나(`wait`/`notify`) | `newCondition()`으로 여러 개 — "the effect of having multiple wait-sets per object" |
| 풀기 | 블록을 나가면 자동 | **직접** — "always immediately call unlock as the first statement in the finally block" |

- 공정 락이어도 **시간 제한 없는 `tryLock()`은 공정성을 무시**한다("does not honor the fairness setting").
- 고르는 법 *(위키의 정리)*: 기본은 `synchronized`(짧고 실수할 곳이 없다). 타임아웃·인터럽트·공정성·여러 조건 가운데 하나라도
  필요하면 `ReentrantLock`. "가상 스레드라서 `ReentrantLock`"은 JDK 24부터는 이유가 아니다.

[Oracle, Java SE 25 API — `java.util.concurrent.locks.ReentrantLock` · `Lock` · `Condition`,
https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/locks/ReentrantLock.html , 2026-09-27 확인]

## CAS와 atomic 타입

CAS(Compare-And-Swap)는 "메모리 값이 내가 읽은 값과 같으면 새 값으로 바꾸고, 다르면 실패"를 원자적으로 하는 연산이다.
atomic 타입은 실패하면 다시 읽고 재시도한다 — lock 없이(non-blocking) 원자성을 얻는다.

- **"CPU 명령 하나"는 x86에서만 그대로 맞다.** x86은 `lock cmpxchg` 한 명령이다. AArch64는 CPU가 LSE(ARMv8.1)를 지원하면 CAS 한 명령이고,
  아니면 `ldaxr`/`stlxr`(배타적 읽기·쓰기)를 실패할 때마다 되풀이하는 루프다. HotSpot은 LSE를 지원하는 CPU에서 자동으로 `UseLSE`를
  켠다(로컬 Apple Silicon JDK 25: `UseLSE = true`). [HotSpot 소스 `src/hotspot/cpu/aarch64/macroAssembler_aarch64.cpp`의
  `MacroAssembler::cmpxchg`, `src/hotspot/cpu/x86/x86.ad`, master, 2026-09-27 확인]
- **"lock이 없으니 synchronized보다 빠르다"(자료 p63)는 경합이 낮을 때만 대체로 맞다.** 경합이 높으면 재시도가 몰리고, 캐시
  라인이 코어 사이를 계속 오가면서 오히려 느려질 수 있다.
- 그래서 JDK 8에 **`LongAdder`**가 들어왔다 — 카운터를 여러 셀로 나눠 스레드마다 다른 셀을 더하고, 읽을 때 합친다. 통계·지표
  카운터처럼 쓰기가 많고 읽기가 드문 곳에 맞는다.
- **`updateAndGet`·`accumulateAndGet`에 넘기는 함수는 부작용이 없어야 한다** — "it may be re-applied when attempted updates fail due to
  contention among threads." 재시도 때 함수가 다시 불리기 때문이다. 안에서 로그를 쓰거나 카운터를 올리면 여러 번 일어난다.
- DB 낙관적 락과 같은 모양이라는 연결은 [[동시성 문제]]의 원자성 절에 있다. 충돌이 드물면 싸고 잦으면 재시도 비용이 커지는 것도
  같다. *(위키의 연결)*

### ABA 문제

CAS는 "값이 **같은지**"만 본다. 그 사이에 A → B → A로 바뀌었다 돌아와도 "안 바뀌었다"고 보고 성공한다. 값만 중요한 카운터에서는
상관없지만, lock-free 스택처럼 "그 사이에 구조가 바뀌었는가"가 중요한 곳에서는 틀린 결과를 낸다.

- 해법은 값과 함께 **버전을 바꾸는 것**이다. `AtomicStampedReference`는 참조와 정수 "stamp"를 함께 원자적으로 바꾼다 — 패키지 문서는
  이 stamp를 "version numbers corresponding to series of updates"에 쓸 수 있다고 적는다. `AtomicMarkableReference`는 boolean 하나를
  붙인다("logically been deleted" 표시). DB 낙관적 락의 **버전 컬럼**과 같은 생각이다. *(위키의 연결)*
- javadoc에는 "ABA"라는 단어가 없다. "Java는 GC가 있어서 참조의 ABA가 C보다 드물다"(해제된 주소가 바로 재사용되지 않으므로)는 널리
  쓰이는 설명이지만 1차 자료로 확인하지 못했다.

[Oracle, Java SE 25 API — `java.util.concurrent.atomic` 패키지 · `AtomicStampedReference` · `AtomicReference`,
https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/package-summary.html , 2026-09-27 확인]

### 여러 값을 함께 바꿀 때

atomic 패키지는 스스로 "lock-free thread-safe programming on **single variables**"라고 밝힌다. 필드 둘을 같이 바꿔야 하면
(→ [[원자성 문제가 나는 시나리오]]의 「여러 값을 함께 바꾸기」) 두 길이 있다 *(위키의 정리 — javadoc이 이 패턴을 직접 권하지는 않는다)*:

- 같은 락으로 쓰기와 읽기를 모두 감싼다.
- 두 값을 **불변 객체 하나**로 묶고 `AtomicReference`로 그 참조를 한 번에 바꾼다(`updateAndGet(old -> new Range(...))`).

### 안쪽 구현

JDK 9(JEP 193)에 `VarHandle`이 들어와 `java.util.concurrent`가 `Unsafe` 대신 쓰기 시작했다(JDK-8080603). 다만 클래스마다 다르다.
`AtomicReference`는 `VarHandle`을 쓰고, `AtomicInteger`·`AtomicLong`은 지금도 `jdk.internal.misc.Unsafe`를 쓴다 — 소스 주석:
"This class intended to be implemented using VarHandles, but there are unresolved cyclic startup dependencies." 면접에서는 "직접
CAS를 쓸 일이 있으면 `VarHandle`"까지만 알면 된다. [OpenJDK JEP 193, https://openjdk.org/jeps/193 ; `AtomicInteger.java` · `AtomicReference.java`,
https://github.com/openjdk/jdk , master, 2026-09-27 확인]

## 무엇을 고르나

[[원자성 문제가 나는 시나리오]]의 네 가지 모양과 가시성에 맞춘다 *(위키의 정리)*.

| 문제 | 먼저 고를 것 | 그다음 |
|---|---|---|
| 가시성만 — 종료 플래그, 설정값 한 개 갱신 | `volatile` | — |
| 읽고-고치고-쓰기 — 카운터 | `AtomicInteger`·`AtomicLong` | 쓰기가 몰리면 `LongAdder` |
| 확인 후 행동 — 없으면 넣기, 지연 초기화 | `ConcurrentHashMap.computeIfAbsent`·`putIfAbsent` | 컬렉션 밖이면 락, 지연 초기화면 `volatile` DCL 또는 holder 클래스 |
| 여러 값을 함께 바꾸기 | `synchronized` (쓰기와 읽기 모두) | 불변 객체 + `AtomicReference` |
| 기다리는 방법이 중요 — 타임아웃·인터럽트·공정성·여러 조건 | `ReentrantLock` | — |

## 면접에서

자료의 Gold 답(Q2·Q2-1·Q2-2)을 이렇게 보강한다.

1. **짝** — volatile ↔ 가시성, synchronized·atomic ↔ 원자성. 자료와 같다. 단 volatile은 "캐시 우회"가 아니라 "happens-before
   보장"으로 설명한다. synchronized도 가시성을 준다는 것(해제 → 획득)을 덧붙인다.
2. **synchronized의 비용** — "항상 blocking"이 아니라 "경합이 없으면 CAS 한 번과 lock-stack push로 끝나는 경량 락, 경합이 생기면
   스핀하다 모니터로 부풀어 스레드가 BLOCKED로 가고 그때 전환 비용이 든다"고 말한다.
3. **synchronized vs ReentrantLock** — 의미는 같고, 차이는 `tryLock`·타임아웃·인터럽트·공정성·여러 `Condition`. 대가는 `finally`의 `unlock`.
4. **CAS의 조건** — "경합이 낮으면 lock보다 유리하고, 높으면 재시도 폭주 — 카운터라면 `LongAdder`"까지. 꼬리 질문 ABA에는
   "값만 비교해서 A → B → A를 못 알아챈다, 버전을 같이 바꾸는 `AtomicStampedReference`"로 답한다.
5. **복합 연산** — "`ConcurrentHashMap`을 써도 `containsKey` 뒤 `put`은 경쟁한다" → `computeIfAbsent`.
6. 여유가 있으면 — biased locking 제거(JEP 374), lightweight locking의 lock-stack(JDK 23 기본), 가상 스레드 pinning 해결(JEP 491).

|---|---|---|
| volatile = 캐시 우회, RAM 직접 접근 (p63) | 틀림 | [[동시성 문제]] 참고 |
| atomic은 lock이 없어 성능이 더 좋다 (p63) | 단서 필요 | 경합이 낮을 때만. 높은 경합에서는 `LongAdder` |
| synchronized는 blocking, 상태 전환 비용 (p66) | 틀림(과단순화) | 경합 없으면 lightweight lock(CAS + lock-stack), 경합 시 스핀 → inflate 뒤에야 BLOCKED |
| synchronized는 모니터로 구현 (p69) | 맞음 | 바이트코드 `monitorenter`/`monitorexit`, `ACC_SYNCHRONIZED`를 덧붙이면 좋다 |

근거 (2026-09-26 확인, 위 본문에 인용한 것은 2026-09-27):

- `LongAdder` javadoc, JDK 25 — "under high contention, expected throughput of this class is significantly higher" —
  https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/atomic/LongAdder.html
- JEP 374 Deprecate and Disable Biased Locking (JDK 15) — https://openjdk.org/jeps/374
- JDK-8256425 Obsolete Biased Locking in JDK 18 — https://bugs.openjdk.org/browse/JDK-8256425
- JEP 491 Synchronize Virtual Threads without Pinning (JDK 24) — https://openjdk.org/jeps/491
- JDK 25 기본값 `LockingMode=2`(lightweight)는 로컬 OpenJDK 25.0.2의 `-XX:+PrintFlagsFinal`로 확인. `LockingMode` 플래그는 JDK 24에서
  deprecated, JDK 26에서 사용자가 설정할 수 없게 됐다(위 표).
