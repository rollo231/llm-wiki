# Data integration tools

[[ETL and ELT]]는 **순서**를 말하고 [[Change data capture]]는 **추출 방식**을 말한다. 여기는 그
일을 실제로 하는 **도구들의 축**이다.

⭐ **"데이터를 옮기고 다듬는다"는 목적은 같은데 주력하는 지점이 다르다. 성능 순위로 매기면 선택이
어려워진다.**

## 축 셋 — 우리 과제가 어떤 모양인가

| | 초점 | 이럴 때 |
|---|---|---|
| 🔹 **NiFi** | **시각적 수집·라우팅·흐름 운영** | 파일·장비·프로토콜이 섞이고 **운영 추적이 중요**하다 |
| 🔸 **Hop** | **시각적 ETL 변환** | 전통 ETL 방식으로 변환을 조립하고 싶다 |
| ▪️ **SeaTunnel** | **배치·스트림·CDC 통합 동기화** | 여러 저장소 사이를 배치·CDC로 맞추는 일이 주다 |

> "우리 과제가 **'잡다한 소스 라우팅'인지, '테이블 변환 UX'인지, '다양한 커넥터 동기화'인지**부터
> 정하는 것이 가이드의 시작이다."

⚠️ **Flink CDC처럼 더 특화된 도구가 이미 있다면 그 축은 중복하지 않는다.** 팀 표준이 이미
Kafka Connect·Flink CDC로 고정돼 있으면 SeaTunnel을 고르는 것은 중복이다.

## 도구별로 무엇인가

### NiFi — 눈으로 짜는 수집·라우팅

수집·변환·라우팅·전달을 **시각적 캔버스**에서 조립하는 Dataflow 플랫폼. 프로세서(처리 상자)를 연결해
파일·로그·API 응답을 흘려보내고, **어디서 막혔는지 화면으로 추적한다.**

- **시각적 흐름** — 프로세서와 연결선으로 파이프라인 설계
- **라우팅** — 조건에 따라 다른 목적지로 분기
- **추적** — 데이터가 어디서 지연·실패했는지 확인. 운영·보안·**감사 흔적**까지 염두
- **수집 허브** — 다양한 프로토콜·파일 형식을 한곳에서 받음

⭐ 전형적 진입 패턴: **출처가 잡다할 때, 통합 코드베이스를 키우기 전에 NiFi로 데이터 경로를 먼저
설정하고 출발한다.** 이후 Kafka·오브젝트 스토리지·DB로 내보낸다.

### Hop — 시각적 ETL 변환

읽기·조인·필터·집계·쓰기 스텝을 캔버스에서 조립하는 ETL 플랫폼. **환경(개발·운영)별 설정**으로 분리
실행하고, **메타데이터 중심 설계**로 같은 파이프라인을 다른 엔진·환경에 맞게 돌린다.

맞는 상황: 코드보다 시각적 변환이 협업에 유리한 팀, 특히 **기존 ETL 도구에 익숙한 팀이 그 방식을
이어 가고 싶을 때.**

### SeaTunnel — 배치·스트림·CDC 통합 동기화

풀려는 문제: **배치 잡 하나, 스트림 잡 하나, CDC 잡 하나가 제각각 따로 만들어지기 쉽다.**
소스에서 읽어 변환한 뒤 싱크로 보내는 구조를 반복 사용하게 해, **매번 처음부터 짜는 비용을 줄인다.**

판단 기준: **"이동·동기화 작업을 얼마나 한 패턴으로 모을 수 있는가."**

### ⚠️ Camel — 데이터 도구가 아니다

엔드포인트를 **라우트(from/to)** 로 연결하는 **엔터프라이즈 애플리케이션 통합** 프레임워크.
EIP(기업 통합 패턴)의 구현체이고, 수백 가지 컴포넌트로 HTTP·파일·메시지 큐·메일·SaaS API의 프로토콜
차이를 흡수한다. Java DSL·YAML로 경로를 선언한다.

⭐ **"'데이터 수집 도구'와 '애플리케이션 통합 프레임워크'를 구분한다. 같은 '연결'이라도 목적과 담당
범위가 다르다."** 레이크·CDC·오케스트레이션 중심이면 NiFi·Flink CDC·[[Apache Airflow]]가 더 적합하고,
Camel은 **레거시·B2B·프로토콜이 복잡한 엔터프라이즈 통합**이 과제일 때다.

> "Camel은 애플리케이션 통합 쪽으로 두고, **데이터 플랫폼 도구와 섞지 않는 편이 낫다.**"

## ⚠️ 두 개를 쓰려면 경계를 문서에 고정한다

> "한 조직이 도구를 두 개 쓰는 것도 가능하지만, **경계를 명확히 하지 않으면 비용만 커진다.**
> 예: '데이터 소스 수집은 NiFi, 대량 동기화는 SeaTunnel'처럼 **역할을 문서에 고정해 두면 된다.**"

이것이 이 층의 유일한 운영 규칙이다 — 도구를 줄이는 게 아니라 **경계를 적어 두는 것.**
[[Data orchestration]]의 역할 3분할과 같은 형태의 처방이고, 같은 이유로 작동한다.

## 무엇도 오케스트레이터가 아니다

이 페이지의 도구 전부가 **"언제, 어떤 의존으로 돌릴지"는 담당하지 않는다.**
그건 [[Data orchestration]]의 일이다 — SeaTunnel도, Hop도 [[Apache Airflow]]를 대체하지 않고,
*"Hop은 그 안에서 실제 변환 작업을 담당한다."*
