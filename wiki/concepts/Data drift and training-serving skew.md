# Data drift and training-serving skew

배포된 모델의 성능이 떨어지는 원인 두 가지. **둘은 다른 문제이고 해법도 다르다** — 강의가 이 둘을
한 챕터에 묶은 이유는 증상이 똑같아서다: **에러 로그가 0건인데 모델만 조용히 망가진다.**

| | Training-Serving Skew | Data Drift |
|---|---|---|
| 무엇이 다른가 | **우리 코드**가 학습과 서빙에서 다르게 동작한다 | **세상**이 변해서 입력 데이터가 달라진다 |
| 시점 | 배포 순간부터 이미 틀렸다 | 시간이 지나며 서서히/갑자기 |
| 해법 | 파이프라인 일원화 ([[Feature store]]) | 모니터링 + 재학습 |

## Training-Serving Skew — 침묵의 살인자

학습에 쓴 데이터/전처리 로직이 서빙 환경의 실시간 데이터/로직과 **일치하지 않아** 예측 성능이
떨어지는 현상.

### 왜 필연적으로 생기나 — 두 환경의 구조적 차이

| | 학습 (연구실) | 서빙 (운영) |
|---|---|---|
| 누가 | 데이터 사이언티스트 | 백엔드·플랫폼 엔지니어 |
| 데이터 | 과거 데이터 (batch), 대용량 이력 | 실시간 데이터 (streaming), 건별 |
| 언어·도구 | Python · Pandas · Spark | Java · Go · C++ |
| 지연 허용 | 복잡한 집계, 고지연 OK | 단순화, 초저지연(ms) |

**핵심 원인은 언어와 환경이 달라 같은 로직을 이중으로 구현하는 것이다.** 사람도 다르고 언어도
다르니 미세한 처리 차이가 생긴다.

### 강의의 사례 — 33배 뻥튀기

"최근 30일 평균 결제액" 피처. 구매 100만 → 취소 -100만 → 구매 2만 이 발생했을 때:

| | 로직 | 계산 | 결과 |
|---|---|---|---|
| 학습 | 구매 - 취소 = 순매출 | (100만 - 100만 + 2만) / 1건 | **20,000원** → 소액 구매 고객(정상) |
| 서빙 | **취소 미반영**(누락) | (100만 + 100만 + 2만) / 3건 | **673,333원** → VIP 고객(오판) |

서빙 개발자가 '취소 예외처리'를 빠뜨린 것만으로 평균 금액이 33배가 됐다. 결과는 고가 상품 추천
실패 — 강의 제시 수치로 CTR 5.5% 기대 → 1.2%, CVR 0.3%.

**시스템 에러 로그는 0건이다.** 그래서 기존 IT 모니터링으로는 절대 잡히지 않는다.

### 해법 — [[Feature store]]로 파이프라인 일원화

피처 변환 로직을 **한 곳에 정의**하고, 학습은 offline store에서 서빙은 online store에서 **같은
로직의 결과**를 읽는다. 원칙: **Write Once, Compute Anywhere.**

실무 체크리스트 3종:

- **피처 계약(Feature Contract) 명문화** — 스키마, 윈도우 크기, 예외 처리 규칙을 데이터 정의서로.
- **동일 코드·라이브러리 재사용** — 학습과 서빙이 공유하는 공통 라이브러리 구축.
- **오프라인-온라인 통계 모니터링** — 서빙 데이터의 분포가 학습 데이터와 달라지는지 실시간 감시.

## Data Drift vs Concept Drift

파이프라인이 완벽해도 **입력되는 데이터 자체가 변하면** 모델은 낡는다.
강의의 표현: **모델에도 유통기한이 있다. 성능 저하는 버그가 아니라 시간의 함수다.**

### Data Drift — 입력 분포의 변화 (Covariate Shift)

입력값 `P(X)`의 통계적 분포가 학습 시점과 달라진다. 징후: 이전에 없던 카테고리·행동, 특정 연령층·
시간대 비중 급변, 계절성/트렌드 이동.

> **사례 — 코로나19 마스크 대량 구매.** 2019년 학습 데이터에서 마스크 대량 구매는 희귀 패턴이라
> '사기/매점매석'으로 판정됐다. 2020년에는 생존을 위한 필수 행동인데도 모델은 여전히 사기로 차단한다
> → 정상 거래 오탐지(false positive). **세상은 변했는데 AI는 과거의 기준을 고수한다.**

### Concept Drift — X와 Y의 관계 변화

입력 분포는 그대로여도 **정답을 결정하는 기준선(decision boundary)** 자체가 이동한다 —
`P(Y|X)` 가 변한다.

> **사례 — 스팸 메일의 진화.** 과거엔 "당첨! 100% 무료 증정" 같은 명확한 키워드로 쉽게 분류됐다.
> 지금은 "CJ대한통운 배송 안내입니다"처럼 일상적인 단어를 쓰면서 클릭 시 악성 링크로 보낸다.
> 입력(X)은 비슷해 보이지만 **결과값(Y)의 기준이 완전히 뒤바뀌었다.**

**발생 유형 3종:** Sudden(락다운처럼 순식간) · Gradual(인플레이션·트렌드처럼 서서히) ·
Recurrent(블랙프라이데이·계절처럼 반복).

### 원인 — 외부와 내부

| 환경적(외부) | 비즈니스적(내부) |
|---|---|
| 팬데믹·사회적 이슈 | 마케팅 캠페인 (신규 사용자층 급증) |
| 경기 변동·인플레이션 (가격 민감도) | 제품 UI/UX 개편 (클릭 로그 패턴 변화) |
| 규제·정책 변화 (수집 환경 변화) | 가격 정책·서비스 변경 |
| 계절성 | **데이터 파이프라인 변경** (로깅 로직 수정, 단위 cm→m) |

> ⚠️ **마지막 항목이 데이터 엔지니어에게 가장 중요하다.** 우리가 로깅을 고치거나 단위를 바꾸는
> 엔지니어링 작업이 곧 drift의 원인이 된다. 즉 drift는 외부에서만 오는 게 아니다.

## 감지 — 직감이 아닌 통계 지표

기준 분포(학습 시점)를 저장해두고 실시간 분포와 비교한다.

- **PSI** (Population Stability Index) — 강의가 임계값 예시로 드는 지표. `PSI > 0.2` 면 재학습 트리거.
- **KL Divergence** · **KS Test** · **Chi-square**.

## 방어 — Self-Healing MLOps

**재학습 트리거 3종:** drift 임계치 초과(PSI > 0.2) · 성능 저하 감지(Accuracy/F1 하락) ·
스케줄/이벤트(정기 업데이트, 시즌 이슈).

트리거되면 5단계가 자동으로 돈다:

1. **데이터 수집** — 최신 피처/라벨 로드, 품질·스키마 검증, 데이터셋 버전 관리
2. **모델 학습** — 전처리 파이프라인 실행, 하이퍼파라미터 튜닝, 재현 가능한 환경
3. **모델 평가** — Champion vs Challenger, 오프라인 지표 검증, 공정성/바이어스 체크
4. **배포** — 카나리/블루-그린, 섀도우 모드 테스트, 자동 롤백 가드레일
5. **관측성** — 실시간 추론 모니터링, 피드백 루프, 로그·트레이스

**자동화의 안전장치 두 개:**

- **쿨다운(cool-down) 기간** — 무분별한 재학습 방지.
- **Human-in-the-loop** — 고위험군 모델 배포 시 전문가 승인 의무화.

## 데이터 엔지니어 역할의 이동

강의의 프레이밍: **단순 '배관공'에서 '데이터 품질 및 거버넌스 지휘자'로.**

핵심 책임 3축 — 신선도·품질 관리(SLO 정의, Data Contract 수립) / [[Feature store]] 거버넌스
(재사용성·표준화, lineage 추적, ground truth 피드백) / 재학습 오케스트레이션(drift 기반 트리거 설계,
모델 버전 관리, FinOps).

문화는 **Data as a Product** — 데이터를 부산물이 아니라 내부 고객(데이터 사이언티스트·모델)이
쓰는 '제품'으로 관리한다. KPI 예시: **MTTD(drift 감지) < 10분 · MTTR(복구·재학습) < 4시간 ·
데이터 다운타임 99.9% uptime.**

## 열린 질문

- **Feature Store가 skew를 정말 없애나?** offline·online 두 스토어를 두는 순간 **두 스토어 간
  일치**는 여전히 보장해야 할 문제로 남는데, 강의는 "Write Once, Compute Anywhere"로 넘어간다.
  Part 2 Ch5가 "Feature Store은 만능이 아니다"를 다룰 예정이라 그때 채운다.
- **PSI > 0.2 의 근거** — 강의가 임계값을 제시하지만 출처나 도출 방식은 없다.
