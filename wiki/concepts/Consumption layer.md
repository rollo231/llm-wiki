# Consumption layer

**데이터가 사람·앱에 도달하는 마지막 계층.** [[Analytical data storage tiers|레이크하우스]]에 잘
쌓아 두는 것과, 그것을 **어떤 형태의 조회로 내보내는지**는 별개의 설계 문제다.

⭐ **이 층을 가르는 축은 제품이 아니라 조회 형태(query shape)다.**

> "한 제품에 검색·집계·서비스 저장을 한꺼번에 맡기면 **성능과 운영이 오히려 복잡해질 수 있다.**"

## 조회 형태 6종

| 조회 형태 | 질문의 모양 | 맞는 기술 |
|---|---|---|
| **문장 검색** | "상품명에 이 단어가 든 것, 관련도 순으로" | [[Apache Lucene]] · Solr |
| **실시간 숫자 집계** | "지금 무슨 일이 얼마나 일어나고 있나" | Druid · Pinot |
| **사전 집계** | "매번 같은 조건으로 같은 합계를" | Kylin |
| **키 조회** | "이 사용자 ID의 최근 활동" | [[Apache Cassandra]] · [[Apache HBase]] |
| **시계열 구간** | "지난 10분 평균 온도, 진동이 기준을 넘은 시간대" | IoTDB |
| **메모리 반복 조회** | "같은 값을 계속 읽는다" | Ignite · [[Redis]] |
| *(폭넓은 SQL 분석)* | "조건을 그때그때 바꿔 가며 탐색" | → [[SQL execution layer]] |

⭐ **판단 방법이 구체적이다** — 필요한 기능을 **문장으로 적고** 그 문장에 직접 연결되는 기술부터 본다.

> "'상품명 검색', '실시간 매출 집계', '사용자 ID 조회'처럼 구체적인 문장으로 정리해 두면 된다.
> **제품 이름을 비교하기 전에 서비스에서 가장 자주 발생하는 조회가 무엇인지** 먼저 확인하면 선택
> 범위를 줄일 수 있다."

## 실시간 OLAP 서빙 4종 — 축은 "누가 언제 보는가"

| | 정체 | 가르는 질문 |
|---|---|---|
| **Druid** | 실시간 이벤트 관측형 OLAP. 시간으로 잘라 저장, 구간·롤업·필터 | **운영자·분석가**가 넓은 기간을 훑는 **내부 대시보드** |
| **Pinot** | 초저지연·고동시성 사용자 대면 OLAP. 스트림 적재 후 즉시 색인 | **앱 사용자**가 각자의 결과를 여는 **제품 화면** |
| **Kylin** | 차원 조합을 **큐브**로 미리 계산해 두는 OLAP 엔진 | 조회 **조건이 일정한** 고정 리포트 |
| **Doris** | 자체 저장·테이블 모델을 가진 MPP 웨어하우스 → [[SQL execution layer]] | **폭넓은 SQL 분석** — 위 셋과 따로 비교한다 |

Druid와 Pinot의 판단 기준은 성능 수치가 아니라 셋이다 — **결과를 보는 사람 · 동시에 들어오는 요청
수 · 허용할 수 있는 응답 시간.** 업무가 일부 겹치므로 경계가 딱 갈리지는 않는다. 처음부터 둘 다
도입할 필요는 없고, 같은 이벤트라도 내부 대시보드와 제품 화면의 조회 방식이 크게 달라지면 그때
엔진을 나눈다.

⚠️ **Kylin의 큐브는 [[Dimensional modeling]]의 차원 조합을 미리 물질화한 것이다.** 그래서 같은
약점을 물려받는다 — **조회 조건이 바뀌면 큐브를 다시 설계하고 다시 만들어야 하고, 큐브가 많아질수록
저장 공간과 생성 시간이 늘어난다.** 탐색형 분석에는 맞지 않는다. 오늘날 같은 요구를 레이크하우스·
실시간 OLAP·MPP 웨어하우스도 처리하지만, **반복되는 집계를 미리 계산한다는 원리 자체는 여전히
유효하다.**

## 특화 저장소 둘

- **IoTDB** — 산업·IoT 시계열. 초당 여러 번 들어오는 센서 값을 압축 저장하고 시간 창·다운샘플·집계로
  읽는다. **공장·라인·설비·센서의 소속 관계를 계층형 경로로 표현**한다. ⚠️ 범용 OLTP·전문 검색·자유
  조인 분석용이 아니다. Druid·Pinot도 시간에 쌓이는 이벤트를 다루지만 목적은 대시보드·서비스용
  집계다 — **"장치에서 반복해 들어오는 측정값"** 이 IoTDB의 자리다.
- **Ignite** — 여러 서버의 메모리를 하나의 분산 저장 공간처럼 쓰는 인메모리 컴퓨팅·캐시. 데이터가
  있는 서버에서 계산까지 수행한다. **[[Redis]]와 역할이 겹치지만 분산 SQL·컴퓨팅·디스크 저장 옵션까지
  더 넓다** — ⚠️ 기능이 많은 만큼 데이터 배치·메모리 사용량·장애 복구를 세밀하게 운영해야 한다.
  도입은 **용도를 하나로 제한**하는 편이 낫다. → [[Caching strategies]]

## 사람에게 도달하는 마지막 칸 — BI와 노트북

위 표의 어느 저장소를 쓰든, 마지막에는 사람이 본다. 그 층도 둘로 갈린다.

| | 역할 |
|---|---|
| **[[Apache Superset]]** | **공유·운영 대시보드.** 고정된 리포트의 기준. 다중 소스를 하나의 BI 화면에 |
| **Zeppelin** · Jupyter | **실험용 노트북.** 대시보드로 고정하기 전, 가설 검증과 중간 과정 기록 |

⭐ 흔한 배치는 **운영 리포트의 기준은 BI에, 깊은 탐색은 노트북으로 분리**하는 것이다.
⚠️ **"노트북만으로 전사 소비를 맡기면 버전 관리와 권한이 흐트러지기 쉽다."**
⚠️ 반대로 **BI가 거버넌스를 대신하지 않는다** — 잘못된 집계 정의·중복 대시보드·과도한 권한은 BI 안에서도
반복된다 → [[Data catalog and semantic layer]]

## ⭐⭐ 또 하나의 다이얼 — 오차를 허용할 것인가

조회 형태를 정하고 나면 **정확도**라는 다이얼이 남는다. *"정확한 유니크 수를 매번 전체를 저장해
계산하면, 스트림처럼 서로 다른 값이 매우 많은 데이터에서 비용이 크게 늘어난다."*

**Apache DataSketches**는 카디널리티·분위수·빈도를 **작은 요약(스케치)으로 근사**하는 알고리즘
라이브러리다.

- **근사 집계** — 유니크 수·분위수를 작은 메모리로 추정
- ⭐ **병합 가능** — 파티션·시간 구간 스케치를 **합쳐서** 확장한다
- Druid·Pinot·웨어하우스·스트림 엔진이 이런 스케치를 **내부 또는 확장으로 활용**한다

⚠️ **"정확한 조인·재무 결산에는 부적합하지만 대시보드·모니터링에는 잘 맞는다."**

> ⭐⭐ **판단은 기술이 아니라 합의다 — "오차를 허용할 수 있는지부터 합의해 두면 된다."**
> 허용되면 스케치 계열이 비용 대비 효과가 크고, 허용되지 않으면 정확한 집계나 별도 집계 테이블이 맞다.

⭐ 이것은 [[Batch and stream processing]]의 **"최대 허용 지연을 숫자로 정하라"** 와 **같은 형태의
처방**이다. 이 층에는 미리 합의할 숫자가 둘 있다 — **허용 지연**과 **허용 오차.**
→ [[Data SLA and observability]]

### 같은 다이얼의 두 번째 사례 — 공간 조인 (2026-08-19)

[[Apache Sedona]] 문서가 **정확히 같은 형태의 처방**을 공간 조인에 내놓는다. 기하를 S2 셀 ID 집합으로
바꿔 `explode` 하면 공간 술어가 **평범한 equi-join**이 된다.

- 셀 레벨을 낮추면 → 셀이 커지고, 행이 줄고, **false positive가 늘어난다**
- 정확한 술어(`ST_Contains`)로 refine 하면 정확해지고, **생략하면 빨라진다**
- 문서가 생략을 명시적으로 허가한다 — *"You can skip this step if you don't need 100% accuracy."*

⭐ 즉 **근사 집계(스케치)가 카디널리티에 하는 일을 셀 ID가 공간 관계에 한다.** 다이얼의 구조가 같다 —
요약으로 바꾸고, 병합/조인 가능하게 만들고, 오차를 합의로 처리한다.
→ [[Spatial join execution]], [[Apache Sedona docs - Spatial join execution]]

## ⭐ 팬아웃은 중복이 아니라 설계다

> "하나의 플랫폼에서 여러 기술을 함께 쓰는 것은 자연스럽다. **같은 원본 데이터를 복제하더라도 검색용
> 색인, 집계용 테이블, 키 조회용 저장소는 각각 다른 방식으로 구성된다.**"

즉 이 층에서 데이터 복제는 정규화 위반이 아니라 **조회 형태별 물질화**다. [[Medallion architecture]]의
gold 층이 하나의 테이블이 아니라 **여러 형태의 사본**으로 갈라지는 지점이 여기다.

역할을 억지로 합치지 않는 것이 원칙이다 — *"OLAP 엔진에 검색 기능을 억지로 추가하기보다 검색 서버를
별도로 두는 편이 관리하기 쉽다. 숫자 집계는 OLAP 엔진이, 텍스트 검색과 결과 순위는 Solr가 담당하도록
역할을 나눈다."*

### ⚠️ 팬아웃의 값 — 소스가 말하지 않는 부분

사본이 늘면 **사본마다** 신선도·정합성·권한이 따로 생긴다.

- **어느 사본이 기준인가** — [[SQL execution layer]]가 이미 경고한 *"어떤 테이블의 기준 데이터가
  어디에 있는지"* 문제가 여기서 N배가 된다. → [[Data catalog and semantic layer]]의 리니지
- **사본은 언제 늦는가** — 검색 색인과 집계 테이블의 지연이 서로 다르므로 **화면 두 개가 다른 숫자를
  보여 준다.** [[Data SLA and observability]]의 *침묵의 실패* 가 가장 잘 일어나는 자리다.
- **역방향 유입** — 원본 → 사본이 아니라 사본에만 쓰이는 값이 생기면 [[ETL and ELT]]의 reverse ETL
  문제로 돌아온다.

소스는 **"역할을 나누면 관리하기 쉽다"** 까지만 말하고 나누고 난 뒤의 비용은 말하지 않는다.

## ⚠️ 이 층에 벡터 검색이 없다

소스(2026년 자료)의 검색 항목은 **역색인 기반 렉시컬 검색뿐이다.** 임베딩·ANN·하이브리드 검색이
등장하지 않는다. 이 위키는 이미 [[Vector database]]와 [[Hybrid search and reranking]]을 갖고 있으므로
**조회 형태 표에 한 줄이 빠져 있다고 읽어야 한다.**

| 조회 형태 | 질문의 모양 | 맞는 기술 |
|---|---|---|
| **의미 검색** | "이 문장과 뜻이 가까운 문서" | [[Vector database]] (ANN) |
| **렉시컬 + 의미 결합** | 위 둘을 함께, 식별자도 놓치지 않고 | [[Hybrid search and reranking]] (BM25 + RRF) |

⭐ 그리고 [[Hybrid search and reranking]]의 논지가 정확히 이 층의 문제다 — **"의미는 남고 식별자는
사라진다."** 벡터만으로는 상품 코드를 못 찾고, 역색인만으로는 뜻을 못 찾는다. **Lucene 계열과 벡터
검색은 대체가 아니라 같은 조회 형태의 두 절반이다.**
