# NoSQL

**[[Schema-centric data modeling|스키마 중심 설계]]가 확장·유연성에서 무너진 자리에 들어온 저장소
계열.** 하나의 기술이 아니라 **네 가지 다른 물건의 묶음**이고, 공통점은 "관계형 모델의 일부를
포기하고 다른 것을 얻었다"는 것뿐이다.

> ⚠️ **이 페이지의 절반은 "NoSQL이 해결해주지 않는 것"이다.** 강의가 이 부분을 정직하게 다루고,
> 그게 이 주제에서 가장 쓸모 있는 대목이다.

## 왜 등장했나 — 서비스가 먼저 바뀌었다

기술이 아니라 **없던 서비스가 생긴 것**이 원인이다.

- **Facebook / Instagram** — 사용자 폭발, 피드·좋아요·댓글·팔로우 이벤트가 초당 대량 생성.
  **쓰기(write) 이벤트가 OLTP보다 훨씬 자주 발생.**
- **LinkedIn** — 사람–사람–회사–직무 관계가 복잡하고, **관계 탐색(who knows who)이 핵심 기능.**

> **"새로운 서비스는 정확한 트랜잭션보다 대규모 이벤트 처리, 낮은 지연, 높은 가용성이 먼저 필요해졌다."**

서비스가 요구한 네 가지 변화:

| 요구 | 귀결 |
|---|---|
| 사용자·트래픽 급증 | 단일 DB 확장 한계 → **수평 확장이 기본 전제** |
| 이벤트·로그 폭발(반정형·비정형) | 스키마 변화 잦음 → **문서·키-값 접근이 더 적합** |
| 24/7 가용성 | 장애 시에도 지속 → **복제·분산·부분 실패 허용** |
| 빠른 개발 속도 | 마이그레이션 비용이 병목 → **유연한 모델** |

## 네 가지 타입

| 워크로드 | 타입 | 고르는 이유 | 대표 |
|---|---|---|---|
| 초고속 캐시·세션·피드 최신 데이터 | **Key-Value** | 단순 키 조회, 낮은 지연 | Redis(in-memory), DynamoDB(managed·persistent) |
| 사용자 프로필·게시물·JSON 형태 | **Document** | 스키마 유연, 문서 단위 조회 | MongoDB, Couchbase, DocumentDB |
| 초대규모 이벤트·타임시리즈·로그 | **Wide-column** | 분산 쓰기/읽기, 대량 처리 | Cassandra, HBase, ScyllaDB |

⭐ **wide-column 두 대표의 실물**: [[Apache Cassandra]](하둡 없이 독립 서비스 DB, 멀티리전 복제) ·
[[Apache HBase]](HDFS 위, 행키 핫스팟). 같은 계열인데 **사용 환경이 다르다** — 아래 *파티션 키가
시스템을 결정한다* 가 두 제품에서 어떻게 다르게 나타나는지 보면 이 축이 분명해진다.
| 사람–사람–콘텐츠 관계 탐색 | **Graph** | 관계 탐색·경로 질의 최적 | [[Neo4j]], [[Amazon Neptune]] |

각 타입의 실전 자리:

- **Key-Value** — 단순함이 곧 속도. 고유 키 하나에 값을 통째로 저장, 인덱싱 오버헤드가 거의 없다.
  Redis: 실시간 랭킹(Sorted Set) · 세션 관리(TTL) · API 결과 캐싱. DynamoDB: 장바구니, 유저별
  설정값, 대규모 단순 조회.
- **Document** — 유연함이 곧 개발 속도. JSON 문서 단위 저장, schema-less. 콘텐츠 메타데이터(필드
  구성이 자주 바뀜), 유저 프로필(중첩 구조), 이커머스 상품 정보(가전과 의류의 사양 필드가 전혀 다름).
- **Wide-column** — 대규모 쓰기의 끝판왕. 열 기반 저장, 노드 추가 시 선형 확장. IoT 센서, 클릭 로그,
  광고 노출 이력, 메신저 대화(타임라인 순 저장·조회), 인플루언서 피드 fan-out.
- **Graph** — 관계가 곧 데이터. 노드와 엣지를 직접 저장, **JOIN 없이 연결 고리를 탐색.** 추천 엔진의
  N차 관계, 이상거래 탐지(FDS: 동일 IP/기기를 공유하는 다중 계정), 지식 그래프.
  → [[Graph database]] · [[Graph data model]]

## ⭐ NoSQL이면 확장성이 자동 해결될까 — 아니다

> **"NoSQL = 분산 DB = 자동 스케일"은 단순화다. 실제로는 샤딩/파티셔닝 설계가 성공과 실패를 좌우한다.**

### 운영 현실 1 — 파티션 키가 시스템을 결정한다

파티션 키(샤딩 키)는 **한 번 정해지면 바꾸기 어렵다.** 실패 패턴:

- 특정 키에 트래픽 집중 → **핫 파티션(hot partition)**
- 시간 기반 키로 쓰기 집중 (최신 시간대 파티션에만 쓰기가 몰린다)

결과: 일부 노드 과부하 → **전체 latency 상승**, 그리고 **노드를 추가해도 병목이 해소되지 않는다.**

> 핫 파티션은 NoSQL의 **대표적 장애 원인**이다. 이건 [[Apache Kafka]]의 파티션 설계와 같은 종류의
> 문제 — 키 선택이 곧 부하 분포다.

### 운영 현실 2 — 일관성 완화는 애플리케이션 복잡도로 전가된다

분산에서 "항상 최신"을 유지하는 비용이 크니 NoSQL은 종종 일관성을 완화한다. 그 결과 **애플리케이션이
감당해야 하는 것들**:

재시도 설계 · 중복 처리(멱등성) · 순서 꼬임 처리 · 보정 배치(job) 운영.

> 일관성 = 어떤 값이 업데이트되면 그 직후 어떤 서버/노드에서 읽더라도 항상 최신 값이 보이는 상태.

**CAP** 이 이 trade-off의 대표 개념이다 — 분산 시스템은 네트워크 단절(Partition)을 완전히 피할 수
없고, 그 상황에서 일관성(Consistency)과 가용성(Availability)을 동시에 완벽히 만족시키기 어렵다.
그래서 **시스템마다 무엇을 우선할지 고른다.**

| | |
|---|---|
| **C**onsistency | 모든 노드가 같은 시점에 같은 값을 봄 |
| **A**vailability | 일부 장애가 있어도 요청에 응답 가능 |
| **P**artition Tolerance | 네트워크 단절·지연이 있어도 시스템 유지 |

### 운영 현실 3 — 백업·복구·관측이 더 어렵다

데이터가 한 곳이 아니라 여러 노드에 나뉘어 있으므로 복제본·파티션·네트워크 상태를 **함께** 봐야
한다. 장애도 전체 다운보다 **부분 실패**로 나타난다.

> ⭐ **"운영 포인트가 줄어드는 것이 아니라 분산된다."**

- **백업/복구** — 여러 노드를 **같은 시점 기준으로 맞추기 어렵고**, 복구 후에도 replica 간 동기화
  확인이 필요하다. 데이터가 클수록 네트워크·시간 비용 증가.
- **리밸런싱** — 노드 추가/제거/장애 시 데이터 재배치가 필요하고, 재배치 중 성능이 저하되며,
  잘못하면 특정 노드에 부하가 집중된다.
- **Partial failure** — 겉보기엔 서비스가 살아 있어 **원인 파악이 더 어렵다.**
- **관측 포인트 증가** — QPS/latency · partition hotness/skew · replication lag ·
  timeout/failed requests/leader change. 물어야 할 질문이 바뀐다:
  **어느 노드가 느린가 · 어느 파티션이 과열됐나 · 어느 replica가 뒤처졌나.**

→ [[Data SLA and observability]]의 "침묵의 실패"가 분산 환경에서 갖는 구체적 형태.

## 그리고 NoSQL도 답하지 못하는 것

RDBMS/NoSQL은 **저장·확장·성능** 문제를 다룬다. 하지만 이 질문들에는 답하지 못한다:

- 활성 사용자의 정의는?
- 매출은 환불/쿠폰/포인트 처리를 포함하나?
- 전환의 윈도우는 7일인가 30일인가?

> **"이 데이터가 무엇을 의미하는가는 스키마만으로 부족하다."** → [[Data semantics]]
