# 객체지향 프로그래밍

상태와 그 상태를 다루는 행동을 객체 하나에 묶고, 객체들이 메시지를 주고받으며 협력해 기능을 만드는 프로그래밍 방식이다. [[Java 면접 5 빈출 질문]] Q2는 "역할과 책임을 갖는 자율적인 객체들의 협력으로 프로그래밍 하는 것"이라 정의하고, 목적을 변경에 유연한 코드로 든다. 이 페이지는 객체지향 주제의 허브이고, 각 특성과 원칙은 자기 페이지에서 다룬다.

## 객체 · 클래스 · 인스턴스

자료(Q1)는 객체를 "소프트웨어 세계에 구현할 대상", 클래스를 설계도, 인스턴스를 설계도로 구현된 실체로 나눈다. 모델링 쪽의 구분으로는 쓸 수 있지만 Java 용어와는 다르다. JLS는 "An object is a class instance or an array"(§4.3.1)라고 정의한다. Java에서 객체와 인스턴스는 같은 것이고, 클래스는 그 객체의 타입이다. 면접에서 「객체와 인스턴스의 차이」를 물으면 "Java에서는 같은 것을 가리키고, 인스턴스는 특정 클래스와의 관계를 강조할 때 쓰는 말"이라고 답하는 편이 안전하다. 이 답은 위키의 정리다.

## 역할 · 책임 · 협력 · 메시지

자료 Q3~Q6의 정의는 조영호 『오브젝트』(위키북스, 2019)의 정의와 거의 같다. 자료는 출처를 밝히지 않는다. 책 원문은 확인하지 못했고, 아래 오른쪽 칸은 책을 정리한 2차 자료에서 옮겼다.

| 용어 | 자료 | 『오브젝트』 (2차 자료) |
|---|---|---|
| 협력 | 기능을 구현하기 위해 수행하는 객체들의 상호 작용 | 객체들이 애플리케이션의 기능을 구현하기 위해 수행하는 상호작용 |
| 책임 | 협력에 참여하기 위해 수행하는 행동 | 객체가 협력에 참여하기 위해 수행하는 로직 |
| 역할 | 협력 안에서 수행하는 책임의 집합, 객체의 추상화 | 객체들이 협력 안에서 수행하는 책임들의 집합 |
| 메시지 | 협력에 쓸 수 있는 유일한 소통 수단, How가 아니라 What | 객체들이 협력하기 위해 사용할 수 있는 유일한 의사소통 수단 |
| 메서드 | 메시지를 수신했을 때 실제로 실행되는 함수 | 메시지를 수신했을 때 실제로 실행되는 함수 또는 프로시저 |

책임에서 시작해 객체를 설계하는 방법은 Wirfs-Brock과 Wilkerson의 책임 주도 설계(RDD, OOPSLA '89)로 거슬러 올라간다. 서지 정보만 확인했다.

네 용어는 한 문장으로 이어진다. 협력이 필요한 책임을 정하고, 책임을 묶어 역할을 만들고, 역할을 맡은 객체에게 메시지를 보낸다. 메시지가 What만 말하고 How(메서드)는 받는 객체가 고르므로, 같은 메시지에 다른 객체가 다르게 응답할 수 있다. 이것이 [[다형성]]이고, 묻지 말고 시키라는 [[캡슐화]]의 행동 메서드와 같은 생각이다. 이 연결은 위키가 했다. 자료 Q3의 예(면접자 역할은 다른 사람이 맡아도 면접이 성립한다)는 역할이 대체 가능성의 단위라는 뜻이다.

## 4대 특성

자료(Q13)는 다형성 · 캡슐화 · 상속 · 추상화를 「객체지향 패러다임의 4원칙」이라 부른다. 흔히 쓰는 말은 「4대 특성」이고, 원칙은 [[SOLID 원칙]] 쪽 용어다.

- 캡슐화: 상태와 행동을 묶고 내부를 숨긴다. 자료가 Q7에서 가장 중요하다고 꼽은 특성이다([[캡슐화]]).
- 상속: 하위 클래스가 상위 클래스의 타입과 구현을 물려받는다([[상속과 조합]] · [[상속을 쓰는 이유]]).
- 다형성: 한 타입으로 여러 구현 객체를 다룬다([[다형성]]).
- 추상화: 공통점을 남기고 차이를 버려 핵심만 드러낸다. Java에서는 인터페이스와 추상 클래스가 그 도구다([[인터페이스와 추상 클래스]]).

Q13의 서술에는 세 곳의 오류가 있다.

- 다형성을 "하나의 객체에 여러 가지 타입을 대입"이라 했다. 방향이 거꾸로다. 한 타입(참조 변수)에 여러 구현 객체를 대입하는 것이고, 슬라이드 p94의 정의도 그렇다([[다형성]]).
- 다형성 구현 방법으로 오버로딩 · 오버라이딩 · 함수형 인터페이스를 든다. 오버로딩은 컴파일 타임에 정해지는 별개의 기법이다([[오버로딩과 오버라이딩]]). 함수형 인터페이스는 추상 메서드가 하나인 인터페이스일 뿐이고(JLS §9.8), 람다의 값은 그 인터페이스를 구현한 클래스의 인스턴스다(§15.27.4). 인터페이스를 통한 서브타입 다형성의 한 경우이지 별도 수단이 아니다([[람다와 스트림]]).
- 상속을 "객체들 간의 관계를 구축하는 것"이라 했다. 상속은 클래스(타입) 사이의 관계다. 객체 사이의 관계는 조합 쪽이다([[상속과 조합]]).

## 절차지향과의 차이

자료(Q8)는 "객체지향은 상태와 행위를 묶을 수 있지만, 절차지향은 상태를 가질 수 없다"고 한다. 틀리다. 절차지향 프로그램도 전역 변수와 구조체로 상태를 가진다. 차이는 데이터와 그 데이터를 다루는 절차가 분리돼 있느냐, 한 단위로 묶여 있느냐다. Oracle Java Tutorial은 객체를 "An object stores its state in fields … and exposes its behavior through methods"라고 설명한다. 자료의 뒷문장(파일을 나눠도 행위만 흩어 놓은 것)은 이 분리를 가리키는 것이라 맞다.

의존 방향으로도 차이를 말할 수 있다. Martin은 1996년 DIP 글에서 전통적인 절차적 설계에서는 상위 모듈이 하위 모듈에 의존한다고 하고, 이 방향을 뒤집는 것을 「역전」이라 부른다([[SOLID 원칙]]).

자료 Q16은 반대편을 묻는다. 변화가 잦지 않은 일회성 프로젝트라면 절차지향이 더 효율적이라는 답이다. 판정할 사실이 아니라 의견이다. 객체지향의 비용(추상화와 간접 참조)은 변경이 있을 때 회수되므로, 바뀔 일이 없는 코드에서는 회수할 것이 없다는 논리로 이해하면 된다. 이 해석은 위키의 것이다.

## static의 단점

자료(Q14)는 두 가지를 든다.

1. 다형성을 쓸 수 없다. 맞다. static 메서드는 오버라이드되지 않고 숨겨진다(JLS §8.4.8.2, [[오버로딩과 오버라이딩]]). 그러나 자료가 호출 형식을 「객체.메소드」라고 쓴 것은 틀리다. `클래스명.메서드()`로 부르고, 인스턴스로 불러도 대상 참조는 버려진다(§15.12.4.1: "If the invocation mode is static, then there is no target reference").
2. 객체의 상태를 쓸 수 없어 필요한 인자를 모두 밖에서 넣어야 한다. 맞다. static 메서드 안에서는 `this`와 `super`를 쓸 수 없다(§8.4.3.2).

빠진 단점이 더 중요하다. 위키가 보충한 것이다.

- 테스트에서 바꿔 끼우기 어렵다. static 호출은 구현에 직접 묶여서 목(mock)으로 대체하기 힘들다. 『Effective Java』 3판 Item 5는 자원에 의존하는 클래스를 static 유틸리티로 만들지 말고 의존 객체를 주입하라고 한다(2차 자료).
- static 필드는 전역 가변 상태가 되기 쉽다. 모든 스레드가 공유하므로 동기화 문제가 그대로 따라온다([[동시성 문제]]).
- 호출하는 쪽이 특정 클래스에 강하게 결합된다([[결합도와 응집도]]).

상태가 없는 순수 함수(`Math.max`)나 팩터리 메서드처럼 바꿔 끼울 일이 없는 곳에서는 static이 적절하다는 단서도 붙여야 균형이 맞는다.

## 클린 코드

자료(Q15)는 클린 코드를 남이 읽어도, 1년 뒤의 내가 읽어도 쉽게 이해되는 코드로 정의한다. 널리 인용되는 문장과 같은 방향이다. Fowler는 "Any fool can write code that a computer can understand. Good programmers write code that humans can understand."라고 썼다(『Refactoring』 2판 1장). Martin 『Clean Code』 1장이 모은 정의 가운데 Dave Thomas의 "Clean code can be read, and enhanced by a developer other than its original author."가 자료와 가장 가깝다.

## 면접에서

- 객체지향의 정의는 「상태와 행동을 묶은 객체들이 메시지로 협력한다」에 목적(변경에 유연함)을 붙여 답한다.
- 절차지향과의 차이를 「상태 유무」로 말하지 않는다. 데이터와 절차의 분리 대 결합, 그리고 의존 방향으로 말한다.
- 4대 특성은 「원칙」이라 부르지 않고, 다형성은 「한 타입에 여러 객체」로 말한다. 구현 수단은 오버라이딩이다.
- static 질문에는 다형성 불가와 상태 불가에 테스트 용이성과 전역 상태를 덧붙이고, 쓸 만한 곳(순수 함수, 팩터리)도 함께 말한다.
