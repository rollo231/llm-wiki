# 불변 객체

만들어진 뒤 관찰할 수 있는 상태가 바뀌지 않는 객체. 반대는 가변 객체다(`ArrayList` · `HashMap` · `StringBuilder`). 면접에서는 가변과 불변의 차이, 언제 쓰는지를 묻는데, 답은 결국 멀티스레드 안전성으로 모인다([[Java 면접 4 빈출 질문]] Q1 · Q2).

## 불변이면 왜 스레드 안전한가

공유 상태가 문제가 되는 것은 누군가 쓰기 때문이다([[동시성 문제]]). 생성 뒤 아무도 쓰지 않으면 원자성 문제가 생길 곳이 없다. 남는 것은 가시성 하나, 곧 다른 스레드가 참조를 받았을 때 생성자가 쓴 필드 값을 제대로 보느냐다. 이것을 JLS §17.5의 `final` 필드 의미론이 해결한다.

> "A thread that can only see a reference to an object after that object has been completely initialized is guaranteed to see the correctly initialized values for that object's final fields." — JLS §17.5

그래서 불변이면 안전하다는 말에는 조건이 붙는다.

1. 필드가 모두 `final`이어야 한다. `final`이 아닌 필드는 생성자에서 한 번만 써도, 참조를 경쟁적으로 넘겨받은 스레드가 기본값(0 · null)을 볼 수 있다. 이 경우에는 `volatile` 필드나 동시성 컬렉션, 락 같은 안전한 공개(safe publication)가 따로 필요하다.
2. 생성자에서 `this`가 새지 않아야 한다. JLS의 사용 모델이 직접 금지한다: "do not write a reference to the object being constructed in a place where another thread can see it before the object's constructor is finished." 생성자 안에서 리스너로 자기를 등록하는 것이 전형적인 누출이다.
3. 가변 객체를 품으면 복사해서 받고 복사해서 내준다. `final List<String>`은 참조가 고정일 뿐 내용은 바뀐다. 생성자에서 방어적으로 복사하고, getter는 수정 불가 뷰나 복사본을 돌려준다([[캡슐화]]).

JLS §17.5는 바로 String을 예로 든다(Example 17.5-2). 스레드 1이 `"/tmp/usr".substring(4)`를 공유 변수에 넣고 스레드 2가 그것을 읽을 때, String의 필드가 final이 아니었다면 스레드 2는 offset의 기본값 0을 보고 처음에는 `"/tmp"`로, 나중에는 `"/usr"`로 볼 수 있다. 원문은 "if the fields of the String class were not final, then it would be possible (although unlikely) that thread 2 could initially see the default value of 0 for the offset"이다. (예제의 offset 필드는 옛 String 구현의 것이다.) [JLS SE 25 §17.5, https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.5 , 2026-09-27 확인]

## "상태가 전혀 안 바뀐다"는 아니다

String에도 생성 뒤에 쓰이는 필드가 있다. `private int hash;`는 `final`이 아니고, `hashCode()`를 처음 부를 때 계산해 기록한다. 소스 주석은 이것을 "subject to a benign data race"라고 부른다. 두 스레드가 동시에 계산해도 같은 값을 쓰므로 해가 없다는 뜻이다. 그래서 불변을 정확히 정의하면, 필드가 안 바뀌는 것보다 넓게 밖에서 관찰할 수 있는 상태가 안 바뀌는 것이다. [OpenJDK `String.java`, https://github.com/openjdk/jdk , master, 2026-09-27 확인]

JDK의 비슷한 타입들은 불변의 강도가 다르다.

| 타입 | 강도 | 근거 |
|---|---|---|
| `String` · `Integer` 등 박싱 타입 | 불변 | 필드 final, 연산은 새 객체를 돌려준다 |
| `List.of` · `Map.of` | 수정 불가(unmodifiable). 불변은 아니다 | javadoc: "if the contained elements are themselves mutable, this may cause the List's contents to appear to change" |
| `record` | 얕은 불변 | `Record` javadoc: "a shallowly immutable, transparent carrier". 컴포넌트가 가변 객체면 그 안은 바뀐다 |
| `Collections.unmodifiableList` | 뷰 | 원본을 고치면 뷰로도 바뀐 것이 보인다 |

## 언제 쓰나

자료(Q2)는 캐싱과 동기화를 쉽게 하는 것만 든다. 쓰임은 더 있다. 아래 목록은 Effective Java Item 17에 정리된 것으로 2차 자료다.

- 동기화 없이 공유할 수 있다. 락이 필요 없다. 여러 값을 함께 바꿔야 할 때 값들을 불변 객체 하나로 묶고 참조만 `AtomicReference`로 바꾸는 패턴도 여기서 나온다([[동기화 기법]]의 「여러 값을 함께 바꿀 때」).
- 인스턴스를 공유하고 캐시할 수 있다. 바뀌지 않으니 같은 값은 한 인스턴스를 나눠 써도 된다. `Integer.valueOf`는 "will always cache values in the range -128 to 127". 문자열 intern도 같은 발상이다.
- 맵 키와 집합 원소로 안전하다. `hashCode`가 바뀌지 않아서 `HashMap`에 넣은 뒤 못 찾게 되는 일이 없다.
- 방어적 복사가 필요 없다. 받은 것을 그대로 저장하고 그대로 내줘도 된다.
- 실패 원자성이 있다. 연산이 도중에 예외를 던져도 원래 객체는 그대로다.

대가는 값마다 새 객체를 만드는 비용이다. 여러 단계로 값을 조립할 때는 `StringBuilder`처럼 가변 짝 클래스를 쓴다. `StringBuilder`와 동기화된 `StringBuffer`의 차이, 문자열 리터럴이 풀에서 공유되는 방식은 [[Java 면접 기타 빈출 질문 2 문자열 예외 제네릭]]에 있다.

데이터 엔지니어링에서 원본은 고치지 않고 새 버전을 쓰는 것도 같은 발상이다. [[Delta Lake]]는 데이터 파일을 불변으로 두고 로그만 덧붙인다. [[함수형 프로그래밍]]의 불변성도 같은 원칙이다. 이 연결은 위키가 붙였다.

## 면접에서

1. 차이: 생성 뒤 관찰 가능한 상태가 바뀌는가. 자료와 같다.
2. 안전한 이유까지 말한다. 쓰기가 없으니 원자성 문제가 없고, 가시성은 `final` 필드가 보장한다(JLS §17.5). 조건으로 `final` 필드, `this` 누출 금지, 가변 멤버의 방어적 복사를 덧붙인다.
3. 꼬리 질문에 대비한다. "`List.of`는 불변인가요?"에는 수정 불가일 뿐 원소가 가변이면 바뀐다고, "`record`는?"에는 얕은 불변이라고 답한다.
4. 쓰임: 캐싱 말고도 맵 키, 방어적 복사 불필요, 여러 값을 한 번에 바꾸기.
