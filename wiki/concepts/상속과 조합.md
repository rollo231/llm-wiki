# 상속과 조합

- 상속(inheritance)은 하위 클래스가 상위 클래스의 타입과 구현을 함께 물려받는 것이다. is-a 관계다(고양이는 동물이다).
- 조합(composition)은 한 객체가 다른 객체를 필드로 가지고 그 메서드에 일을 맡기는 것이다. has-a 관계다(자동차는 엔진을 가진다).

## 자료의 관점 — 상속은 다형성을 위한 것

[[Java 면접 5 객체지향 프로그래밍]]은 일관되게 이렇게 말한다(p85, p91).

- 상속은 주로 다형성을 구현하기 위해 쓰고, 코드 재사용은 부가적인 장점이다.
- is-a 관계가 명확하고 향후 변화가 거의 없을 때 쓴다.
- 조합은 다형성과 관계가 없고, 결합도가 낮아 유연하다. is-a가 명확하지 않으면 조합을 선호한다.

『Effective Java』의 "상속보다 컴포지션을 사용하라"와 같은 방향이다. 다만 "상속의 주목적은 다형성"은 여러 관점 가운데 하나이고 정의는 아니다. 이 평가는 위키의 관찰이다.

## 상속의 단점 (p86–88)

1. 강한 결합: 하위가 상위의 구현에 묶여서, 상위를 고치면 하위가 깨진다. 흔히 "깨지기 쉬운 기반 클래스" 문제라고 부른다.
2. 캡슐화 파괴: 오버라이딩으로 확장하려면 상위의 내부 동작(어떤 메서드가 어떤 메서드를 부르는지)을 알아야 한다([[캡슐화]]).

두 단점이 한 번에 드러나는 예가 『Effective Java』 3판 Item 18에 있다. 자료에는 없고 위키가 보충했다.

```java
class CountingSet<E> extends HashSet<E> {
    int addCount = 0;
    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);   // 물려받은 addAll이 안에서 add()를 부른다
    }
}
// addAll(List.of(1, 2, 3)) → addCount=6, size=3 (기대값은 3)
```

`HashSet`은 `addAll`을 오버라이드하지 않고, 물려받은 `AbstractCollection.addAll`이 원소마다 `add`를 부른다. 이것은 문서화된 계약이 아니라 구현 세부라서, 하위 클래스가 모르면 두 번 세고, 알고 기대면 JDK 구현이 바뀔 때 깨진다. 조합으로 `Set`을 필드로 두고 위임하면 이 문제가 없다. [OpenJDK 25.0.2 `HashSet.java` · `AbstractCollection.java`, 로컬 재현, 2026-09-27 확인]

그렇다고 상속을 쓸 곳이 없는 것은 아니다. 확장용으로 설계된 클래스, 같은 사람이 양쪽을 관리하는 경우, 위임 코드의 비용은 [[상속을 쓰는 이유]]에 정리했다.

## 자료의 "조합은 다형성과 무관"에 대한 단서

조합 자체는 다형성이 아니지만, 필드 타입을 인터페이스로 두면 조합으로도 다형성을 얻는다. 전략 패턴이 그렇다. 실무에서 권하는 형태는 인터페이스로 타입을 공유하고 구현은 조합으로 재사용하는 것이다. 상속이 한꺼번에 주던 두 가지(타입 공유와 구현 재사용)를 인터페이스와 조합이 나눠 맡는 셈이다. 이 단서는 위키의 관찰이다. 관련 내용은 [[인터페이스와 추상 클래스]]와 [[다형성]]에 있다.

## 면접에서

- 상속을 "코드 재사용"으로만 답하면 Silver에 머문다(자료의 이유 칸). is-a와 다형성을 먼저 말한다.
- 상속의 단점은 결합도와 캡슐화 파괴 두 가지로 답한다. 여기에 리스코프 치환 원칙(LSP), 곧 "하위 타입은 상위 타입 자리에 넣어도 동작이 깨지지 않아야 한다"를 덧붙이면 is-a가 언제 성립하는지 기준까지 줄 수 있다. 자료는 LSP를 언급하지 않으며, 이 부분은 위키가 보충했다.
- 조합과의 차이는 "조합은 다형성과 무관"이라고 하기보다, 상속은 타입과 구현을 한 번에 묶고 조합은 둘을 분리한다고 말하는 편이 더 정확하다.
