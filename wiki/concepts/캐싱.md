# 캐싱

자주 조회되는 데이터를 원본 저장소(source of truth)보다 빠른 곳에 두고 원본 조회를 줄이는 것이다. [[AI DE 강의 4-05 캐싱 레이어와 캐싱 전략]]은 캐시가 원본을 대체하지 않고 보호한다고 정리한다(p102). 원본이 데이터의 기준점이고 캐시는 보조 계층이다. 대표 구현은 [[Redis]]다.

## 캐시의 역할과 위험

역할은 셋이다(p102). 응답 시간 단축, 원본 부하 감소(DB QPS와 connection 사용량), 트래픽 급증 완충(이벤트·캠페인·배포 때 원본 보호)이다.

위험도 있다(p103). 오래된 데이터 반환, 캐시와 원본의 불일치, 캐시 만료 때 원본 폭주, hot key 집중, hit가 낮아 효과가 없는 경우다. 그래서 캐싱 전략은 속도만이 아니라 성능·신선도·안정성·운영 비용의 균형 문제다.

miss가 많으면 캐시는 오히려 손해다(p115). Redis 조회 비용이 더해지고, 원본도 여전히 조회하고, 응답 경로만 길어지고, 메모리만 쓴다.

## 무엇을 캐시하나

캐시가 효과적인 조건은 네 가지다(p101, p106). 같은 데이터가 반복 조회되고, 원본 조회 비용이 크고, 약간 지연된 데이터가 허용되고, TTL 동안 재사용될 가능성이 높아야 한다. 여기에 key로 빠르게 찾을 수 있고 크기가 너무 크지 않아야 한다.

캐시하면 안 되는 데이터(p109)는 강한 정합성이 필요한 결제 상태, 포인트 차감 같은 금전성 데이터, 항상 최신이어야 하는 권한 데이터, 한 번만 조회되는 데이터, 너무 큰 JSON blob, key 종류가 너무 많아 hit가 거의 나지 않는 데이터다.

| 패턴 | 키 예시 | 자료구조 | 이유 |
|---|---|---|---|
| 세션 | `user:session:*` | String 또는 Hash | TTL 관리, 서버 간 공유 |
| 조회 캐시 | `product:detail:*` | String(JSON) | RDB 쿼리 비용 절감 |
| 목록 | `category:list` | List 또는 Set | 정적 목록의 빠른 반환 |
| 순위 | `ranking:daily` | Sorted Set | 실시간 정렬 |
| 피처 | `feature:user:*` | Hash 또는 String | 무거운 연산 결과를 저장해 두고 즉시 서빙 |

표는 강의 p108을 따랐다. 마지막 행은 [[피처 스토어]]의 온라인 스토어와 같은 쓰임이다.

## 읽기 전략과 쓰기 전략

강의는 캐싱 전략을 두 축으로 나눈다(p117). 조회할 때 캐시를 어떻게 쓸지(읽기), 원본이 바뀔 때 캐시를 어떻게 갱신하거나 지울지(쓰기)다.

| 전략 | 축 | 흐름 | 장점 | 단점 |
|---|---|---|---|---|
| Cache-aside | 읽기 | 앱이 캐시 조회 → miss면 앱이 원본 조회 → 캐시에 TTL과 저장 | 필요한 것만 올라감, 단순, 캐시 장애 때 원본으로 우회 쉬움 | 첫 요청은 항상 miss, cold cache, 동시 miss 폭주, 무효화 별도 |
| Read-through | 읽기 | 앱은 캐시 계층에만 요청, miss 처리와 원본 조회를 캐시 계층이 감쌈 | 앱 코드 단순, 적재 규칙 중앙화 | 캐시 계층 복잡, 장애 추적 경로가 길다 |
| Refresh-ahead | 읽기 | 만료 전에 미리 갱신 | 읽기 지연 감소 | 강의에 설명 없음 |
| Write-through | 쓰기 | 쓸 때 캐시와 원본을 함께 갱신한 뒤 응답 | 쓰기 직후 최신, stale 가능성 감소 | 쓰기 경로가 느림, 한쪽만 성공하면 보상 처리 필요 |
| Write-behind | 쓰기 | 캐시에 먼저 쓰고 응답, worker가 모아서 원본에 비동기 반영 | 쓰기 응답 빠름, 급증 흡수, 묶어서 반영 | 캐시 장애 때 미반영 데이터 유실, 재처리 구조 필요 |

표는 강의 p118–128을 정리한 것이다. 강의의 예시는 이렇다.

- Cache-aside: 상품 상세. TTL 5~30분. 가격·재고·쿠폰처럼 자주 바뀌는 값은 같은 key에 섞지 않는다. 변경 주기가 다른 데이터를 한 캐시 객체로 묶으면 TTL을 정할 수 없다(p121).
- Write-through: 사용자 프로필. 닉네임을 바꾼 직후 화면에 반영돼야 하고 조회가 쓰기보다 훨씬 많다(p126).
- Write-behind는 정산·결제·주문 같은 강한 정합성 데이터에 위험하다(p128).

Prefetching(자주 쓰이고 안정적인 데이터를 미리 적재)은 Ch2 소단원 1(p77–78)에 따로 나온다. Refresh-ahead는 p117의 분류와 p130의 선택 기준에 이름만 있고 설명 슬라이드가 없다.

## 무효화

원본이 바뀌었을 때 기존 캐시를 처리하는 방법은 세 가지다(p129–130).

| 방식 | 효과 | 언제 |
|---|---|---|
| 삭제 | 다음 조회에서 miss가 나고 새 값을 적재 | 최신성이 중요하거나 쓰기 로직이 복잡할 때 |
| 갱신 | 쓰기 직후 읽기가 최신 | 최신성이 중요하고 읽기 지연을 줄이고 싶을 때 |
| 짧은 TTL | 명시적으로 지우지 않고 자연 만료 | 약간 오래된 데이터가 허용될 때 |

강의는 무효화를 캐싱에서 가장 어려운 부분으로 꼽는다. 지우지 않으면 오래된 값을 주고, 너무 자주 지우면 hit ratio가 떨어진다.

## TTL 설계

TTL이 짧으면 신선도가 좋아지는 대신 miss와 원본 부하가 늘고, 길면 반대다(p132). 강의가 제시하는 권장값은 다음과 같다(p131). 출처 없는 경험칙이며 값은 자료의 것이다.

| 데이터 | 권장 TTL | 근거(강의) |
|---|---|---|
| 상품 가격 | 5~30초 | 결제 직전 가격이 달라지면 안 된다. 찰나의 반복 조회만 막는다 |
| 상품 설명 | 10분~1시간 | 정적. 변경 때 강제 삭제와 병행 |
| 카테고리 목록 | 1~24시간 | 변동이 가장 적고 조인이 무거운 쿼리 |
| 사용자 세션 | 30분~수 시간 | 조회 때마다 TTL을 늘리는 sliding window |
| 추천 결과 | 수초~수분 | 클릭에 따라 바뀌지만 추천 엔진 부하를 막아야 |
| 랭킹 | 10초~1분 | 순위가 바뀌는 느낌은 주면서 집계 쿼리 폭주는 막는다 |
| 실험 설정 | 수 분~수십 분 | 잘못된 설정을 급히 고칠 수 있게 너무 길지 않게 |

## 캐시 스탬피드

강의는 위험 목록에 "캐시 만료 시 원본 저장소 폭주"(p103)와 "동시에 같은 key가 miss되면 원본으로 요청이 몰릴 가능성"(p119)을 적지만 대응을 다루지 않는다. 아래는 위키가 보충한 것이다.

- 요청 합치기(request coalescing, single-flight): 같은 key의 miss가 동시에 여럿이면 하나만 원본을 조회하고 나머지는 그 결과를 기다린다.
- TTL jitter: 같은 시점에 적재된 key들이 한꺼번에 만료되지 않도록 TTL에 무작위 값을 더한다.
- 확률적 조기 갱신: 만료가 가까울수록 높은 확률로 미리 갱신한다. Vattani·Chierichetti·Lowenstein의 「Optimal Probabilistic Cache Stampede Prevention」(PVLDB 8(8), 2015)이 이 방식(XFetch)을 제안하고 최적성을 보였다. [http://www.vldb.org/pvldb/vol8/p886-vattani.pdf , 2026-09-28 확인]

## Hot key

수많은 key 가운데 몇 개에만 트래픽이 몰리는 현상이다(p86). 클러스터로 샤딩해도 한 key는 한 노드에만 있으므로 그 노드만 과부하된다. 강의는 "트래픽이 90% 이상 몰리는"이라고 정의에 수치를 넣지만 출처가 없다. [[NoSQL]]의 핫 파티션과 같은 구조의 문제다.

## 지표로 본다

강의는 캐시 튜닝을 감으로 하지 말라고 한다(p91–92). hit ratio(`keyspace_hits`·`keyspace_misses`), 메모리(`used_memory`·fragmentation), `evicted_keys`, `expired_keys`, 처리량, `SLOWLOG`, 연결 수, p95·p99 지연을 보고, 단일 지표가 아니라 흐름을 본다. 배포 후 hit ratio가 떨어졌는지, eviction 뒤 DB 부하가 늘었는지, Redis는 빠른데 API 지연이 긴지를 캐시·애플리케이션·원본 DB 지표를 함께 놓고 판단한다. 운영 지표 전반은 [[AI 시스템 모니터링]]에 있다.
