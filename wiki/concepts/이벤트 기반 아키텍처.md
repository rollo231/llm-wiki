# 이벤트 기반 아키텍처

서비스가 서로를 직접 호출하는 대신, **"무슨 일이 일어났다"는 이벤트를 발행하고 관심 있는 쪽이 구독해
반응하는** 비동기 구조. [[AI DE 강의 1-11 EDA와 Kafka]]는 이를 데이터 관점의 전환
**"Data at Rest → Data in Motion"**(고여 있는 데이터에서 흐르는 데이터로)으로 소개한다.

## 요청-응답과의 비교

| | 직접 호출(요청-응답) | 이벤트 기반 |
|---|---|---|
| 결합 | 강결합 — 주문 서비스가 배송 API의 주소·스펙을 안다 | 느슨한 결합 — "주문 발생"만 던지고 누가 받는지 모른다 |
| 장애 | 연쇄 장애 — 배송이 죽으면 주문도 타임아웃 | 장애 격리 — 이벤트는 브로커에 남고, 복구 후 이어서 처리 |
| 부하 | 호출자가 끝날 때까지 대기, 폭주 시 병목 | 이벤트가 쌓이면 컨슈머만 늘린다 |
| 배포 | 함께 바꿔야 한다 | 독립 배포 |

## 전통 메시지 브로커와 이벤트 스트리밍

| | 전통 브로커(RabbitMQ·ActiveMQ) | 이벤트 스트리밍([[Apache Kafka]]) |
|---|---|---|
| 보관 | 전달되면 큐에서 삭제(휘발) | 읽어 가도 보존 기간 동안 디스크에 남음(영속) |
| 전달 | 브로커가 누구에게 줄지 정해 밀어 넣음(Push) | 컨슈머가 자기 속도로 가져감(Pull) |
| 과거 | 이미 처리된 메시지는 사라짐 | 오프셋을 되감아 **재처리(replay)** |

재생 가능성 덕분에 로직 버그를 고친 뒤 과거 이벤트로 다시 계산할 수 있다 — 스트리밍 쪽의
[[데이터와 모델 버전 관리]] 수단이다.

## 허브 앤 스포크

소스와 타깃이 직접 연결되면 N×M개의 연결이 생긴다. 브로커를 중앙 허브로 두면 1:N이 된다 — 웹 로그·DB CDC·
IoT 센서가 한 허브로 들어가고, 실시간 대시보드·레이크/DW·이상 탐지가 각자 구독한다.
"하나의 이벤트, 여러 용도(One Data, Multi Use)".

## DB 변경을 이벤트로 — CDC

애플리케이션이 이벤트를 직접 발행하지 않아도, DB의 변경 로그를 읽어 이벤트로 만들 수 있다. 주문 서비스는
DB에 저장만 하고, [[변경 데이터 캡처]]가 그 변경을 브로커로 흘려 배송 서비스가 반영한다
([[AI DE 강의 1-08 CDC]]의 MSA 동기화 사례).

## 설계 시 주의

- **순서** — Kafka는 파티션 안에서만 순서를 보장한다. 같은 엔티티의 이벤트는 같은 키로 보내야 한다.
- **중복** — at-least-once 전달에서는 같은 이벤트가 두 번 올 수 있다. 소비 로직을 **멱등**하게(upsert) 만든다.
- **계약** — 서비스 간 약속인 이벤트 구조를 명시하고 버전 관리한다. → [[스키마 진화]]
- **운영 복잡도** — 브로커·스키마 레지스트리 같은 구성 요소가 늘어난다.
