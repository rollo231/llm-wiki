# 자동 재학습

모델 성능이 떨어졌거나 입력 분포가 바뀐 것을 감지하면, 사람이 손대지 않아도 데이터 수집 → 학습 → 평가 → 배포 → 관측을 다시 도는 고리다. [[AI DE 강의 1-13 Skew와 Drift]]는 이 고리를 Self-Healing 파이프라인이라 부르고, 문제를 감지하면 "수동 개입 없이 재학습(Retraining) 트리거가 작동"한다고 설명한다(덱 18 p2). [[AI DE 강의 2-02 MLOps와 ML 생애주기]]는 MLOps의 목표 가운데 하나로 "성능 저하 감지를 통한 자동 재학습"을 들고(p4), 그 파이프라인을 짓는 일을 데이터 엔지니어의 책임으로 둔다(p17).

재학습이 필요한 이유는 [[데이터 드리프트]]에 있다. 세상이 바뀌어 학습 때의 분포가 더는 맞지 않으면, 코드를 고쳐서는 해결되지 않고 새 데이터로 다시 학습해야 한다. 이 페이지는 그 대응 쪽을 모은다. 감지 지표(PSI·KL·KS)는 [[데이터 드리프트]]에, 고리가 MLOps 라이프사이클의 어디에 해당하는지는 [[MLOps]]에 있다.

## 트리거

1-13(덱 18 p4)은 재학습을 시작하는 조건을 셋으로 든다.

| 트리거 | 예 |
|---|---|
| 드리프트 | 분포 지표가 임계치를 넘는다("PSI > 0.2", KL Divergence 급증) |
| 성능 저하 | Accuracy·F1 하락 |
| 일정·이벤트 | 정기 업데이트, 시즌 이슈 |

⚠️ "PSI > 0.2"는 널리 쓰이는 관례(0.1 · 0.25 경계)에 없는 값이다. 정정과 출처는 [[데이터 드리프트]]의 「PSI 임계치 — 강의 정정」에 있다.

Part 4는 트리거를 무엇으로 판단하는지를 운영 지표 쪽에서 다시 말한다. 운영 지표의 목적 가운데 하나가 "재학습 필요성 판단"이고([[AI DE 강의 4-15 AI 시스템 지표와 SLA]] p6), AI 서비스 대시보드는 일반 웹 서비스가 보지 않는 "재학습 후보 데이터 생성 상태"까지 본다([[AI DE 강의 4-16 모니터링 대시보드와 알람]] p26). 데이터 엔지니어가 만드는 MLOps 데이터 흐름에도 "재학습 트리거 데이터"가 들어간다([[AI DE 강의 4-13 데이터 엔지니어링의 GPU 활용]] p305).

## 다섯 단계

1-13(덱 18 p4)의 Self-Healing 파이프라인은 다섯 단계다.

| 단계 | 내용 | 이어지는 페이지 |
|---|---|---|
| 1. 데이터 수집 | 최신 피처·라벨 로드, 품질·스키마 검증, 데이터셋 버전 관리 | [[데이터 SLA]] · [[데이터와 모델 버전 관리]] |
| 2. 모델 학습 | 전처리 실행, 하이퍼파라미터 튜닝, 재현 가능한 학습 환경 | [[학습-서빙 스큐]] |
| 3. 모델 평가 | Champion vs Challenger, 오프라인 지표 검증, 공정성·편향 체크 | — |
| 4. 배포 | 카나리·블루-그린, 섀도우 모드 테스트, 자동 롤백 가드레일 | [[모델 서빙]] |
| 5. 관측 | 실시간 추론 모니터링, 피드백 루프, 로그·트레이스 | [[AI 시스템 모니터링]] · [[데이터 관측성]] |

Champion vs Challenger는 지금 서비스 중인 모델(champion)과 새로 학습한 후보(challenger)를 같은 기준으로 비교해, 후보가 이길 때만 교체하는 방식을 가리키는 일반적인 용어다. 강의는 이름만 들고 비교 기준은 말하지 않는다.

이 다섯 단계가 [[MLOps]]의 6단계 순환 라이프사이클 가운데 2~5단계를 자동으로 도는 고리라는 대응은 [[MLOps]]의 「자동화된 고리」 절에 있다.

## 안전장치

1-13은 자동화를 그냥 두지 않고 두 장치를 함께 든다(덱 18 p4).

- 정책 기반 제어: 무분별한 재학습을 막는 쿨다운(Cool-down) 기간.
- Human-in-the-loop: 고위험 모델을 배포할 때는 전문가 승인을 거친다.

실행 순서도 준다(덱 18 p6). 자동화하기 전 단계로 재학습 절차, 승격(Promotion) 규칙, 롤백을 담은 플레이북을 먼저 명문화하라고 한다. 사람이 손으로 돌릴 수 있는 절차가 먼저 있어야 그것을 자동화할 수 있다는 순서로 읽힌다. 이 해석은 위키의 것이다.

[[데이터 관측성]]의 서킷 브레이커가 이상을 감지하면 파이프라인을 멈추는 쪽이라면, 자동 재학습은 이상을 감지하면 모델을 새로 만드는 쪽이다. 둘은 방향이 반대라서 쿨다운과 사람 승인 같은 안전장치가 함께 나온다. 이 대조는 위키가 한 것이다.

목표 수치의 예로 1-13은 드리프트 감지 시간(MTTD) 10분 미만, 복구·재학습 시간(MTTR) 4시간 미만을 든다(덱 18 p5). 출처는 없다.

## 데이터 엔지니어의 몫

고리의 모든 단계가 데이터에 기댄다. 강의가 데이터 엔지니어에게 맡기는 부분은 이렇다.

- 재학습 오케스트레이션: 드리프트 기반 트리거, 모델 버전·메타데이터 관리, 비용 최적화([[AI DE 강의 1-13 Skew와 Drift]] 덱 18 p5).
- 입력 데이터의 품질: 잘못된 데이터로 재학습하면 에러 없이 틀린 모델이 배포된다. [[AI DE 강의 1-14 데이터 SLA와 모니터링]]의 나비효과(VIP 구매 데이터 수집 실패 → 잘못된 데이터로 재학습 → 엉뚱한 추천 → 이탈)가 이 경우다([[데이터 SLA]]). 자동화할수록 1단계의 품질·스키마 검증이 유일한 관문이 된다는 점은 위키의 정리다.
- 라벨: 재학습 1단계는 "최신 피처·라벨"을 읽는데, 정답 라벨은 늦게 온다. [[AI DE 강의 2-04 ML 데이터 파이프라인]]은 라벨 지연이 학습 주기를 늘린다고 하고, Part 4는 prediction-label join delay를 SLI로 재고 "label 도착 후 1시간 이내 반영"을 SLO로 건다([[AI DE 강의 4-15 AI 시스템 지표와 SLA]] p20–21). 운영 쪽 처리는 [[데이터 드리프트]]의 빈칸에 모았다.
- 버전과 계보: 어떤 데이터로 어떤 모델을 학습했는지를 남긴다([[데이터와 모델 버전 관리]]). Part 4는 이 연결을 Feature Store(Feast) · Model Registry(MLflow) · Pipeline Orchestrator(Kubeflow Pipelines) 세 축으로 든다([[AI DE 강의 4-13 데이터 엔지니어링의 GPU 활용]] p320).
- 처리 속도: ETL 병목은 실험 속도, 배치 추론 처리량과 함께 재학습 주기에 직접 영향을 준다([[AI DE 강의 4-14 RAPIDS 가속 ETL]] p330).

## 사례

- Tesla의 섀도우 모드는 새 모델의 예측을 실제 운전자 조작과 백그라운드에서 비교해 엣지 케이스를 모은다. 모인 데이터가 다시 학습 데이터가 되는 고리다([[AI DE 강의 1-16 AI 파이프라인 구축 사례]]).

## LLM에서는

LLM은 지식을 파라미터에 담으므로 사실이 바뀔 때마다 다시 학습하기 어렵다. [[검색 증강 생성]]은 재학습 없이 인덱스를 갱신해 지식을 최신으로 유지하는 방법으로 소개된다([[AI DE 강의 3-12 RAG의 이해와 한계]]). 그러면 LLM 시스템에서 재학습 고리의 자리는 인덱스 갱신 파이프라인이 넘겨받는다. 이 연결은 위키의 정리이고, 강의는 인덱스 갱신의 트리거나 검증 절차를 다루지 않는다([[LLMOps]]).

## 빈칸

- 재학습 주기와 비용: 트리거 방식(드리프트·성능)과 정기 재학습 가운데 무엇을 언제 고르는지, 재학습 한 번의 비용을 어떻게 따지는지 없다.
- 평가 기준: Champion vs Challenger의 비교 지표, 통계적 유의성, 오프라인 지표와 온라인 지표가 어긋날 때의 판단이 없다. 배포 단계의 승격·롤백 지표와 임계값도 어디에도 없다([[모델 서빙]]의 빈칸).
- 피드백 루프의 편향: 모델이 고른 결과(추천 노출 등)가 다음 학습 데이터가 되면 데이터가 모델 쪽으로 치우친다. 강의는 피드백 루프를 관측 단계의 한 줄로만 든다.
- 재학습과 지속 학습(continual learning)의 구분: Part 2의 라이프사이클 5단계 이름은 "Monitoring & Continual Learning"인데([[AI DE 강의 2-02 MLOps와 ML 생애주기]]), 강의는 트리거 기반 재학습과 지속 학습을 구분해 말하지 않는다.
