# DB 면접 3 Lock과 동시성 제어

## 요약

### Q1. DB Lock이란 무엇이고, 어떤 종류가 있나요? (p24–26)

- Gold: 여러 트랜잭션의 공유 데이터 접근을 제어하는 메커니즘이다. 공유 락은 여러 트랜잭션이 동시에 같은 데이터를 읽을 수 있지만 해제될 때까지 수정은 못 한다. 배타 락은 해제될 때까지 다른 트랜잭션이 읽기와 수정 모두 못 한다.
- 등급을 가른 것: Silver는 차이는 맞았지만 공유 락이 "여러 트랜잭션이 동시에 읽기 가능"하다는 점과 목적이 "액세스 제어"라는 표현이 없었다.

### Q1-1. 낙관적 락과 비관적 락의 차이는? (p27–29)

- Gold: 비관적 락은 충돌이 날 것으로 보고 접근할 때 `SELECT FOR UPDATE`로 선점한다. DB 단에서 동작하므로 예외 시 자동으로 롤백되고, 충돌이 많을 때 맞다. 낙관적 락은 선점하지 않고 변경할 때 Version을 확인하는 compare-and-set 방식이다. 애플리케이션 단에서 구현하며 예외 시 롤백을 직접 구현해야 하고, 충돌이 적을 때 맞다.
- 등급을 가른 것: Bronze는 "락을 거느냐 안 거느냐"만 말했고, Silver는 구현과 사용 시점은 맞았지만 DB 단 대 애플리케이션 단, 롤백 주체의 차이를 빠뜨렸다.

### Q1-2. 언제 낙관적 락을, 언제 비관적 락을 쓰나요? (p30–32)

- Gold: 충돌이 드물고 롤백·재시도 비용이 낮으면 낙관적 락이다. 임계 영역이 짧아 충돌 확률 자체가 낮을 때 특히 맞다. 충돌이 잦거나 임계 영역이 길어 재시도 비용이 크면 비관적 락으로 선점하는 편이 효율적이다.
- 등급을 가른 것: Silver는 기준(충돌 빈도)과 이유(재시도 대 대기)는 맞았지만 임계 영역 길이라는 기준이 없었다.

### Q1-3. 분산 락이란? 왜 사용하나요? (p33–35)

- Gold: DB의 비관적 락은 그 DB 안의 로우만 잠근다. 재고를 차감한 뒤 외부 결제 API를 부르거나 캐시와 DB를 함께 갱신하는 것처럼 한 DB 트랜잭션으로 묶을 수 없는 자원을 함께 제어해야 할 때, Redis 같은 중앙 저장소에 락을 걸어 DB 바깥까지 동시성을 제어하는 것이 분산 락이다.
- 등급을 가른 것: Silver는 필요한 이유를 "DB가 여러 대라 비관적 락이 동작하지 않아서"로 설명했고, 자료는 이를 오해로 본다.

### Q2. Lost Update Problem이 무엇이고, 왜 격리 수준으로 해결하지 못하나요? (p36–38)

- Gold: read-modify-write 사이클에서 생긴다. SELECT로 읽고 애플리케이션에서 계산한 뒤 UPDATE로 쓰는 사이클을 두 트랜잭션이 동시에 돌면, 두 번째 쓰기가 첫 번째 변경을 포함하지 않는다. 잔액 1000원을 동시에 읽고 +500, +300을 하면 최종 잔액이 1500원 또는 1300원이 된다. 격리 수준은 Dirty Read·Non-Repeatable Read 같은 읽기 문제는 막지만 Lost Update 같은 쓰기 문제는 해결하지 못한다.
- 등급을 가른 것: Bronze는 현상만, Silver는 정의와 격리 수준의 한계는 말했지만 read-modify-write라는 패턴 이름과 예시가 없었다.

### Q2-1. Lost Update Problem을 해결하는 방법 (p39–41)

- Gold: 낙관적 락이나 비관적 락으로 해결한다. 또 SELECT한 값을 UPDATE에 넣지 않고 `UPDATE accounts SET balance = balance + 100 WHERE id = 1`처럼 원자적 쓰기 연산 하나로 처리하면 DB가 묵시적 배타 락을 얻어 자동으로 해결된다. 이때 MVCC 덕분에 다른 트랜잭션의 읽기는 막히지 않는다.
- 등급을 가른 것: Silver는 두 락만 말하고 UPDATE 문 하나로 끝내는 원자적 쓰기를 빠뜨렸다.

## 핵심

- 공유·배타 락, 낙관·비관 락, 분산 락은 [[데이터베이스 락]] 한 페이지에 모았다. 낙관적 락의 compare-and-set은 Java의 CAS와 같은 생각이다([[동기화 기법]]). 이 연결은 위키가 했다.
- Lost Update의 read-modify-write는 Java의 `count++`와 같은 구조다([[동시성 문제]]). 이 연결도 위키가 했다.
- Q2-1의 원자적 UPDATE는 맞는 답이고 실무에서 가장 먼저 쓸 방법이다. 계산을 SQL 안으로 옮길 수 있을 때만 쓸 수 있다.

## 주의·결함

- ❌ "격리 수준으로는 Lost Update를 해결하지 못한다"(p38)는 일반론으로 틀렸다. Snapshot Isolation과 SERIALIZABLE은 막고, PostgreSQL의 REPEATABLE READ는 동시 갱신을 오류로 중단시킨다. InnoDB의 REPEATABLE READ에서는 실제로 유실된다([[트랜잭션 격리 수준]]).
- ❌ 롤백 여부를 락 종류에 붙인 서술(p29)은 틀렸다. 롤백은 트랜잭션의 일이고, 낙관적 락에서 애플리케이션이 직접 할 일은 재시도다([[데이터베이스 락]]).
- ⚠️ 배타 락이 걸린 행은 "읽기도 불가"(p26)라고 한다. InnoDB의 일반 SELECT는 MVCC 스냅숏을 읽으므로 막히지 않는다. 막히는 것은 잠금 읽기와 쓰기다. 자료 스스로 p41에서 이 점을 쓴다([[데이터베이스 락]]).
- ⚠️ 분산 락 답(p35)의 예시는 락이 원자성까지 주는 것처럼 읽힌다. 락은 상호 배제만 주고, 결제 실패 시 되돌리기는 보상 트랜잭션 같은 다른 장치의 몫이다. Redis 락의 안전성 논쟁(fencing token)도 빠졌다([[데이터베이스 락]]).
