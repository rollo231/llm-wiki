## 요약

### 01. 온톨로지

- 정의(p3): 특정 도메인 안의 개념, 클래스, 속성, 그리고 이들 사이의 관계를 컴퓨터가 이해하고 처리할 수 있는 형태로 명확하게 정의한 지식 체계다. 철학의 "존재론"에서 온 말이라고 밝힌다.
- 스키마가 "어떤 컬럼이 있는가"를 정의한다면 온톨로지는 "이 데이터가 현실 세계에서 무엇을 의미하는가"까지 표현한다. 예: 사람은 회사를 다닌다, 주문은 상품을 포함한다.
- 필요성(p4): 현실의 데이터는 여러 시스템에 흩어져 있고 같은 대상을 다른 이름과 구조로 표현한다. 스키마만으로는 "같은 개념인가, 어떤 관계인가, 어떤 규칙을 따라야 하는가"를 설명하기 어렵다. 온톨로지는 개념을 통일하고 관계를 명시해 서로 다른 소스를 의미 중심으로 통합한다.
- 스키마와의 차이(p5): `orders` 테이블은 `order_id`, `user_id`, `product_id`를 담을 수 있지만, 주문이 비즈니스적으로 무엇인지, 사용자와 상품이 어떤 의미 관계인지, 다른 시스템의 개념과 어떻게 매핑되는지는 말하지 못한다. 온톨로지는 "주문은 사용자가 생성한다", "주문은 상품을 포함한다" 같은 관계를 모델링한다.

### 02. 핵심 구성 요소 (p7)

| 요소 | 뜻 | 예 |
|---|---|---|
| 클래스(Class) | 개념의 유형 | 사람, 회사, 주문, 상품 |
| 인스턴스(Instance) | 실제 개별 대상 | Blake, 아마존, 주문 12345 |
| 속성(Property) | 개체가 가진 정보 | 사람의 이름, 상품의 가격 |
| 관계(Relation) | 개체와 개체 사이의 연결 | 사람은 회사를 다닌다 |
| 제약(Constraint) | 모델이 따라야 하는 규칙 | 모든 주문은 반드시 한 명의 구매자와 연결 |

### 03. 온톨로지와 RDF, RDFS, OWL

- 온톨로지는 무엇을 정의할지에 대한 설계 원리이고, RDF는 그 정의와 데이터를 어떻게 표현할지에 대한 표준 모델이다(p8). RDF는 정보를 주어-술어-목적어 트리플로 적는다. 예: `Jeff - worksAt - Amazon`, `주문123 - contains - 상품A`.
- RDFS(p9–10)는 기본 스키마 정보를 정의한다고 설명한다. `rdfs:Class`, `rdfs:subClassOf`, `rdf:Property`, `rdfs:domain`(속성이 주로 어떤 주어 클래스에 적용되는지), `rdfs:range`(목적어가 어떤 클래스나 데이터 타입이어야 하는지). 예제는 `Employee`가 `Person`의 하위 클래스이고 `worksAt`의 domain이 `Person`, range가 `Organization`일 때 실제 데이터 `Jeff - type - Employee`, `Jeff - worksAt - Amazon`을 적는 것이다.
- OWL(p11)은 RDFS보다 표현력이 강한 온톨로지 언어다. 두 클래스가 동일하다, 서로 배타적이다, 어떤 속성은 역관계·대칭·추이적이다, 어떤 클래스는 조건을 만족하는 개체의 집합이다, 어떤 속성은 반드시 하나만 가진다 같은 규칙을 적는다.
- OWL을 꼭 써야 하나(p12): RDF는 꽤 자주 유용하고 RDFS도 메타모델링에 유용하지만 OWL이 필요한 경우는 제한적이다. 동일 개체 판별, 상속·배타 규칙을 품질 검증에 쓸 때, 정책·권한 규칙을 논리적으로 검증할 때, GraphRAG에서 개체 타입·관계 추론이 중요할 때가 그렇다. 단순 메타데이터 수집, lineage 시각화, 태그 검색 정도면 "OWL까지 가는 순간 오히려 과설계가 된다".

### 04. 온톨로지가 있다고 말할 수 있는가 (p14–15)

1. 개념 정의서가 있는가. 테이블명이 아니라 "User란 무엇인가, Customer와 Subscriber는 어떻게 다른가" 수준.
2. 관계가 컬럼 연결이 아니라 의미로 정의되어 있는가. `owns`, `subscribesTo`, `fulfills`, `derivedFrom` 같은 이름과 뜻.
3. 기계가 읽고 검증·매핑·추론·검색 확장·의미 기반 질의에 쓸 수 있는가.

결론 슬라이드는 개념 체계, 관계 정의, 속성과 제약, 사람과 시스템의 공유, 실제 검증·검색·추론·통합의 기준으로 쓰임을 모두 갖춘 경우를 온톨로지로 본다.

## 핵심

- RDFS의 domain과 range를 슬라이드는 "~이어야 한다"는 제약처럼 설명하지만, 명세의 의미론에서 둘은 추론 규칙이고, 검사에 쓸지는 응용에 맡겨져 있다. `worksAt`의 range가 `Organization`인데 `Jeff worksAt 서울`이라고 적으면 오류가 나지 않고 "서울은 Organization이다"가 추론된다. 명세 인용과 설명은 [[온톨로지]]에 있고, "이어야 한다"를 실제로 검사하는 도구는 [[SHACL]]이다([[AI DE 강의 3-11 SHACL 검증]]).
- 판단 질문 세 개 가운데 3번(기계가 읽는가)이 가장 쓸모 있다. 1·2번만 있으면 잘 쓴 용어 사전이고, [[AI DE 강의 1-15 데이터 거버넌스와 카탈로그]]의 비즈니스 메타데이터와 다르지 않다. 온톨로지가 카탈로그와 갈리는 곳은 정의가 검증·추론에 실제로 쓰이느냐다. 이 대비는 위키가 정리한 것이다([[데이터 거버넌스와 카탈로그]]).
- "OWL은 과설계가 되기 쉽다"는 조언은 강의 안에서 가장 실무적이다. [[AI DE 강의 3-03 시맨틱]]이 그린 스펙트럼(용어 사전 → 공통 엔티티 모델 → 온톨로지·지식 그래프)에서 어디까지 올라갈지를 정하는 기준이 된다([[시맨틱 계층]]).

## 주의·결함

- ⚠️ p9는 `rdf:Property`를 RDFS가 정의하는 항목으로 나열한다. `rdf:Property`는 `rdf:` 네임스페이스의 어휘이고, RDF Schema 1.1 문서가 이를 설명할 뿐이다. 나머지 넷은 `rdfs:` 어휘다.
- ⚠️ p9의 range 설명("목적어가 어떤 클래스나 데이터 타입이어야 하는지")은 추론 규칙을 제약으로 읽게 만든다. 위 「핵심」 참고.
- 온톨로지 정의(p3)에 출처가 없다. 흔히 인용되는 Gruber(1993)의 정의("an explicit specification of a conceptualization")와 그것을 다듬은 Studer 외(1998)의 "공유된 개념화의 형식적·명시적 명세"가 이 슬라이드 부제("공유된 개념과 관계의 공식 명세")에 가깝다. 이 대응은 위키가 붙인 것이다. Gruber의 논문은 T. R. Gruber, 「A Translation Approach to Portable Ontology Specifications」, Knowledge Acquisition 5(2), 1993, pp. 199–220이고, 저자 페이지가 이 논문을 "specification of a conceptualization" 정의를 처음 실은 논문으로 소개한다(https://tomgruber.org/writing/ontolingua-kaj-1993.htm , 2026-09-28 확인). Studer 외(1998)의 원문 문구는 확인하지 못했다.
- p5와 p6, p12와 p13은 같은 슬라이드다.
- "온톨로지의 RDF, RDFS, OWL"(목차 p2)과 "온톨로지와 RDF, RDFS, OWL"(본문 p8)로 절 제목이 다르다.
