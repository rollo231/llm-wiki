# AI DE Course - Data governance and catalog

**출처:** 패스트캠퍼스(Fast Campus) 데이터 엔지니어링 강의 · **Part 1 후반부**
"데이터 거버넌스와 카탈로그: AI가 데이터를 잘 찾게 만드는 법 (1)(2)(3)". 원본(로컬):
`raw/data-engineering/ai-de-course/part1/` 의 `22.`~`24.` (6p + 6p + 7p = 19p).
강의 홈: [[AI Data Engineering (Fast Campus course)]].
(챕터 번호는 추론 — [[AI DE Course - Data drift and training-serving skew]]의 주의 참조.)

## 이 덱의 핵심 프레이밍 — 자물쇠에서 나침반으로

거버넌스의 목적을 뒤집는다. **이것이 이 챕터의 기여다.**

| PAST — 수비형 거버넌스 | CURRENT — 공격형·활용 거버넌스 |
|---|---|
| *"이 데이터는 중요하니까 아무도 못 보게 막아!"* | *"어떻게 하면 더 쉽고 빠르게 데이터를 쓸까?"* |
| 법적 리스크 회피·보안. 데이터를 **금고에 가두는** 것 | AI·분석가가 즉시 찾아 쓸 수 있게 돕는 **나침반** |
| 보안 중심 · 접근 통제 · 규제 준수 | 쉬운 발견 · 빠른 활용 · 신뢰성 |

> ⚠️ **WARNING: 거버넌스 없는 데이터 레이크는 썩은 물이 고인 늪(Data Swamp)이 된다.**
> 아무도 찾지 못하고, 무엇인지 알 수 없어 결국 폐기되는 쓰레기 데이터의 무덤.

[[AI DE Course - Ch2-7 Delta Lake and ACID]]가 늪의 원인을 **기술적 결함**(ACID·스키마 강제 없음)으로
설명했다면, 이 덱은 **조직적 결함**(찾을 수 없음·정의 모호·신뢰 불가)으로 설명한다. 두 챕터가
같은 단어를 다른 층위에서 쓴다.

## (1) 80%의 시간은 어디로 가나

강의 주장: **데이터 과학자가 데이터 탐색·정제·준비에 80%의 시간을 쓴다.** 최고급 인력이 모델
개발이 아니라 데이터 이해에 시간을 허비한다. 원인 3종:

| 원인 | 실제 질문 | 무엇이 없나 |
|---|---|---|
| **위치·소유자 불명** (Where & Who?) | "작년 매출 데이터가 어디 있지?" | 사내 메신저로 수소문하는 데 며칠 |
| **모호한 데이터 정의** (What?) | "이 컬럼의 '가격'은 세금 포함인가요?" | 메타데이터와 비즈니스 용어 정의. 과거 코드를 뒤지거나 개발자를 찾아다녀야 |
| **신뢰할 수 없는 품질** (Trust?) | "오늘 아침에 업데이트된 최신본이 맞나요?" | **데이터 계보(lineage)** — 없으니 검증에 또 시간을 허비 |

> **결과: 데이터 사이언티스트가 '데이터 고고학자'로 전락한다.**

두 번째 항목("세금 포함인가?")은 [[Data catalog and semantic layer]]의 **semantic layer**가 푸는
문제와 정확히 같다 — 그 페이지의 "매출에 환불이 포함되나?"와 같은 종류의 질문이다.

### 현대 거버넌스의 3대 요소

| | 표준화 (Standardization) | 권한 관리 (Access Mgmt) | 가시성 (Visibility) |
|---|---|---|---|
| 한 줄 | "전사적으로 같은 언어를 씁니다" | "안전하면서도 빠르게 엽니다" | "어디에 무엇이 있는지 밝힙니다" |
| 내용 | 이름·형식·계산 공식 통일 | 무조건 막는 게 아니라 **직무에 따라 유연하게 허용하고 승인을 자동화** | 위치·품질·흐름을 한눈에 |
| 실행 | 전사 데이터 사전, 명명 규칙 통일, **지표 정의 일원화** | **RBAC**, 민감 정보 마스킹, 셀프서비스 승인 워크플로우 | **데이터 카탈로그**, **lineage 시각화**, 품질 점수 모니터링 |

## (2) 카탈로그와 메타데이터 3분류

정의: **"우리 회사 내부 데이터를 위한 구글 검색 엔진이자 도서관 색인 카드."**
검색 결과 예시: `20대 VIP 구매 내역 → 위치: AWS Redshift · 형식: Parquet · Update: 10분 전`.

### 3가지 메타데이터 — 이 덱의 실용적 산출물

**"이 세 가지가 모두 모여야만 완벽한 데이터 지도가 완성된다."**

| | 기술적 메타데이터 | 비즈니스 메타데이터 | 운영 메타데이터 |
|---|---|---|---|
| 한 줄 | "데이터의 **물리적 뼈대**" | "데이터의 **의미와 책임**" | "데이터의 **건강 상태**" |
| 담는 것 | DB/테이블명(물리적 주소), 스키마(컬럼 구조·타입), 파티션 정보 | 용어 사전(Glossary), **데이터 소유자(Owner)와 연락처**, 규제·보안(PII 여부·접근 권한 등급) | **최신성**(마지막 업데이트 시간), **품질 점수**(Null 비율·정합성 체크 결과), **사용량**(조회 빈도·인기 테이블 순위) |

> **이 3분할이 [[Data catalog and semantic layer]]의 3분할(metastore / data catalog / semantic layer)과
> 다른 축이라는 점에 주의.** 그 페이지는 **도구/사용자**로 나눈다(기계용 / 사람용 / 정의용).
> 이 덱은 **정보의 종류**로 나눈다. 모순이 아니라 다른 절단면이다 — 기술적 메타데이터는 주로
> metastore에, 비즈니스 메타데이터는 data catalog에, 운영 메타데이터는 관측성 도구에 산다.

### 데이터 계보 (Lineage)

```
원본 데이터 (Source)  →  가공/변환 (ETL)  →  AI 모델 (Consumption)
로그 테이블 A            중간 집계 테이블 B     추천 시스템 모델 C
* 스키마 변경됨!         Daily Batch Job       장애 발생 !
                    ← ← ← 장애 원인 역추적 ← ← ←
```

3가지 용도:

- **빠른 원인 규명(RCA)** — 모델이 이상하게 동작할 때 족보를 역추적해 **"어제 원본 테이블 스키마가
  변경됨"을 1분 만에** 찾아낸다
- **사전 영향도 분석** — *"내가 이 테이블을 수정하면 누가 다칠까?"* 변경 전에 하위(downstream) 영향
  범위를 미리 파악해 장애를 예방
- **신뢰성·투명성** — 블랙박스 같은 AI가 어떤 데이터를 학습했는지 증명

→ [[Data SLA and observability]]의 RCA 프로세스에서 이게 재료가 된다.
스키마 변경이 하류를 깨는 경로는 [[Change data capture]]에서도 같은 문제로 나온다.

## (3) 자동화 — 이 덱의 가장 현실적인 부분

> **현실적인 의문: "수십만 개가 넘는 테이블의 메타데이터를 도대체 누가, 언제 일일이 수동으로
> 입력하나요?" 담당자가 엑셀에 타자 치듯 입력해야 한다면 이 시스템은 지속 가능할까요?**

### 수동 카탈로그가 실패하는 3단계

1. **위키/엑셀 의존의 한계** — 매일 수백 개 테이블이 생성·변경되는 속도를 사람이 따라잡을 수 없다
2. **담당 공백과 최신성 저하** — 담당자가 퇴사하거나 바빠서 업데이트를 놓치면 즉시 메타데이터와
   실데이터가 불일치
3. **신뢰 붕괴 = "예쁜 쓰레기"** — 잘못된 설명을 믿고 분석했다가 낭패를 본 사용자는 **다시는
   카탈로그를 찾지 않는다**

> 3번이 핵심 통찰이다 — **카탈로그의 실패 모드는 '없음'이 아니라 '틀림'이다.**

### 자동화 처방

- **실시간 동기화** — DB 스키마 크롤링, 쿼리 로그 분석으로 테이블 변경을 자동 감지·반영
- **자동 리네이지** — **SQL 파싱**으로 데이터 흐름을 자동 시각화
- **운영 목표(SLA)** — 메타데이터 최신성 **< 24h 유지** · 변경 감지 알림 **100% 커버리지**

### LLM 기반 자동 태깅 & 자연어 검색

**"AI가 AI를 돕는다."** 카탈로그 AI가 컬럼명·데이터 패턴·샘플 값을 분석해 비즈니스 의미와 보안
등급을 스스로 판단하고 태그를 붙인다.

| Column | Sample Data | AI Suggested Tags |
|---|---|---|
| `user_id` | `u_829102` | Primary Key |
| `phone_encrypted` | `010-****-1234` | **PII** · Sensitive · Contact |
| `last_login_ts` | `2024-03-07…` | Timestamp |

**자연어 질의(Text-to-SQL)** — *"최근 3개월 동안 탈퇴한 고객들의 결제 이력 데이터 어디 있어?"* →
관련 테이블 2개(`user_churn_log_90d`, `payment_history`)를 찾아주고 JOIN 쿼리까지 생성.

> **운영 포인트: "Human-in-the-loop" — AI의 추천을 담당자가 최종 검수하여 정확도를 지속 향상시킨다.**

이 지점이 [[Data catalog and semantic layer]]가 남긴 열린 질문("LLM 에이전트가 웨어하우스를 질의하는
맥락에서 semantic layer가 다시 뜬다")과 맞물린다 — 다만 강의는 semantic layer라는 용어를 쓰지 않고
**카탈로그 자체가 그 역할을 흡수하는 그림**을 제시한다.

### 도구와 규칙

- **도구** — **DataHub · Amundsen · Atlan** 도입. 레이크·DW와 안정적 연동, 메타데이터 수집
  파이프라인 자동화.
- **CI/CD 규칙 (강제)** — 신규 테이블 배포 시 **3줄 이상 설명 필수화** · **데이터 오너·도메인 정보
  명시 강제** · **보안 등급·분류 태그 누락 시 배포 차단**.
- **운영 SLA** — 스키마 변경 시 즉시 알림 · 데이터 품질 경보(Null 급증·적재 지연) ·
  자동 리네이지 추출 **성공률** 모니터링.
- **문화 정착** — 도메인별 **데이터 스튜어드(Steward)** 지정 · 주간 태그 리뷰 미팅 · 온보딩 교육 ·
  전사 인식 개선 캠페인.

> **CI/CD로 메타데이터를 강제하는 것이 이 덱에서 가장 실행 가능한 제안이다** — 문서화를 선의에
> 맡기지 않고 배포 게이트로 만든다.

### 궁극 목표 — 데이터 민주화

마케터·기획자·분석가 등 **누구나 스스로 안전하게 데이터를 찾고 활용하는 상태.**
강의의 결론: **엔지니어의 진짜 역할은 도구 구축이 아니라 이 상태를 만드는 것.**

## 검증 필요

- **"데이터 과학자가 80%의 시간을 탐색에 낭비"** — 출처 없음. 케이스 스터디 챕터는 같은 종류의 문제를
  **"데이터 준비가 전체 작업 시간의 70% 이상"** 으로 제시한다. 두 수치는 대상이 다르지만
  (탐색·이해 vs 준비 전체) **둘 다 근거가 없다.**
  → [[AI DE Course - Ch3-1,2 Batch and ETL]]의 '검증 필요' 참조.

## 기존 페이지와의 대조

- **보강** — 3가지 메타데이터 분류(기술·비즈니스·운영), lineage의 3용도, **수동 카탈로그의 실패
  메커니즘**, LLM 자동 태깅, **CI/CD 강제 규칙**, DataHub·Amundsen·Atlan.
- **일치** — lineage 수집이 자동이어야 하고 SQL 파싱이 주요 경로라는 것이
  [[Data catalog and semantic layer]]와 같다. 거버넌스의 본질이 "사람과 프로세스"라는 것도 —
  이 덱이 데이터 스튜어드·문화 정착을 강조하는 것으로 같은 결론에 도달한다.
- **다른 절단면** — 위의 메타데이터 3분류 주의 참조.
- **없는 것** — **OpenLineage**가 언급되지 않는다. lineage 포맷 표준화 이야기가 빠져 있다.
