## 요약

### 01. Training-Serving Skew란

- **정의** — 모델 학습 때 쓴 데이터 분포·처리 방식과 실제 서빙 때의 입력 데이터가 서로 다른 상태. 모델 자체는 정상이어도
  입력 차이만으로 성능이 급격히 떨어질 수 있다.
- **증상** — 오프라인 평가 지표는 높은데 프로덕션 성능은 계속 떨어진다.
- **영향** — 잘못된 의사결정의 자동화, 비즈니스 KPI 악화, 재학습 → 배포 반복으로 운영 비용 증가.

### 02. 원인

- **주요 원인(p41)** — Feature 생성 로직 불일치 · 데이터 분포 변화(Data Drift) · 라벨 생성 방식 차이 · 데이터 누락·지연 ·
  서빙 환경의 제약.
- **학습과 서빙 파이프라인의 성질이 다르다(p42–43)**

| | 학습 파이프라인 | 서빙 파이프라인 |
|---|---|---|
| 데이터 | 과거 | 현재·실시간 |
| 범위 | 전체 데이터 접근 가능 | 부분 데이터, 누락 가능 |
| 지연 | 처리 지연 허용 | 지연 시간 제약 |
| 설계 중심 | 정확성 | 안정성과 일관성 |

  → "학습·서빙이 같은 Feature를 만들기 어려운 구조"
- **환경 차이가 왜 스큐가 되나(p44)** — Feature는 단순한 값이 아니라 **데이터 소스 + 집계 기준 + 시간 해석 + 전처리 규칙**의
  결과다. 환경이 다르면 이 조합을 완전히 똑같이 구현할 수 없다: 환경 차이 → 구현 차이 → Feature 값 차이 → 스큐.
- **왜 반복되나(p45)** — 학습과 서빙은 다른 코드·다른 팀·다른 실행 환경이다(학습: 과거/완전/배치, 서빙: 현재/부분/지연·누락
  가능). Feature 로직은 자연스럽게 갈라진다. **문제는 이 분리를 설계로 통제하지 않는 것**이다.

### 03. 대표적인 네 가지 형태

| 형태 | 학습 쪽 | 서빙 쪽 | 무엇이 달라지나 |
|---|---|---|---|
| **시간 기준** — Event Time vs Processing Time | 배치로 이벤트 시간(실제 행동 시각) 기반 집계가 쉽다 | 실시간이라 처리 시간(시스템이 받은·처리한 시각) 기반이 되기 쉽다 | "최근 10분"에 들어가는 이벤트 집합 — 지연·누락 이벤트 때문에 달라진다 |
| **집계 범위** — Full vs Partial Window | 전체 데이터로 정확한 기간 전체(예: 7일치 완전) 집계 | 최신 구간만 실시간, 나머지는 배치 값·캐시가 섞인 부분 집계 | 지연·캐시·배치 갱신 주기 때문에 기간의 일부만 반영된다 |
| **결측 처리** — Null→0 vs Drop vs 조회 실패 | 결측을 0·평균으로 채우거나 결측 row를 drop | 실시간 조회 실패·지연도 결측으로 나타난다 | **진짜 값 없음과 조회 실패를 같은 0으로** 처리하면 입력 분포가 달라진다. 결측 처리는 전처리가 아니라 의미 정의다 |
| **스케일링** — Global vs Local Normalization | 학습 전체 분포의 mean·std·min·max(global) | 최근 window·사용자 단위로 즉석 재계산(local) | 같은 원시 값이 다른 입력이 된다. 학습은 라이브러리, 서빙은 직접 구현하면서 공식이 달라지기도 한다 |

### 04. 해결의 출발점

- **스큐는 모델 성능 문제가 아니라 Feature 생성 규칙 문제다.** 위 네 규칙이 운영에서 가장 자주 깨진다.
- **원칙: Training은 Serving을 따라가야 한다** — 서빙에서 가능한 규칙을 학습에도 동일하게 적용한다.
- **네 패턴에 대한 현실적인 대응(p51)**

| 형태 | 대응 |
|---|---|
| 시간 기준 | Time semantics 고정 — event vs processing 중 하나를 골라 양쪽에 동일 적용, 지연 이벤트를 얼마나 허용할지(워터마크) 정책화 |
| 집계 범위 | Window를 데이터 가용성에 맞게 설계 — 실시간에서 full window가 불가능하면 feature를 재정의, long-term(배치) + short-term(실시간)으로 분리 |
| 결측 처리 | Missing을 의미로 분리 — 값 없음과 조회 실패를 같은 0으로 처리하지 않음, `is_missing` 플래그·fallback 정책 |
| 스케일링 | Scaling 파라미터를 아티팩트로 고정 — global stats(mean·std·min·max)를 버전으로 함께 배포, 학습·서빙 동일 로직 |

- **규칙을 시스템으로 강제하는 대표 수단** — 공용 변환 로직 / Feature Contract / (필요 시) Feature Store.
  → [[피처 스토어]]

## 핵심

- **Part 2 데이터 절반에서 가장 좋은 강의다.** Part 1에서 스큐는 "취소 예외 처리 누락" 일화 하나였다
  ([[AI DE 강의 1-13 Skew와 Drift]]). 이 강의는 그것을 **네 가지 규칙 부류의 점검표**로 바꾼다 — 새 피처를 만들 때
  "시간 기준·집계 범위·결측·스케일링을 양쪽이 같게 정했나"를 물을 수 있다. → [[학습-서빙 스큐]]
- **"Training은 Serving을 따라가야 한다"는 의도된 맞교환이다.** 학습 쪽은 full window·이벤트 시간으로 더 정확한 피처를
  만들 수 있지만, 서빙에서 재현할 수 없는 정확성은 버리고 **입력이 똑같다는 보장**을 택한다. 모델이 학습한 세계와 운영에서
  보는 세계를 일치시키는 편이 오프라인 지표를 높이는 것보다 낫다는 판단이다. *(위키의 관찰)*
- **시간 기준 형태는 [[스트림 처리]]의 이벤트 시간 vs 처리 시간 그대로다.** Part 1은 그 구분을 스트림 엔진의 정확성 문제로
  다뤘고, 여기서는 같은 구분이 학습과 서빙 사이의 불일치로 나타난다. 대응(워터마크 정책화)도 같은 장치다.
- **스케일링 파라미터를 아티팩트로 배포하라는 대응은 버전 관리 요구다** — 학습 때 계산된 통계값도 모델의 일부다.
  → [[데이터와 모델 버전 관리]]
- **Part 1 사례를 네 형태에 대 보면** — 취소의 부호 차이(-100만 vs +100만)는 예외·결측 처리 규칙의 차이이고, 분모 차이
  (1건 vs 3건)는 집계 기준의 차이다. 한 피처에 두 형태가 겹쳐 있었다. *(위키의 연결)*
- **"오프라인은 높은데 프로덕션은 낮다"는 증상은 [[데이터 누수]]와 같다.** 누수는 학습·평가 데이터에 미래 정보가 섞여
  오프라인 지표가 **부풀려진** 것이고, 스큐는 오프라인 지표는 정직한데 서빙 입력이 **달라진** 것이다. 증상만으로는 구분되지
  않으므로, 학습 데이터 생성 시점 정합성과 서빙 입력 분포를 따로 점검해야 한다. *(위키의 관찰)*
- **바로 뒤 강의와 긴장이 있다** — [[AI DE 강의 2-07 Batch vs Online 서빙 아키텍처]]는 온라인 서빙의 운영 요소로 "Feature
  조회 실패 시 기본값"을 든다. 이 강의의 결측 처리 형태가 경고하는 바로 그 지점인데, 강의는 둘을 잇지 않는다.

## 주의·결함

- ✅ **원인 목록에 Data Drift가 들어 있는 것은 Google의 정의와 맞는다.** Zinkevich의 「Rules of Machine Learning」은 스큐를
  학습과 서빙의 **성능 차이**로 정의하고 원인 셋 중 하나로 데이터 변화를 든다. [Google for Developers, 「Rules of Machine
  Learning」 — "Training-serving skew is a difference between performance during training and performance during
  serving. This skew can be caused by: A discrepancy between how you handle data in the training and serving pipelines.
  A change in the data between when you train and when you serve. A feedback loop between your model and your
  algorithm." https://developers.google.com/machine-learning/guides/rules-of-ml , 2026-09-14 확인] 반면 TFDV·Vertex AI는
  스큐를 **학습 vs 서빙 분포 비교**, 드리프트를 **시간에 따른 변화**로 쓴다 — 용어가 두 갈래다. → [[학습-서빙 스큐]]
  - 이 때문에 위키가 Part 1에서 세운 "스큐는 코드, 드리프트는 세상 — 원인이 반대"라는 대비는 과장이었고, 로직 불일치형
    스큐에만 맞도록 좁혔다(2026-09-14 위키 정정).
- **원인 목록이 여러 축을 섞는다** — 로직 불일치(Feature 로직·라벨 생성), 세상의 변화(Data Drift), 데이터 가용성(누락·지연,
  서빙 제약)이 한 목록에 있다. 그런데 03의 네 형태는 **전부 규칙 불일치**이고 드리프트는 그중에 없다. 04의 대응도 드리프트를
  다루지 않는다. 어느 원인을 이 강의가 막는지 밝히지 않는다. *(위키의 관찰)* → [[데이터 드리프트]]
- **"Feature Contract"와 "공용 변환 로직"은 이름만 나온다** — 계약에 무엇을 적는지, 공용 로직을 어떤 형태(라이브러리·SQL·
  피처 스토어 정의)로 공유하는지 설명이 없고, 세 강제 수단의 비교(언제 피처 스토어까지 가나)도 없다. 피처 스토어가 필요한
  조건은 [[AI DE 강의 2-10 Feature Store 기본 개념]]에 따로 있다.
