# AI DE 강의 3-10 지식 그래프 파이프라인

[[AI 데이터 엔지니어링 강의]] Part 3의 Ch3 소단원 3이다. 온톨로지를 잘 정의해도 그래프는 저절로 생기지 않는다는 데서 출발해, 원천 데이터에서 RDF 그래프를 만들고 검증·적재·갱신하기까지를 단계별로 설명한다. 강의의 결론은 지식 그래프가 "그래프가 들어가는 ELT/ETL 파이프라인"이고, 데이터 엔지니어는 새로운 데이터 제품용 파이프라인을 하나 더 운영하게 된다는 것이다.

## 요약

### 01. 파이프라인의 중요성 (p32–34)

실제 시스템은 원천 데이터 수집, 정규화, 식별자 설계, 엔터티 분리, 관계 생성, RDF 변환, 검증, 적재, 업데이트를 파이프라인으로 운영해야 한다. 강의는 "그래프는 단순 파일 변환이 아니라 데이터 엔지니어링 파이프라인의 문제"라고 한다. 개요의 흐름은 수집 → 정규화 → 의미 매핑 → 그래프 생성 → 검증 → 제공이다.

### 02. 세부 단계 (p35–44)

| 세부 단계 | 내용 | 예 |
|---|---|---|
| 1. 원천 데이터 수집 | 소스는 보통 하나가 아니다. 어떤 소스가 있고 어떤 키로 연결되는지 파악한다. "그래프 생성은 단일 소스 적재가 아니라 다중 소스 통합" | 이커머스(MSA): 회원 DB, 주문 DB, 상품·브랜드 마스터, 이벤트 로그, 운영 문서. 데이터 플랫폼: 메타스토어, Airflow, BI, 카탈로그, 품질 검사, 권한·조직 정보 |
| 2. 정규화·품질 정리 | RDF 변환 전에 테이블부터 바로잡는다. 잘못된 상태로 만들면 관계가 오염되고 초기 오염은 크게 번진다 | 중복 고객, 브랜드명 표기 차이(`iphone`·`Iphone`), datetime·timestamp 불일치, NULL 처리, 공백·대소문자 |
| 3. 식별자 설계 | 같은 대상을 같은 개체로 묶는 기준. "좋은 그래프는 좋은 edge보다 좋은 node identity부터 시작." 안정적인 비즈니스 키나 복합 키를 쓴다 | Dataset = platform + database + schema + table, Job = orchestrator + dag/task, Dashboard = tool + workspace + dashboard_id |
| 4. 엔티티·관계 분해 | 테이블을 개체와 연결로 다시 본다. 조인 테이블은 단순 연결일 수도, 독립 개체일 수도 있다 | `order_items`에 수량·할인액·옵션·상태가 붙으면 관계가 아니라 개체로 승격 |
| 5. 온톨로지 매핑 | 소스 컬럼을 온톨로지 클래스·프로퍼티에 잇는다. 매핑 명세는 코드에 하드코딩하지 말고 따로 관리한다 | `orders.customer_id` → `ex:placesOrder`의 연결 근거 |
| 6. RDF 생성 | 행을 트리플로 바꾼다. Direct Mapping은 DB 구조를 거의 그대로 반영해 빨리 시작할 수 있지만 target vocabulary를 바꾸지 못하고, R2RML은 원하는 온톨로지 기준으로 커스텀 매핑하며 "실무에서 많이 사용" | |
| 7. 검증·품질 관리 | SHACL shape로 클래스별 필수 속성, 최소 개수, 값 타입, 관계 형태를 검사한다. "단순 파이프라인보다 검증이 더 중요" | Order에 Customer 타입이 붙음, Brand 연결 없는 Product, 문자열 가격, 중복 생성된 개체 |
| 8. 추론·보강 | 그래프를 지식 레이어로 올린다. 운영 안정성 때문에 필요한 범위까지만 두기도 한다 | `VIPCustomer` 인스턴스를 `Customer`로도 해석, A → B → C upstream으로 간접 영향 범위 계산 |
| 9. 저장·질의·서비스 | triple store 적재, SPARQL endpoint, 검색·추천·지식 탐색 UI, AI context layer, GraphRAG. "결국 쿼리 가능한 구조를 만들어야 의미가 있다" | "이 고객이 주문한 상품의 브랜드는?" |
| 10. 증분 갱신과 운영 | 전체 재생성인가 증분인가, 삭제·중복 병합·버전 충돌, lineage와 provenance를 어떻게 남기나 | 새 Job run마다 lineage event 반영, 데이터셋 스키마 변경 시 graph validation 재실행 |

### 03. 데이터 엔지니어의 관점 (p45)

현실적인 구현 순서: 원천 수집 → 정규화 레이어 → 식별자 정책 수립 → 매핑 레이어 → RDF 생성 및 적재 → SHACL 검증 → SPARQL·검색·API 제공 → 스케줄링·증분 갱신.

## 핵심

- 이 강의는 Part 3에서 Part 1·2와 가장 잘 이어진다. 2단계의 "초기 오염이 크게 번진다"는 [[데이터 SLA]]의 침묵의 실패와 같은 걱정이고, 10단계의 전체 재생성과 증분 반영 사이의 선택, 중복 병합은 [[배치 처리]]와 [[멱등성]]의 문제(같은 입력을 다시 흘려도 개체가 두 번 생기지 않아야 한다)다. 강의는 이 연결을 말하지 않는다. 위키가 이은 것이다.
- 3단계 식별자 설계가 사실상 엔티티 해석(entity resolution)이다. 식별자가 흔들리면 7단계의 "같은 개체가 두 번 생성됨" 오류가 생기므로, 검증이 잡는 오류의 상당수는 앞 단계에서 만들어진다.
- 7단계 검증을 강의는 "SHACL이 중요"로 요약한다. 규칙 묶음을 그래프용 데이터 계약처럼 운영한다는 발상은 다음 강의에서 나온다([[AI DE 강의 3-11 SHACL 검증]] · [[SHACL]] · [[데이터 계약]]).
- 8단계의 "A가 B의 upstream이고 B가 C의 upstream이면 간접 영향"은 추이적 속성 추론이다. OWL로 `upstreamOf`를 추이적 속성으로 선언하면 얻을 수 있는 결과인데, 강의는 추론 수단을 밝히지 않는다([[온톨로지]]). 위키의 보충이다.

## 주의·결함

- ❗ 단계 수와 번호가 세 곳에서 서로 맞지 않는다. 개요는 1~7단계(p33–34), 세부 설명은 1~10단계(p35–44), 구현 순서는 1~8(p45)이고, 개요 머리의 화살표 흐름은 여섯 단계다. 같은 번호가 다른 일을 가리킨다.

| 번호 | 개요 (p33–34) | 세부 (p35–44) | 구현 순서 (p45) |
|---|---|---|---|
| 1 | 원천 데이터 수집 | 원천 데이터 수집 | 원천 데이터 수집 |
| 2 | 정규화·품질 정리 | 정규화·품질 정리 | 정규화 레이어 구축 |
| 3 | 식별자와 엔터티 기준 | 식별자 설계 | 식별자 정책 수립 |
| 4 | 온톨로지 & 매핑 | 엔티티와 관계 분해 | 매핑 레이어 구현 |
| 5 | 트리플/그래프 생성 | 온톨로지와 매핑 | RDF 생성 및 적재 |
| 6 | 검증과 보강 | RDF 생성 | SHACL 검증 |
| 7 | 저장과 서비스 | 검증과 품질 관리 | SPARQL/검색/API 제공 |
| 8 | — | 추론과 보강 | 스케줄링/증분 갱신 |
| 9 | — | 저장, 질의, 서비스 연결 | — |
| 10 | — | 증분 갱신과 운영 | — |

개요와 세부는 "엔티티와 관계 분해"를 넣느냐, 검증과 보강을 한 단계로 보느냐에서 갈린다. 구현 순서는 적재를 검증보다 앞에 두어(5 "RDF 생성 및 적재" → 6 "SHACL 검증") 세부 설명(7 검증 → 9 적재)과 순서가 반대다. 추론·보강 단계는 구현 순서에 없다.
- ⚠️ 6단계의 Direct Mapping과 R2RML은 둘 다 2012-09-27 W3C Recommendation이다(https://www.w3.org/TR/rdb-direct-mapping/ · https://www.w3.org/TR/r2rml/ , 2026-09-28 확인). "R2RML이 실무에서 많이 사용"은 단서가 필요하다. R2RML은 관계형 DB 전용이고, CSV·JSON·XML까지 다루는 RML(R2RML의 상위 집합, W3C 표준이 아닌 KG-Construct Community Group 초안)과 데이터를 옮기지 않고 SPARQL을 SQL로 바꿔 실행하는 Ontop 같은 가상 지식 그래프 도구도 쓰인다. 출처와 인용은 [[온톨로지]]에 있다. 어느 쪽이 더 많이 쓰이는지는 확인하지 못했다.
- p45 "식별자 정책 수림"은 "수립"의 오타다.
- 개요 머리의 "의미 매핑"과 세부의 "온톨로지와 매핑"은 같은 단계를 다른 이름으로 부른다.
