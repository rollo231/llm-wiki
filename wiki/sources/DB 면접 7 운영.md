# DB 면접 7 운영

[[인프런 DB 면접 강의]]의 Section 7이자 마지막 섹션. 슬로우 쿼리 대응과 EXPLAIN, 데이터가 늘었을 때의 대응, Clustering·Replication·Sharding의 구분과 MySQL 복제 구현, 데드락, 장애 대응 순서와 모니터링 메트릭을 묻는다. 주 질문 4개, 꼬리 질문 5개. 앞 섹션은 [[DB 면접 6 커넥션과 커넥션 풀]]이다.

## 요약

### Q1. 운영 중 슬로우 쿼리가 발생하면 어떻게 대처하나 (p108–110)

- Gold: 네 단계다. 슬로우 쿼리 로그(`long_query_time`)를 켜서 문제 쿼리를 찾고, EXPLAIN으로 실행 계획을 분석해 풀스캔이나 비효율적 조인을 찾고, 인덱스 추가나 쿼리 리팩토링으로 고치고, 그래도 안 되면 테이블 구조 변경이나 캐싱을 검토한다.
- 등급을 가른 것: Bronze는 "EXPLAIN으로 보고 인덱스를 건다"만 말하고 발견 단계가 없었다. Silver는 발견 → 분석 → 조치 흐름은 좋았지만 인덱스로 안 될 때의 후속 대응을 빠뜨렸다.

### Q1-1. EXPLAIN에서 무엇을 봐야 하나 (p111–113)

- Gold: `type`이 ALL(풀스캔)인지 ref/range(인덱스 사용)인지, `rows`의 예상 스캔 행 수가 과도하지 않은지, `key`에 실제 쓰인 인덱스, `Extra`에 Using filesort·Using temporary 같은 비효율 연산이 있는지 본다.
- 등급을 가른 것: Bronze는 `type`만, Silver는 `type`과 `key`만 말하고 `rows`와 `Extra`를 빠뜨렸다.

### Q1-2. 데이터가 많아져 쿼리가 느려지면 어떻게 하나 (p114–116)

- Gold: 먼저 쿼리 수준에서 푼다(인덱스 최적화로 풀스캔 제거, 조인·서브쿼리 튜닝). 그래도 안 되면 병목 원인에 따라 고른다. 조회 범위가 넓으면 파티셔닝, 안 쓰는 데이터가 테이블을 키우면 아카이빙, 읽기 부하면 캐싱이나 Replication, 쓰기 처리량 자체가 한계면 마지막으로 샤딩이다.
- 등급을 가른 것: Silver는 "인덱스를 최적화하고 필요하면 샤딩"으로 두 끝만 말하고, 원인에 따라 전략을 고르는 중간 단계를 빠뜨렸다.

### Q2. Clustering, Replication, Sharding의 차이 (p117–119)

- Gold: Clustering은 DB 스토리지 하나를 두고 여러 DB 서버를 묶는 방식으로, Active-StandBy로 가용성을 유지하며 정합성을 보장한다. Replication은 Master(쓰기)와 Slave(읽기)로 나누고 각자 스토리지를 가진다. 읽기 부하를 나눌 수 있지만 동기화 지연이 생길 수 있다. Sharding은 테이블을 특정 기준으로 나눠 여러 DB 서버에 저장한다. 읽기·쓰기 모두 나눌 수 있지만 여러 샤드에 걸친 조인과 트랜잭션이 복잡해진다.
- 등급을 가른 것: Bronze는 "다 서버를 여러 대 두는데 방식이 다르다"로 차이를 말하지 못했다. Silver는 정의는 맞았지만 정합성 보장 여부와 장단점을 빠뜨렸다.

### Q2-1. Replication은 어떻게 구현되나 (p120–122)

- Gold: MySQL 기준으로 세 단계다. Master에서 쓰기 트랜잭션이 Binlog에 기록되고, Slave의 IO Thread가 Master의 Binlog를 복사해 Relay log에 저장하고, Slave의 SQL Thread가 Relay log를 읽어 같은 트랜잭션을 재실행한다.
- 등급을 가른 것: Silver는 "Slave로 복사된다"는 결론만 말하고 Binlog → Relay log → SQL Thread 과정을 빠뜨렸다.

### Q3. 데드락이 무엇이고 DB에서 왜 생기나 (p123–125)

- Gold: 둘 이상의 트랜잭션이 서로가 가진 락을 기다리며 무한 대기하는 상태다. 핵심 원인은 서로 다른 순서로 락을 얻는 것이다. A가 레코드 1을 잠그고 2를 요청하는 동안 B가 2를 잠그고 1을 요청하면 서로를 기다린다. 트랜잭션이 길수록 락 보유 시간이 늘어 확률이 오른다.
- 등급을 가른 것: Silver의 "락이 꼬여서"가 모호하다고 지적했다. 왜 꼬이는지(획득 순서)와 시나리오가 빠졌다.

### Q3-1. 데드락을 어떻게 감지하고 대처하나 (p126–128)

- Gold: InnoDB는 wait-for graph로 데드락을 자동 감지하고 비용이 적은 트랜잭션을 롤백한다. 예방으로는 락 획득 순서를 일관되게 유지하고, 트랜잭션 범위를 최소화하고, `lock_wait_timeout`을 설정한다.
- 등급을 가른 것: Silver는 자동 감지만 말하고 예방 방법(순서 통일, 범위 최소화, 타임아웃)을 빠뜨렸다.

### Q4. DB에 장애가 나면 어떤 순서로 접근하나 (p129–131)

- Gold: 네 단계다. 모니터링 대시보드로 현상을 파악하고(CPU·메모리·커넥션 수·슬로우 쿼리 수), `SHOW PROCESSLIST`로 실행 중인 쿼리와 락 대기를 확인하고, 원인을 쿼리 문제(슬로우 쿼리·풀스캔) / 락 경합(데드락·장시간 트랜잭션) / 리소스 부족(커넥션 풀 고갈·디스크 I/O 포화)으로 나누고, 원인별로 대응한다(EXPLAIN 튜닝, 트랜잭션 범위 축소·락 해제, 스케일 업·아웃이나 풀 조정).
- 등급을 가른 것: Bronze는 "로그를 보고 해결한다"로 순서가 없었다. Silver는 흐름은 좋았지만 `SHOW PROCESSLIST`와 원인 분류 단계를 빠뜨렸다.

### Q4-1. DB 모니터링의 주요 메트릭 (p132–134)

- Gold: 트래픽·DB 내부·리소스 세 관점으로 본다. 트래픽은 QPS와 슬로우 쿼리 수, DB 내부는 InnoDB Buffer Pool Hit Ratio(낮으면 디스크 I/O 증가 신호)·Replication Lag·락 대기 시간, 리소스는 활성 커넥션 수와 CPU·메모리다.
- 등급을 가른 것: Silver는 CPU·메모리·슬로우 쿼리 수 같은 서버 메트릭만 말하고, DB 내부 동작을 반영하는 메트릭을 빠뜨렸다.

## 핵심

- 슬로우 쿼리(Q1), EXPLAIN(Q1-1), 데이터 증가(Q1-2)는 발견 → 분석 → 쿼리 수준 조치 → 구조 변경의 한 사다리다([[실행 계획]]). Q1-2의 파티셔닝·아카이빙·Replication·샤딩 구분은 [[샤딩]]에 옮겼다.
- Q2의 세 방식 구분에서 Replication과 Sharding은 맞지만 Clustering의 정의는 벤더마다 다르다([[복제]]).
- MySQL 복제의 세 단계(Q2-1)는 구조로는 맞고 스레드 이름이 바뀌었다([[복제]] · [[MySQL]]).
- 장애 대응 순서(Q4)와 메트릭(Q4-1)은 그대로 써도 되는 틀이다. 원인 분류의 세 칸은 [[DB 면접 3 Lock과 동시성 제어]] · [[DB 면접 6 커넥션과 커넥션 풀]] · [[실행 계획]]으로 이어진다. 이 연결은 위키가 했다.

## 주의·결함

- ❌ 데드락 예방으로 든 `lock_wait_timeout`(p128)은 메타데이터 락 타임아웃이다. 행 락 대기는 `innodb_lock_wait_timeout`(기본 50초)이 정한다([[데드락 재현과 해법]]).
- ⚠️ "비용이 적은 트랜잭션을 롤백"(p128)은 InnoDB가 변경한 행 수로 작은 트랜잭션을 고르는 것을 뭉뚱그린 말이다([[데드락 재현과 해법]]).
- ⚠️ Clustering을 "공유 스토리지 + Active-StandBy"(p119)로 정의하지만, Oracle RAC는 여러 인스턴스가 한 DB를 함께 처리하고 MySQL NDB Cluster는 shared-nothing이다([[복제]]).
- ⚠️ Master/Slave, IO Thread·SQL Thread(p119·p122)는 MySQL 8.0.22 이후 source/replica, receiver/applier로 바뀐 옛 용어다. 8.0.27부터 applier는 기본으로 멀티스레드다([[복제]]).
- EXPLAIN 컬럼 설명(p113)과 `long_query_time`(p110)은 맞다. EXPLAIN ANALYZE(실제 실행 시간)가 빠져 있다([[실행 계획]]).
