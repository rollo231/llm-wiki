## 요약

### 배치 처리 (p4–7)

- **정의** — 데이터를 발생 즉시 처리하지 않고 일정 기간 모았다가 한꺼번에 처리한다. "실시간이 더 좋은 것
  아닌가?"에 대한 답은 **"효율성과 안정성 측면에서 배치는 대체 불가"**.
- **빨래 비유** — 양말 한 짝을 빨려고 세탁기를 돌리면 준비 비용(물·전기·세제)이 작업 가치보다 크다.
  데이터에서는 DB 연결과 네트워크 비용이 "세탁 준비"다.
- **은행 사례** — 낮(12:00)에는 결제·이체가 폭증하므로 분석 쿼리를 돌리면 시스템이 마비될 수 있다.
  새벽(02:00)에 하루치를 한 묶음으로 정산하고 아침(06:00)에 리포트를 낸다. 바쁜 낮(Hot Path)에는 고객 응대만,
  무거운 분석(Cold Path)은 새벽으로 미룬다.
- **핵심 가치** — 효율성(준비 비용 절감, 리소스 최적화, 네트워크·I/O 최소화)과 안정성(재작업 범위가 명확하고
  **실패한 날짜 구간만 다시 실행**하면 된다).

### ETL (p8–14)

| 단계 | 내용 |
|---|---|
| Extract | RDBMS·NoSQL·파일·SaaS API에 맞는 커넥터. 운영 영향 최소화(스로틀링, 새벽 추출), 고급 기법으로 CDC. **"소스 시스템에 절대 부하를 주지 말라"** |
| Transform | 가장 고통스럽고 CPU·메모리를 가장 많이 쓰는 단계. 정제(M/Male/남성 → M), PII 마스킹(900101-*******), 포맷 통일(2026.02.16 → 2026-02-16), 조인·집계 |
| Load | 정제를 마친 데이터만 DW에 적재. 골든 레코드(조직 내 단 하나의 진실), GIGO 방지 |

- **ETL이 필연이던 이유** — 20년 전 스토리지는 매우 비쌌다(Teradata·Oracle 증설). 비싼 저장소에 넣기 **전에**
  정제하고 줄이는 것이 생존 전략이었다.
- **ETL 서버의 한계** — 소스와 저장소 사이의 ETL 서버가 병목이 된다. 단일 장애 지점, 데이터가 늘어도 서버는
  그대로, 수시간~수일의 대기. 블랙프라이데이처럼 트래픽이 20배로 몰리면 CPU 100%로 유실·지연.

### ELT (p15–20)

- **전환의 계기** — 클라우드 오브젝트 스토리지로 저장 비용이 급락했다. "저장소가 이렇게 싼데 굳이 줄여서
  넣어야 하나?"
- **흐름** — Extract → **Load(원본 그대로, 벌크 적재)** → Transform(웨어하우스 내부에서 SQL·dbt로).
  철학은 **"Load First, Think Later"**. 비유는 급한 이사(짐을 박스째 옮기고 새 집에서 푼다).
- **가능하게 한 기술** — MPP. Snowflake·BigQuery·Redshift가 수백 노드로 나눠 계산한다(scale-out).
- **In-DB Processing** — 데이터를 밖으로 꺼내지 않고 `CREATE TABLE AS SELECT`·`MERGE` 같은 SQL로 변환한다.
  외부 서버로 보냈다가 다시 넣는 네트워크 비용이 사라지고, DW의 쿼리 옵티마이저를 그대로 쓴다.
- **강점** — 원본이 보존되므로 파이프라인의 "타임머신"이 된다. 적재와 변환이 분리돼 로직이 바뀌거나 버그가
  나오면 **SQL만 고쳐 과거 데이터로 다시 계산**한다.

### 비교와 선택 (p21–24)

| 비교 | ETL | ELT |
|---|---|---|
| 변환 위치 | 별도 ETL 서버 | DW 내부 |
| 적재 속도 | 느림 | 매우 빠름 |
| 보존 | 정제 데이터만 | 원본 + 정제 |
| 유연성·재현성 | 낮음 | 높음 |

- **ETL을 써야 할 때** — 금융·의료. GDPR·HIPAA·신용정보법 때문에 PII는 **적재 전에** 마스킹·암호화·
  토큰화해야 한다. 최소 권한 원칙으로 불필요한 민감 정보는 ETL 단계에서 뺀다.
- **ELT를 써야 할 때** — 스타트업·이커머스·게임처럼 분석 민첩성이 중요한 곳. schema-on-read, 레이크 지향
  ("로그 하나도 버리지 마").
- **도구** — Fivetran(관리형 EL), Airbyte(오픈소스 통합), Snowflake·BigQuery·Redshift(저장·연산),
  dbt(SQL 모델링), Apache Airflow(오케스트레이션).

## 핵심

- ETL → ELT 전환의 원인은 기술 유행이 아니라 **"무엇이 비싼가"의 역전**이다 — 저장이 비쌀 때는 넣기 전에
  줄이고, 저장이 싸지고 연산이 병렬화되자 일단 넣고 나중에 가공한다. → [[ETL과 ELT]]
- 배치의 진짜 장점으로 **재실행 범위의 명확함**을 든다. 멱등성·재처리 가능성은 이후 [[변경 데이터 캡처]]와
  [[Apache Kafka]]에서 스트리밍 쪽 해법으로 다시 나온다. → [[배치 처리]]
- ELT가 원본(PII 포함)을 레이크에 그대로 쌓는다는 점은, 뒤의 [[데이터 거버넌스와 카탈로그]]가 다루는
  민감 정보 태깅·접근 통제 문제로 이어진다. *(위키의 연결이다.)*
