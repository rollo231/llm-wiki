# DB 면접 4 인덱스

[[인프런 DB 면접 강의]]의 Section 4. 인덱스의 정의와 장단점에서 시작해 Hash가 아니라 B-Tree인 이유, 탐색 과정, 클러스터링·비클러스터링 인덱스, InnoDB의 2단계 검색을 묻는다. 두 번째 주 질문은 복합 인덱스의 컬럼 순서이고, Bool 컬럼 인덱스와 `LIKE` 패턴으로 이어진다. 주 질문 2개, 꼬리 질문 6개. 앞 섹션은 [[DB 면접 3 Lock과 동시성 제어]], 다음 섹션은 [[DB 면접 5 NoSQL과 RDBMS 비교]]다.

## 요약

### Q1. 인덱스란 무엇이고, 장단점은? (p43–45)

- Gold: 저장 성능을 희생하고 검색 성능을 높이려고 만든 자료 구조다. 장점은 조회 속도가 빨라지고 시스템 부하가 줄어드는 것이다. 단점은 DB의 약 10% 저장 공간이 필요하고, INSERT·DELETE·UPDATE가 잦은 컬럼에 걸면 오히려 느려진다는 것이다. UPDATE와 DELETE는 기존 인덱스를 지우지 않고 "사용하지 않음"으로 처리하므로 인덱스가 비대해질 수 있다.
- 등급을 가른 것: Bronze는 "검색이 빨라진다"와 "공간이 든다"만, Silver는 변경 시 인덱스도 갱신해야 한다는 점까지는 말했지만 저장 성능을 희생한다는 맞교환과 "마킹 처리로 비대해진다"는 메커니즘이 없었다.

### Q1-1. 왜 Hash 테이블이 아니라 주로 B-Tree를 쓰나요? (p46–48)

- Gold: 해시 테이블 안의 데이터는 정렬되어 있지 않아 부등호 연산이 안 된다. 인덱스는 기준 값보다 크거나 작은 범위 검색이 많으므로 B-Tree를 쓴다. 다만 등호 연산만 쓰는 경우에는 해시 인덱스가 B-Tree보다 훨씬 좋은 성능을 낼 수 있다.
- 등급을 가른 것: Bronze는 해시가 O(1)이라는 것만 알았고, Silver는 범위 검색의 한계는 말했지만 등호 연산에서는 해시가 빠르다는 맞교환을 빠뜨렸다.

### Q1-2. 인덱스는 어떻게 동작하나요? (p50–52)

- Gold: 검색할 값을 루트 노드에서부터 비교해 브랜치 노드를 거쳐 리프 노드까지 내려간다. 리프 노드의 레코드 주소로 실제 데이터 파일의 레코드를 읽는다.
- 등급을 가른 것: Silver는 탐색 과정은 맞았지만 "레코드 주소로 데이터 파일을 읽는" 마지막 단계가 없었다.

### Q1-3. 클러스터링 인덱스와 비클러스터링 인덱스의 차이 (p53–55)

- Gold: 클러스터링 인덱스는 PK에 적용되고 PK 값이 레코드의 물리적 저장 위치를 정한다. 리프 노드에 레코드의 모든 컬럼이 있다. 비클러스터링 인덱스는 PK 외 컬럼에 적용되고 리프 노드에 그 레코드의 PK만 있다. 그래서 비클러스터링 인덱스로 찾으면 PK를 얻은 뒤 클러스터링 인덱스를 다시 탐색한다.
- 등급을 가른 것: Bronze는 적용 대상만, Silver는 정렬 저장과 PK 재탐색은 말했지만 리프에 "모든 컬럼"이 있는지 "PK만" 있는지의 차이가 없었다.

### Q1-4. InnoDB에서 비클러스터링 인덱스는 어떻게 동작하나요? (p56–58)

- Gold: 비클러스터링 인덱스의 리프에는 PK만 있다. 이 PK로 클러스터링 인덱스(데이터 파일)를 다시 탐색하고, 클러스터링 인덱스의 리프에 레코드의 모든 정보가 있으므로 이 2단계 검색으로 최종 데이터를 가져온다.
- 등급을 가른 것: Silver는 과정은 맞았지만 "클러스터링 인덱스를 다시 탐색한다"는 2단계 구조가 분명하지 않았다.

### Q2. 복합 인덱스 사용 시 주의할 점은? (p60–62)

- Gold: 두 번째 컬럼은 첫 번째 컬럼에 의존해 정렬되므로 컬럼 순서가 중요하다. `=` 조건처럼 적은 데이터를 고르는 컬럼을 앞에, 범위 검색 컬럼을 뒤에 둔다. 단일 컬럼 인덱스보다 쓰기가 더 비효율적이므로 변경이 적은 컬럼을 고른다.
- 등급을 가른 것: Bronze는 "순서가 중요하다"는 결론만, Silver는 "카디널리티가 높은 컬럼을 앞에"까지 말했지만 정렬 의존이라는 원리와 등호·범위 조건의 배치를 빠뜨렸다.

### Q2-1. 동료가 Bool 타입에 인덱스를 건다면? (p63–65)

- Gold: Bool은 키가 True·False 둘뿐이라 리프 노드가 전체 데이터의 약 50%가 된다. 인덱스 레인지 스캔은 랜덤 I/O라서 전체의 20~30% 이상을 읽을 때는 순차 I/O인 풀 스캔이 더 효율적이다. EXPLAIN으로 실제 실행 계획을 확인해 근거를 마련하자고 의견을 내겠다.
- 등급을 가른 것: Silver는 카디널리티 관점은 맞았지만 랜덤 I/O 대 순차 I/O라는 근거가 없었다.

### Q2-2. 왜 `LIKE 'abc%'`만 인덱스를 타고 `'%abc%'`는 타지 않나요? (p66–68)

- Gold: B-Tree 인덱스는 왼쪽 값을 기준으로 정렬되어 있다. 앞이 고정된 패턴은 정렬 순서를 쓸 수 있지만, 앞에 와일드카드가 붙으면 시작점을 정할 수 없어 인덱스를 쓰지 못한다. 자료의 질문 표기는 "LIKE%"와 "%LIKE%"다.
- 등급을 가른 것: Silver는 결론은 맞았지만 "왼쪽 값 기준 정렬"이라는 원리가 없었다.

## 핵심

- 이 섹션의 뼈대는 둘이다. B-Tree가 정렬된 구조라서 범위·접두어 검색과 복합 인덱스의 순서 규칙이 모두 나온다는 것, 그리고 InnoDB에서는 테이블 자체가 PK 순의 B-Tree라는 것이다. 둘 다 [[데이터베이스 인덱스]]에 정리했다.
- Q2-1의 Gold가 "EXPLAIN으로 확인하자"로 끝나는 것은 좋은 답의 틀이다. 비율 규칙을 외우기보다 실행 계획을 보자는 쪽이 맞다([[실행 계획]]).
- MySQL과 PostgreSQL의 인덱스 구조 차이(p59 그림)는 [[DB 면접 5 NoSQL과 RDBMS 비교]]의 Q1-4에서 다시 나온다([[MySQL]] · [[PostgreSQL]]).

## 주의·결함

- ❌ Q1-2의 "리프의 레코드 주소로 데이터 파일을 읽는다"(p52)는 InnoDB와 맞지 않는다. 바로 뒤 p55·p58이 설명하는 클러스터링 구조와도 어긋난다. MyISAM이나 PostgreSQL 힙 구조의 설명이다([[데이터베이스 인덱스]]).
- ⚠️ "해시 인덱스가 훨씬 빠르다"(p48)는 InnoDB에서는 쓸 수 없는 선택지다. InnoDB는 사용자가 만드는 인덱스로 BTREE만 지원한다([[데이터베이스 인덱스]]).
- ⚠️ "DB의 약 10% 저장 공간"(p45)은 자료가 출처를 밝히지 않았고 위키도 1차 자료에서 찾지 못했다. "사용하지 않음 처리로 비대해진다"도 절반이다. InnoDB의 purge와 PostgreSQL의 VACUUM이 나중에 회수한다([[데이터베이스 인덱스]]).
- ⚠️ 클러스터링 인덱스는 "PK에 적용"(p55)만이 아니다. PK가 없으면 NOT NULL UNIQUE 인덱스, 그것도 없으면 숨은 인덱스가 클러스터링 인덱스가 된다. 보조 인덱스 리프에는 PK"만"이 아니라 인덱스 컬럼과 PK가 함께 있고, 커버링 인덱스면 2단계 검색을 건너뛴다([[데이터베이스 인덱스]]).
- ⚠️ Bool의 "리프가 약 50%"와 "20~30% 이상이면 풀 스캔"(p65)은 값이 고르게 나뉠 때의 이야기다. 드문 값만 찾는다면 인덱스가 유효할 수 있다. 20~30%라는 비율은 자료가 출처를 밝히지 않았고, MySQL 매뉴얼은 고정 비율 규칙을 이미 버렸다고 적는다([[데이터베이스 인덱스]]).
