# AI DE 강의 3-01 스키마 중심 설계와 RDBMS

[[AI 데이터 엔지니어링 강의]] Part 3의 첫 소단원. Part 3 전체의 출발점으로 RDBMS가 무엇을 잘하는지(관계와 키, 제약, 트랜잭션, ACID, 정규화, 조인)를 정리하고, 끝에서 스키마 중심 설계의 약점 두 가지(변경 비용, 의미 표현의 한계)를 꺼낸다. 이 약점이 다음 소단원의 NoSQL과 그다음의 시맨틱으로 이어진다.

## 요약

### 01. RDBMS란 (p4–5)

- 관계형 모델을 구현한 DBMS다. 데이터는 테이블(Relation)로, 테이블은 행(튜플)과 열(속성)로 이뤄지고, 테이블 사이 연결은 키로 표현한다.
- 강의의 표현: "관계형이 의미하는 것은 표가 아니라 관계"(p5). PK는 엔터티를 유일하게 식별하고, FK는 테이블 간 관계를 강제한다. 관계를 강제하면 중복이 줄고, 참조 무결성이 생기고, 조인으로 일관되게 조회할 수 있다.

### 02. 스키마란 (p6–7)

- "스키마는 데이터 형식의 선언이 아니라 규칙"(p6). 테이블 정의(컬럼·타입·NULL 허용), 제약(UNIQUE·CHECK·FK), 인덱스로 무엇이 들어올 수 있는지 제한하고 어떻게 연결되는지 명시한다.
- 제약은 버그를 저장 단계에서 막는다. NOT NULL은 필수값 누락, UNIQUE는 중복, CHECK는 범위·형식, FK는 존재하지 않는 참조를 막는다. "애플리케이션 버그를 DB가 1차 방어"(p7).

### 03. 트랜잭션 (p8–10)

- 여러 읽기·쓰기를 하나의 논리적 단위로 묶어, 중간 상태가 밖에 보이지 않고 성공하거나 전부 원래대로 돌아가게 한다. `BEGIN → 작업 → COMMIT 또는 ROLLBACK`.
- 예시는 주문 생성·결제 기록·재고 차감 세 작업이다. 하나라도 실패하면 전부 취소돼야 한다.
- 핵심 데이터는 상태를 갖는다(`created → paid → shipped → refunded`). 트랜잭션은 상태 전이가 규칙을 깨지 않게 보장한다.

### 04. ACID (p11–15)

| 성질 | 강의의 정의 | 예시 질문 |
|---|---|---|
| Atomicity | 부분 성공 없음(all-or-nothing) | 주문은 됐는데 결제 기록이 실패하면? |
| Consistency | DB가 정의한 제약을 깨는 상태 전이를 허용하지 않는다 | 재고가 0인데 -1이 되면? |
| Isolation | 동시 트랜잭션이 서로를 망가뜨리지 않는다([[데이터베이스 락]]·[[MVCC]]·[[트랜잭션 격리 수준]]) | 1개 남은 상품을 두 명이 동시에 결제하면? |
| Durability | 커밋된 결과는 장애에도 사라지지 않는다(로그·저장 장치) | 결제 완료 응답 뒤 서버가 죽으면? |

결론으로 "RDBMS는 OLTP(업무 트랜잭션)에 최적"이라고 한다(p11).

### 05. 정규화 (p16)

"정규화는 중복 제거가 아니라 업데이트 안정성"(p16). 중복이 많으면 고객 이름 하나를 바꿀 때 주문 행을 모두 고쳐야 하는 업데이트 이상이 생긴다. 엔터티를 분해하고 관계로 표현해 쓰기 무결성을 지킨다.

### 06. Join (p17)

조인은 흩어진 데이터를 질의 시점에 의미 있는 정보로 합치는 관계형 모델의 표현력이다. 하지만 조인할 테이블이 N개면 조인 가짓수가 "기하급수적으로" 늘고, 네스티드 루프·해시 조인 선택에 따라 성능 편차가 크다. 규모가 커지면 표현력이 병목이 된다.

### 07. 스키마 중심 설계의 약점 (p18–19)

1. 변경: 스키마 변경은 마이그레이션이고 다운타임·락·백필 문제가 따른다. 여러 서비스가 같은 테이블을 공유하면 "스키마 합의"가 병목이 된다.
2. 비정형·다양성: 키가 자주 바뀌는 이벤트 로그, 컬럼으로 표현하기 어려운 문서, 조인이 폭발하는 복잡한 관계, 질의 모델이 다른 임베딩. 결론은 "스키마는 형식을 잡지만, '의미'는 별도 계층이 필요"(p19).

## 핵심

- 강의가 ACID의 C를 "DB가 정의한 제약을 지키는 것"으로 좁혀 설명한 것은 이 덱 안에서 일관된다(p7의 제약 목록과 p13이 같은 제약을 가리킨다). ACID 전반과 다른 곳에서 나온 ACID(Delta Lake의 트랜잭션 로그)와의 연결은 [[관계형 데이터베이스]]에 모았다.
- p19의 네 가지 약점은 Part 3 나머지의 목차 구실을 한다. 키가 바뀌는 이벤트와 문서는 [[NoSQL]](3-02), 관계 폭발은 그래프([[그래프 데이터 모델]], [[그래프 데이터베이스]]), "의미는 별도 계층"은 [[시맨틱 계층]](3-03)으로 이어진다. 이 대응은 위키의 정리다.
- 조인 가짓수는 "기하급수적"이라는 표현보다 더 빨리 는다. 조인 순서 탐색 공간은 left-deep 트리만 따져도 n!이고, bushy 트리까지 넣으면 (2(n−1))!/(n−1)!이다. 지수보다 빠른 팩토리얼급이다. 이는 질의 최적화 교과서의 표준 결과로 검증 과정에서 확인했지만 원문은 열어 보지 않았다(2026-09-28).

## 주의·결함

- p16 정규화 슬라이드는 설명 그림 없이 velog 글 URL 하나만 단다. 정규형(1NF~BCNF)은 다루지 않는다.
- p17–19 세 슬라이드가 같은 daumcdn(티스토리) 이미지 URL을 되풀이한다. 서명·만료 파라미터가 붙은 CDN 주소라 원 출처를 알 수 없다.
- 슬라이드가 "시멘틱"과 "시맨틱"을 섞어 쓴다. 소단원 표지(p2·20·35·49)는 "시맨틱"이고, 파트 표지(p1)와 본문 머리글은 "시멘틱"이다. 위키는 표준 표기 「시맨틱」을 쓰고 원문 인용만 그대로 둔다.
- ACID의 Isolation을 "서로 영향을 주지 않음"(p11)으로 설명하지만, 같은 덱이 곧바로 격리 수준(p14)을 언급한다. 격리 수준에 따라 허용되는 간섭이 다르다는 점은 설명하지 않는다. 수준별로 허용되는 이상 현상은 [[트랜잭션 격리 수준]]에 있다.
