# AI DE 강의 3-03 시맨틱

[[AI 데이터 엔지니어링 강의]] Part 3 Ch1의 마지막 소단원(4). "스키마가 형식을 정의한다면 시멘틱은 의미를 정의"한다는 대비로 시맨틱을 정의하고, 구성 요소(Entity·Attribute·Relationship·Context), 없을 때 생기는 문제, AI에서 중요한 이유, 용어 사전에서 지식 그래프까지의 스펙트럼을 다룬다. Part 3 나머지(그래프, 온톨로지, GraphRAG)의 문제 제기에 해당한다.

## 요약

### 01. Semantic이란 (p51–52)

- 시맨틱은 데이터가 비즈니스에서 무엇을 의미하는지를 정의한다. 스키마는 컬럼·타입·제약으로 저장 구조를 보장하지만, 값이 어떤 기준으로 계산됐는지, 무엇을 포함·제외하는지, 어떤 기간·타임존·시점 기준인지는 모른다. 강의의 정의: "시멘틱은 데이터 해석의 계약(contract)"(p51).
- 스키마만으로는 설명하기 어려운 것(p52): `user_id`와 `member_id`가 같은 개념인지, `created_at`이 생성·가입·주문 중 어느 시각인지, `status`가 업무·결제·배송 중 어느 상태인지, 두 테이블의 연결이 식별 관계인지 이벤트 관계인지 집계 관계인지.

### 02. 구성 요소 (p53–54)

| 요소 | 뜻 | 예 |
|---|---|---|
| Entity | 의미적으로 독립된 대상 | 사용자, 주문, 상품, 세션, 모델, 피처 |
| Attribute | 개체의 속성 | 사용자 나이, 주문 금액 |
| Relationship | 개체 사이 연결 | 사용자가 주문을 생성, 상품이 카테고리에 속함 |
| Context | 데이터가 해석되는 조건과 배경 | 시간, 채널, 지역, 정책 버전, 실험군, 모델 버전 |

Context가 중요한 이유로 같은 용어의 여러 정의를 든다. `active_user`는 최근 7일 로그인, 최근 30일 유효 행동, 유료 사용자만 중 하나일 수 있고, `Revenue`는 총 결제액, 취소 제외 순매출, 세전·세후 매출 중 하나일 수 있다(p54).

### 03. 중요성 (p55–57)

- 시맨틱이 없으면 같은 고객이 `user_id`·`member_id`·`customer_id`·`account_id`로 흩어지고, 같은 지표를 팀마다 다르게 정의하고, 문서·로그·테이블·메타데이터가 분리돼 사람이 맥락을 추론해야 한다. 결과는 통합 비용 증가, 지표 충돌, 잘못된 조인, RAG·추천·QA 품질 저하다(p55).
- AI는 값보다 의미적 연결과 문맥을 더 자주 요구한다(p56). "이 사용자와 비슷한 고객은", "이 문서와 관련된 정책·제품·팀은", "이 장애와 비슷한 과거 이슈는", "이 피처가 어떤 모델·데이터셋·서비스와 연결되는가" 같은 질문이다.
- 스키마 중심 사고(어느 테이블, 어떤 타입, 어떤 키로 조인)와 시맨틱 중심 사고(어떤 개체, 어떤 관계, 다른 시스템의 어떤 개념, 어떤 문맥)를 비교하고, "AI 시대 데이터 엔지니어는 두 관점을 함께 다뤄야 함"이라고 맺는다(p57).

### 04. 실무 적용 — 스펙트럼 (p58)

| 단계 | 형태 |
|---|---|
| 가장 약한 형태 | 공통 용어 정의, 지표 사전, 데이터 카탈로그, 컬럼 설명 |
| 더 구조화된 형태 | 공통 엔티티 모델, 표준 식별자 체계, 도메인 간 관계 정의 |
| 더 발전한 형태 | 온톨로지, 지식 그래프, semantic layer, context-aware retrieval |

### 05. 요약 (p59)

RDBMS는 구조를, NoSQL은 유연성과 확장을 잘 다루지만 둘 다 의미를 설명하지 못한다. 데이터 엔지니어는 파이프라인을 넘어 데이터의 의미, 시스템 간 개념 연결, 문맥 보존을 맡아야 한다.

## 핵심

- 정의("해석의 계약"), 구성 요소, 스펙트럼의 전문은 [[시맨틱 계층]]에 모았다.
- p58의 스펙트럼이 이 강의의 지도다. 가장 약한 형태(카탈로그·컬럼 설명)는 Part 1의 [[데이터 거버넌스와 카탈로그]]가 이미 다뤘고, 가장 발전한 형태(온톨로지·지식 그래프·context-aware retrieval)는 Part 3의 Ch2~4가 다룬다([[온톨로지]], [[지식 그래프]]). Part 1과 Part 3을 잇는 이 연결은 위키의 관찰이다.
- "시맨틱은 해석의 계약"은 Part 1의 "스키마는 계약"과 짝을 이룬다. 스키마 계약이 형식을 지키고, 시맨틱 계약이 뜻을 지킨다. [[스키마 진화]]의 "호환성 검사가 못 잡는 것"(타입은 같은데 단위가 바뀌는 변경)이 정확히 시맨틱 계약이 없어서 생기는 문제다. 이 대응도 위키의 정리다.

## 주의·결함

- "semantic layer"를 두 가지 뜻으로 쓴다. p48과 이 소단원의 제목에서는 시맨틱 전반("비즈니스 의미를 데이터 위로 올리는 레이어")이고, p58 스펙트럼에서는 온톨로지·지식 그래프와 나란한 한 형태다. 업계에서 semantic layer는 대개 지표 정의를 한곳에 두고 BI 도구가 공유하는 계층(dbt Semantic Layer, LookML 같은)을 가리키는데, 강의는 이 구분을 하지 않는다. 이 업계 용법 서술은 위키의 보충이고, dbt·Looker 문서 인용은 [[시맨틱 계층]]에 있다(2026-09-28 확인).
- 스펙트럼의 단계를 나누는 기준(기계가 읽을 수 있는가, 추론이 되는가)을 말하지 않는다. 온톨로지 여부 판단 기준은 Ch3에서 따로 나온다([[온톨로지]]).
- 표기 혼용(시멘틱/시맨틱)은 [[AI DE 강의 3-01 스키마 중심 설계와 RDBMS]]의 주의 참조.
