## 요약

### 저장소 세 종류 (덱 04 p2)

| 종류 | 특징 |
|---|---|
| RDBMS | 구조화된 테이블, ACID 트랜잭션, SQL |
| NoSQL | 유연한 스키마(JSON·문서·키-값), 수평 확장, 비정형 데이터 |
| 클라우드 저장소 | 오브젝트 스토리지(S3·GCS), 컴퓨팅·저장 분리, 사실상 무제한 용량 |

처리 방식은 **ETL → ELT**, 스키마 전략은 **schema-on-write → schema-on-read**로 옮겨 간다.

### DW → Data Lake → Lakehouse (덱 04 p3)

| | Data Warehouse | Data Lake | Lakehouse |
|---|---|---|---|
| 특징 | ETL로 정제된 정형 데이터, schema-on-write | 모든 원시 데이터를 그대로, schema-on-read | DW의 관리 기능(ACID·거버넌스) + 레이크의 유연성·저비용 |
| 등장 배경 | BI를 위한 신뢰할 수 있는 단일 진실 공급원 | 소셜·IoT 비정형 데이터, ML 학습 데이터 | 두 시스템 운영의 비효율(사일로·중복 ETL), AI/BI 통합 수요 |
| 장점 | 고성능 SQL, 데이터 품질 | 유연성·확장성, 저비용 | 단일 플랫폼, BI+AI, 신뢰성+유연성 |
| 단점 | 비정형 처리 불가, 비용 | 데이터 늪, 품질 관리 약화 | 복잡성 |

### 사일로와 데이터 레이크 (덱 04 p4–6)

- **사일로** — 부서별 중복 저장으로 버전 불일치와 신뢰 하락, 데이터 공유가 어려워 의사결정 지연,
  시스템·라이선스 중복 투자.
- **데이터 레이크 4요소** — 확장성(오브젝트 스토리지), 접근성(메타데이터 카탈로그 + schema-on-read),
  보안(중앙 IAM, 전송·저장 시 암호화), 비용 관리(수명주기 정책으로 콜드 데이터를 저렴한 계층으로).
- **온프레미스 vs 클라우드** — 온프레미스는 통제·보안이 쉽고 네트워크 지연이 작지만 초기 비용이 크고
  물리 확장에 한계가 있다. 클라우드는 확장·사용량 과금·관리형 서비스가 장점이고 거버넌스·보안 설계가 필요하다.

### OLTP와 OLAP (덱 05)

- **OLTP** — 실시간 트랜잭션, 레코드 단위 빠른 접근. 예: 은행 계정계, 배달 앱 주문 DB.
- **OLAP** — 대량 데이터 분석, 필요한 열만 스캔. 예: DW에서 OLAP 큐브를 만들어 조회.
- 디스크 레이아웃의 차이(행 단위 연속 저장 vs 열 단위 분할 저장) → [[행 기반과 열 기반 저장]].

설계 5단계(p12):

| 단계 | 내용 |
|---|---|
| 1. 워크로드 진단 | I/O 패턴, 읽기·쓰기 비율(CRUD vs 조회) |
| 2. 저장 방식 결정 | 트랜잭션 → 행 기반(RDBMS), 분석 → 열 기반(DW·레이크) |
| 3. 하이브리드 설계 | 고객 요청은 OLTP가 받고, CDC 파이프라인으로 OLAP에 동기화 |
| 4. 스키마 전략 | OLTP는 정규화로 무결성, OLAP는 스타 스키마·비정규화로 조인 최소화 |
| 5. 최적화 | Snappy·Zstd 압축, 날짜·지역별 파티셔닝 |

마무리 로드맵(p15): 워크로드 진단 → Parquet/Avro 도입 검증 → CDC→Lakehouse 실시간 동기화 PoC →
카탈로그·품질 규칙 → 파티셔닝·압축 튜닝.

## 핵심

- 진화의 동력은 **두 시스템을 따로 운영하는 비용**이다. DW는 정형·고품질·고비용이고, 레이크는 무엇이든
  싸게 담지만 늪이 된다. 둘을 함께 운영하면 중복 ETL과 사일로가 생긴다 → Lakehouse는 "하나로 합친다".
  → [[데이터 레이크하우스]]
- 설계 5단계의 3단계(하이브리드)가 Part 1 전체의 지도다 — 고객 요청은 OLTP가 받고,
  [[변경 데이터 캡처]]로 분석 저장소에 흘려보낸다. 이 연결을 뒤 강의가 하나씩 채운다
  ([[AI DE 강의 1-08 CDC]], [[AI DE 강의 1-06 Delta Lake와 ACID]]).

## 주의·결함

- ⚠️ **Avro를 열 기반 포맷으로 분류한다** — 덱 05 p8의 열 기반 레이아웃 제목이 "Disk Storage Layout
  (Parquet/Avro)"이고, p15 로드맵도 "Parquet/Avro 도입 검증 — 컬럼 프루닝 테스트"라고 쓴다. Avro는 행 기반
  포맷이며, **같은 강의의 [[AI DE 강의 1-05 열 기반 저장 Parquet와 Avro]]도 Avro를 "Row-Oriented
  Format"으로 명시한다** — 코스 내부 모순이다. → [[Apache Avro]]
- "I/O 부하 1/10~1/100", "압축률 1:3 vs 1:10+"는 출처 없는 수치다. 실제 비율은 컬럼 수, 읽는 컬럼의 비율,
  값 분포에 따라 달라진다.
- 덱 04 p4의 세 번째 항목 제목이 템플릿 문구 **"주제를 입력해주세요"** 그대로 남아 있다.
- 덱 05는 15p 중 7장이 섹션 타이틀이다("OLTP vs OLAP" 타이틀은 두 번 나온다).
