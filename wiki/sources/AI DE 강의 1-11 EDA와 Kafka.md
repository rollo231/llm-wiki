## 요약

### 배경 (p2–3)

- **패러다임** — 요청 시에만 DB를 조회하는 동기식 요청-응답은 모바일·IoT의 데이터 쓰나미에서 과부하의 주범이 된다.
  **Data at Rest → Data in Motion**, 해법은 이벤트 발생 즉시 반응·전파하는 비동기 구조(EDA).
- **Kafka의 탄생** — 2010년경 LinkedIn이 하루 수십억 건의 사용자 활동·지표를 처리하려 했는데, ActiveMQ·RabbitMQ
  같은 기존 MQ는 전달 보장과 복잡한 기능에 집중하느라 처리량이 부족했다. "무거운 기능은 다 빼자" — 처리량과 수평
  확장에만 집중한 로그 기반 설계. 2011년 오픈소스 공개.

### 구성 요소 (p5–10)

| 요소 | 비유 | 역할 |
|---|---|---|
| 프로듀서 | 보내는 사람 | 토픽·파티션 결정(라우팅), 직렬화, **일정량을 모아 배치 전송**, 키 지정으로 순서 보장 |
| 브로커 | 우체국 | 디스크에 영구 저장, **순차 쓰기**로 느린 디스크에서도 빠름, 3대 이상 클러스터, 복제로 고가용성 |
| 컨슈머 | 수신인(직접 가져감) | **Pull** 방식으로 자기 처리 능력만큼(배압), 서로 다른 시스템이 같은 데이터를 동시에 소비 |

- **ZooKeeper vs KRaft** — 별도 ZooKeeper 앙상블(외부 의존, 이중 관리, 파티션이 수십만 개면 컨트롤러 병목) vs
  브로커끼리 Raft 합의로 메타데이터 직접 관리(단일 프로세스, 빠른 컨트롤러 페일오버). "3.3+부터 Production Ready,
  향후 주키퍼는 완전히 제거될 예정."
- **데이터 흐름 예** — 아이폰 주문 이벤트 → Order 토픽 → 리더 파티션 기록·팔로워 복제 → 컨슈머 그룹 A(배송
  지시)와 B(추천 쿠폰)가 같은 이벤트를 각자 소비. 주문 시스템은 배송·마케팅을 몰라도 된다.

### 데이터 모델 (p11–16)

| 개념 | 정의 | 주의 |
|---|---|---|
| 토픽 | 데이터가 흐르는 논리적 채널(폴더·테이블과 유사). 예: `order.completed`, `click.log` | 클러스터 하나에 수천~수만 개 |
| 파티션 | 토픽의 물리적 분할. 파티션 수만큼 컨슈머가 병렬 처리 | **파티션 수는 한 번 늘리면 줄일 수 없다** |
| 오프셋 | 파티션 안에서 메시지마다 붙는 순차 정수. 컨슈머가 "5번까지 읽음"을 커밋하면 재시작 후 6번부터 | 파티션 안에서만 유일, 삭제돼도 번호는 재사용하지 않음 |

- **순서 보장** — ⚠️ **토픽 전체 순서는 보장되지 않고 파티션 안에서만 보장된다.** 순서가 중요하면 키(User ID·
  Order ID)를 지정해 같은 파티션으로 보낸다.
- **복제** — 모든 읽기·쓰기는 리더 파티션에서, 팔로워는 복제만. 리더 브로커가 죽으면 팔로워가 즉시 승격.
- **로그 컴팩션** — 기간 기반 보존(예: 7일 뒤 삭제)과 달리 **키별 최신 값만** 남긴다(User A의 주소 Seoul → Busan
  → Jeju에서 Jeju만). 컴팩션된 토픽은 사실상 키-값 저장소이고, CDC로 DB의 현재 스냅샷을 구성할 때 필수다.

### EDA 심화 (p17–20)

- **강결합 vs 느슨한 결합** — 직접 호출은 스펙 변경이 전파되고 연쇄 장애가 나며 호출자가 대기한다. 이벤트는
  누가 받는지 모르고, 배송이 죽어도 이벤트는 남으며, 컨슈머만 늘리면 된다.
- **전통 브로커 vs 이벤트 스트리밍** — 휘발(전달 후 삭제)·Push·과거 추적 불가 vs 영속(보존 기간)·Pull·**오프셋을
  되감아 재처리(replay)**. "재생 가능성이 파이프라인의 복원력을 보장한다."
- **허브 앤 스포크** — 웹 로그·DB CDC(Debezium)·IoT(MQTT)가 Kafka로 들어가고 대시보드·레이크/DW·이상 탐지가
  구독한다. 소스와 타깃의 N×M 연결을 1:N으로.
- **컨슈머 그룹** — 파티션을 나눠 맡고, 장애 시 남은 컨슈머에게 파티션을 재분배(리밸런싱).

### 성능과 고려사항 (p21–22)

- **Zero-Copy** — 일반 전송은 디스크 → 커널 → 유저(앱) → 커널 → NIC로 "4회 복사, 4회 문맥 전환", sendfile은
  커널 페이지 캐시에서 NIC 버퍼로 직접 "2회 복사, 2회 문맥 전환". "CPU 사용량 약 60% 감소."
- **도입 고려사항** — 운영 복잡도(브로커·KRaft·스키마 레지스트리, 전문 인력), 실시간성 한계(Near Real-time에 최적,
  마이크로초가 필요한 초단타 매매 등엔 부적합), 순서 보장 이슈(키·파티셔닝 설계 선행).

## 핵심

- Kafka의 설계는 한 문장으로 요약된다: **브로커는 단순하게(로그에 추가하고 보관만), 똑똑함은 컨슈머에게(Pull,
  오프셋 관리).** 이 선택 하나가 순차 I/O·zero-copy 성능, replay, 컨슈머 그룹 확장을 함께 준다. *(덱 p3 "무거운
  기능은 다 빼자"와 p18 "스마트 컨슈머"에서 위키가 정리)* → [[Apache Kafka]]
- **순서 보장의 단위는 파티션이다** → 키 설계가 곧 정합성 설계다. [[AI DE 강의 1-08 CDC]]의 입출금 순서 문제와
  같은 이야기다.
- **로그 컴팩션은 스트림을 테이블로 바꾼다** — "변경 이벤트의 흐름"과 "현재 상태"가 같은 토픽의 두 보기다.
  → [[변경 데이터 캡처]] · [[이벤트 기반 아키텍처]]

## 주의·결함

- ⚠️ **"Fortune 500대 기업의 80% 이상이 사용"** — Kafka 공식 사이트의 문구는 "More than 80% of all **Fortune 100**
  companies trust, and use Apache Kafka."다. 대상 목록이 다르다. [https://kafka.apache.org/ , 2026-09-14 확인]
- ⚠️ **"향후 주키퍼는 완전히 제거될 예정"은 이미 지난 일이다.** Kafka 4.0(2025-03-18)이 ZooKeeper 모드를 제거하고
  KRaft만 지원한다 — 덱 PDF 생성일(2026-02-19)보다 약 11개월 앞선다. "3.3부터 production ready"는 맞다(KRaft가
  production ready로 선언된 첫 버전이 3.3.x이며, 3.3.0은 버그로 사용이 권장되지 않아 실질적으로 3.3.1, 2022-10-03).
  [Apache Kafka 4.0 릴리스 공지 https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/ ;
  4.0 업그레이드 노트 "Apache Kafka 4.0 only supports KRaft mode - ZooKeeper mode has been removed."
  https://kafka.apache.org/40/getting-started/upgrade/ , 2026-09-14 확인]
- ⚠️ **Zero-copy 수치** — zero-copy 성능 수치로 널리 인용되는 IBM developerWorks 글(Palaniappan·Nagaraja,
  2008-09-02)은 **전송 시간** 약 65% 감소를 보고한다. 덱은 지표가 "CPU 사용량 약 60%"로 바뀌어 있다. 또 그 글에
  따르면 sendfile만으로는 **복사 3회(그중 CPU 복사 1회)·문맥 전환 2회**이고, 덱의 "2회 복사"는 NIC가 gather 연산을
  지원해 마지막 CPU 복사까지 없앤 경우다. [하버드 CSCI E-28 강의 자료의 사본
  https://cscie28.dce.harvard.edu/lectures/lect02/6_Extras/zero-copy/ , 2026-09-14 확인] 덱은 TLS를 켜면 Kafka가
  sendfile을 쓰지 않는다는 점도 말하지 않는다 → [[Apache Kafka]]
- 순차 쓰기가 "메모리급 속도"를 내는 이유(OS 페이지 캐시)는 설명되지 않는다.
