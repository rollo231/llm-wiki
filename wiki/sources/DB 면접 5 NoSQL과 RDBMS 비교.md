# DB 면접 5 NoSQL과 RDBMS 비교

## 요약

### Q1. RDBMS와 NoSQL의 차이, 언제 각각을 쓰나 (p70–72)

- Gold: RDBMS는 명확한 스키마를 가지며 트랜잭션과 조인이 강력하다. 데이터 구조가 명확하고 변경이 빈번하며 관계형 데이터를 다룰 때 맞다. NoSQL은 느슨한 스키마로 유연성과 수평 확장(Scale-Out)에 강하다. 스키마가 불명확하거나 대용량 데이터를 저장하고, 조인이 적고 변경이 적은 데이터에 맞다.
- 등급을 가른 것: Bronze는 "관계형 / 비관계형"이라는 이름을 반복했을 뿐이다. Silver는 스키마·확장 방향과 선택 기준은 맞았지만 RDBMS의 조인·트랜잭션 강점과 NoSQL의 "조인 없는 집합 지향 모델"이라는 근본 차이를 빠뜨렸다.

### Q1-1. 데이터 모델링 관점에서 설계 방식이 어떻게 다른가 (p73–75)

- Gold: RDBMS는 데이터 중심으로 설계한다. 먼저 정규화해 중복을 없애고, 나중에 어떤 쿼리든 조인으로 대응한다. NoSQL은 액세스 패턴 중심으로 설계한다. "어떤 쿼리를 날릴 것인가"를 먼저 정의하고 그에 맞게 비정규화해 저장한다. 조인이 없으므로 필요한 데이터를 한 번의 조회로 가져오도록 설계하는 것이 요점이다.
- 등급을 가른 것: Silver는 "정규화해서 나눈다 / 한 문서에 모은다"는 저장 방식만 말하고, 설계 순서가 다르다는 점(데이터 중심 대 액세스 패턴 중심)을 빠뜨렸다.

### Q1-2. RDBMS에서도 Scale-Out이 가능한가 (p76–78)

- Gold: 읽기 확장은 Read Replica를 추가해 가능하다. 쓰기는 Master가 맡고 읽기 트래픽을 여러 Replica로 나눈다. 쓰기 확장은 샤딩으로 가능하지만, 조인과 트랜잭션이 여러 샤드에 걸치면 구현이 매우 복잡해진다. 그래서 "불가능한 건 아니지만 비용이 크다"가 정확한 표현이다.
- 등급을 가른 것: Silver의 "RDBMS는 Scale-Up만 가능"을 자료가 "흔한 오해"로 부른다.

### Q1-3. NoSQL은 왜 Scale-Out에 좋나 (p79–81)

- Gold: RDBMS는 테이블 간 관계 때문에 복잡한 조인이 따라와 샤딩 구현이 어렵다. NoSQL은 집합 지향 모델이라 연관 데이터가 함께 저장되어 있어 다른 샤드에서 조인할 필요가 없고, DB 자체가 샤딩을 지원하므로 스케일 아웃에 유리하다.
- 등급을 가른 것: Silver는 "샤딩이 쉽다"는 결론만 말하고, 왜 쉬운지(조인 없는 집합 지향 모델이라 데이터를 독립적으로 나눌 수 있다)를 빠뜨렸다.

### Q1-4. MySQL과 PostgreSQL은 어떤 차이가 있나 (p82–84)

- Gold: 네 가지다. 기본 격리 수준(MySQL은 REPEATABLE READ, PostgreSQL은 READ COMMITTED), 인덱스(InnoDB는 PK가 클러스터링 인덱스이고 리프에 데이터가 있지만 PostgreSQL은 리프에 위치 식별자만), 구조(MySQL은 DB → 테이블, PostgreSQL은 DB → 스키마 → 테이블이라 권한을 묶기 쉽다), MVCC 구현(MySQL은 언두 로그, PostgreSQL은 "원본에 마킹 후 새 레코드를 추가하는 MGA 방식").
- 등급을 가른 것: Silver는 격리 수준과 MVCC 차이는 말했지만 인덱스 방식과 스키마 구조의 차이를 빠뜨렸다.

### Q2. CAP 이론이 무엇인가 (p85–87)

- Gold: 분산 시스템은 C(일관성)·A(가용성)·P(분할 내성)를 모두 만족할 수 없다. 네트워크 분단은 피할 수 없는 결함이라 P는 사실상 필수이고, 결국 C와 A 중 하나를 고르는 문제가 된다. CP는 MongoDB처럼 일관성을, AP는 Cassandra처럼 가용성을 우선한다.
- 등급을 가른 것: Silver는 정의와 예시(MongoDB CP, Cassandra AP)는 같았지만 "P가 사실상 필수라 C와 A 중 선택"이라는 점을 빠뜨렸다.

### Q2-1. 실무에서 C와 A 중 어떤 기준으로 고르나 (p88–90)

- Gold: 데이터 불일치가 비즈니스에 얼마나 치명적인가로 판단한다. 결제·재고처럼 불일치가 금전 손실로 이어지는 도메인은 CP, SNS 좋아요 수나 추천 피드처럼 잠깐 뒤처져도 영향이 적은 도메인은 AP를 고르고 Eventual Consistency로 시간이 지나면 모든 노드가 맞춰지게 한다. 다만 Eventual Consistency는 "언제" 수렴하는지 보장하지 않으므로 즉시 정합성이 필요한 곳에는 맞지 않는다.
- 등급을 가른 것: Silver는 예시는 맞았지만 판단 기준(불일치의 비즈니스 영향)과 Eventual Consistency를 빠뜨렸다.

## 핵심

- 모델링 질문(Q1-1)의 "데이터 중심 대 액세스 패턴 중심"은 그대로 써도 되는 뼈대다([[NoSQL]]).
- RDBMS Scale-Out(Q1-2)의 "불가능하지 않지만 비용이 크다"는 [[복제]](읽기)와 [[샤딩]](쓰기)으로 나눠 답하는 틀이다.
- Q2-1의 "불일치의 비즈니스 비용으로 고른다"는 [[CAP 정리]]의 "선택은 연산·데이터 단위로 세밀하게 일어난다"와 같은 방향이다. 다만 자료는 선택을 시스템(제품) 단위로 말한다. 이 비교는 위키가 한 것이다.
- MySQL과 PostgreSQL의 네 가지 차이는 [[PostgreSQL]]에 표로 모았다.

## 주의·결함

- ❌ "RDBMS는 변경이 빈번한 데이터, NoSQL은 변경이 적은 데이터"(p72)는 틀린 일반화다. Cassandra 같은 LSM 기반 저장소는 쓰기에 최적화되어 있다([[NoSQL]]).
- ⚠️ "집합 지향 모델"(p81)은 Fowler·Sadalage의 aggregate-oriented를 옮긴 말이다. 키-값·문서·column-family에만 해당하고 그래프 DB는 빠진다([[NoSQL]] · [[샤딩]]).
- ⚠️ "MGA"(p84)는 PostgreSQL 문서의 용어가 아니다. 나머지 세 차이는 맞다([[PostgreSQL]]).
- ⚠️ "C·A·P를 모두 만족할 수 없다", "MongoDB는 CP, Cassandra는 AP"(p86·p87)는 이 위키의 [[CAP 정리]]가 이미 문제 삼은 틀과 같다. Brewer 2012가 "셋 중 둘"을 정정했고, 두 제품 모두 설정에 따라 일관성이 달라진다([[CAP 정리]]).
- Eventual Consistency가 수렴 시점을 보장하지 않는다는 서술(p90)은 맞다([[CAP 정리]]).
