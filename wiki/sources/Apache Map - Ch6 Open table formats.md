# Apache Map - Ch6 Open table formats

『Apache로 읽는 데이터 기술의 지도』(이현수, 2026) **Ch6. 파일을 테이블처럼 다루기** — 개념 8개,
PDF pp.43–51. 트래커: [[Apache data technology map (book)]].

**이번은 새 계층이 아니라 기존 페이지를 메우는 인제스트다.** [[Table formats]]가 이미 이 영역을
갖고 있었지만 **Delta 한 종류만 알고, 선택 기준은 아예 비어 있었다**(그 페이지 §아직 답하지 못하는 것).
[[SQL execution layer]] 3단계의 1️⃣이 여기다.

## ⭐ 읽는 규칙 4번째 확인 — 논지는 마지막 개념(#8)

> ⭐⭐ **"기술이 바뀌어도 기준은 같습니다. '테이블의 기준은 파일인가, 메타데이터인가?'
> 오픈 테이블 포맷은 후자를 택한 설계입니다."**

그리고 3단계로 압축한다.

| | 단계 | 상태 |
|---|---|---|
| 1️⃣ | **파일 쌓기** | 저비용 저장은 되지만 일관성과 공유가 약함 |
| 2️⃣ | **테이블 규칙** | 스냅샷·스키마·커밋으로 신뢰 가능한 테이블이 됨 |
| 3️⃣ | **레이크하우스** | 여러 엔진·배치·스트림이 같은 테이블을 중심으로 모임 |

목표 문장도 제시한다 — *"특정 제품 이름보다, **레이크가 왜 저장소에서 플랫폼으로 불리게 됐는지**를
이해하면 된다."*

⭐ 그리고 실질적 귀결 하나가 위키에 없던 축이다 — **"거버넌스·품질·권한도 파일 경로가 아니라 테이블
단위로 관리된다."** [[Object storage layout]]이 *경로 = 권한·생애주기* 라고 정리한 것의 **위층**이다:
테이블 포맷이 있으면 권한의 단위가 경로에서 테이블로 올라간다.

## ⭐ 비교 절 (개념 5) — 3축, 그리고 또 성능이 아니다

> "세 이름을 **경쟁 제품 순위로만 매기면** 선택이 어려워집니다."

- 🔹 **Iceberg** — 엔진 공유·스냅샷. 배치 레이크하우스 + 여러 쿼리 엔진이면 **기본 출발점**
- 🔸 **Hudi** — upsert·CDC·증분 소비가 잦을 때
- ▪️ **Paimon** — 스트림 쓰기와 배치 읽기를 한 테이블에서 묶을 때

⭐⭐ **"하나로 정해진 선택은 없습니다. 벤치마크 숫자보다, 팀의 기술 역량·이미 쓰는 엔진·변경 패턴을
기준으로 고르는 편이 낫습니다."**

### 이 책의 편집 방침이 확정됐다 — 4/4 비교 절이 성능 순위를 거부한다

| 장 | 비교 절이 든 축 |
|---|---|
| **Ch6** | *"벤치마크 숫자보다 팀의 기술 역량·이미 쓰는 엔진·변경 패턴"* |
| **Ch7** | *"먼저 정해야 할 것은 도구 이름이 아니라 운영 방식"* |
| **Ch8** | *"'가장 빠른 엔진' 하나로 고르기보다 주 부하가 무엇인지"* |
| **Ch9** | *"제품 이름을 비교하기 전에 가장 자주 발생하는 조회가 무엇인지"* |

⭐ **네 장 전부가 명시적으로 성능 비교를 거부하고 "문제의 모양 / 팀의 상태"를 축으로 든다.**
이게 이 책의 실질적 기여이고, 개념당 500자라는 얕은 깊이를 감수한 대가로 얻은 것이다 —
**깊이를 팔아 판단 축을 샀다.** 트래커에 읽는 규칙 2번으로 기록했다.

## Hudi의 CoW vs MoR — 이 장에서 나온 유일한 실제 메커니즘

| | 병합 시점 | 쓰기 | 읽기 |
|---|---|---|---|
| **Copy-on-Write** | 쓸 때 병합해 읽기 쉽게 | 무겁다 | 가볍다 |
| **Merge-on-Read** | 쓰기는 가볍게, 읽을 때 병합 | 가볍다 | 무겁다 |

⭐ [[Latency and throughput]]·[[Caching strategies]]에서 반복된 것과 같은 시소다 — **비용을 없애는 게
아니라 어느 경로로 옮길지 정한다.** 하류가 **전체 재스캔 대신 바뀐 구간만 읽는다**(증분 조회)는 것이
Hudi의 값이고, 그 대가가 이 표다. → [[Table formats]] §Hudi — CoW vs MoR

Hudi는 [[Change data capture]]의 **싱크**로 쓰인다 — Ch7의 Flink CDC가 하류로 지목한 것이 정확히
Kafka·Iceberg·Hudi·Paimon이었다. **두 장이 맞물린다.**

## ⭐⭐ Hive가 남긴 질문

> **"Hive가 남긴 질문 — 누가 스키마의 진실인가."** 다음 세대 카탈로그를 배울 때도 이 질문을 기준으로
> 비교하면 이해가 빠릅니다.

그리고 Hive를 앞쪽에 두는 이유를 스스로 밝힌다 — *"현재 최고의 실행 엔진이어서가 아니라 **데이터
플랫폼의 테이블 사고방식을 처음 세운 표준**이기 때문이다."*

⭐ **Hive는 두 가지를 남겼고 운명이 갈렸다** — **경로 규약은 Iceberg가 걷어냈고, 메타스토어(카탈로그)는
이름만 바뀌어 살아남았다.** [[Table formats]]가 이미 갖고 있던 *Hive는 경로에 의미를 실었고 Iceberg는
해방했다* 의 나머지 절반이 이것이다. → [[Data catalog and semantic layer]]

*"Metastore와 카탈로그 개념을 모르면 Iceberg·거버넌스를 제대로 이해하기 어렵다."*

## ⚠️ Kudu — 범주 오류 방지용 항목

**"Kudu는 Iceberg·Hudi 같은 오픈 테이블 포맷과는 계층이 달라 같은 계열로 묶으면 안 됩니다."**
자체 저장 엔진이다. HDFS(대량 분석 강, 행 수정 약) ↔ OLTP(갱신 강, 초대형 스캔 부담) 사이에 앉아
**행 단위 수정을 지원하면서 컬럼형 스캔을 유지한다.** Impala와 짝. → [[Table formats]] §이건 테이블
포맷이 아니다

## 이 장이 위키의 열린 질문에 한 일

[[Table formats]] §이 페이지가 아직 답하지 못하는 것이 갱신됐다.

| 항목 | 전 | 후 |
|---|---|---|
| 선택 기준 | ❌ 완전 공백 | ✅ **3축 해소** — 단 Delta가 그 축의 어디인지는 여전히 모른다 |
| Iceberg time travel | ❓ 미확인 | ✅ 확인 (*"과거 스냅샷으로 되돌아가 검증"*) |
| Iceberg 온디스크 구조 | ⚠️ 1차 소스 없음 | ⚠️ **부분** — 이름·역할은 확인, **계층 구조·통계 항목은 여전히 없음** |

⭐ **그리고 역전이 하나 있다.** 이 위키가 일반 지식으로 적어 둔 Iceberg 스케치(스냅샷 → 매니페스트
리스트 → 매니페스트 → 데이터 파일 + 컬럼 통계, hidden partitioning, partition evolution)가
**이 책이 주는 설명보다 더 자세하다.** 책은 "매니페스트가 데이터 파일 목록을 추적한다" 수준에서 멈춘다.

**즉 2차 소스로 채울 수 있는 깊이의 한계가 여기서 드러났다** — 이 책은 *선택 축*은 주고 *구조*는
못 준다. [[Wiki gap analysis - DE readiness]]의 **1차 자료** 축이 여전히 1순위인 이유가 재확인됐다.

## 👍 강점 · ⚠️ 약점

**강점** — 4장 연속 같은 프로필이다.

- 출처 없는 수치 **0건**(Ch6은 수치가 아예 없다).
- 8개 중 6개에 *"~가 만능은 아니다"* / *"~로 묶으면 안 된다"* 류의 경계 문장.
- **범주 구분을 반복해서 강조한다** — 파일 포맷 ≠ 테이블 포맷 ≠ 저장 엔진 ≠ 카탈로그. 개념 1이 이걸
  선언하고 개념 7(Kudu)·개념 6(Hive)이 각각 확인한다.

**약점** — 내부 동작이 없다(4장 연속). Iceberg 매니페스트의 계층, Paimon의 컴팩션 정책, Hudi의
타임라인·파일 그룹이 전부 이름 수준. ⚠️ 그리고 **이 장은 "운영"을 한 번도 말하지 않는다** —
스냅샷 만료·고아 파일 정리·컴팩션 스케줄 같은, 테이블 포맷을 실제로 굴릴 때 드는 비용이 없다.
[[Table formats]] §Iceberg 문서가 필요한 이유의 3번(*스냅샷 만료·고아 파일 정리*)이 그대로 남는다.

## 위키에 들어온 것

**새 페이지 없음. 기존 페이지 갱신 4곳.**

| | |
|---|---|
| [[Table formats]] | **대폭 갱신** — 선택 3축 · Hudi CoW/MoR · Paimon 신설 · Kudu 경계 · Hive 메타스토어 절 · 파일→테이블→플랫폼 3단계 · 열린 질문 갱신. 별칭 추가(Paimon·Kudu·CoW/MoR·스냅샷·매니페스트) |

**승격 판단**: Iceberg·Hudi·Paimon·Kudu·Hive 모두 ⏸ — **[[Table formats]]가 이미 이 영역의 집이고
별칭 타깃**이라, 개념당 500자로 엔티티를 떼면 그 페이지를 조각내기만 한다.
⭐ 단 **Iceberg는 1차 문서(Iceberg 스펙)를 인제스트하는 시점에 전용 엔티티로 승격한다** — 그때는
구조를 담을 내용이 생긴다. **Hive Metastore도 Ch10(Polaris·Gravitino)을 읽은 뒤 카탈로그 비교가
가능해질 때 재검토**한다(Doris를 Ch9까지 미룬 것과 같은 방식).
