# AI DE 강의 4-09 워터마크와 윈도우 연산

[[AI 데이터 엔지니어링 강의]] Part 4 Ch3의 넷째 소단원이다. 무한 스트림을 유한한 계산 단위로 자르는 윈도우, 그 구간을 언제 닫을지 정하는 워터마크, 늦은 데이터가 왔을 때 결과를 어떻게 내보낼지 정하는 출력 규칙을 역할로 나눠 설명한다.

## 요약

### 01. 워터마크와 윈도우의 필요성 (p198–200)

- 배치 집계는 데이터 전체가 이미 있지만, 스트리밍에는 "다 모이는 시점"이 없어서 무한 입력을 유한한 단위로 자르는 장치가 필요하다. 그것이 윈도우다(p198).
- 앞 소단원의 결제 B(발생 10:04, 도착 10:12)를 다시 쓴다. 10:00~10:10 결과에 넣을 것인가, 이미 결과를 냈다면 수정할 것인가, 너무 늦었다고 버릴 것인가(p199).
- 역할 분담(p200): 윈도우는 "어느 계산 구간에 넣을 것인가", 워터마크는 "이 구간을 언제 닫을 것인가", 출력 시점 규칙은 "중간 결과를 낼 것인가, 최종만 낼 것인가, 늦은 데이터가 오면 다시 낼 것인가"를 맡는다.

### 02. 윈도우 (p201–206)

- 윈도우는 어떤 이벤트를 같은 집계 단위로 볼지, 키별 상태를 어느 범위까지 들고 있을지, 결과의 시간 단위를 무엇으로 볼지를 정한다(p201).
- 고정 윈도우(겹치지 않는 일정 길이, 5분마다 결제 건수), 이동 윈도우(일정 길이, 일정 간격마다 시작, 겹칠 수 있음, 최근 10분 평균을 1분마다), 세션 윈도우(고정 길이 없음, 활동이 일정 시간 끊기면 종료)의 세 가지다(p202–204).
- 고르는 질문(p205–206): 결과가 끊어진 구간이어야 하는가, 최근 흐름을 계속 갱신해야 하는가, 활동 묶음 자체가 분석 단위인가, 한 이벤트가 여러 결과에 들어가도 되는가.

### 03. 워터마크 (p207–209)

- 워터마크는 이벤트 발생 시각 기준으로 어느 시점까지 데이터가 대부분 도착했다고 볼지 나타내는 기준선이다. 결과를 닫을 기준, 늦은 데이터 판단 기준, 오래된 상태를 정리할 기준을 준다(p207).
- 늦은 데이터는 워터마크가 이미 지나간 구간에 속하는 이벤트이고, 허용 지연은 그런 데이터를 추가로 받아 줄 시간 범위다. 선택지는 바로 버림, 일정 시간까지 반영, 별도 경로로 분리, 수정 결과를 다시 출력이다. 허용 지연이 길수록 더 많이 반영하지만 상태를 더 오래 들고 결과 확정도 늦어진다(p208).
- 워터마크는 "모든 데이터가 도착했다"는 보장이 아니라 정확성, 지연, 상태 비용 사이의 절충 기준이고, 운영 가능한 마감선을 만드는 장치라고 정리한다. Spark의 보장을 예로 든다. 설정한 지연보다 덜 늦은 데이터는 반영이 보장되고, 더 늦은 데이터는 반영될 수도 안 될 수도 있다(p209).

### 04. 결과 출력과 정합성 (p210–213)

- 윈도우 결과가 나오는 시점은 워터마크가 윈도우 끝을 지날 때, 조기 결과를 내도록 설정했을 때, 늦은 데이터가 와서 결과가 수정될 때다. 중간 결과, 정시 결과, 늦은 데이터 반영 결과를 구분한다(p210).
- 결제 예시의 첫 결과는 A·C 2건이고, B가 10:12에 도착하면 수정 결과는 3건이다. 이때 "3건을 새 행으로 추가할 것인가, 기존 2건을 3건으로 갱신할 것인가, 2건과 3건을 모두 이벤트로 남길 것인가"를 묻는다(p211–212).
- 출력 방식을 Append(확정된 결과만 추가, 파일·로그성 테이블), Upsert(같은 키의 결과를 덮어씀, 대시보드·집계 테이블, 윈도우 키 설계 중요), Update(변경된 결과만 출력, 싱크가 업데이트를 지원해야 함)로 나눈다(p213).

### 05. 실무 설계 판단 (p214–216)

- 윈도우 크기는 지표의 시간 단위, 보고 싶은 빈도, 상태 크기와 계산 비용으로, 이동 간격은 갱신 주기·중복 계산 비용·대시보드 표시 주기로 정한다(p214).
- 세션 간격은 "활동이 끊겼다"의 정의, 도메인별 평균 행동 간격, 과분할과 과병합의 균형으로, 워터마크 지연은 실제 지연 분포, 늦은 데이터 허용 범위, 결과 지연 허용치, 상태 저장 비용으로 정한다(p215).
- 남은 문제를 다음 소단원으로 넘긴다(p216). 너무 늦게 온 데이터의 복구, 이미 나온 결과의 재계산, 원본 이벤트 보존, 배치 재처리와 스트리밍의 공동 설계다.

## 핵심

- 윈도우·워터마크·출력 규칙을 세 질문으로 나눈 p200이 이 소단원의 뼈대다. 전문은 [[스트림 처리]]에 모았다.
- p208이 허용 지연을 워터마크와 따로 정의한다. Part 1에서 구분되지 않았던 두 개념이 여기서 따로 정의된다([[AI DE 강의 1-12 실시간 처리 엔진]]). 둘이 한 엔진 안에서 어떻게 겹치는지는 여기서도 말하지 않는다(아래 「주의·결함」).
- p216에서 스트리밍만으로 해결되지 않는 문제(너무 늦은 데이터, 재계산)를 아키텍처 문제로 넘기는 연결이 좋다. 다음 소단원 [[AI DE 강의 4-10 람다·카파와 현대 아키텍처]]가 이를 받는다.

## 주의·결함

- ✅ p209의 Spark 보장은 문서와 일치한다. 프로그래밍 가이드는 "any data less than 2 hours behind… is guaranteed to be aggregated… Data delayed by more than 2 hours is not guaranteed to be dropped; it may or may not get aggregated"라고 적는다. [https://spark.apache.org/docs/latest/streaming/apis-on-dataframes-and-datasets.html , 2026-09-28 확인]
- ❌ p213의 출력 방식 「Append / Upsert / Update」는 Spark의 출력 모드와 다르다. Spark Structured Streaming의 출력 모드는 Append, Complete, Update다("Append mode (default)… Complete mode… Update mode", 같은 가이드, 2026-09-28 확인). Upsert는 출력 모드가 아니라 싱크 쪽의 반영 방식이다. 같은 키 결과를 덮어쓰는 것은 Update 모드 출력을 upsert 가능한 싱크(키 기반 MERGE, Flink의 upsert-kafka 같은 changelog 싱크)에 쓸 때 생긴다. Complete(결과 표 전체를 매번 다시 쓰기)는 빠졌다. 강의의 세 분류는 엔진의 출력 모드와 싱크 의미론을 한 목록에 섞은 것이다. Flink의 changelog 설명은 위키가 문서로 대조하지 않았다.
- 워터마크 지연(p215)과 허용 지연(p208)을 따로 정의하지만, 둘이 한 엔진 안에서 어떻게 겹치는지는 말하지 않는다. Flink에는 워터마크 전략과 별도로 윈도우의 `allowedLateness`가 있고, Spark에는 워터마크 하나로 둘을 겸한다. 이 차이는 위키의 보충이다.
