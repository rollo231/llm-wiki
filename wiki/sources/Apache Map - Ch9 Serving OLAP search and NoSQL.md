# Apache Map - Ch9 Serving OLAP search and NoSQL

『Apache로 읽는 데이터 기술의 지도』(이현수, 2026) **Ch9. 빠르게 읽고 바로 보여 주기** — 개념 11개,
PDF pp.74–85. 트래커: [[Apache data technology map (book)]].

[[Apache Map - Ch8 SQL on the lake]]가 그대로 예고한 장이다 — *"다음 파트는 같은 '데이터를 읽고
싶다'는 요구를, 더 특화된 저장소와 서비스로 나누는 주제로 이어집니다."*

**이 장에서 새로 들어온 계층: [[Consumption layer]].**

## ⭐ 논지는 다시 마지막 개념이다 (#11)

Ch8과 구조가 같다 — 개념 1~10은 카탈로그이고 **개념 11이 분류 축**이다.

> "이 장의 기술은 모두 데이터를 빠르게 제공하지만, **처리하는 요청은 서로 다릅니다.**
> **한 제품에 검색·집계·서비스 저장을 한꺼번에 맡기면 성능과 운영이 오히려 복잡해질 수 있습니다.**
> 사용자가 데이터를 어떻게 조회할지부터 구분해 두면 됩니다."

⭐ **가르는 축은 제품이 아니라 조회 형태다.** 문장을 검색할지, 숫자를 집계할지, 키로 특정 데이터를
찾을지, 센서 값을 시간별로 볼지, 자주 쓰는 값을 메모리에서 읽을지.

| 라벨 | 조회 형태 | 제품 |
|---|---|---|
| 🔹 **검색** | 텍스트로 찾고 순위를 매김 | Lucene · Solr |
| 🔸 **OLAP 서빙** | 집계·필터 결과를 빠르게 제공 | Druid · Pinot · Kylin |
| ▪️ **NoSQL** | 키·wide-column으로 대규모 온라인 저장 | Cassandra · HBase |
| ✅ **특화** | 시계열 / 인메모리 | IoTDB / Ignite |
| *(구분)* | 폭넓은 분석은 따로 본다 | Doris · 레이크 SQL → [[SQL execution layer]] |

⭐⭐ 그리고 **실행 가능한 방법 하나를 준다.**

> "필요한 기능을 **'상품명 검색', '실시간 매출 집계', '사용자 ID 조회'처럼 구체적인 문장으로 정리해
> 두면 됩니다. 그 문장과 직접 연결되는 기술부터 검토하면 됩니다.**
> **제품 이름을 비교하기 전에** 서비스에서 가장 자주 발생하는 조회가 무엇인지 먼저 확인하면 선택
> 범위를 줄일 수 있습니다."

이 코스·책 계열에서 본 판단 도구 중 가장 값이 싸고 즉시 쓸 수 있는 것이다. [[Wiki gap analysis - DE readiness]]가
지적한 ***"재야 한다"는 있고 "이렇게 잰다"가 없다*** 의 반례에 해당한다 — 여기는 **"이렇게 정한다"가
있다.**

## 개념 11개

| # | Tier | 개념 | 요지 |
|---|---|---|---|
| 1 | 🔸 | **Druid** | 실시간 이벤트 관측 OLAP. 시간으로 잘라 저장, 컬럼형 + 세그먼트 분산. **넓은 기간을 훑는 대시보드**. ⚠️ 임의 조인·OLTP 대체 아님 |
| 2 | 🔸 | **Pinot** | 초저지연·고동시성 **사용자 대면** OLAP. 스트림 수신 후 즉시 색인, 필터·그룹 집계·상위 순위. ⚠️ 복잡 조인·범용 탐색 아님 |
| 3 | 🔸 | Druid vs Pinot | **"대시보드냐 서비스냐"** — 아래 |
| 4 | 🔸 | **Kylin** | 차원 조합을 **큐브**로 사전 계산. ⚠️ 조건이 바뀌면 큐브 재설계, 큐브가 늘면 저장·생성 비용 |
| 5 | 🔸 | **IoTDB** | 산업·IoT 시계열. 고빈도 압축 저장 + 시간 창 조회. **공장·라인·설비·센서를 계층형 경로로** |
| 6 | 🔹 | **Cassandra** | 멀티리전 복제 wide-column. 파티션 키 분산, 쓰기 확장 → [[Apache Cassandra]] |
| 7 | 🔹 | **HBase** | HDFS 위의 키 조회. 행키·컬럼 패밀리, **핫스팟** → [[Apache HBase]] |
| 8 | 🔸 | **Ignite** | 분산 인메모리 캐시·컴퓨팅. Redis보다 넓고(분산 SQL·컴퓨팅·디스크) 그만큼 운영 부담 |
| 9 | 🔹 | **Lucene** | 역색인 **라이브러리**. 토큰화 → 역색인 → 스코어링 → [[Apache Lucene]] |
| 10 | 🔹 | **Solr** | Lucene 기반 분산 검색 **서버**. HTTP API·샤드·복제·패싯 |
| 11 | 🔸 | 소비 계층 나누는 기준 | **이 장의 논지** — 위 |

## Druid vs Pinot (개념 3) — 축은 "누가 보는가"

> "기능이 비슷해 보여도 **주로 누가 결과를 조회하는지**에 따라 고르는 기준이 달라집니다."

- 🔹 **Druid** — 운영자·분석가가 여러 지표를 보는 **내부 대시보드**. 트래픽 변화·캠페인 성과·장애 현황.
- 🔸 **Pinot** — 많은 앱 사용자가 각자의 결과를 조회하는 **서비스 화면**. 개인화 통계·실시간 순위·
  제품 내 분석.

판단 항목 셋: **결과를 보는 사람 · 동시에 들어오는 요청 수 · 허용할 수 있는 응답 시간.**
⚠️ *"두 제품이 다루는 업무는 일부 겹치므로 경계가 딱 갈리지는 않는다"* 고 스스로 인정하고,
**처음부터 둘 다 도입하지 말라**고 못 박는다.

Doris는 여기서 의도적으로 빠진다 — *"Doris 같은 분석 웨어하우스는 더 폭넓은 SQL 분석을 담당하므로
따로 비교하는 편이 좋습니다."* Ch8의 3축(Doris/Impala/Spark SQL)과 Ch9의 3축(Druid/Pinot/Kylin)이
**겹치지 않게 설계되어 있다.** 이 책의 비교 절 배치는 꽤 정교하다.

## ⭐ 팬아웃 원칙 — 이 장의 두 번째 수확

> "하나의 플랫폼에서 여러 기술을 함께 쓰는 것은 자연스럽습니다. **같은 원본 데이터를 복제하더라도
> 검색용 색인, 집계용 테이블, 키 조회용 저장소는 각각 다른 방식으로 구성됩니다.**"

그리고 반복해서 "억지로 합치지 말라"고 말한다.

- Cassandra 항목: *"실시간 집계나 텍스트 검색까지 필요하다면 Cassandra 하나로 모두 처리하기보다
  Pinot나 Solr 같은 전용 시스템에 데이터를 전달해 역할을 나누는 편이 관리하기 쉽다."*
- Solr 항목: *"OLAP 엔진에 기능을 억지로 추가하기보다 검색 서버를 별도로 두는 편이 관리하기 쉽다."*
- Ignite 항목: *"처음 도입할 때는 원본 DB 앞의 캐시처럼 용도를 하나로 제한하는 편이 이해와 운영에
  도움이 된다."*

⚠️ **다만 나누고 난 뒤의 값은 말하지 않는다.** 사본이 늘면 사본마다 기준·신선도·권한이 따로 생긴다 —
검색 색인과 집계 테이블의 지연이 달라 **화면 두 개가 다른 숫자를 보여 주는** 상황이 [[Data SLA and observability]]의
*침묵의 실패* 가 가장 잘 일어나는 자리다. 이 비용은 [[Consumption layer]] §팬아웃의 값에 따로 적었다.

## ⚠️ 비판 1 — 벡터 검색이 없다

2026년 자료인데 **검색 항목이 역색인 렉시컬 검색뿐이다.** 임베딩·ANN·하이브리드 검색이 조회 형태
표에 아예 없다. Lucene 계열도 현재 dense vector 색인을 지원하는데 언급이 없다.

⭐ 이 위키는 [[Vector database]]와 [[Hybrid search and reranking]]을 이미 갖고 있어서 **빠진 줄이
어디인지 정확히 보인다.** 그리고 그 페이지의 논지 — **"의미는 남고 식별자는 사라진다"** — 가 바로 이
층의 문제다. **Lucene의 역색인과 벡터 ANN은 대체가 아니라 같은 조회 형태의 두 절반이다.**

## ⚠️ 비판 2 — Apache 렌즈의 왜곡, 두 번째 확인

[[Apache Map - Ch8 SQL on the lake]]에서 잡은 패턴이 반복된다.

| 장 | Apache 밖의 실제 기본값 | 책의 처리 |
|---|---|---|
| Ch8 SQL 실행 | **Trino/Presto** · Snowflake · BigQuery · Databricks SQL | 지나가듯 두 번 언급, Tier 1 0개 |
| Ch9 검색 | **Elasticsearch · OpenSearch** | Lucene 항목에서 이름만 |

⭐ **Ch9는 Tier 1이 4개(Cassandra·HBase·Lucene·Solr)인데, 그 4개가 모두 성숙기·레거시 쪽이다.**
가장 활발한 두 항목(Druid·Pinot)은 Tier 2다. 즉 이 책의 Tier는 **채택 연차의 함수**에 가깝고 현재
성장세를 반영하지 않는다. Ch8이 "Apache 밖"이라는 왜곡을, Ch9는 "Apache 안에서의 시간 지체"라는
왜곡을 보여 준다.

**보정 규칙: Tier는 "오래 쓰인 정도"로 읽고, "지금 고를 것"으로 읽지 않는다.**

## 👍 이 장의 강점

- **모든 항목에 `한계` 줄이 붙는다.** 11개 중 8개가 명시적 ⚠️ 한계 항목을 갖는다 —
  *"범용 웨어하우스·트랜잭션 DB 대체가 아님"*, *"레이크 전체 탐색이나 범용 BI를 위한 엔진은 아님"*,
  *"자유로운 조인·리포팅용 분석 DB가 아님"*. **무엇이 아닌지를 먼저 말하는 형식**이 일관된다.
- **출처 없는 수치가 0건이다.** Pinot의 *"밀리초~1초 미만"* 이 유일한 수치이고 성능 주장 대신 목표
  범위 표기다. Ch8과 같은 프로필.
- **비교 절이 서로 겹치지 않게 설계되어 있다**(위 §Druid vs Pinot).

⚠️ 여전한 약점은 Ch8과 같다 — **각 제품의 내부 동작이 없다.** Druid의 세그먼트, Pinot의 색인 종류,
Cassandra의 일관성 수준(quorum), Lucene의 스코어링 공식이 전부 이름만 나온다. **선택은 도와주고
운영은 도와주지 않는다.**

| | 페이지 |
|---|---|
| 새 개념 | [[Consumption layer]] — 조회 형태 6종 + OLAP 서빙 4종 비교 + 팬아웃 원칙과 그 값 |

| 흡수 | Druid · Pinot · Kylin · IoTDB · Ignite → [[Consumption layer]]의 별칭과 표 |

**승격 판단** ([[Apache data technology map (book)]] §엔티티 승격 기준 적용):

- **Lucene** ✅ — [[Apache Calcite]]와 같은 형태의 부품(Solr·Elasticsearch·OpenSearch의 공통 기반)이고
  [[Hybrid search and reranking]]의 절반이 여기 있다. **Solr는 별칭으로 흡수** — 내용이 "Lucene +
  분산·API"라 별도 페이지로 만들면 중복이 된다.
- **Cassandra** ✅ — [[NoSQL]]·[[CAP theorem]]·[[Replication and consensus]]가 계속 참조할 실물
  예시가 없었다.
- **HBase** ✅ — 행키 핫스팟이라는 고유 운영 규칙이 있고 [[Apache Hadoop]]·Phoenix가 가리킨다.
- **Druid·Pinot** ⏸ — 지식의 단위가 **비교**이지 개별 제품이 아니다. 각각 500자로는 껍데기가 된다.
- **Doris** ❌ — Ch8에서 보류했던 판단을 여기서 종결한다. Ch9가 Doris를 *"따로 비교하는 편이 좋다"* 며
  의도적으로 배제하므로 4자 비교표가 성립하지 않는다. [[SQL execution layer]]와 [[Consumption layer]]
  두 곳의 표에 남긴다.
