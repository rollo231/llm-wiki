# AI DE 강의 5-03 LLM의 한계와 RAG

[[AI 데이터 엔지니어링 강의]] Part 5 덱 `02` 「LLM과 RAG」의 뒷부분이다. LLM의 세 가지 한계에서 출발해 RAG를 정의하고, 필요한 이유, 작동 원리 다섯 단계, 활용 사례 넷을 든 뒤 LangChain 소개로 끝난다. RAG의 구조와 한계는 Part 3의 [[AI DE 강의 3-12 RAG의 이해와 한계]]가 원 논문부터 더 깊이 다뤘다. 이 덱은 그보다 개론이고, 3-12를 참조하지 않는다.

## 요약

### LLM의 한계와 해결 방안 (p10)

| 문제 | 설명 | 해결 방안 |
|---|---|---|
| 최신 정보 부족 | 훈련 데이터에 한정돼 최신 사실·도메인 정보를 반영하지 못함 | RAG 도입. 외부 지식 연결, 유사도 검색으로 근거 문서 활용 |
| 환각(Hallucination) | 사실과 다른 답변을 자신 있게 제공 | 정확성 검증. 출처 제공과 사실 확인 |
| 컨텍스트 제한 | 긴 문서 처리 제한, 출처 제시 어려움, 비용·지연 | 벡터 DB 활용. 의미 기반 검색으로 관련 문서만 찾아 씀 |

### RAG란 무엇인가 (p11)

RAG는 검색(Retrieval)과 생성(Generation)을 결합해, 외부 지식을 검색해 LLM에 제공하고 그 근거로 답하게 하는 방식이다. 작동 구조 그림은 사용자 질문 → 임베딩 → 벡터 DB 검색 → Top-K 관련 문서 → 프롬프트의 Context → LLM 생성이고, 단계를 질문 분석·문서 검색·답변 생성 셋으로 요약한다.

### 왜 RAG가 필요한가 (p12)

최신성 확보(훈련 데이터에 없는 정보, 사내 문서·DB 연동), 정확성 향상(검색된 문서 기반 답변으로 환각 감소), 도메인 특화(사내 문서·매뉴얼), 출처 제공(근거 문서 표시로 검증 가능성) 네 가지다.

### RAG 작동 원리 (p13)

문서 로딩·전처리(PDF·TXT·MD 로드, 텍스트 추출·정제) → 청킹·분할(의미 단위로 청킹, 오버랩 설정) → 임베딩 생성 → 벡터 DB 저장·인덱싱 → 검색·생성(Top-K 문서 검색, LLM 답변 생성).

### RAG 활용 사례 (p14)

문서 검색·QA 시스템(내부 지식 베이스), 고객지원 챗봇(매뉴얼·FAQ), 검색 엔진 보강(의미 기반 재랭킹, 개인화), 규정·정책 준수 도우미(출처 포함 답변) 넷이다.

### LangChain 소개 (p15)

LangChain을 LLM 애플리케이션 개발 프레임워크로 소개한다. 기능은 데이터 연결, 검색, 메모리(대화 기록·컨텍스트 관리), 에이전트이고 구성 요소는 Prompts·LLMs·Chains·Agents다. 현재 상태는 [[LangChain]]에 적었다.

## 핵심

- p10의 한계 세 가지와 p12의 필요성 네 가지는 [[검색 증강 생성]]의 동기 설명과 같은 자리다. Part 3(3-12)이 기억만으로 답하지 않고 찾아보고 답하는 방식으로 설명한 것을 이 덱은 문제-해결 표로 옮겼다.
- p13의 다섯 단계는 [[AI DE 강의 2-01 데이터 파이프라인의 진화와 데이터 엔지니어]]의 Basic RAG Pipeline(인덱싱과 검색·생성 두 구역)과 같은 구조다. 인덱싱 쪽 부품은 [[AI DE 강의 5-02 임베딩과 벡터 검색]]과 [[벡터 데이터베이스]]에 있다.
- 청킹은 이번에도 방법이 없다. p13의 "의미 단위로 청킹, 오버랩 설정" 한 줄이 Part 5에서 청킹에 관한 전부다. 위키는 Part 3 시점에 청킹 방법을 Part 5가 채울 것으로 적어 두었는데([[검색 증강 생성]]의 빈칸), 원본을 보니 그렇지 않았다.
- 한계 표의 "컨텍스트 제한"에 벡터 DB를 해결책으로 짝지은 것은, 긴 입력을 전부 넣지 말고 관련된 것만 골라 넣으라는 뜻이다. 컨텍스트 창이 커진 뒤에도 Lost in the Middle 때문에 이 선택은 의미가 남는다([[검색 증강 생성]]). 이 연결은 위키가 붙였다.

## 주의·결함

- ⚠️ p10의 "2K 토큰 제한"은 낡았다. 2,048은 GPT-3의 값이다("All models use a context window of nctx = 2048 tokens.", https://arxiv.org/pdf/2005.14165). 지금은 Claude Opus 5.5·Sonnet 5·Fable 5.1이 1M 토큰, Haiku 4.5가 200K 토큰이고(https://platform.claude.com/docs/en/about-claude/models/overview), Gemini 2.5 Pro의 입력 한도는 1,048,576 토큰이다(https://ai.google.dev/gemini-api/docs/models/gemini-2.5-pro). [2026-09-28 확인] 작성 시점(2026-05)에도 이미 낡은 수치다.
- ⚠️ p10의 "30% 환각률"은 LLM 일반의 수치로 쓸 1차 출처가 없다. 환각률은 모델·과제·평가 방식에 따라 크게 달라진다. 검증 과정에서 찾은 것은 특정 과제의 보고뿐이었다.
- 출처 없는 수치가 p12·p14의 카드마다 붙어 있다. "99% 정보 정확도", "100% 출처 표시", "-60% 처리시간" 같은 것이다. 위키는 옮기지 않는다([[AI 데이터 엔지니어링 강의]]의 Part 5 자료 평가).
- ⚠️ p15의 LangChain 통계("50K+ GitHub Stars", "1M+ 월간 다운로드")는 크게 낡았다. 2026-09 기준 수치는 [[LangChain]]에 있다. 에이전트 구성도 LangChain 1.0(2025-10) 이후 LangGraph 기반으로 바뀌었는데 슬라이드는 그 전의 Chains·Agents 구성으로 설명한다.
- p12의 "전문 지식 활용: 특정 분야의 전문 문서를 학습하여"는 RAG를 학습처럼 적었다. RAG는 모델을 다시 학습시키지 않고 검색 결과를 입력에 넣는다. 같은 덱 p11의 정의와 어긋나는 표현이다. 위키의 판단이다.
