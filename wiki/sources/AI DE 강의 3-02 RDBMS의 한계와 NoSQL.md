## 요약

### 소단원 2 — RDBMS의 한계와 NoSQL의 등장 1 (p20–34)

RDBMS가 강했던 문제는 트랜잭션으로 상태 전이 보장, 제약으로 무결성, 조인으로 관계 표현, 즉 주문·결제·정산 같은 OLTP다(p22). 한계는 세 가지다.

| 한계 | 강의의 설명 |
|---|---|
| 1. 스케일업 (p23–24) | QPS가 늘면 DB CPU 90% 고정, p95/p99 지연 급증. read replica는 쓰기 병목에 효과가 제한된다. 단일 primary 중심 설계라 한 노드가 감당할 양이 폭증하고, scale-up은 물리적·비용적 한계에 닿는다 |
| 2. 스키마 변경과 개발 속도 (p25) | 컬럼 추가·타입 변경이 테이블 락이나 장시간 백필을 부른다. 여러 팀이 한 스키마를 공유하면 "변경은 기술 문제가 아니라 조직 합의 비용"이 된다(누가 소유하나, 어떤 서비스가 영향받나, 배포 순서는) |
| 3. 분산 환경의 강한 일관성 비용 (p26–27) | 노드가 여럿이면 트랜잭션이 네트워크를 건너 동기 복제·분산 락·2PC가 필요하다. 네트워크는 느리고 부분 장애는 필연이다. 그래서 NoSQL은 더 단순한 데이터 모델, 선택 가능한 일관성, 쉬운 샤딩·복제를 택했다 |

NoSQL의 등장 배경은 새 서비스다(p28). Facebook·Instagram은 피드·좋아요·팔로우 이벤트가 초당 대량으로 생기고, LinkedIn은 사람-회사-직무 관계 탐색이 핵심 기능이다. 서비스가 요구한 변화는 수평 확장, 반정형 데이터, 24/7 가용성, 빠른 개발 속도 네 가지다(p29).

NoSQL 네 타입(p30–34):

| 타입 | 대표 도구 | 핵심 원리(강의) | 쓰임(강의) |
|---|---|---|---|
| Key-Value | Redis, DynamoDB | 키 하나에 값을 통째로. 인덱싱 오버헤드가 거의 없다 | 게임 랭킹(Sorted Set), 세션(TTL), API 캐시, 장바구니 |
| Document | MongoDB, Couchbase, DocumentDB | JSON 문서 단위 저장, schema-less | 콘텐츠 메타데이터, 중첩 유저 프로필, 사양이 제각각인 상품 |
| Wide-column | Cassandra, HBase, ScyllaDB | "열(Column) 기반 저장", 쓰기 최적화, 노드 추가 시 선형 확장 | IoT 센서·클릭 로그, 채팅 내역, 피드 fan-out |
| Graph | Neo4j, AWS Neptune | 노드·엣지를 직접 저장, JOIN 없이 탐색 | 추천(N차 관계), 이상거래 탐지, 지식 그래프 |

### 소단원 3 — RDBMS의 한계와 NoSQL의 등장 2 (p35–48)

"NoSQL은 확장성을 자동 제공하지 않는다"(p37). 운영 현실 세 가지:

1. 파티션 키가 시스템을 결정한다(p38–39). 한 번 정하면 바꾸기 어렵고, 특정 키 쏠림(핫 파티션)이나 시간 기반 키의 쓰기 집중이 생기면 노드를 추가해도 병목이 풀리지 않는다. p39는 서비스 두 개의 요청이 P1(Hot Partition)에 몰리는 그림이다.
2. 일관성 완화는 애플리케이션 복잡도를 만든다(p40–41). 재시도 설계, 중복 처리(idempotency), 순서 꼬임 처리, 보정 배치를 애플리케이션이 떠안는다. 이 trade-off를 설명하는 대표 개념으로 CAP를 든다.
3. 백업·복구·관측이 어렵다(p42–44). 여러 노드의 백업 시점 맞추기, 리밸런싱 중 성능 저하, 전체 장애가 아닌 partial failure. 관측 지표로 partition hotness/skew, replication lag, leader change를 들고, 물어야 할 질문을 "어느 노드가 느린가, 어느 파티션이 과열됐는가, 어느 replica가 뒤처졌는가"로 정리한다. "운영 포인트가 줄어드는 것이 아니라 분산됨"(p42).

그리고 방향을 튼다(p45–48). RDBMS와 NoSQL은 저장·확장·성능을 다룰 뿐, "활성 사용자 정의는? 매출은 환불·쿠폰 포함? 전환 윈도우는 7일/30일?"에는 답하지 못한다. 스키마 중심의 한계는 같은 KPI가 여러 개가 되고(정의가 SQL에 흩어지고 팀마다 제외 조건이 달라 "지표가 계약이 아니라 쿼리가 됨", p46), SQL이 비즈니스 로직이 된다는 것(재사용 불가, 변경 영향 추적 불가, p47)이다. 마지막 슬라이드(p48)가 시맨틱 계층을 "비즈니스 의미를 데이터 위로 올리는 레이어"로 예고한다.

## 핵심

- 운영 현실 세 가지(p37–44)가 이 강의에서 가장 실무에 가깝다. "NoSQL = 분산 DB = 자동 스케일"이라는 단순화를 파티션 키, 일관성 완화의 비용, 부분 장애로 반박한다. 전문과 CAP 정리는 [[NoSQL]]에 모았다.
- ❗ Wide-column 저장소를 "열(Column) 기반 저장"이라고 한 것(p33)은 틀렸다. Cassandra·HBase의 column family는 한 행의 열들을 row key와 함께 붙여 저장하므로 대체로 행 지향이고, Parquet 같은 분석용 열 기반 저장과 다르다. 근거와 Part 1 Avro 오분류와의 연결은 [[행 기반과 열 기반 저장]]과 [[NoSQL]]에 있다.
- p40의 "일관성 완화의 대가로 재시도·중복 처리(idempotency)를 애플리케이션이 떠안는다"는 Part 1 CDC·스트림 처리에서 나온 [[멱등성]]과 같은 문제다. 여기서는 원인이 전달 보장이 아니라 저장소의 일관성 모델이다.
- p25의 "스키마 변경은 조직 합의 비용"은 Part 1의 "스키마는 계약"과 같은 관찰을 반대편에서 본 것이다([[스키마 진화]]).
- p46의 "지표가 계약이 아니라 쿼리가 됨"이 다음 소단원 [[AI DE 강의 3-03 시맨틱]]의 동기다([[시맨틱 계층]]).

## 주의·결함

- ❗ p33 wide-column = 열 기반 저장(위 핵심 참조).
- CAP의 C를 "모든 노드가 같은 시점에 같은 값을 봄"(p41)으로 설명한다. Gilbert–Lynch(2002)의 C는 linearizability(원자적 일관성)다. 모든 연산에 전체 순서가 있고 각 연산이 한 시점에 끝난 것처럼 보여야 한다. 강의의 풀이는 직관적 설명일 뿐이다. C와 A의 선택은 강의도 "이 상황에서"(네트워크 단절 시) 생긴다고 맞게 쓰지만, 같은 슬라이드가 C·A·P를 나란한 세 특성으로 나열해 "셋 중 둘"로 읽힐 여지를 남긴다. Brewer 자신이 2012년에 "The '2 of 3' formulation was always misleading"이라고 썼다. 근거 인용은 [[NoSQL]].
- p39는 설명 없이 substack CDN 이미지 URL만 있다(핫 파티션 그림).
- 소단원 3의 목차(p36)는 04 「시멘틱」까지 네 절인데, 04는 한 장(p48)뿐이고 본격 설명은 다음 소단원 4로 넘어간다.
- NoSQL 네 타입 표(p30)는 쓰임과 선택 이유만 적고 트레이드오프(무엇을 포기하는지)는 적지 않는다. 포기하는 것은 소단원 3이 따로 다룬다.
- Graph DB의 "JOIN 없이 연결고리를 탐색"(p34)은 Ch5에서 index-free adjacency로 다시 나온다([[AI DE 강의 3-14 그래프 DB의 특징]]).
