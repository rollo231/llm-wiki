## ⭐ 도구가 아니라 시간 기준이 먼저다

> **"실시간 계산에서 먼저 정해야 할 것은 도구가 아니라 시간 기준."**

데이터가 실제로 일어난 시각과 시스템이 처리한 시각이 벌어지는 이유: 네트워크 지연 · 재시도 ·
장애 복구 · 브로커 적체 · **여러 입력원의 도착 순서 차이**.

### 세 개의 시각

| 시각 | 뜻 | 예 |
|---|---|---|
| **데이터 발생 시각** (event time) | 이벤트가 실제로 일어난 순간 | 사용자가 결제 버튼을 누른 순간 |
| **수집 시각** (ingestion time) | 브로커나 시스템이 받아 기록한 순간 | **Kafka 브로커가 메시지를 로그에 기록한 순간** |
| **처리 시각** (processing time) | 처리 엔진의 연산자가 실제로 계산한 순간 | — |

> **수집 시각을 별도로 세우는 게 정확하다.** 많은 자료가 event time / processing time 둘로만 나누는데,
> 실무 디버깅에서는 "브로커까지는 왔는데 엔진이 안 읽었다"와 "브로커에도 안 왔다"를 구분해야 한다.
> Ch5-3의 *source ingestion lag* vs *stream processing lag* 지표 분리가 정확히 이 구분이다.

### ⭐ 시간 기준은 질문 자체를 바꾼다

> **처리 시각 기준 질문: "시스템이 그 시간에 본 데이터는 무엇인가"**
> **이벤트 발생 시각 기준 질문: "실제로 그 시간에 일어난 데이터는 무엇인가"**
>
> **"같은 이벤트라도 질문이 다르면 들어갈 시간 구간이 달라진다."**

**스트리밍 집계 설계 순서 3단계:**

1. 어떤 시간을 기준으로 계산할지 결정
2. 늦게 들어온 데이터를 어떻게 처리할지 결정
3. **시간 구간 결과를 언제 확정할지 결정**

## 처리 시각 — 빠르지만 재현성이 약하다

| 특징 | 장점 | 한계 |
|---|---|---|
| 엔진이 실행되는 시스템 시각 기준 | 빠른 결과 | **데이터가 늦게 도착하면 원래 시간 구간에 반영 불가** |
| 별도 이벤트 시각 추출 부담 적음 | 단순한 구현 | **장애 후 다시 처리하면 결과가 달라질 수 있음** |
| 구현 단순 | 낮은 지연 | 과거 데이터를 다시 읽을 때 **원래 사건 시각의 의미가 깨짐** |
| | 운영 관제에 유리 | |

> **처리 시각 기준 5분 집계의 의미: "최근 5분 동안 시스템이 처리한 데이터의 집계"** —
> 실제로 그 5분 동안 발생한 데이터가 아니다.

**잘 맞는 사례:** 현재 초당 처리량 · 현재 오류율 · 현재 적체량 · 시스템 지연 경보 ·
실시간 운영 대시보드.

> ⭐ **"빠르게 나오면 더 좋은 지표라는 단순 판단 — 운영 지표에는 맞을 수 있지만, 정산·분석·사용자
> 행동 집계에는 위험."**

## 이벤트 발생 시각 — 의미는 보존되지만 대가가 있다

**특징:** 비즈니스 의미 보존 · 실제 사건 순서에 가까운 계산 · **과거 데이터 재처리에 유리** ·
**늦게 도착한 데이터 처리 필요**.

> ⭐ **"'이벤트 발생 시각 필드만 있으면 끝'이 아니다. 시각 필드만으로는 부족하고, 시간 구간을 언제
> 닫을지 결정하는 규칙이 필요하다."**

**이 한 줄이 소단원 4 전체의 존재 이유다.**

### 늦게 도착하는 원인

네트워크 지연 · **모바일 오프라인 후 재접속** · 브로커 적체 · 재시도 · 장애 복구 ·
여러 지역에서 들어오는 데이터 · 여러 시스템의 처리 속도 차이.

> **"늦게 온 데이터는 그냥 버리면 된다는 단순 처리? 운영 지표에는 가능할 수 있지만,
> 정산·분석·모델 학습 데이터에서는 큰 왜곡이 발생할 수 있다."**

**"모델 학습 데이터"가 목록에 들어 있는 게 중요하다** — 늦게 온 데이터를 버리면 학습셋이 편향되고,
그것이 [[Data drift and training-serving skew]]의 skew로 이어진다. **강의가 이 연결을 만들지 않는다.**

### 재처리에 강한 이유

| 상황 | 처리 시각 기준 | 이벤트 발생 시각 기준 |
|---|---|---|
| 어제 쌓인 이벤트를 오늘 다시 읽어 재계산 | **오늘 다시 처리한 시각으로 집계** → 어제 사건이 오늘 시간 구간에 들어감 | 데이터 안의 실제 발생 시각으로 집계 → **빠르게 다시 읽어도 원래 시간 구간 유지** |

**잘 맞는 사례:** 클릭 로그 재집계 · **결제 데이터 정산** · **모델 학습용 로그 재구성** ·
신규 지표 추가 후 과거 데이터 재계산 · 장애 구간 복구 후 재처리.

> **이 목록이 곧 Ch3-5(카파 아키텍처)의 전제다** — "같은 입력을 다시 읽어도 같은 의미의 결과"가
> 나와야 로그 재생이 성립한다.

## ⭐ 같은 데이터, 다른 결과 — 결제 3건 예시

| 이벤트 | 실제 발생 시각 | 시스템 도착 시각 |
|---|---|---|
| 결제 A | 10:02 | 10:02 |
| **결제 B** | **10:04** | **10:12** |
| 결제 C | 10:07 | 10:07 |

집계 목표: `10:00~10:10 결제 건수`

| 질문 | 답 |
|---|---|
| **"10:00~10:10 동안 시스템이 처리한 결제는 몇 건인가?"** (처리 시각) | **2건** (A, C) — B는 10:12에 도착했으므로 다음 구간 |
| **"10:00~10:10 동안 실제로 발생한 결제는 몇 건인가?"** (이벤트 발생 시각) | **3건** (A, B, C) |

> **강의가 정답을 슬라이드에 적지 않고 질문만 던진다.** (p192·p193이 같은 표에 다른 질문만 붙인
> 구성) 의도적 여백으로 보이지만, **자료만 보면 답이 없어 자습에는 불친절하다.**

## 왜 윈도우와 워터마크가 필요한가

| | 배치 집계 | 스트리밍 집계 |
|---|---|---|
| | 데이터 전체가 이미 존재 → 전체를 읽은 뒤 결과 계산 | 데이터가 계속 추가, **전체가 "다 모이는 시점"이 없음** |

> **"키별 전체 집계를 기다리면 결과를 낼 수 없다. 무한 입력을 유한한 계산 단위로 자르는 장치가
> 필요하고, 그 계산 단위가 윈도우."**

### ⭐ 역할 분담 — 세 가지 질문

| 장치 | 질문 |
|---|---|
| **윈도우** | 이 이벤트를 **어느 계산 구간에 넣을 것인가** |
| **워터마크** | 이 시간 구간을 **언제 닫을 것인가** |
| **출력 시점 규칙** | 중간 결과를 낼 것인가 / 최종 결과만 낼 것인가 / **늦게 온 데이터가 오면 다시 낼 것인가** |

> ⭐ **이 3분할이 이 소단원의 핵심 기여다.** 많은 자료가 윈도우와 워터마크를 뭉뚱그리는데,
> **"넣기 / 닫기 / 내보내기"** 로 나누면 각각 독립적으로 설계·튜닝할 수 있다는 게 보인다.

## 윈도우 3종

윈도우가 결정하는 것: 어떤 이벤트를 같은 집계 단위로 볼 것인가 · **키별 상태를 어느 범위까지 들고
있을 것인가** · 결과의 시간 단위를 무엇으로 볼 것인가.

| 윈도우 | 특징 | 예 |
|---|---|---|
| **고정 (Tumbling)** | 일정한 길이, 서로 겹치지 않음. 전체 시간을 균일하게 쪼개 **배치 처리와 유사한 결과** | 5분마다 결제 건수 |
| **이동 (Sliding/Hopping)** | 일정한 길이, 일정 간격마다 새 윈도우 시작, **구간이 겹칠 수 있음** | 최근 10분 평균을 1분마다 갱신 |
| **세션 (Session)** | 고정 길이 없음. **활동이 일정 시간 끊기면 하나의 세션 종료** | 사용자 방문 흐름, 장바구니 행동 묶음 |

**선택 기준 4문항:**

- 결과가 끊어진 구간이어야 하는가
- 최근 흐름을 계속 갱신해야 하는가
- **활동 묶음 자체가 분석 단위인가**
- **한 이벤트가 여러 결과에 들어가도 되는가** ← 이동 윈도우의 핵심 판단

## 워터마크

> **"이벤트 발생 시각 기준으로, 어느 시점까지 데이터가 대부분 도착했다고 볼지 나타내는 기준선."**

**필요한 이유:** 이벤트는 순서대로 도착하지 않는다 · 과거 시각의 이벤트가 나중에 도착 가능 ·
**그렇다고 무한정 기다릴 수 없다.**

**역할 셋:** 시간 구간 결과를 닫을 기준 · 늦은 데이터 판단 기준 · **오래된 상태를 정리할 기준**.

> **세 번째가 실무적으로 중요하다** — 워터마크가 없으면 상태가 무한히 자란다. Ch3-2에서 본
> "상태 크기"가 곧 비용이므로, 워터마크는 정확성 장치이자 **비용 통제 장치**다.

### 늦은 데이터와 허용 지연

| | 뜻 |
|---|---|
| **늦은 데이터** | 워터마크가 이미 지나간 시간 구간에 속하는 이벤트 |
| **허용 지연** (allowed lateness) | 늦게 도착한 데이터를 추가로 받아줄 시간 범위 |

선택지 넷: 바로 버림 · 일정 시간까지 반영 · **별도 경로로 분리** · **수정 결과를 다시 출력**.

> **"허용 지연이 길수록: 더 많은 늦은 데이터 반영 가능, 대신 상태를 더 오래 보관, 결과 확정도
> 늦어진다."**

### ⭐ 워터마크는 정답 시계가 아니라 절충 기준

> ⭐ **"모든 데이터가 도착했다는 절대 보장이 아니다. 더 기다릴 것인가, 결과를 낼 것인가의 기준이고,
> 정확성·지연·상태 비용 사이의 절충이다."**

Spark의 보장을 정확히 인용한다:

> **"설정한 지연 시간보다 덜 늦은 데이터는 집계 반영이 보장된다. 그보다 더 늦은 데이터는 반영될
> 수도 있고 안 될 수도 있다."** → **운영 가능한 마감선을 만드는 장치.**

**"반영될 수도 있고 안 될 수도 있다"를 명시하는 게 정확하다.** 워터마크를 "그 이후는 무조건 버림"
으로 이해하는 오해가 흔한데, 실제 보장은 **하한 보장(at-least)** 이지 상한 배제가 아니다.

## 결과 출력과 정합성

### 윈도우 결과는 언제 나오나

- 워터마크가 윈도우 끝을 지났을 때
- 조기 결과를 내도록 설정했을 때
- **늦은 데이터가 도착해 결과가 수정될 때**

중요한 구분 셋: **중간 결과 · 정시 결과 · 늦은 데이터 반영 결과.**

### ⭐ 수정 결과의 해석 — 다시 결제 3건

첫 결과: A, C 포함 → **2건**
늦은 데이터 도착: B가 10:12에 도착(실제 발생 10:04) → 수정 결과: A, B, C → **3건**

> ⭐ **"3건을 새 행으로 추가할 것인가, 기존 2건을 3건으로 갱신할 것인가, 2건과 3건을 모두 이벤트로
> 남길 것인가?"**
>
> **이 질문이 스트리밍 정합성의 핵심이고, 답은 싱크(sink)의 성질이 결정한다.**

### 출력 방식 3종 — 저장소 설계와 묶인다

| 방식 | 동작 | 적합한 저장소 |
|---|---|---|
| **Append** | 확정된 결과만 추가 | 파일 저장소, 로그성 테이블. **결과 지연 가능** |
| **Upsert** | 같은 키의 결과를 덮어씀 | 실시간 대시보드, 집계 테이블. **윈도우 키와 집계 키 설계가 중요** |
| **Update** | 변경된 결과만 출력 | 집계 테이블 갱신. **싱크가 업데이트를 지원해야 함** |

> **"출력 방식과 저장소 설계"를 한 슬라이드에 묶은 게 좋다.** 스트리밍 정합성은 엔진만의 문제가
> 아니라 **싱크의 성질과 함께 정해진다**는 것이 요점이고, 이것이 Ch3-1의
> *"exactly-once는 특정 sink 안에서 성립"* 과 이어진다.

## 실무 설계 판단 — 값을 무엇으로 정하나

| 설정 | 결정 기준 |
|---|---|
| **윈도우 크기** | 비즈니스 지표의 시간 단위 · 결과를 얼마나 자주 보고 싶은가 · **상태 크기와 계산 비용** |
| **이동 간격** | 갱신 주기 · **중복 계산 비용** · 대시보드 표시 주기 |
| **세션 간격** | "사용자 활동이 끊겼다"의 정의 · 도메인별 평균 행동 간격 · **과분할과 과병합의 균형** |
| **워터마크 지연 시간** | **실제 데이터 지연 분포** · 늦은 데이터 허용 범위 · 결과 지연 허용치 · 상태 저장 비용 |

> ⭐ **"실제 데이터 지연 분포"를 첫 기준으로 놓는 게 맞다.** 워터마크 지연을 감으로 정하지 말고
> **도착 지연의 p95/p99를 재서 정하라**는 뜻인데, **강의가 "분포를 어떻게 재는가"는 말하지 않는다.**

### 남은 문제 — Ch3-5로 넘어가는 다리

> - 너무 늦게 온 데이터는 어떻게 복구할 것인가
> - **이미 나온 결과를 나중에 다시 계산할 수 있는가**
> - 원본 이벤트를 남겨두어야 하는가
> - **배치 재처리와 스트리밍 처리를 어떻게 함께 설계할 것인가**

**네 질문이 그대로 람다/카파 아키텍처의 문제 정의다.**

## 기존 페이지와의 대조

- **[[Stream processing semantics]] 대폭 보강** — Part 1 CH04-5,6에서 세운 페이지인데, 여기의
  **"넣기/닫기/내보내기 3분할"**, **출력 방식 3종과 싱크 설계**, **"워터마크는 하한 보장"**,
  **설정값 결정 기준 4표**가 모두 새롭다.
- **[[Data drift and training-serving skew]]와의 미연결 고리** — "늦은 데이터를 버리면 모델 학습
  데이터가 왜곡된다"가 skew 패턴 1(시간 기준 불일치)과 같은 이야기인데 강의가 잇지 않는다.
- **[[AI DE Course - Part4 Ch1 CAP theorem and system limits]]의 Lamport** — "두 사건 중 무엇이 먼저
  일어났는지 말할 수 없다"가 event time 문제의 이론적 뿌리다. 같은 챕터 두 소단원인데 연결이 없다.

## 자료 품질

- ✅ **결제 3건 예시를 두 소단원에 걸쳐 일관되게 재사용** — 이 코스에서 드문 서술 규율
- ✅ **"넣기/닫기/내보내기" 3분할**이 명료
- ✅ Spark의 워터마크 보장을 **정확한 표현으로** 인용 ("반영될 수도 있고 안 될 수도")
- ✅ 출력 방식과 싱크 설계를 묶어서 다룸
- ✅ 출처 없는 수치 없음
- ⚠️ **결제 예시의 답을 적지 않는다** (p192·p193). 강의 영상에서는 말하겠지만 슬라이드만으로는 불완전
- ⚠️ **워터마크 생성 방식이 없다** — bounded-out-of-orderness, periodic vs punctuated, **여러
  파티션의 워터마크를 어떻게 합치는가(min 취하기)** 가 전혀 안 나온다. **idle partition 문제**
  (한 파티션이 조용하면 워터마크가 안 올라감)도 없다 — 실무에서 가장 자주 만나는 함정이다
- ⚠️ **"실제 데이터 지연 분포"를 재라고 하면서 측정 방법이 없다**
- ⚠️ 윈도우 도식 슬라이드가 대부분 텍스트만 — 겹치는 이동 윈도우는 그림이 있어야 이해가 빠르다
