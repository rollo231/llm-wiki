## ⭐ 두 계층 — 중심 질문이 다르다

메시지 브로커와 스트림 처리 엔진은 **모두 소스와 싱크 사이에 위치하는 중간 계층**이지만 해결 대상이
다르다.

| | 중심 질문 |
|---|---|
| **브로커** | 이벤트를 **어떻게 안전하게 흘리고 보관**할 것인가 |
| **엔진** | 계속 들어오는 이벤트를 **어떤 시간 기준과 상태 기준으로 계산**할 것인가 |

> ⭐ **"이 구분이 흐려지면 Kafka만 두고도 실시간 집계가 끝난다고 오해하거나, 반대로 Flink나 Spark만
> 붙이면 메시징 계층이 없어도 된다고 착각하는 문제가 발생한다."**
>
> **양방향 오해를 모두 짚는 게 좋다.** 후자("엔진이 있으니 브로커는 불필요")는 재처리 가능한 입력
> 계층이 없으면 체크포인트 복구가 성립하지 않는다는 점에서 특히 위험하다 — 이 소단원 뒷부분에서
> 실제로 그 이유를 설명한다.

### 운반 계층 (Message Broker)

핵심 역할 셋:

- **시스템 분리** — Producer와 Consumer를 분리하여 결합도를 낮춤
- **버퍼링** — 두 시스템 간 처리 속도 차이를 완충하여 과부하 방지
- **유통 및 보관** — 라우팅, 다중 구독, 재전달, 보관 기간 관리, **장애 시 재처리를 위한 입력 데이터
  원본 보존**

| 제품 | 강조점 |
|---|---|
| **Apache Kafka** | 이벤트 스트림의 발행/구독 + **디스크에 안전하게 영속화** |
| **RabbitMQ** | 처리 완료 응답(Acknowledgements) 메커니즘을 통한 **Reliable delivery** |
| **Pub/Sub** | Topic과 Subscription 모델 기반의 유연한 비동기 메시징 |

### 계산 계층 (Stream Processing Engine)

핵심 역할 셋:

- **복잡한 실시간 연산** — Filter/Map을 넘어 **집계·조인·윈도우 단위 연산**
- **상태 및 시간 관리** — 과거 데이터를 기억하는 **Stateful processing**, **Event-time** 기준 처리
- **장애 복구** — **Checkpoint**를 활용해 실패 지점부터 정확히 상태를 복구

## ⭐ 단순 Consumer App으로는 부족한 이유

| | 내용 |
|---|---|
| **Stateless Processing** | 각 레코드를 독립적으로 처리, 이전 데이터 정보 불필요. 예: `SELECT * FROM stream WHERE price > 10000` 필터링, JSON → Avro 변환. **브로커에 연결된 단순한 Python/Java Consumer app으로 구현 가능** |
| **한계** | 실무의 비즈니스 요구는 대부분 **특정 기간 동안, 특정 유저의 패턴**을 요구. **"데이터 간의 관계를 파악하려면 반드시 '기억(State)'이 필요하다."** |

> ⭐ **여기가 브로커/엔진 경계선의 정확한 위치다.** Stateless면 consumer app으로 충분하고,
> Stateful이 필요한 순간 엔진이 필요해진다.

### Stateful Processing

> **"과거에 처리한 데이터의 결과나 맥락(State)을 메모리나 로컬 디스크에 저장하고, 새로 들어온
> 데이터와 결합하여 연산하는 방식."**

예: *"최근 5분간 로그인 실패 5회 이상인 계정 차단"*, *"실시간 누적 매출액 산출"*.

> **"스트림 처리 엔진의 진짜 역할: 수억 건의 이벤트가 지나가는 동안, 거대한 '상태(State)'를 빠르고
> 안전하게 읽고 쓸 수 있도록 관리하는 것."**

| 연산 유형 | 예 |
|---|---|
| **Stateless** | 결제 금액이 100만 원 이상인가? |
| **Stateful** | 실시간 이동 평균(최근 1시간 평균 기온) · **패턴 탐지**(1분 이내에 동일 카드로 3개국 이상에서 결제 발생) · **스트림-스트림 조인**(주문 이벤트와 결제 이벤트 결합) |

### ⭐ State Backend — 왜 외부 DB를 안 쓰나

> **"매 레코드 처리 시마다 외부 DB(Redis, MySQL)에 접근하면 네트워크 지연으로 실시간성 확보
> 불가능. 스트림 엔진은 상태를 계산 노드 내부 디스크/메모리에 직접 저장하는 '로컬 저장소' 방식을
> 채택한다."**

| 유형 | 특징 |
|---|---|
| **HashMap 기반 (Memory)** | 자바 객체 형태로 메모리에 저장. 속도가 극도로 빠르나 **상태 크기가 메모리 용량으로 제한** |
| **RocksDB 기반 (Embedded DB)** | 로컬 디스크(SSD)에 **LSM-Tree** 구조로 저장. **메모리보다 큰 상태(수 TB)** 를 다룰 때 유리, 효율적인 직렬화 제공 |

> ⭐ **이 대비가 좋다 — 그리고 방금 다룬 Ch2와 정면으로 충돌하는 것처럼 보인다.**
> Ch2는 "Redis에 상태를 두면 빠르다"고 했고, 여기는 "Redis에 접근하면 실시간성 확보 불가"라고 한다.
> **모순은 아니다 — 접근 빈도의 차이다.** 요청당 몇 번 조회하는 서빙 경로(Ch2)와 레코드당 매번
> 읽고 쓰는 스트림 연산(여기)은 다른 문제다. **하지만 강의가 이 구분을 명시하지 않아, 두 챕터를
> 이어 읽으면 혼란스럽다.**

## 스트림 처리 엔진의 핵심 4가지

### 1. 상태를 기억하는 계산

> **"지금 들어온 한 건만 본다가 아니라, 이전까지의 흐름을 기억한 채 현재 이벤트를 해석."**

실시간 집계가 함께 관리해야 하는 것: 키별 상태 · 시간 구간별 중간 결과 · **아직 닫히지 않은 계산
구간** · **늦게 들어올 수 있는 데이터**.

### 2. 시간 기준을 해석하는 계산

데이터가 들어온 시각, 실제로 발생한 시각, 시스템이 본 시각, 결과를 내보내는 시각이 **서로 다를 수
있다.**

> **"스트림 처리 엔진은 데이터를 단순히 읽는 것이 아니라, 어떤 시간 기준으로 계산할지 해석하는
> 계층. 시간 기준을 정하지 않으면 늦게 들어온 데이터 때문에 집계가 쉽게 틀어진다."**

→ 상세는 [[AI DE Course - Part4 Ch3 Event time watermarks and windows]].

### 3. 늦게 도착한 데이터와 시간 구간 계산

늦는 원인: 네트워크 지연 · 서비스 장애 · 재전송 · **지역 간 시간 차이**.

엔진이 결정해야 하는 것 셋: **이 시간 구간을 언제 닫을 것인가** · 얼마나 늦은 데이터까지 반영할
것인가 · **오래된 중간 상태를 언제 지울 것인가**.

### 4. 장애가 나도 이어가는 복구 구조

| 엔진 | 복구 방식 |
|---|---|
| **Flink** | **체크포인트**를 통해 각 연산자의 상태와 **입력 위치를 함께** 저장. 실패 시 이 지점부터 일관되게 재시작 |
| **Spark Structured Streaming** | 입력 위치 기록 + 체크포인트 + **쓰기 전 기록** + **다시 처리 가능한 입력** + **중복에 안전한 출력 저장소**의 조합 |
| **Kafka Streams** | 상태 저장소를 복구한 뒤 재개. 상태 저장소는 **변경 이력을 기록한 주제(changelog topic)** 를 바탕으로 복원 |

> ⭐ **"제대로 보장하기 위해 다시 읽을 수 있는 입력 계층과 상태 저장 공간이 필요하다."**
>
> **이 한 줄이 브로커가 없으면 엔진의 exactly-once가 성립하지 않는 이유다.** 앞서 지적한 "엔진만
> 있으면 브로커 불필요" 오해의 답이 여기 있다. 그리고 **Ch3-1의 "exactly-once는 특정 시스템 경계
> 안에서만 성립"** 이 무슨 뜻인지도 여기서 구체화된다 — 재읽기 가능한 입력 + 중복에 안전한 출력이
> 그 "경계"다.

## 대표 엔진 3종

| 엔진 | 한 줄 | 잘 맞는 문제 |
|---|---|---|
| **Apache Flink** | **상태와 시간 제어를 전면에 둔 엔진.** 세밀한 상태 관리와 시간 제어 능력이 압도적. 대규모 실시간 이상 탐지, **복잡한 이벤트 처리(CEP)의 표준** | 사용자별 상태 유지 · 긴 시간 구간 집계 · **늦게 도착한 데이터가 많은 환경** · 상태 크기가 큰 실시간 계산 · 정교한 시간 기준이 중요한 분석과 탐지 |
| **Spark Structured Streaming** | **Micro-batch 처리.** 지연 시간은 Flink보다 약간 길지만 **기존 Spark SQL 및 배치 에코시스템과의 완벽한 통합**이 강점 | SQL/DataFrame 중심 조직 · 기존 Spark 배치 파이프라인과의 통합 · **배치와 스트림을 같은 개발 모델로** 다루고 싶은 환경 |
| **Kafka Streams** | **애플리케이션 내부에서 동작하는 처리 라이브러리.** 별도 클러스터 불필요 | Kafka가 이미 핵심 입력 계층인 환경 · **별도 대형 처리 클러스터보다 서비스 안쪽 처리 흐름이 필요한 경우** · Java/Scala 기반 데이터 서비스 |

각 엔진의 모델을 한 줄로 요약한 것도 정확하다:

- **Flink** — bounded/unbounded 모두 처리, 상태 기반 계산을 **엔진의 중심 개념**으로 취급
- **Spark** — 입력을 "계속 추가되는 표", 결과를 "계속 갱신되는 표"로 보고 **점진적 쿼리**
- **Kafka Streams** — 처리 흐름을 **프로세서 토폴로지**로 정의, **상태 저장소(state store)** 기반

> **Part 1 CH04-5,6([[AI DE Course - Ch4-5,6 Stream processing engines]])의 "Flink vs Spark"가
> 여기서 3종으로 늘고 축이 정밀해진다.** Part 1이 "지연 vs 통합성"이었다면, 여기는
> **"상태 관리 능력 vs 에코시스템 vs 배포 형태"** 3축이다. Kafka Streams가 추가된 것이 특히 중요하다 —
> **클러스터를 세우지 않는 선택지**를 처음 보여준다.

## 기존 페이지와의 대조

- **새 concept:** [[Message broker]] (운반/계산 경계)
- **새 entity:** [[Apache Flink]] · [[Apache Spark]]
- **[[Stream processing semantics]] 대폭 보강 필요** — State Backend(HashMap vs RocksDB),
  체크포인트가 "상태 + 입력 위치"를 함께 저장한다는 점, exactly-once의 성립 조건이 모두 새롭다.
- **[[Batch and stream processing]]** — "오케스트레이터는 배치 전용"이라는 Part 1 경계에,
  **"브로커는 운반, 엔진은 계산"** 이라는 두 번째 경계가 추가된다.
- ⚠️ **Ch2와의 표면적 충돌** (Redis를 상태 저장소로 쓸 수 있나) — 위 참조.
