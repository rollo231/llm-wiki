## 요약

[[Apache Sedona]]가 **공간 조인을 실제로 어떻게 실행하는가.** [[Apache data technology map (book)]]
Ch11이 남긴 공백 — *"인덱스의 종류(R-tree·quadtree·grid)나 조인 알고리즘이 없다"* — 을 정면으로
메우는 문서 묶음이다. 파생 개념은 [[Spatial join execution]].

핵심 구조는 **격자 ≠ 인덱스 ≠ refine** 3층이고, 튜닝 다이얼은 전부 `sedona.*` 설정으로 노출된다.

## 핵심 takeaway

### 1. 물리 연산자가 세 개뿐이고, 무엇이 선택되는지가 성능 전부다

| 연산자 | 조건 | 문서 서술 |
|---|---|---|
| `RangeJoin` / `DistanceJoin` | 양쪽 다 큼 | 공간 파티셔닝 + 인덱스. Sedona의 본체 |
| `BroadcastIndexJoin` | 한쪽이 임계값 이하 | *"maintains the partitioning of the non-broadcast side and doesn't require a shuffle"* |
| `BroadcastNestedLoopJoin` | 위 둘이 실패 | *"the slowest option"* |

물리 플랜에 그대로 이름이 뜬다:

```
== Physical Plan ==
BroadcastIndexJoin pointshape#52: geometry, BuildRight, BuildRight, false ST_Contains(...)
:- Project [st_point(...) AS pointshape#52]
+- SpatialIndex polygonshape#30: geometry, QUADTREE, [id=#62]
```

⭐ `SpatialIndex ... QUADTREE` 줄이 **인덱스가 실제로 붙었는지 확인하는 방법**이다.
브로드캐스트 측 인덱스는 Sedona가 만든다 — *"Sedona will create a spatial index on the
broadcasted table."*

브로드캐스트 힌트가 **어느 쪽에 붙어야 하는지가 조인 타입마다 정해져 있다**:

| 조인 타입 | 브로드캐스트 가능한 쪽 |
|---|---|
| Inner | 양쪽 (둘 다 힌트면 left 선호) |
| Left semi / Left anti / Left outer | right |
| Right outer | left |

### 2. 파라미터 표 — 책에 전혀 없던 것

`sedona.*` 또는 `spark.sedona.*` 두 접두 모두 유효하고, **`sedona.` 쪽이 우선**한다
(`spark.` 접두는 `spark-defaults.conf`·K8s 설정에서 미리 줄 수 있다는 장점).

| 파라미터 | 기본값 | 값 |
|---|---|---|
| `sedona.global.index` | `true` | 인덱스 사용 (SQL range/distance join 한정) |
| `sedona.global.indextype` | **`rtree`** | `rtree` / `quadtree` |
| `sedona.join.gridtype` | **`kdbtree`** | `quadtree` / `kdbtree` |
| `sedona.join.autoBroadcastJoinThreshold` | `spark.sql.autoBroadcastJoinThreshold`와 동일 | `10MB` 등, `-1`로 비활성 |
| `sedona.join.indexbuildside` | `left` | (advanced) |
| `sedona.join.spatitionside` | `left` | (advanced) 파티셔닝 지배 측 |
| `sedona.join.numpartition` | `-1` (기존 유지) | (advanced) |
| `sedona.join.optimizationmode` | `nonequi` | `all` / `none` / `nonequi` |
| `spark.sedona.join.knn.includeTieBreakers` | `false` | 동거리 tie 전부 포함 |

CRS 관련 (v1.9.0 신규): `spark.sedona.crs.geotools` 기본 `raster` — **벡터는 proj4sedona,
래스터는 GeoTools**로 갈린다. `all`이 레거시(전부 GeoTools).

### 3. RDD API는 격자 3종을 노출한다 — SQL은 2종

> *"Three spatial partitioning methods are available: KDB-Tree, Quad-Tree and R-Tree."*

SQL 경로(`sedona.join.gridtype`)는 `quadtree`/`kdbtree` 둘만 받는다. R-Tree 파티셔너는 RDD
API 전용이다.

**두 RDD는 반드시 같은 파티셔너를 공유해야 한다** — 한쪽을 파티셔닝한 뒤 `getPartitioner()`를
다른 쪽에 넘긴다. 이 계약을 깨면 결과가 조용히 틀린다.

인덱스는 **둘 중 한쪽에만** 만들고, *"In general, you should build it on the larger
SpatialRDD"* 라고 권한다.

### 4. ⭐ 공간 파티셔닝은 객체를 복제한다

RDD 문서가 SpatialRDD의 네 가지 내부 RDD를 나열하면서 명시한다:

> 2. `spatialPartitionedRDD`: The RDD generated by spatial partition a rawSpatialRDD.
>    **Note that: this RDD has replicated spatial objects.**
> 4. `indexedRDD`: ... **Note that: this RDD has replicated spatial objects.**

경계에 걸친 폴리곤이 여러 파티션에 들어가야 조인이 완전해지므로 복제는 설계상 전제다. 대가로
**중복 쌍 제거가 사용자 몫**이 된다(§7의 S2 절에서 같은 문제가 다시 나온다).

네 RDD는 질의 종류에 따라 쓰이는 것이 다르고 공존하지 않는다:

| 질의 | 쓰이는 RDD |
|---|---|
| Range/KNN, 인덱스 없음 | `rawSpatialRDD` |
| Range/KNN, 인덱스 사용 | `indexedRawRDD` |
| Join/Distance join, 인덱스 없음 | `spatialPartitionedRDD` |
| Join/Distance join, 인덱스 사용 | `indexedRDD` |

→ 반복 질의는 해당 RDD를 캐시하라. 공간 자기상관·co-location 마이닝처럼 self-join을 반복하는
작업이 대표 사례로 나온다.

### 5. ⭐ 파티션 수가 다른 모든 튜닝보다 먼저다

Optimizer 문서 맨 앞의 tip:

> Sedona join performance is **heavily affected by the number of partitions**. If the join
> performance is not ideal, please increase the number of partitions by doing `df.repartition(XXX)`
> right after you create the original DataFrame.

튜닝 튜토리얼도 같은 말을 반복한다 — *"as the first step, you should always consider increasing
the number of your SpatialRDD partitions (2 - 8 times more than the original number)"*.

### 6. ⚠️ `LEFT JOIN`은 최적화되지 않는다 — 문서가 우회를 처방한다

> Range and distance joins **do not support** a LEFT JOIN as below: […]
> This will lead to a **BroadcastIndexJoin** which can become very inefficient with two large
> datasets. Otherwise, the **BroadcastNestedLoopJoin** is triggered which is the slowest option.

또 못박아 둔다: *"All join queries in SedonaSQL are inner joins."*

처방은 inner join으로 ID 쌍을 만들고 그것과 equi-`LEFT JOIN` 하는 2단 구성이다.

```sql
WITH inner_join AS (
    SELECT dfA.a_id, dfB.b_id
    FROM dfA, dfB
    WHERE ST_INTERSECTS(dfA.geometry, dfB.geometry)
)
SELECT dfA.*, inner_join.b_id
FROM dfA LEFT JOIN inner_join ON dfA.a_id = inner_join.a_id;
```

⭐ 문서가 덧붙이는 운영 조언 — *"One can define this strategy as stored procedure or a DBT
macro to simplify the repeated code."* **공간 조인의 SQL 관용구가 재사용 자산이 된다는 신호.**

### 7. S2 근사 equi-join — 정확도를 성능과 바꾸는 다이얼

최적화 조인마저 느릴 때(*"possibly caused by complicated and overlapping geometries"*)의 탈출구.
Spark의 **평범한 equi-join 알고리즘을 그대로 쓴다**는 게 핵심이다.

```sql
-- 1. 양쪽에 S2 셀 ID (기하 하나가 여러 ID를 낳음)
SELECT id, geom, explode(ST_S2CellIDs(geom, 15)) AS cellId FROM lefts
-- 2. cellId 로 equi-join
-- 3. (선택) ST_Contains 로 false positive 제거
-- 4. (선택) GROUP BY 로 중복 제거
```

> A **smaller level** indicates bigger cells, **less exploded rows, but more false positives**.

⭐ 3단계 생략 허가가 명문화돼 있다 — *"You can skip this step if you don't need 100% accuracy
and want faster query speed."* 이건 [[Consumption layer]]의 오차 다이얼(DataSketches)과 같은
형태의 축이다.

⭐ 그리고 **point-in-polygon 조인에서는 4단계(중복 제거)가 불필요**하다고 명시한다 —
*"If you are doing point-in-polygon join, this is not a problem."* 중복은 polygon-polygon,
polygon-linestring, linestring-linestring에서만 생긴다.

거리 조인에 쓰려면 `ST_Buffer(geom, METER_DISTANCE/111000.0)`로 원을 만들어 셀 ID를 생성한다.
⚠️ 문서가 스스로 한계를 적는다 — *"might lead to inaccurate results if your data is close to the
poles or antimeridian."*

### 8. ⚠️ 거리의 단위는 좌표계의 단위다

> Sedona uses the **Euclidean distance** between two objects so the distance unit has the same CRS
> of the original coordinates.

경위도에 `ST_Distance(...) < 2`라고 쓰면 2도다. 해법 둘: `ST_Transform`으로 미터계로 옮기거나
`ST_DistanceSphere`/`ST_DistanceSpheroid`(단위 미터)를 쓴다.

⚠️ 측지 거리 조인의 한계도 명시된다 — *"distance join with geodesic distance calculators work
best for point data. For non-point data, it only considers their centroids."*

⭐ 뒤집어 읽으면 **평면 좌표계에는 CRS가 필요하지 않다** — 좌표 단위가 곧 거리 단위다. 임의의
평면 좌표(픽셀·마이크론)에 그대로 쓸 수 있다는 뜻이고, 이게
[[SpatialData and Sedona interop]]의 전제가 된다.

거리 조인 술어로 인정되는 함수: `ST_Distance`, `ST_HausdorffDistance`, `ST_FrechetDistance`(평면) ·
`ST_DistanceSphere`, `ST_DistanceSpheroid`(미터). `<`는 *fully within*, `<=`는 *intersects
within* 으로 구분해 서술한다.

### 9. KNN join — 필터의 위치가 질문을 바꾼다

`ST_KNN(R, S, k, use_spheroid)`. R이 질의 측, S가 객체 측. **비점 기하는 centroid로 대체**된다.
left inner join만 지원하고, 이웃이 없는 질의 행은 결과에서 빠진다.

⚠️ 문서가 의미론 함정을 직접 설명한다:

- **Filter before KNN** — *"What are the K nearest high-rated restaurants?"*
- **Filter after KNN** — *"Of the K nearest restaurants, which ones are high-rated?"*

옵티마이저가 필터를 객체 측 리더로 밀어내리면 전자가 된다. 이걸 막는 전용 함수가
`barrier(expression, var, value, ...)`이다.

⚠️ 또 하나 — 하드코딩 SQL로 만든 DataFrame을 `ST_KNN`으로 조인하면 Spark가 이를 **UDF로 접어
`UnsupportedOperationException`** 을 던진다. 회피는 `.cache()`로 materialize.

### 10. 래스터도 같은 최적화를 탄다

`RS_Intersects`·`RS_Contains`·`RS_Within`이 `RangeJoin`/`BroadcastIndexJoin`으로 계획된다.
1.9.1에서 `RS_DWithin(left, right, distance)`가 거리 조인 술어로 추가됐고, 구현 서술이 이례적으로
구체적이다:

> `distance` is always in **meters**: both sides are projected to WGS84 first, each side's envelope
> is expanded by `distance` meters using the Haversine polar-radius approximation […] and the
> resulting envelopes drive an **R-tree filter**. Surviving candidates are **refined per-row** by
> `RS_DWithin`, which delegates to the Geography `dWithin` to compute the minimum geodesic distance
> between the convex hulls via **S2's `ClosestEdgeQuery`**.

⭐ **filter–refine 2단 구조가 문서에 명시된 유일한 대목**이다. 그리고 극지·antimeridian을 걸치는
래스터는 *"given a global filter envelope instead"* — **인덱스 필터를 의도적으로 느슨하게 두고
행별 술어로 정답을 만든다.** 정확성을 위해 프루닝을 포기하는 예외 처리.

## 발췌 (원문)

파티셔너 공유 계약:

```scala
objectRDD.spatialPartitioning(GridType.KDBTREE)
queryWindowRDD.spatialPartitioning(objectRDD.getPartitioner)   // ← 같은 파티셔너를 넘긴다

val buildOnSpatialPartitionedRDD = true   // join query 일 때만 TRUE
queryWindowRDD.buildIndex(IndexType.QUADTREE, buildOnSpatialPartitionedRDD)
val result = JoinQuery.SpatialJoinQueryFlat(objectRDD, queryWindowRDD, usingIndex, spatialPredicate)
```

range join으로 인정되는 술어 (튜토리얼):

> All joins triggered by `ST_Intersects`, `ST_Contains`, `ST_Within`, `ST_DWithin`, `ST_Touches`,
> and `ST_Crosses` are considered a range join.

## 기존 페이지와의 관계

**정정 1건 + 확장 다수.**

- ⚠️ **정정** — [[Apache Sedona]]가 책에서 옮긴 *"기존 GIS 도구가 단일 머신·중규모에 강하다면,
  Sedona는 레이크·스트림 규모"* 는 이제 절반만 맞다. **SedonaDB**가 단일 노드 자리를 직접
  차지했다 → [[Apache Sedona docs - Runtimes and GeoStats]].
- **확장** — [[Apache Sedona]]에 격자·인덱스·연산자·파라미터가 없었다. 이 페이지가 그 층이다.
- **확장** — [[Consumption layer]]의 오차 다이얼에 S2 조인이 같은 형태로 붙는다.
- **확장** — [[Distributed processing]]의 셔플 회피 논의에 브로드캐스트 인덱스 조인이 붙는다.
- ⭐ **[[Spatial aggregation]]의 issue #210 제약**에 대한 답의 *실행 층*이 여기다.
  데이터 경로는 [[SpatialData and Sedona interop]].

## 문서/코드 불일치 · 미확인

- `sedona.global.indextype` 기본값은 `rtree`인데, Optimizer 문서의 물리 플랜 예시 두 개는 모두
  `SpatialIndex ... QUADTREE`를 보여준다. **브로드캐스트 인덱스 조인의 인덱스 종류가 같은
  파라미터를 따르는지 문서에 명시가 없다.** 미확인.
- `sedona.join.spatitionside` — 오타로 보이지만(`partition`) 문서에 이 철자로 실려 있어 그대로 옮겼다.
  실제 코드의 키 이름은 미확인.
- R-Tree 격자가 왜 SQL 경로에는 없는지 설명이 없다.
- KDB-tree가 왜 기본값인지(밀도 적응) **문서는 말하지 않는다** — [[Spatial join execution]]에
  적은 그 설명은 자료구조 성질로부터의 추론이다.
