## 람다 아키텍처

**네이선 마즈(Nathan Marz)** 가 제안. 배치 처리의 정확성과 실시간 스트리밍의 저지연성을 결합.

> **"단일 시스템으로는 수 페타바이트의 데이터를 정확하게 분석(배치)하면서 동시에 실시간 인사이트
> (스트림)를 제공하기 어려워 등장."**

| 레이어 | 목표 | 역할 |
|---|---|---|
| **배치 레이어** | **Accuracy** | 마스터 데이터셋을 관리하며 정교하고 정확한 분석 결과 산출 |
| **스피드 레이어** | **Latency** | 최근 데이터의 지연을 최소화하여 즉각적인 결과 제공 |
| **서빙 레이어** | **Unified View** | 두 계층의 결과를 통합하여 사용자 쿼리에 대한 완전한 뷰 제공 |

**출발점의 긴장:** 정확한 결과는 보통 전체 데이터를 다시 계산해야 확보 가능 / 빠른 결과는 부분
데이터와 점진 계산에 의존 / 두 계열이 서로 다른 시스템 위에서 발전하던 시기 / **당장의 응답성과 최종
정확성을 동시에 얻고 싶은 요구**.

### ⭐ 람다가 남긴 유산

> **"람다가 강조한 좋은 문제의식:"**
> - **원본 데이터 보존**
> - **재처리 가능성**
> - 코드 변경 시 과거 결과 재계산 필요
> - 실시간 계층 오류를 배치 계층이 결국 수정
>
> ⭐ **"람다의 가장 큰 공헌은 재처리를 아키텍처 수준의 요구사항으로 끌어올린 점.
> 배치 계층이 속도 계층의 일시적 오류를 결국 덮어쓴다는 사고."**

**사례 — 이상 결제 탐지:**

| 계층 | 역할 |
|---|---|
| **Speed** | 결제 발생 즉시 블랙리스트 대조 및 패턴 분석, 의심 거래 차단 |
| **Batch** | 수개월간의 결제 트렌드를 전수 조사하여 새로운 사기 패턴 학습 및 모델 고도화 |

> **이 사례는 사실 람다의 순수한 예가 아니다** — Speed와 Batch가 "같은 지표를 다르게 계산"하는 게
> 아니라 **아예 다른 일**(차단 vs 모델 학습)을 한다. 진짜 람다의 문제는 *같은 집계를 두 번 구현*
> 하는 데서 오는데, 이 사례에서는 그 문제가 드러나지 않는다.

## 람다의 한계 — 인지 비용

> ⭐ **"람다의 가장 큰 비용은 계산 비용보다 인지 비용과 유지보수 비용."**

**구조적 한계 (복잡성의 함정):**

- 두 개의 코드베이스를 유지 — 배치용 로직과 실시간용 로직을 각각 개발하고 **동기화**
- 같은 변환 로직을 배치 계층과 속도 계층에 **각각 구현**
- 같은 의미의 결과를 서로 다른 시스템에서 맞춰야 하는 구조
- **프레임워크가 다르면 코드 스타일, 상태 처리, 오류 처리도 달라짐**

**운영상의 부담:** 두 처리 프레임워크 운영 · 두 결과 저장소 관리 · 결과 병합 로직 유지 ·
장애 원인 추적 경로 증가 · **성능 병목 지점 두 배**

**개발상의 부담:** 같은 의미의 결과 검증 · 배치·실시간 코드 간 버전 차이 · 디버깅 시 추적 범위 확대 ·
**추상화 프레임워크를 도입해도 누수 발생 가능**

> **마지막 항목이 정직하다** — "Summingbird 같은 추상화를 쓰면 되지 않나"에 대한 선제적 답이다.

### ⭐ 람다는 잘못된 답이 아니라 당시 도구의 산물

**2010년대 초반의 도구 지형:**

| 도구 | 문제 |
|---|---|
| **Hadoop** (배치) | 계산은 정확하지만 결과가 나오기까지 **몇 시간, 며칠** |
| **Storm** (초기 스트림) | 1초 만에 결과를 보여주지만 **데이터가 중복되거나 유실**, 100% 정확하지 않음 |

> **"비즈니스를 위해서는 결과가 빨리 나와야 하면서도, 돈이 오가는 문제니 결국엔 100% 정확해야 한다."**

정리:
- 람다는 **중요한 문제를 정확히 짚었다**
- 다만 해결 방식이 구조적으로 무거웠다
- 당시 배치 시스템 + 당시 스트림 시스템을 묶어 만든 **현실적 해법**
- **도구가 성숙할수록 단일 처리 경로에 대한 요구가 증가**

> ⭐ **아키텍처 패턴을 "당시 제약의 함수"로 읽는 이 시각이 이 소단원의 가치다.** 패턴을 정답/오답으로
> 배우면 왜 폐기됐는지 모르는데, 제약의 함수로 읽으면 **제약이 바뀔 때 무엇이 바뀌는지** 예측할 수
> 있다.

## 카파 아키텍처

> **핵심: 배치 경로와 속도 경로를 따로 두지 않고, 하나의 스트림 처리 경로로 실시간 처리와 재처리를
> 모두 수행한다.**
>
> **전제 조건: 과거 데이터를 다시 읽을 수 있는 로그 보존 — 불변 이벤트 로그.**

**핵심 구조 3요소:** 장기 보관 가능한 입력 로그 · 동일한 스트림 처리 로직 ·
결과 저장소 또는 Materialized View.

### Kreps가 제안한 재처리 흐름 (로그 재활용)

1. 충분히 긴 기간 동안 입력 로그 보관
2. 코드 변경 시 **새 버전의 스트림 작업 기동**
3. 과거 오프셋부터(Earliest) 다시 읽어 **새 결과 테이블 계산**
4. 새 작업이 현재 시점까지 따라잡으면 **결과 전환**
5. 이전 버전 작업 종료

> ⭐ **"재처리를 별도 배치 파이프라인이 아니라 같은 스트림 파이프라인의 빠른 재생으로 해석.
> 복잡도의 초점이 '두 개의 코드 경로'에서 '재생 가능한 로그'로 이동."**

**이 5단계가 사실상 블루/그린 배포의 데이터 버전이다** — 새 로직으로 병렬 계산하고 따라잡으면
스위치. **Ch3-1의 "replay와 backfill" 이 여기서 왜 필요한지가 드러난다.**

### 장점과 전제

| 장점 | 전제 |
|---|---|
| **단순성** — 단일 처리 경로 | 충분한 **로그 보존 기간** |
| **일관성** — 단일 코드베이스 | **빠른 재생이 가능한 처리 엔진** |
| **생산성** — 개발·테스트·디버깅 단순화 | 결과 저장소 전환 또는 갱신 전략 |
| 재처리 방식 명확화 | ⭐ **같은 입력을 다시 읽어도 의미를 유지하는 시간 기준과 상태 설계** |

> ⭐ **마지막 전제가 Ch3-3,4와 직결된다.** 처리 시각 기준으로 계산하면 로그를 다시 읽어도 원래
> 결과가 안 나온다 — **카파는 event time을 요구한다.** 강의가 이 의존 관계를 명시하지는 않지만
> "같은 입력 → 같은 의미의 결과"라는 문구로 암시한다.

**성숙한 도구:** Kafka(이벤트 로그의 영구 보관과 재생) + Flink/Spark(exactly-once 정합성을 보장하며
고속 연산).

### ⭐ 카파의 도전과제 — 3가지

| 과제 | 내용 |
|---|---|
| **저장 비용의 압박** | Kafka 같은 시스템에 **수년치 원본 데이터를 모두 보관**하는 것은 스토리지 비용 측면에서 큰 부담 |
| **상태 관리** | **매우 긴 윈도우**(예: 최근 1년 사용자 행동)를 관리할 때 메모리 사용량이 기하급수적으로 늘어날 위험 |
| **기술 장벽** | 스트리밍 엔진의 정교한 기능(Watermark, State Store)을 완벽히 다루기 위해 **높은 숙련도 요구** |

> **첫 번째 과제에 대한 현대적 답(Kafka tiered storage, Iceberg 위의 로그 보관)이 언급되지 않는다.**
> "수년치를 Kafka에" 대신 "핫 구간은 Kafka, 콜드는 객체 스토리지"가 실제 운영 방식인데,
> 이 소단원은 카파를 2014년 형태 그대로 소개한다.

**적용 사례 — 실시간 추천:** 사용자가 상품을 클릭하는 순간(Stream) 과거 한 달간의 취향
로그(Kafka Replay)와 결합해 0.5초 이내에 추천 갱신.

> ⚠️ **"0.5초 이내"** 는 출처 없는 수치다.

## 현대의 아키텍처 — 5개 축

> ⭐ **"람다 다음에 하나의 정답이 등장한 구조가 아니다. 저장·처리·조직·연결·신뢰가 각각 다른 방향으로
> 진화했다. 현대 아키텍처는 한 가지 이름보다 여러 축의 조합으로 이해하는 편이 정확하다."**

| 축 | 이름 | 내용 |
|---|---|---|
| **저장·관리 플랫폼** | **Lakehouse** | 레이크의 유연성 + 웨어하우스의 성능. **개방형 스토리지 표준**(Iceberg·Delta·Hudi)으로 벤더 종속 제거, **ACID·스키마 강제·타임 트래블** |
| **batch/stream 통합 처리** | **Unified Path** | 배치와 스트림을 다른 계산 세계로 보지 않는 접근. 같은 엔진 또는 같은 API로 둘 다 처리. **이중 코드 경로 축소** |
| **도메인 ownership** | **Data Mesh** | 중앙집중형 IT 병목 제거, 데이터를 도메인별 제품으로. **Domain Ownership**(도메인 팀이 품질·배포 전권) + **Self-Serve Platform**(인프라 팀은 플랫폼만 제공) |
| **메타데이터·자동화** | **Data Fabric** | 물리적으로 모으지 말고 메타데이터와 AI로 엮기. **Active Metadata**(AI가 메타데이터를 상시 분석해 활용 경로 자동 추천) + **Knowledge Graph**(관계를 그래프로 가시화, 의미론적 검색) |
| **경계 규약** | **Data Contract** | 목록에만 있고 설명 없음 |

> ⭐ **"Unified Path"가 카파의 계승자다.** 카파가 "스트림 하나로 통일"이었다면 Unified Path는
> "배치와 스트림을 같은 API로" — Flink의 bounded/unbounded 통합, Spark의 Structured Streaming이
> 이 방향이다. **Ch3-2에서 본 두 엔진의 설계가 여기서 아키텍처 흐름으로 설명된다.**
>
> ⭐ **Data Fabric 항목이 Part 3와 직결된다.** *Knowledge Graph로 의미론적 검색*은 Part 3 전체
> ([[Knowledge graph]] · [[GraphRAG]])의 요약이고, *Active Metadata*는 [[DataHub]] 같은 메타데이터
> 그래프의 지향점이다. **강의가 Part 3를 인용하지 않지만 같은 이야기다.**

> ⚠️ **Data Contract는 목록에 이름만 있고 설명 슬라이드가 없다.** Part 3 Ch3-4의
> [[AI DE Course - Part3 Ch3 SHACL and graph data contracts]]에서 "그래프용 데이터 계약"을 한 소단원
> 다뤘는데, **여기서 일반 데이터 계약을 다루지 않는 것은 공백이다.**
