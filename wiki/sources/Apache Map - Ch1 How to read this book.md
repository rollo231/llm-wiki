# Apache Map - Ch1 How to read this book

『Apache로 읽는 데이터 기술의 지도』(이현수, 2026) **Ch1. 이 책을 읽는 법** — 개념 5개,
PDF pp.4–9. 트래커: [[Apache data technology map (book)]].

이 장은 기술 소개가 아니라 **책 전체의 좌표계**다. 나머지 10개 장 85개 개념이 다 이 다섯 페이지의
틀 안에 배치된다. 그래서 목차 중심으로 읽을 때 실제로 읽어야 하는 유일한 장이기도 하다.

## 1. Apache가 표준이 된 이유는 기술이 아니라 거버넌스다

Spark·Kafka·Airflow·Iceberg는 하는 일이 전혀 다른데 같은 이름표를 달고 있다. **Apache는 제품
브랜드가 아니라 오픈소스 프로젝트를 관리하는 비영리 재단**(Apache Software Foundation)이고, 이
재단의 특징은 **특정 회사가 프로젝트를 소유하지 못하게 하는 것**이다. 기업이 만들어 기부한 기술도
재단에 들어오면 공개된 규칙과 커뮤니티 투표로 운영된다.

저자가 드는 근거는 네 가지다.

- 특정 벤더에 묶이지 않아 **클라우드를 옮겨도 기술을 이어 쓸 수 있다**
- 공개된 규칙과 투표로 운영되어 **방향이 갑자기 바뀌기 어렵다**
- 같은 재단 안의 프로젝트끼리 **연동 사례가 풍부하다**
- 자료와 경험자가 많아 **문제가 생겼을 때 참고할 곳이 넓다**

논지의 핵심은 앞의 두 개다. **데이터 플랫폼은 한번 도입하면 몇 년씩 쓰는 기반 설비이므로 "오래
이어 쓸 수 있는가"가 핵심 질문이 된다.** 기술적 우월성이 아니라 수명이 선택 기준이라는 뜻이다.

⚠️ 저자는 곧바로 반대편도 못 박는다 — **Apache라는 이름은 품질 보증서가 아니다.** 활발한
프로젝트가 있는가 하면 관리가 끊겨 사실상 멈춘 것도 있다. 그래서 이름이 아니라 채택률과 역할로
분류하겠다는 것이 다음 절의 Tier 체계다.

## 2. 티어는 우열이 아니라 읽는 순서다

- 🔹 **Tier 1** — "특별한 이유가 없으면 여기서 고른다"에 해당하는 표준급. Spark·Kafka·Parquet·
  Airflow처럼 **어느 회사에 가도 만날 가능성이 높고** 주변 도구와 연결하기 쉽다.
- 🔸 **Tier 2** — 기술적으로 충분히 성숙했지만 모두에게 기본값은 아닌, **목적이 뚜렷할 때 검토하는**
  전문 기술. 지리 데이터의 Sedona, 그래프 관계의 HugeGraph.

> "좋은 기술이지만 필요 없는 곳에 넣으면 관리할 항목만 늘어납니다."

읽는 방법까지 지정한다 — **Tier 1은 순서대로 훑어 큰 그림을 잡고, Tier 2는 필요한 순간에 사전처럼
펼쳐 본다.** 90개를 처음부터 끝까지 읽는 자료가 아니라고 저자 본인이 말하는 셈이다.

⚠️ **Apache 공식 등급이 아니다.** 저자가 "얼마나 널리 쓰이고 운영 사례가 쌓였는지"를 기준으로 매긴
실무용 분류다. 전체 라벨 분포(Tier 1 22개 / Tier 2 68개)와 편향 주의점은
[[Apache data technology map (book)]] 참조.

이 판단 형식은 [[AI Data Engineering (Fast Campus course)]]가 매 챕터에서 *"안 해도 되는 경우"* 를
먼저 말하던 것과 같고, [[Spatial omics platform roadmap]]이 **"정석은 도입 목록이 아니라 도입
순서다"** 로 뒤집은 것과도 같다. 세 자료가 독립적으로 같은 형태에 도달한다.

## 3. 레퍼런스 아키텍처 — 역할 5단계 + 가로지르는 2계층

> "기술을 하나씩 따로 외우면 금방 잊어버립니다. 대신 '데이터가 어디서 들어와 어디로 나가는가'라는
> 흐름을 먼저 그려 두면, 새로운 이름을 만났을 때 어느 역할인지 짐작하기 쉽습니다."

| | 역할 | 하는 일 | 대표 |
|---|---|---|---|
| 1️⃣ | 소스 | 데이터가 처음 생기는 곳 | 서비스 DB · 앱 로그 · 센서 |
| 2️⃣ | 수집 | 흩어진 데이터를 끌어와 한 방향으로 흘려보낸다 | NiFi · Kafka Connect · Flink CDC |
| 3️⃣ | 처리 | 정제·결합·계산 | Spark · Flink |
| 4️⃣ | 저장 | 파일과 테이블 형태로 보관 | Parquet · Iceberg · Hudi |
| 5️⃣ | 소비 | 질문하고 시각화 | Doris · Pinot · Superset |

여기에 여러 단계를 **가로지르는** 두 가지가 더 있다.

- **오케스트레이션**(Airflow) — 일정과 순서를 관리한다
- **기반 계층**(ZooKeeper, YARN) — 눈에 잘 띄지 않지만 클러스터를 조율한다

⭐ 두 축을 구분하는 문장이 이 장의 핵심이다. **"앞의 다섯 역할이 '무엇을 하는가'라면, 이 둘은
'언제, 어떤 자원으로 하는가'를 담당한다."** 그리고 기반 계층은 **"평소에는 존재를 잊고 지내다가
문제가 생겼을 때 드러나는 부분"** 이다.

또 하나의 설계 주장: **각 단계는 앞 단계의 결과를 받아 다음 단계에 넘기는 역할만 한다. 그래서 한
단계의 도구를 바꿔도 나머지를 처음부터 다시 만들 필요가 없다.**

새 이름을 만났을 때의 판단 절차는 결국 한 문항이다 — **"이건 수집·처리·저장·소비 중 어디에 해당하는
도구인가."**

## 4. 레이크하우스 기본 스택 — Spark · Parquet · Iceberg · Airflow · Superset

3절의 흐름도를 실제 이름으로 채운 첫 번째 조합. **하루에 한 번, 혹은 몇 시간에 한 번** 데이터를 모아
정리하고 보고서를 만드는 일반적인 분석 환경. 저자는 **"처음 데이터 플랫폼을 만든다면 이 조합에서
출발해도 크게 후회할 일이 없다"** 고 쓴다.

| 이름 | 역할 | 배워야 할 개념 |
|---|---|---|
| Spark | 대용량 데이터를 여러 대로 나눠 처리하는 엔진 | 계산 |
| Parquet | 분석에 유리하도록 열 단위로 저장하는 파일 포맷 | 파일 |
| Iceberg | 흩어진 파일 묶음을 하나의 테이블처럼 다루게 해 주는 계층 | 테이블 |
| Airflow | 어떤 작업을 언제, 어떤 순서로 돌릴지 관리 | 일정 |
| Superset | 저장된 데이터를 SQL과 대시보드로 보여 주는 도구 | 화면 |

⭐ **"이름은 다섯 개지만 실제로 배워야 할 개념은 계산·파일·테이블·일정·화면 다섯 가지다."**
그리고 이 조합의 핵심은 **역할이 겹치지 않는 데 있다** — Parquet은 파일을 어떻게 쓸지, Iceberg는
그 파일들을 테이블로 어떻게 묶을지, Spark는 그것을 어떻게 계산할지를 각각 담당한다. 그래서
**"실제로 Spark를 다른 엔진으로 교체하면서 Iceberg 테이블은 그대로 쓰는 경우도 흔하다."**

한계도 명시한다 — **"방금 일어난 일"을 몇 초 안에 보여 주는 데는 적합하지 않다.**

## 5. 실시간 스택 — Kafka · Flink · Pinot/Druid

배달 앱의 주문 상태, 쇼핑몰의 재고 감소처럼 **"밤에 한 번 정리하는" 방식으로는 만들 수 없는** 경험.
역할 구성 순서는 4절과 같고, 각 역할의 도구만 실시간 쪽으로 바뀐다.

1. **Kafka** — 여러 서비스가 만든 이벤트를 순서대로 받아 두는 공용 로그
2. **Flink** — 로그를 계속 읽으면서 집계·필터·결합을 실시간으로 수행
3. **Pinot 또는 Druid** — 방금 처리된 결과를 빠르게 조회할 수 있게 보관
4. **대시보드·서비스 화면** — 사용자가 지금 상태를 바로 확인

**Druid vs Pinot**: Druid는 운영자가 보는 모니터링 대시보드처럼 **넓은 기간을 훑는 분석**에 강하고,
Pinot은 서비스 사용자가 직접 열어 보는 화면처럼 **동시 접속이 많고 응답이 아주 빨라야 하는** 상황에
강하다. ⭐ 기준은 성능 수치가 아니라 **"누가, 얼마나 자주 이 화면을 여는가"** 다.

⭐ 그리고 4절과의 관계를 못 박는다 — **실시간 스택은 레이크하우스를 대체하지 않는다.** 실제 회사는
둘을 함께 쓴다. Kafka에 쌓인 **같은 이벤트**를 Flink가 즉시 처리해 화면에 보여 주고, 동시에
레이크하우스 쪽에도 저장해 나중에 깊이 있는 분석에 쓴다.

> "실시간은 빠르지만 비용과 운영 난도가 함께 올라가므로, 정말 초 단위가 필요한 영역에만 적용하는
> 편이 좋습니다."

## 위키와의 연결

- **5역할은 위치의 축, [[Medallion architecture]]는 정제도의 축이다.** 서로 대체 관계가 아니다 —
  bronze/silver/gold는 4️⃣ 저장 안에서의 층이고, 5역할은 그 테이블이 파이프라인의 어디쯤인지다.
  두 축을 겹쳐 놓으면 "silver 테이블을 만드는 Spark 잡"처럼 좌표가 두 개 찍힌다.
- **4절 + 5절 = [[Lambda and Kappa architecture]]다.** 책은 그 이름을 쓰지 않고 "둘을 함께 쓴다"
  까지만 말한다. 같은 Kafka 이벤트가 실시간 경로와 레이크하우스 경로로 갈라지는 것이 바로 Lambda의
  speed/batch layer이고, 위키가 이미 더 정확한 어휘(재처리를 아키텍처 요구로 승격)를 갖고 있다.
- **"오케스트레이션이 5역할을 가로지른다"** 는 [[Batch and stream processing]]의 *오케스트레이터는
  배치 전용* 이라는 경계와 일치한다. 3절의 표에서 Airflow가 2️⃣~5️⃣ 어디에도 들어가지 않는 이유가
  그것이다.
- **역할 교체 가능성**("Spark를 바꿔도 Iceberg 테이블은 그대로")은 [[Table formats]]가 말하는
  *Hive는 경로에 의미를 실었고 Iceberg는 해방했다* 의 실무적 귀결이다. 엔진 교체 가능성은
  테이블 포맷이 사 준 것이다.
- **[[Analytical data storage tiers]]와 층위가 맞는다** — 이 책의 4️⃣ 저장 + 5️⃣ 소비 분리가 곧
  레이크하우스가 스토리지와 쿼리 엔진의 결합을 푼 결과다.

## 짚어 둘 것 — 기본 스택 5개에 카탈로그가 없다

⚠️ **"레이크하우스 기본 스택"의 다섯 이름에 카탈로그가 빠져 있다.** Iceberg 테이블을 "여러 엔진이
공유하는" 것이 Iceberg의 정의인데, 그 공유는 카탈로그가 테이블의 현재 메타데이터 포인터를
관리해 줘야 성립한다. 책 자신도 Ch10에서 Polaris를 *"Iceberg 중심 레이크 카탈로그"*, Gravitino를
*"통합 메타데이터·카탈로그"* 로 소개한다 — 즉 빠진 게 아니라 **Ch1에서 단순화한 것**이다.

이 위키에서는 이게 사소한 누락이 아니다. [[Object storage layout]]과
[[Spatial omics platform roadmap]]이 도달한 결론이 정확히 *경로 = 권한·생애주기, 나머지는
카탈로그* 였고, 로드맵은 카탈로그 저장소를 Postgres로 정정했다. **"계산·파일·테이블·일정·화면"
다섯 개념에 여섯 번째로 "카탈로그"를 넣어 읽는 게 맞다.**

Ch1의 5역할에서 카탈로그의 자리는 오케스트레이션·기반 계층과 같은 **가로지르는 계층**이다.
