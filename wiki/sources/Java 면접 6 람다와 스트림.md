# Java 면접 6 람다와 스트림

[[인프런 Java 면접 강의]]의 마지막 섹션(Section 6). 주 질문은 "람다와 스트림이 무엇인가" 하나이고, 꼬리 질문 셋이 왜 도입했나 → 함수형 프로그래밍이 무엇인가 → 지연 연산이 무엇인가 순으로 파고든다. 여기서 말하는 스트림은 Java의 Stream API이고, 데이터 엔지니어링의 [[스트림 처리]]와는 다른 것이다.

## 요약

### Q1. 람다와 스트림이 무엇인가요? (p105–107)

- Gold: 람다는 메서드를 하나의 식으로 표현한 익명 함수로, 주로 함수형 인터페이스의 구현체를 간결하게 쓸 때 쓴다. 스트림은 컬렉션의 요소를 하나씩 참조해 람다식으로 처리하게 해 주는 내부 반복자다.
- 등급을 가른 것: Bronze("익명 함수", "컬렉션 처리 기능")는 키워드만 있고 배경과 동작이 없다. (Silver 답은 없다.)

#### Q1-1. Java 8에서 람다와 스트림을 도입한 이유가 가독성 때문만일까요? (p108–110)

- Gold: 주된 이유 셋. ① 멀티코어 CPU가 보편화되어 `parallelStream()`으로 병렬 처리를 쉽게 하려고. ② 부수 효과를 줄이려고. 자료는 "람다와 스트림은 순수 함수 기반으로 동작하므로 외부 상태를 변경하지 않아 멀티스레드 환경에서도 안전"하다고 쓴다. ③ 선언적 코드로 how가 아닌 what에 집중하려고.
- 등급을 가른 것: Silver는 함수형과 선언적 코드까지 말했지만 멀티코어 병렬 처리라는 배경을 빠뜨렸다.
- ⚠️ "순수 함수 기반이라 안전하다"는 틀렸다. Java는 순수성을 강제하지 않는다. "멀티코어가 가장 핵심"이라는 순위도 자료가 매긴 것이다([[람다와 스트림]]).

#### Q1-2. 함수형 프로그래밍이 정확히 무엇인가요? (p111–114)

- Gold: 순수 함수와 불변성을 기반으로 하는 패러다임이다. ① 순수 함수: 같은 입력에 같은 출력을 내고, 외부 상태를 바꾸지 않아 부수 효과가 없다. ② 불변성: 상태를 바꾸지 않고 필요하면 새 데이터를 만든다. ③ 함수를 일급 객체로 다룬다(변수 할당·인자·반환값).
- 등급을 가른 것: Silver는 순수 함수까지만 말하고 불변성과 일급 함수를 빠뜨렸다.
- p114 (코드 슬라이드, 텍스트 없음)에는 위반 예시가 두 개 있다. `greet(name)`이 바깥의 `List<String> log`에 이름을 넣는 것은 "순수 함수 위반 → 외부 상태(log)를 건드림"이고, `addName(list, name)`이 인자로 받은 리스트에 `add`하는 것은 "불변성 위반 → 원본 데이터를 수정함"이다.

#### Q1-3. 스트림의 지연 연산(Lazy Evaluation)이 무엇인가요? (p115–117)

- Gold: 중간 연산(filter·map)은 호출할 때 실행되지 않고, 최종 연산(collect·forEach)이 호출될 때까지 미뤄진다. 효과는 두 가지다. ① `.filter().limit(5)`에서 5개를 찾는 순간 나머지를 건너뛴다. ② 중간 연산들을 하나의 파이프라인으로 합쳐 한 번 순회로 처리한다.
- 등급을 가른 것: Silver는 정의만 있고 성능 최적화 효과가 없다.

## 핵심

- p114의 코드 슬라이드는 Q1-1 Gold와 어긋난다. p110에서는 "람다는 외부 상태를 변경하지 않는다"고 해 놓고, 네 쪽 뒤에서는 람다와 메서드가 외부 상태를 얼마든지 바꿀 수 있음을 보여 준다. 순수성은 언어가 보장하는 성질이 아니고 작성자가 지켜야 하는 규율이다. 이 지적은 위키의 관찰이다([[람다와 스트림]] · [[함수형 프로그래밍]]).
- 지연 연산은 Spark의 transformation/action 구분과 같은 생각이다. 계획만 쌓아 두다가 결과가 필요할 때 한 번에 최적화해 실행한다. 두 개념을 이은 것은 위키다([[람다와 스트림]]).
- 스트림의 정의로는 "내부 반복자"가 가장 정확한 말이다. 반복을 누가 제어하는지(호출자인지 라이브러리인지)에 따라 병렬화와 지연 연산이 가능해진다. 이 판단은 위키의 관찰이다([[람다와 스트림]]).
- Q1-1의 세 이유는 하나로 묶을 수 있다. 내부 반복과 부수 효과 없는 동작 파라미터가 있어야 라이브러리가 병렬화할 수 있다. 자료는 셋을 따로 늘어놓는데, 하나로 묶은 것은 위키의 관찰이다([[람다와 스트림]]).

## 주의·결함

- ⚠️ "순수 함수 기반이라 멀티스레드에서 안전"은 틀렸다(p110). Stream 문서는 부수 효과의 가시성을 보장하지 않는다고 쓴다([[람다와 스트림]]).
- ⚠️ 도입 이유의 순위(p110)에도 근거가 없다. Goetz의 설계 문서는 멀티코어를 주된 동기로 들지만 "1위"라고 하지는 않고, 실무에서 `parallelStream`은 제한적으로만 권한다([[람다와 스트림]]).
- 지연 연산 설명(p117)은 맞다. 다만 `sorted` 같은 stateful 중간 연산은 입력 전체를 소비해야 해서 short-circuit이 제한된다는 단서가 없다([[람다와 스트림]]).
- p114는 텍스트가 없는 이미지 슬라이드라 "Follow-Up Question" 표지 없이 Q1-2와 Q1-3 사이에 끼어 있다. 위키는 이를 Q1-2의 부록으로 읽었다(추론).
- 네 문항 모두 Gold 아래 등급이 하나씩만 있다. Q1은 Bronze, Q1-1·Q1-2·Q1-3은 Silver다.
