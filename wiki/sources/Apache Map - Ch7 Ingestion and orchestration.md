# Apache Map - Ch7 Ingestion and orchestration

『Apache로 읽는 데이터 기술의 지도』(이현수, 2026) **Ch7. 데이터를 모으고 일정을 맞추기** — 개념 10개,
PDF pp.52–62. 트래커: [[Apache data technology map (book)]].

**공백률 7/10이었던 장이고, 그중 하나가 실제로 운영 중인 Airflow였다.** [[ETL and ELT]]·
[[Change data capture]]는 원리를 갖고 있었지만 **구현체가 없었다.**

## ⭐ 세 번째 확인 — 이 책은 장마다 마지막 개념이 논지다

Ch8·Ch9와 똑같다. 개념 1~9는 도구 카탈로그이고 **개념 10이 분류 축**이다.

> "이 장에서 나온 도구 이름을 한꺼번에 외우면 구분이 흐려집니다. **역할을 세 가지로만 나눠 보면
> 훨씬 분명해집니다.**"

| | 역할 | 대표 |
|---|---|---|
| 1️⃣ | **수집** — 다양한 소스 입구와 라우팅 | NiFi |
| 2️⃣ | **CDC** — 운영 데이터의 변화를 이벤트로 | Flink CDC |
| 3️⃣ | **오케스트레이션** — 배치 작업의 순서·스케줄·회복 | Airflow · DolphinScheduler |

SeaTunnel·Hop·Camel은 **그 사이에서 옮기거나 변환하는 실행 도구**다.
**"겉보기엔 비슷한 파이프라인 도구처럼 보여도, 맡는 일은 다릅니다."**

그리고 역할 분담을 문장으로 고정하는 예시까지 준다 —
**"소스 데이터의 진입점은 NiFi 또는 CDC, 대량 동기화는 SeaTunnel, 일정은 Airflow."**
[[Apache Map - Ch9 Serving OLAP search and NoSQL]]의 *"문장으로 적어라"* 와 같은 처방이다.

> **읽는 규칙(3장 연속 확인): 각 장은 마지막 개념부터 읽는다.** 남은 8개 장에도 적용한다.

## 비교 절 1 (개념 6) — 통합 도구의 축은 과제의 모양이다

> "세 이름을 **성능 순위로만 매기면 선택이 어려워집니다.** 우리 과제가 '잡다한 소스 라우팅'인지,
> '테이블 변환 UX'인지, '다양한 커넥터 동기화'인지부터 정하는 것이 가이드의 시작입니다."

- 🔹 **NiFi** — 파일·장비·프로토콜이 섞이고 **운영 추적이 중요**할 때
- 🔸 **Hop** — 전통 ETL 방식으로 **변환을 조립**하고 싶을 때
- ▪️ **SeaTunnel** — 여러 저장소 사이를 **배치·CDC로 맞추는** 일이 주일 때

⚠️ 그리고 두 가지 경계선을 그린다.

1. **"Flink CDC처럼 더 특화된 도구가 이미 있다면 그 축은 중복하지 않는 편이 낫다."**
2. **"Camel은 애플리케이션 통합 쪽으로 두고, 데이터 플랫폼 도구와 섞지 않는 편이 낫다."**
   — Camel 항목에서도 같은 말을 한다: *"'데이터 수집 도구'와 '애플리케이션 통합 프레임워크'를 구분한다.
   같은 '연결'이라도 목적과 담당 범위가 다르다."*

⭐ 두 개를 쓸 때의 처방도 구체적이다 — **"경계를 명확히 하지 않으면 비용만 커진다. '데이터 소스 수집은
NiFi, 대량 동기화는 SeaTunnel'처럼 역할을 문서에 고정해 두면 된다."** 도구를 줄이라는 게 아니라
**경계를 적어 두라**는 것이다.

## ⭐⭐ 비교 절 2 (개념 9) — 이 장 최고의 문장

> "어느 쪽을 고르든, **먼저 정해야 할 것은 도구 이름이 아니라 운영 방식입니다. 누가 파이프라인을
> 만들고 배포하는지, 실패하면 누구에게 알릴지, 권한과 비밀정보는 어디에 둘지**를 확실히 해두면
> 선택이 분명해집니다."

| | 운영 철학 | 맞는 팀 |
|---|---|---|
| 🔹 **Airflow** | Python DAG를 **코드화**해 리뷰·테스트·패키징 | 엔지니어가 **Git으로 관리**, 로컬 테스트·CI가 중요 |
| 🔸 **DolphinScheduler** | **시각적 설계** + 분산 스케줄 운영 콘솔 | 운영자·분석 엔지니어가 **UI에서 조립**, 대량 스케줄 화면 중심 |

⭐ **"'어느 쪽이 더 강력한가'보다 '우리 팀이 파이프라인을 어떻게 변경·배포하는가'가 더 맞는 기준이다."**

생태계·클라우드 관리형 옵션·커뮤니티 자료량은 **대체로 Airflow 쪽이 훨씬 넓다**고 명시한다.
DolphinScheduler는 중국·아시아권 채택이 많다. ⚠️ **"이미 하나의 도구를 표준으로 사용하고 있다면,
특별한 이유 없이 둘을 병행하지 않는 편이 낫다."**

### 이 문장이 이 위키에 특히 값이 있는 이유

Ch8·Ch9의 판단 축은 **기술적 성질**이었다(엔진이 데이터를 소유하는가 / 누가 화면을 여는가).
개념 9는 처음으로 **조직의 성질**을 축으로 든다 — 그리고 그게 오케스트레이터에서는 옳다.
[[Wiki gap analysis - DE readiness]]가 지적한 **"자기 측정치가 없다"** 는 축에 직접 걸린다:
네 문항 중 1번(누가 만들고 배포하는가)은 **자기 팀에 대한 사실**이고, 그것을 모르면 도구 비교가
무의미하다.

⭐ 그리고 2~4번(알림 대상 · 권한 · **비밀정보**)은 **두 도구 모두 답을 주지 않는다.** 그래서 이
질문들을 먼저 하라는 순서가 맞다 — 도구가 해결해 주지 않는 것을 먼저 정하는 것.

## Flink CDC — [[Change data capture]]에 붙는 구현체

- **스냅샷 → 로그 추적** 2단계: 처음에는 전체 스냅샷으로 맞추고, 이후 변경 로그만 따라가 지연을 줄인다.
- 하류: Kafka · Iceberg · Hudi · Paimon · 검색 인덱스.
- **Flink가 이미 팀의 스트림 엔진이라면 학습 곡선이 완만하다** — 도구 선택이 기존 스택의 함수라는 예시.

⚠️ 한계를 명시한다: **"스키마 변경·대량 백필·권한·PII 취급은 별도 설계가 필요하고, 소스 DB 부하도
함께 살펴야 한다."** [[Change data capture]]의 *스키마 변경 — CDC가 조용히 죽는 지점* 과 일치하고,
**PII와 권한**은 위키가 CDC 맥락에서 갖고 있지 않던 축이다.

## 👍 이 장의 강점 · ⚠️ 약점

**강점** — Ch7은 이 책에서 **판단 기준의 질이 가장 높은 장**이다.

- 모든 도구 항목이 *"~가 만능은 아니다"* / *"~을 대체하지 않는다"* 로 끝난다. 10개 중 8개.
- 비교 절 2개가 모두 **성능이 아닌 축**을 제시한다(과제의 모양 · 팀의 운영 방식).
- 처방이 실행 가능하다 — *역할을 문서에 고정* · *태스크 3개짜리 DAG로 시작* · *작은 CSV 정제
  파이프라인 하나*.
- 출처 없는 수치 **0건**. Ch8·Ch9와 같은 프로필이 3장 연속이다.

**약점** — Ch8·Ch9와 동일하다. **내부 동작이 없다.**

- Airflow의 **Executor·Scheduler·메타DB** 구조가 없다. DAG·센서·백필이 이름으로만 나온다.
- Airflow의 실제 운영 난점(스케줄러 지연, `catchup` 폭주, 태스크 격리, 동적 DAG의 파싱 비용)이
  전혀 없다. **"오케스트레이션의 가치"까지만 말하고 "오케스트레이터의 비용"은 말하지 않는다.**
- NiFi의 back-pressure·provenance repository, SeaTunnel의 엔진 추상 같은 것도 이름 수준.

⭐ **이 위키에서 Airflow를 이미 운영 중이라는 점을 감안하면, 이 장은 "무엇을 고를까"에는 답하고
"지금 겪는 문제"에는 답하지 않는다.** 그 축은 1차 문서(Airflow 공식 문서)로 채워야 한다 —
[[Wiki gap analysis - DE readiness]]의 *1차 자료* 축.
