## 요약

### 두 지표와 시소의 법칙 (p4–6)

- **Latency** — 요청부터 응답까지의 총 시간(대기 시간 + 처리 시간). 평균(P50)보다 **느린 1%(P99) 관리가 더
  중요할 수 있다**.
- **Throughput** — 단위 시간당 처리량. 웹은 RPS·QPS, DB는 TPS, 데이터는 MB/s.
- **시소의 법칙** — A. 반응성 집중(자원을 한 요청에 독점 → 잦은 문맥 전환과 준비 비용, 비유: 오마카세) vs
  B. 효율성 집중(모아서 한꺼번에 → 모일 때까지 대기가 필연, 비유: 급식소). 원인은 **오버헤드와 자원 공유의
  물리적 한계**다.

### 배치와 스트리밍 (p7–14)

| | 배치 | 스트리밍 |
|---|---|---|
| 방식 | 기간·크기 기준으로 축적 → 스케줄러가 일괄 실행 | 이벤트 발생 즉시 레코드 단위(또는 아주 작은 윈도우) |
| 데이터 | 유한 | 무한(unbounded) |
| 장점 | 준비 비용을 1/N로 나눠 처리량 극대화: 연결·패킷 헤더 비용 감소, 순차 쓰기, 문맥 전환 없음 | 실시간 UX, 데이터가 가장 신선할 때 분석, 24시간 자동 대응(알림) |
| 단점 | 신선도 하락, 실시간 의사결정 불가, "어제 기준" 대시보드 | 건별 오버헤드, 순서 뒤바뀜·유실, exactly-once를 위한 체크포인트·상태 관리의 복잡성 |
| 아키텍처 | 소스 → 스케줄러(Airflow·Cron) → 레이크(HDFS·S3) → 배치 엔진(Spark·Hive·MapReduce) → 데이터 마트·대시보드 | 이벤트 소스 → 브로커(Kafka·Pulsar·Kinesis) → 스트림 엔진(Flink·Spark Streaming) → 실시간 싱크(Redis·Slack·알림 API) |

### 사례 (p15–17)

- **자율주행** — 시속 100km, 전방 50m 장애물. 배치로는 "이미 사고". 센서(LiDAR·카메라) → 엣지 추론
  (TensorRT) → 제동·조향(CAN Bus).
- **이상 거래 탐지(FDS)** — 서울에서 커피를 산 지 10분 만에 뉴욕에서 $5,000 결제. 결제 요청 → 최근 행동
  피처 조회(Redis 피처 스토어) + LightGBM 스코어링 → 승인 거절·본인 인증. 목표 300ms, 최대 500ms.
- **실시간 추천** — 캠핑 의자를 보는 고객에게 랜턴·테이블 추천. Kafka → Flink(실시간 피처·추론) → Redis.
  클릭 반영 200ms 이내.

### 시소의 물리적 원인 (p18–19)

- **CPU 문맥 전환** — 작업을 바꿀 때마다 레지스터를 저장·복원하는 순수 오버헤드. 연속 처리는 **캐시 지역성**을
  높이고, 잦은 전환은 캐시를 차갑게 만든다.
- **네트워크 헤더** — 모든 패킷에 헤더가 붙으므로 작은 데이터를 자주 보내면 헤더 비중이 커진다.
- **디스크 I/O** — 배치는 순차 쓰기로 seek 비용을 줄이고, 스트리밍은 랜덤 I/O가 된다.

### 절충과 선택 (p20–22)

- **마이크로 배치** — 0.5초~수 초 동안 모아 작은 배치로. Spark Structured Streaming의
  `Trigger.ProcessingTime("1 second")` + `checkpointLocation`. 결과는 1~5초 지연에 배치에 가까운 효율.
- **Lambda 아키텍처** — 배치 레이어(불변 마스터 데이터셋을 주기적으로 전체 재처리 → 정확성) + 스피드 레이어
  (최근 데이터를 증분 처리) + 서빙 레이어(두 뷰를 병합). 단점은 코드베이스가 두 개라는 것 → 대안은 스트림만
  쓰는 Kappa.
- **선택 기준** — 데이터 가치가 사라지는 시간(초 단위면 스트리밍), 정확성 요구(1원 오차도 안 되면 배치),
  비용과 운영 역량(24x7 모니터링과 숙련 인력). **황금률: 실시간이 필수인 구간(경보·추천)에만 스트리밍, 나머지는
  배치를 기본으로. Start Simple, Scale Later.**

## 핵심

- Part 1에서 **가장 설명력이 큰 덱**이다. 지연 시간과 처리량의 맞교환을 문맥 전환·캐시·헤더·seek라는 구체적
  원인으로 풀어 준다. 이후 강의의 설계 선택(프로듀서 배치 전송, 마이크로 배치, Avro로 받고 Parquet로 합치기)이
  전부 이 축 위의 한 점으로 읽힌다. → [[지연 시간과 처리량]]
- 결론이 "스트리밍이 미래"가 아니라 **"배치가 기본, 스트리밍은 필요한 곳만"**이다. → [[배치 처리]] ·
  [[스트림 처리]]

## 주의·결함

- ⚠️ **자율주행 슬라이드 한 장에 허용 지연이 세 개다** — 시나리오 박스 "허용 지연 시간 < 100ms", 파이프라인
  제목 "End-to-End Latency < 50ms required", 하단 지표 "Max Latency 30ms". 헤드라인은 "0.001초가 생사를
  가른다"다.
- ⚠️ **같은 슬라이드의 엣지 추론 칸에 Flink가 들어 있다.** 차량 내 제동·조향 제어 루프는 차량에 탑재된
  실시간 시스템의 몫이고, JVM 기반 분산 스트림 엔진을 두는 자리가 아니다. *(위키의 판단이다.)*
- **정확성 = 배치라는 선택 기준은 단순화다.** 같은 덱 p12·p20이 스트리밍·마이크로 배치의 exactly-once를
  말하고, [[AI DE 강의 1-12 실시간 처리 엔진]]은 늦게 온 데이터를 "Update"로 반영하는 전략의 사용처로
  "정산·리포트 갱신"을 든다.
- 출처 없는 예시 수치: 캐시 적중률 92% vs 58%, CPU 효율 95% vs 60%, 헤더 비중 약 40% vs 1% 미만,
  처리량 +500%·지연 -90%, 실시간 추천 전환율 +15%, "Google & Amazon 연구 결과"(인용 없음). **방향만 읽고
  수치는 인용하지 않는다.**
