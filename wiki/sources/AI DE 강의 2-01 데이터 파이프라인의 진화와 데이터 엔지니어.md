## 요약

### (1) 데이터 파이프라인의 과거와 현재, 데이터 엔지니어의 역할

- **강의의 목적(p5)** — "AI 시대의 비즈니스 요구사항에 맞춰 파이프라인을 설계할 수 있는 엔지니어적 시야". 아키텍처
  이해 → 인프라 설계 → 오픈소스로 구축.
- **과거: 분석을 위한 분리(p6–7)** — 서비스 DB(MySQL·PostgreSQL)에 복잡한 집계 쿼리를 날리면 병목과 장애 위험이
  생긴다 → OLTP에서 OLAP을 떼어낸 데이터 웨어하우스의 등장. 그림(ZTM 블로그)은 OLTP와 OLAP 사이에 ETL·ELT·EtLT를
  둔다.
- **ETL과 ELT, 우선순위의 변화(p8–9)** — 저장·컴퓨팅이 비쌌던 시절엔 DW에 넣기 전에 "작고 예쁘게 깎는" ETL,
  클라우드 DW(BigQuery·Snowflake)와 스토리지 비용 급감 뒤엔 "일단 쌓고 나중에 고민"하는 ELT. Part 1
  [[AI DE 강의 1-07 배치 처리와 ETL·ELT]]의 반복이다 → [[ETL과 ELT]]
- **온프레미스 → 클라우드 네이티브(p10–11)**

| | 온프레미스 | 클라우드 네이티브 |
|---|---|---|
| 주요 스택 | Hadoop(HDFS), Spark, Hive, Sqoop, 초기 Airflow | GCP(BigQuery·Dataflow), AWS(S3·Redshift), Confluent(관리형 Kafka) |
| 엔지니어의 일 | 서버 랙 설치·네트워크 설정, Hadoop 자원 할당 최적화, 장애 시 물리 서버 재부팅 | Serverless·Managed(인프라 관리를 클라우드사에 위임), Auto-scaling, IaC(Terraform) |
| 결론 | "인프라 관리에 70% 이상의 시간 소요", 비즈니스 로직 개발이 더딤 | "서버 관리자가 아니라 데이터 아키텍트" |

- **앞으로: ML/AI 특화 파이프라인(p12)** — 일반 파이프라인은 BI 리포트·대시보드가 목적, ML 파이프라인은 학습과
  추론이 목적. 새 요구사항: Feature Pipeline(피처를 실시간 가공), Data Freshness(최신 데이터 즉시 반영),
  Unstructured Data(텍스트·이미지·벡터).
- p13은 밈 이미지 — 빈 관중석에 혼자 앉은 "Data Engineer" vs 꽉 찬 관중석 "AI Engineers".
- **MLOps와 LLMOps 인프라 관리 — DE의 확장 영역(p14)** — Feature Store(학습-서빙 스큐 해결), Vector Database
  (RAG용 벡터 파이프라인), Monitoring(드리프트 감지 → 파이프라인 재실행 트리거), LLMOps(LLM이 최신 정보를 참조하도록
  데이터 지속 공급).
- **최근의 JD(p15, 이미지)** — 선호: Spring Boot 등 Kotlin/Java 백엔드, Kubernetes 운영, MLOps 환경 구축·AI 서비스
  파이프라인 설계. 우대: Kafka·Flink 등 실시간 스택, MongoDB·Redis·ElasticSearch, 대규모 트래픽 백엔드, k8s 기반 추천
  시스템 플랫폼·인프라, MLOps 플랫폼(MLflow·Kubeflow).

### (2) AI 시대를 위한 파이프라인과 데이터 엔지니어의 진화 방향

- **BI 파이프라인 vs AI/ML 파이프라인(p18)**

| 구분 | BI | AI/ML |
|---|---|---|
| 최종 목적 | 리포트, 대시보드, 의사결정 지원 | 예측 모델, 추천 시스템, 생성형 AI 서비스 |
| 주요 데이터 | 구조화된 수치, 로그(테이블) | 비정형(텍스트·이미지·벡터) |
| 데이터 신선도 | T+1일(일 배치)이면 충분 | 실시간 혹은 근실시간 |
| 성공 기준 | 수치의 정확성, 시각화의 명확성 | 모델 성능(Accuracy), 추론 속도 |
| 주요 사용자 | 경영진, 기획자, 데이터 분석가 | 데이터 사이언티스트, ML 엔지니어, AI 모델 |

- **시대별 파이프라인 그림(p19–21, 이미지)**

| 시기(슬라이드 표기) | 그림 | 요점 |
|---|---|---|
| 2015~2018 "ML 이전" | 소스 → Extract → Staging(Transform) → Load → DW → Analyze (firsteigen.com) | 전형적인 ETL → DW → BI |
| 2018~2022 "ML 이후" | Data Pipeline Patterns (dataengineering.wiki) — 온프레미스·엣지·SaaS·클라우드 생산자 → 복제·스트리밍·API 수집 → ODS/메시지 허브 → 레이크·DW·MDM → ML·파트너·BI 소비자 | ML이 **소비자 중 하나**로 등장 |
| 2022~ "AI, LLM" | LLMOps 그림 (sreent.medium.com) — 사내·공개 데이터 → 처리 파이프라인 → 임베딩(벡터 스토어), 사전학습 LLM → 파인튜닝·few-shot → LLM API → 앱, RLHF 루프, 모델 버전 관리·캐싱·모니터링 | 파이프라인의 끝이 모델 API와 사용자 피드백 루프 |

- **Feature Store(p22–23)** — 모델에 입력되는 가공된 데이터(Feature)를 저장·관리하는 중앙 저장소. 필요성: 여러 팀이
  같은 로직의 피처를 재사용(중복 개발 방지), 학습(Offline)과 추론(Online)에 동일한 데이터 공급. 핵심 이점: 모델 배포
  속도 단축, 데이터 정합성 유지. 그림(Featureform)은 배치·실시간 소스, 피처 저장소, 거버넌스·모니터링, 오프라인
  스토어(학습셋)·온라인 스토어를 한 판에 놓는다. → [[피처 스토어]]
- **Vector DB와 LLM(p24–26)** — 텍스트를 벡터로 바꿔 저장·검색. RAG: 대규모 비정형 데이터를 임베딩해 Vector DB에 적재 →
  질문을 임베딩해 유사 벡터 검색 → 결과를 LLM에 전달해 응답 생성. 그림(Basic RAG Pipeline)은 인덱싱(문서 → 청크 분할 →
  임베딩 → Vector DB)과 검색·생성(질의 임베딩 → Top-K 청크 → LLM → 응답) 두 구역으로 나눈다. 엔지니어의 일: 임베딩
  파이프라인 설계, Vector DB 저장 구조·검색 성능 설계, LLM이 참조할 데이터 흐름의 안정 운영. → [[비정형 데이터 파이프라인]]
- **GPU(p27–28)** — 임베딩 생성·학습·추론 모두 계산 집약적이고 CPU에는 구조적 한계가 있다. 그러나 GPU는 비싸서 항상
  켜두기 어렵다 → **언제, 어디서, 왜 GPU를 쓸지 설계**, 학습과 추론의 분리 구조. "데이터 엔지니어는 계산이 발생하는
  흐름까지 설계 대상이 된다." → [[AI DE 강의 2-09 서빙의 CPU·GPU 가속]]
- **AI 활용 자동화(p29–30)** — DE 일에는 반복·소모 작업(코드 작성·리뷰, 로그 확인, 에러 원인 분석)이 많다. 로그 자동
  분석·장애 원인 요약, 에러 패턴 추출, 인프라 이상 징후, 운영 티켓 분류·요약. "AI는 생각을 대신하는 도구가 아니라
  노동을 줄이는 도구."

## 핵심

- **Part 1과 같은 틀, 다른 무게중심.** Part 1 [[AI DE 강의 1-01 기존 DE와 AI DE]]가 "데이터의 소비자가 사람에서 모델로"를
  저장·수집·처리 쪽에서 풀었다면, 이 강의는 같은 틀을 **학습·추론(서빙) 쪽**으로 옮긴다. BI vs AI/ML 표의 "주요 사용자:
  AI 모델"이 그 연결점이다. → [[AI 데이터 엔지니어링]]
- **JD 슬라이드의 스택은 Part 1과 결이 다르다.** [[AI DE 강의 1-03 기술 스택과 툴 생태계]]의 JD가 클라우드·SQL·JVM 엔진·
  Kafka·Airflow였다면, 여기 JD는 **Kotlin/Java 백엔드·Kubernetes·MLOps 플랫폼**이 앞에 온다. 서빙이 백엔드 시스템이라는
  Part 2의 전제가 채용 요건에 먼저 드러난다. 다만 두 슬라이드 모두 표본(회사·건수)이 없다. *(위키의 관찰)*
- **DE의 확장 영역 세 가지가 곧 Part 1 운영 파트의 해결책 목록이다** — 피처 스토어는 [[학습-서빙 스큐]], 모니터링은
  [[데이터 드리프트]], Vector DB는 [[비정형 데이터 파이프라인]]. Part 2는 이 부품들을 "서빙 경로" 위에 다시 놓는다.
  → [[MLOps]]
- **GPU를 "자원 설계" 문제로 소개한다** — 비싸고 항상 켜둘 수 없으니 흐름 설계의 대상이라는 관점은
  [[AI DE 강의 2-09 서빙의 CPU·GPU 가속]]의 "GPU는 마지막 단계"로 이어진다.

## 주의·결함

- ⚠️ **"인프라 관리에 70% 이상의 시간 소요"(p10)** — 출처 없음. 영어·한국어로 원출처를 찾았으나 없었다. 가까운 것은
  벤더 통계 블로그의 "데이터 **예산**의 60~70%"나 Twitter 엔지니어링 블로그의 "Hadoop 운영에 SRE 시간 대부분"(수치 없음)
  같은 다른 주장뿐이다(2026-09-14 확인). 방향(온프레미스는 운영 부담이 컸다)만 받아들이고 수치는 인용하지 않는다.
- **시대 구분(2015~2018 / 2018~2022 / 2022~)은 슬라이드의 자체 구분이다** — 그림은 각기 다른 블로그에서 가져왔고,
  그 그림들이 해당 시기를 대표한다는 근거는 없다. 2015~2018을 "ML 이전"이라 부르는 것도 업계 전반에 대한 서술로는
  거칠다. *(위키의 관찰)*
- **Feature Store 정의 슬라이드(p22)가 Ch5 p9에 문구 그대로 반복된다** → [[AI DE 강의 2-10 Feature Store 기본 개념]]
