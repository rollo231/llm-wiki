## 요약

### (1) 수비에서 공격으로

- **자물쇠 → 나침반** — 과거의 수비형 거버넌스는 법적 리스크와 보안을 위해 데이터를 금고에 가뒀다(보안·접근 통제·
  규제 준수). 지금의 공격형 거버넌스는 AI와 분석가가 데이터를 즉시 찾아 쓰도록 돕는다(쉬운 발견·빠른 활용·신뢰성).
- **경고: 데이터 늪** — 거버넌스 없는 레이크는 아무도 찾지 못하고 무엇인지 몰라 결국 버려지는 데이터의 무덤이 된다.
- **"데이터 과학자 시간의 80% 낭비"의 원인** — 위치·소유자 불명("작년 매출 데이터 어디 있지?" — 메신저로 며칠
  수소문), 모호한 정의("이 '가격'은 세금 포함인가요?"), 신뢰할 수 없는 품질("오늘 아침 최신본 맞나요?" — 계보가
  없다). 결과: 데이터 사이언티스트가 **"데이터 고고학자"**가 된다.
- **현대 거버넌스 3대 요소**

| 요소 | 한 줄 | 수단 |
|---|---|---|
| 표준화 | 전사가 같은 언어를 쓴다 | 전사 데이터 사전, 명명 규칙, 지표 정의 일원화 |
| 권한 관리 | 안전하면서도 빠르게 연다 | 역할 기반 접근 제어(RBAC), 민감 정보 마스킹, 셀프서비스 승인 |
| 가시성 | 어디에 무엇이 있는지 밝힌다 | 데이터 카탈로그(검색), 계보 시각화, 품질 점수 |

### (2) 카탈로그·메타데이터·계보

- **카탈로그** — "사내 구글 검색이자 도서관 색인 카드." 예: "20대 VIP 구매 내역"을 검색하면 위치(AWS Redshift)·
  형식(Parquet)·업데이트(10분 전)가 바로 나온다.
- **3대 메타데이터** — 셋이 모여야 "완벽한 데이터 지도"가 된다.

| 종류 | 한 줄 | 내용 |
|---|---|---|
| 기술적 | 데이터의 물리적 뼈대 | DB·테이블 이름(물리적 주소), 스키마(컬럼 구조·타입), 파티션 정보 |
| 비즈니스 | 데이터의 의미와 책임 | 용어 사전(컬럼의 비즈니스 의미), 소유자(책임 부서·담당자), 규제·보안(PII 여부, 접근 권한 등급) |
| 운영 | 데이터의 건강 상태 | 최신성(마지막 업데이트), 품질 점수(Null 비율·정합성 체크), 사용량(조회 빈도·인기 테이블) |

- **데이터 계보(Lineage)** — 원본 로그 테이블 A → 일 배치 → 중간 집계 테이블 B(스키마 변경!) → 추천 모델 C 장애.
  쓰임새 세 가지: **빠른 원인 규명**(모델이 이상하면 족보를 역추적해 "어제 원본 스키마가 바뀜"을 찾는다), **사전 영향도
  분석**("이 테이블을 고치면 누가 다칠까?" — 하류 범위 파악), **신뢰성·투명성**(AI가 어떤 데이터를 학습했는지 증명).
- **액션** — 핵심 데이터 자산으로 파일럿, 사내 메타데이터 표준 가이드, 핵심 테이블 SLA 정의.

### (3) 자동화와 엔지니어의 역할

- **수동 카탈로그는 왜 실패하나** — 위키·엑셀로는 매일 수백 개씩 생기고 바뀌는 테이블을 따라갈 수 없다. 담당자가
  퇴사하거나 바쁘면 즉시 실제와 어긋난다. 잘못된 설명을 믿고 낭패를 본 사용자는 다시 오지 않는다("예쁜 쓰레기").
- **자동화 처방** — 실시간 동기화(DB 스키마 크롤링, 쿼리 로그 분석으로 변경 자동 감지), 자동 계보(SQL 파싱).
  운영 목표: 메타데이터 최신성 24시간 이내, 변경 감지 알림 100% 커버리지.
- **AI가 AI를 돕는다**
  - **LLM 자동 태깅** — 컬럼명·데이터 패턴·샘플 값을 보고 비즈니스 의미와 보안 등급을 판단한다. 예:
    `customer_info_v2`에서 `user_id` → Primary Key, `phone_encrypted`(`010-****-1234`) → **PII**, `last_login_ts` →
    Timestamp.
  - **자연어 검색(Text-to-SQL)** — "최근 3개월 동안 탈퇴한 고객들의 결제 이력 어디 있어?" → 관련 테이블 두 개
    (`user_churn_log_90d`, `payment_history`)와 조인 SQL을 만들어 준다.
  - 운영 포인트: AI의 추천을 담당자가 최종 검수(Human-in-the-loop).
- **데이터 엔지니어의 역할 = 도구 × 문화**

| 영역 | 내용 |
|---|---|
| 도구·인프라 | DataHub·Amundsen·Atlan 도입, 레이크·DW 연동, 메타데이터 수집 파이프라인 자동화 |
| 배포 규칙(CI/CD) | 신규 테이블 설명 3줄 이상 필수, 오너·도메인 정보 명시 강제, **보안 등급·분류 태그 누락 시 배포 차단** |
| 운영 SLA | 스키마 변경 즉시 알림, 품질 경보(Null 급증·적재 지연), 자동 계보 추출 성공률 모니터링 |
| 문화 | 도메인별 데이터 스튜어드 지정, 주간 태그 리뷰·온보딩 교육, 전사 인식 개선 |

  궁극 목표는 **데이터 민주화** — 마케터·기획자·분석가 누구나 스스로 안전하게 데이터를 찾아 쓰는 상태.

## 핵심

- **카탈로그가 실패하는 원인은 도구가 아니라 최신성이다.** 사람이 채우는 카탈로그는 반드시 실제와 어긋나고, 한 번
  속은 사용자는 돌아오지 않는다. 그래서 처방이 짝을 이룬다: **자동 수집**(크롤링·SQL 파싱)으로 기술 메타데이터를 채우고,
  **배포 게이트**(설명·오너·태그가 없으면 차단)로 사람만 줄 수 있는 비즈니스 메타데이터를 강제한다.
  → [[데이터 거버넌스와 카탈로그]]
- 3대 메타데이터 중 **운영 메타데이터(최신성·품질 점수·사용량)는 [[데이터 SLA]]·[[데이터 관측성]]이 만든 결과**다.
  카탈로그는 SLA의 결과를 사용자에게 보여 주는 창이다. *(위키의 연결)*
- 계보의 세 쓰임새(장애 역추적·영향도 분석·학습 데이터 증명)는 각각 [[데이터 관측성]]·[[스키마 진화]]·
  [[데이터와 모델 버전 관리]]와 이어진다.

## 주의·결함

- ⚠️ **"데이터 과학자 시간의 80% 낭비", "탐색 시간 80% 절감"** — 출처가 없다. 흔히 인용되는 출처인 CrowdFlower
  「2016 Data Science Report」의 설문 결과는 "데이터 정리·정돈 60%, 데이터셋 수집 19%"이고(설문 문항은 가장 많은
  시간을 쓰는 일), 보고서 안의 "최대 80%"는 New York Times 추정을 재인용한 것이다. 게다가 그 항목은 강의가 말하는
  "탐색·이해에 낭비"가 아니라 데이터 **준비**다. [CrowdFlower 2016 Data Science Report
  https://www2.cs.uh.edu/~ceick/UDM/CFDS16.pdf , 2026-09-14 확인]
- **LLM 자동 태깅의 오류 비용이 다뤄지지 않는다** — PII를 놓치는 경우(미탐)는 보안 사고인데, 대응이 "담당자 검수"
  한 줄뿐이다.
- 예시 수치: "1초 만에 탐색", "1분 만에 원인 규명", 메타데이터 최신성 24시간.
