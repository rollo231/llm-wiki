# DB 면접 2 트랜잭션

[[인프런 DB 면접 강의]]의 Section 2이고, 이 PDF의 첫 섹션이다. 트랜잭션과 ACID를 정의한 뒤 트랜잭션을 짧게 유지해야 하는 이유를 묻고, 격리 수준 네 가지, 이상 현상 세 가지, 그 해결(언두 영역·넥스트 키 락), MVCC, "InnoDB는 왜 REPEATABLE READ로도 Phantom Read를 막나"로 내려간다. 주 질문 2개, 꼬리 질문 5개. 다음 섹션은 [[DB 면접 3 Lock과 동시성 제어]]다.

## 요약

### Q1. 트랜잭션이 무엇이고, ACID에 대해 설명해주세요 (p2–4)

- Gold: 트랜잭션은 논리적인 작업 단위이자 장애 시 복구의 단위다. ACID는 트랜잭션이 보장할 네 특성이다. 원자성은 전부 실행되거나 하나도 실행되지 않는 것, 일관성은 전후로 제약 조건에 맞게 데이터가 바뀌는 것, 격리성은 다른 트랜잭션이 끼어들지 못하게 하는 것, 지속성은 커밋되면 장애에도 보존되는 것이다. 격리성을 엄격하게 지키면 동시성이 떨어지므로 실무에서는 격리 수준을 조절해 맞바꾼다.
- 등급을 가른 것: Bronze는 네 이름만 나열했고, Silver는 뜻은 설명했지만 격리성과 동시성의 맞교환을 빠뜨렸다.

### Q1-1. 트랜잭션 사용 시 주의할 점은? (p5–7)

- Gold: 꼭 필요한 최소 범위에만 건다. 첫째, 트랜잭션 동안 커넥션을 점유하므로 길어지면 커넥션 풀이 고갈되어 다른 요청이 전부 기다린다. 트랜잭션 안에서 외부 API를 부르면 응답 시간만큼 커넥션이 잠기므로 밖으로 빼야 한다. 둘째, Lock 유지 시간도 길어져 동시성이 떨어진다.
- 등급을 가른 것: Silver는 "짧게"라는 결론만 있고 왜 기다리는지(커넥션 점유)가 없었다.

### Q2. 트랜잭션 격리 수준의 종류는? (p8–10)

- Gold: READ UNCOMMITTED는 커밋되지 않은 데이터도 읽는다. READ COMMITTED는 커밋된 데이터만 읽는다. REPEATABLE READ는 자기 트랜잭션이 생성되기 이전의 트랜잭션에서 커밋된 데이터만 읽는다. SERIALIZABLE은 모든 읽기와 쓰기에 Lock을 걸어 순차적으로 실행하고, 모든 이상 현상을 막지만 동시성이 가장 낮다.
- 등급을 가른 것: Silver는 네 이름과 높낮이만 말하고, 각 수준에서 무엇을 읽을 수 있는지 설명하지 않았다.

### Q2-1. 격리 수준에 따라 나타나는 문제(Dirty Read, Non-Repeatable Read, Phantom Read) (p11–13)

- Gold: Dirty Read는 완료되지 않은 다른 트랜잭션의 작업이 보이는 현상으로 READ UNCOMMITTED에서 생긴다. Non-Repeatable Read는 한 트랜잭션 안에서 같은 SELECT 결과가 달라지는 현상으로 READ COMMITTED에서 생긴다. Phantom Read는 `SELECT ... FOR UPDATE` 같은 잠금 읽기에서 다른 트랜잭션이 INSERT한 레코드가 보였다 안 보였다 하는 현상으로, InnoDB가 아닌 REPEATABLE READ에서 생긴다.
- 등급을 가른 것: Silver는 정의는 맞았지만 어느 격리 수준에서 생기는지 짝을 짓지 않았다.

### Q2-2. 그 문제를 어떻게 해결하나요? (p14–16)

- Gold: Dirty Read는 언두 영역으로 해결한다. 변경 중인 데이터를 직접 읽지 않고 언두 영역에 보관된 커밋 전 원본을 읽는다. Non-Repeatable Read도 언두 영역을 쓰되, 내 트랜잭션보다 나중에 시작된 트랜잭션이 커밋한 변경은 무시하고 내 시작 시점의 데이터만 보여 준다. Phantom Read는 일반 SELECT에서는 MVCC 스냅숏을 읽어 생기지 않지만, FOR UPDATE는 잠금을 걸려고 현재 레코드를 읽으므로 새 로우가 보인다. SERIALIZABLE이나 InnoDB의 넥스트 키 락으로 해결한다.
- 등급을 가른 것: Silver는 방향(커밋된 것만 읽기, 스냅숏, SERIALIZABLE)은 맞았지만 언두 영역·넥스트 키 락이라는 메커니즘 이름이 없었다.

### Q2-3. MVCC란? 왜 사용하나요? (p17–19)

- Gold: 한 레코드에 여러 버전을 동시에 관리하는 것이다. InnoDB는 UPDATE·DELETE 전의 데이터를 보관하는 언두 영역으로 구현한다. Lock 없이 읽을 수 있어 동시성이 크게 오른다. 트랜잭션이 시작되면 그 시점의 스냅숏으로 읽으므로 다른 트랜잭션이 나중에 바꿔도 시작 시점의 버전만 보고, 그래서 Non-Repeatable Read가 자연스럽게 해결된다.
- 등급을 가른 것: Bronze는 약자만 풀었고, Silver는 정의와 목적은 맞았지만 언두 영역과 "Lock 없이 읽기"라는 원리가 없었다.

### Q2-4. 왜 InnoDB는 REPEATABLE READ만으로도 Phantom Read를 해결할 수 있나요? (p20–22)

- Gold: InnoDB는 레코드 락과 갭 락을 합친 넥스트 키 락을 쓴다. 예를 들어 `SELECT FOR UPDATE WHERE id = 5`를 실행하면 id 5 레코드뿐 아니라 5의 전후 갭에도 락이 걸려, 다른 트랜잭션이 그 범위에 데이터를 넣거나 고칠 수 없다.
- 등급을 가른 것: Bronze는 "갭 락"이라는 말만 알았고, Silver는 "주변 범위에도 락"이라는 방향은 맞았지만 "넥스트 키 락 = 레코드 락 + 갭 락"이라는 구조와 예시가 없었다.

## 핵심

- 트랜잭션과 ACID 자체는 [[관계형 데이터베이스]]에 정리되어 있다. 이 섹션의 몫은 격리 수준과 그 구현이다([[트랜잭션 격리 수준]] · [[MVCC]]).
- Q1-1의 "트랜잭션 안에서 외부 API를 부르지 않는다"는 [[커넥션 풀]] 고갈과 이어진다. 커넥션 풀 크기 문제는 [[DB 면접 6 커넥션과 커넥션 풀]]에서 다시 나온다.
- Gold 답의 구현 설명은 전부 MySQL InnoDB 것이다(언두 영역, 넥스트 키 락). 자료는 Q2-4에서만 InnoDB라고 밝힌다. PostgreSQL은 같은 격리 수준을 다르게 구현한다([[PostgreSQL]]).

## 주의·결함

- ⚠️ REPEATABLE READ가 "트랜잭션이 생성되기 이전"의 커밋을 읽는다는 서술(p10·p19)은 InnoDB와 다르다. 스냅숏은 첫 일관된 읽기 시점에 잡힌다([[MVCC]]).
- ⚠️ "나중에 시작된 트랜잭션의 커밋만 무시한다"(p16)는 틀렸다. 스냅숏 시점에 아직 커밋하지 않은 트랜잭션은 나보다 먼저 시작했어도 보이지 않는다([[MVCC]]).
- ⚠️ SERIALIZABLE을 "모든 읽기·쓰기에 Lock을 걸어 순차 실행"(p10)으로 설명한다. InnoDB 방식이고, 실제로 순차 실행하지도 않는다. PostgreSQL은 SSI로 구현한다([[트랜잭션 격리 수준]]).
- ⚠️ 이상 현상을 격리 수준 하나씩에 짝짓는다(p13). 각 현상은 그 수준 이하에서 모두 생기고, Phantom Read의 정의도 잠금 읽기에 한정되지 않는다([[트랜잭션 격리 수준]]).
- ❌ `FOR UPDATE WHERE id = 5`가 앞뒤 갭을 잠근다(p22)는 틀렸다. unique 인덱스로 한 행을 찾으면 레코드 락만 걸린다. 넥스트 키 락도 앞 갭 하나만 포함한다([[데이터베이스 락]]).
- ⚠️ "넥스트 키 락으로 Phantom Read를 해결한다"(p16·p22)는 절반이다. 잠금 읽기끼리는 막지만, 같은 트랜잭션에서 일반 SELECT와 잠금 읽기를 섞으면 결과가 어긋난다([[트랜잭션 격리 수준]]).
