# Java 면접 4 동시성 이슈

(volatile·synchronized·atomic)와 synchronized의 비용·구현을 묻는다. 끝으로 스레드 풀과 "Spring MVC는 왜 스레드를 수백 개
쓰나"로 넘어간다. 주 질문 3개, 꼬리 질문 5개. 앞 섹션은 [[Java 면접 3 GC]], 다음 섹션은 [[Java 면접 5 객체지향 프로그래밍]]이다.

## 요약

### Q1. 자바의 동시성 이슈를 설명해주세요 (p52–54)

- **Gold** — CPU 캐시와 멀티 스레드 때문에 공유 자원에서 두 문제가 생긴다. **가시성**: 스레드마다 다른 CPU 캐시를 보면서
  캐시와 RAM이 불일치해, 한 스레드가 바꾼 값을 다른 스레드가 못 본다. **원자성**: 동시 쓰기 중에 다른 스레드가 끼어들어 결과가
  틀어진다(5개 스레드가 +1 했는데 3).
- **등급을 가른 것** — Bronze는 "문제가 생긴다"는 현상만, Silver는 두 유형을 이름만 대고 원리를 설명하지 않았다.

### Q1-1. 가시성 문제가 정확히 언제 발생하나요? (p55–57)

- **Gold** — 스레드들이 **서로 다른 코어의 캐시**를 참조할 때. 코어 1의 스레드 A가 값을 바꾸면 코어 1 캐시만 갱신되고, 코어 2의
  스레드 B는 캐시 간 동기화 전까지 옛 값을 읽는다.
- **등급을 가른 것** — Bronze는 "서로 다른 코어 캐시"라는 조건을 빠뜨리고 무엇을 동기화하는지 모호했다.

### Q1-2. 원자성 문제 예제 시나리오 (p58–60)

- **Gold** — 공유 카운터의 `count++`는 한 줄이지만 **읽기 → 더하기 → 쓰기** 3단계다. A와 B가 둘 다 0을 읽고 1을 쓰면 두 번
  더했는데 결과는 1.
- **등급을 가른 것** — Silver는 결과만 말하고 읽기-수정-쓰기 3단계를 빠뜨렸다.

### Q2. 동시성 이슈를 해결하는 방법 (p61–63)

- **Gold** — 세 가지. ① `volatile`은 가시성을 해결한다 — "CPU 캐시를 우회해 RAM에 직접 접근"하므로 모두 최신 값을 본다.
  ② `synchronized`는 lock으로 임계 영역에 한 스레드만 들여 읽기-수정-쓰기 전체를 원자적으로 만든다(메서드·블록 단위).
  ③ atomic 타입은 CAS로 non-blocking 원자성을 준다 — lock이 없어 더 빠르지만 단순 연산에만 쓴다.
- **등급을 가른 것** — Bronze는 synchronized 하나만, Silver는 문제-도구 짝은 맞췄지만 동작 원리가 없었다.

### Q2-1. synchronized의 문제점 (p64–66)

- **Gold** — blocking이다. lock을 못 얻은 스레드는 blocked가 되어 아무것도 못 하고, runnable → blocked → runnable 전환의
  컨텍스트 스위칭 비용이 든다. 임계 영역이 길거나 경합이 심하면 성능 저하가 커진다.
- **등급을 가른 것** — Silver는 "기다려서 느리다"에서 멈추고 블로킹·상태 전환 비용을 설명하지 않았다.

### Q2-2. synchronized는 어떻게 구현되어 있나요? (p67–69)

- **Gold** — 모든 객체가 암묵적으로 가진 **모니터**를 잠근다. 모니터는 상호 배제와 조건 동기화(wait/notify)를 주는 고수준
  동기화 메커니즘이고, 한 번에 한 스레드만 소유한다.
- **등급을 가른 것** — Silver는 "lock을 쓴다"만 말하고 모니터를 빠뜨렸다.

### Q3. 스레드 풀이 무엇이고, 왜 사용하나요? (p70–72)

- **Gold** — 스레드 수를 제한해 두고 **작업 큐**의 작업을 하나씩 맡아 처리하는 기법. 이유 둘: ① 스레드 생성·삭제(OS 시스템 콜)
  비용 절약 ② 요청이 폭증해도 큐에서 대기하므로 스레드 수가 폭증하지 않아 자원 사용이 안정적이다.
- **등급을 가른 것** — Bronze는 "미리 만들어 둔다"만, Silver는 재사용 이점은 말했지만 작업 큐를 빠뜨렸다.

### Q3-1. Spring MVC는 왜 컨텍스트 스위칭 비용을 감수하고 스레드를 수백 개 쓰나요? (p73–75)

- **Gold** — 웹 애플리케이션은 네트워크·DB·파일 같은 **Blocking I/O**가 잦고, 그동안 스레드는 CPU를 쓰지 못한다. 스레드가 적으면
  I/O 대기 중 코어가 논다. 그래서 스레드를 늘려 CPU 가동률을 높인다 — 컨텍스트 스위칭 비용보다 이득이 크다("비싼 CPU가 놀지
  않게").
- **등급을 가른 것** — Bronze는 "많은 요청 처리"라는 현상만, Silver는 Blocking I/O와 CPU 유휴가 생기는 메커니즘을 빠뜨렸다.

## 핵심

- **두 문제의 구분(가시성 vs 원자성)과 count++ 3단계는 면접 뼈대로 그대로 쓸 만하다.** → [[동시성 문제]]
- **해결 수단은 "문제 ↔ 도구" 짝으로 기억하되, volatile의 설명은 바꿔야 한다.** → [[동기화 기법]]
- **스레드 풀과 Spring MVC 질문은 결국 CPU 가동률과 전환 비용의 맞교환이다.** *(위키의 연결)* → [[스레드 풀]] ·
  [[지연 시간과 처리량]]

## 주의·결함

- ⚠️ **가시성의 원인을 "코어 캐시와 RAM의 불일치"로, volatile을 "캐시를 우회해 RAM에 직접 접근"으로 설명한다(p54·p57·p63).**
  하드웨어 캐시는 코히런시 프로토콜로 일관성이 유지되고, 실제 원인은 컴파일러·JIT 최적화와 store buffer이며 기준은 JMM의
  happens-before다. 면접에서 그대로 말하면 역질문에 무너진다. → [[동시성 문제]]
- ⚠️ **"atomic은 lock이 없어 synchronized보다 성능이 좋다"(p63)** — 경합이 낮을 때만 대체로 맞다. → [[동기화 기법]]
- ⚠️ **"synchronized는 blocking"(p66)** — HotSpot은 경합이 없으면 lightweight lock(CAS)으로 처리하고, 경합이 생긴 뒤에야 모니터로
  부풀려 스레드를 BLOCKED로 보낸다. → [[동기화 기법]]
- **스레드 풀·Spring MVC 답에 가상 스레드(JDK 21)가 없다** — 2026년 기준 "스레드를 수백 개 쓰는 이유"의 다음 질문은 거의 확실히
  가상 스레드다. → [[스레드 풀]]
- Q1-1은 Bronze만, Q2-1·Q2-2는 Silver만 있다 — 등급 예시가 질문마다 고르지 않다.
- Q2의 "메서드나 블록 단위로 사용할 수 있다"는 맞지만, 메서드 단위일 때 무엇을 잠그는지(인스턴스 메서드는 `this`, static
  메서드는 Class 객체)는 설명하지 않는다.
