## 요점

### 배치가 왜 대체 불가인가

정의: 발생 즉시 처리하지 않고 일정 기간 모았다가 한꺼번에 처리.

> 강의 주장: **전 세계 데이터 워크로드의 80% 이상이 배치.** (출처 미제시 — 아래 '검증 필요' 참조)

"최신 기술인 실시간 처리가 더 좋은 것 아닌가요?" → **아니다. 효율성과 안정성 측면에서 배치는
대체 불가다.**

- **효율성 — 빨래 비유.** 양말 한 짝을 빨기 위해 세탁기를 돌리는 것은 극도의 낭비다.
  **준비 비용(setup cost)이 실제 작업 가치보다 크기 때문.** DB 연결·네트워크 비용도 '세탁 준비'와
  같다. → 규모의 경제
- **안정성 — 재작업 범위가 명확하다.** 실시간은 에러 시 복구가 어렵지만, 배치는 **문제된 구간만
  다시 실행**하면 된다 (3/1 실패 → 3/1만 re-run).
- **Hot Path / Cold Path 분리.** 점심시간(12:00)에 카드 결제가 폭증하는데 분석 쿼리를 돌리면
  시스템 마비 위험. 무거운 분석은 새벽 02:00으로 미루고 06:00에 리포트 완료.
  **바쁜 낮에는 고객 응대에만 집중한다는 전략이 엔터프라이즈 시스템의 핵심 원리다.**

### ETL 3단계와 각 단계의 실제 난이도

**Extract — "그냥 DB에서 긁어오면 되는 거 아냐?"**

> **가장 중요한 원칙: "소스 시스템에 절대 부하를 주지 말라!"**
> 운영 중인 서비스의 심장을 건드리지 않고 혈액을 채취하는 정교한 수술.

- 대상별로 다른 커넥터가 필요하다: RDBMS(Oracle·MySQL) / NoSQL(MongoDB·Redis) /
  Files(CSV·Excel·Logs) / SaaS API(Salesforce·GA4)
- **운영 영향 최소화** — 대량 조회로 쇼핑몰 DB가 느려져 고객이 결제를 못 하면 치명적. 스로틀링이나
  새벽 시간 추출을 활용.
- **CDC** — 트랜잭션 로그를 읽어 변경분만 실시간 포착하는 고급 기술로 부하를 줄인다
  → [[AI DE Course - Ch3-3,4 CDC]]

**Transform — ETL의 꽃이자 가장 고통스러운 단계.** CPU·메모리를 가장 많이 소모한다.

- **Cleaning** — `M / Male / 남성` → `M` 로 표준화. 오타 수정, 결측치 처리, 타입 변환.
- **Masking** — `900101-1234567` → `900101-*******`. PII 마스킹·암호화.
- **Join & Aggregation** — 주문+고객 결합, 일별 매출 합계 사전 계산.

**Load — 골든 레코드.**

- **Golden Record** = 조직 내 누구도 의심하지 않는 **단 하나의 진실(Single Source of Truth)**.
- **GIGO 방지** — "쓰레기를 넣으면 쓰레기가 나온다". 오염된 데이터 유입을 원천 차단.
- 요리 비유: **"냄비(DW)에 들어가기 전에 모든 손질을 마친다"** 는 위생적(품질 중심) 사고방식.

### 왜 원래 ETL이었나 — 하드웨어 제약

**이 덱에서 가장 좋은 부분이다.** ETL이 설계 철학이 아니라 **생존 전략**이었다고 설명한다.

20년 전 스토리지는 "금보다 비싼 자원"이었다. Teradata·Oracle 장비 증설은 "강남 아파트 한 채 값".

- **비용의 압박** — 1TB 증설이 거대한 예산 결재 사항. 엔지니어는 '용량 부족'의 공포와 싸웠다.
- **데이터 다이어트 강박** — 저장 전에 최대한 부피를 줄여야 했다.
- **결론** — **"비싼 저장소에 넣기 전에 정제·요약하는 ETL은 선택이 아닌 생존 전략이었다."**

### ETL 서버의 한계 — 병목

> ⚠️ **슬라이드 제목 오류:** 이 슬라이드는 "**ELT** 아키텍처의 한계 – 병목 현상"으로 되어 있지만
> 내용은 명백히 **ETL 서버**의 병목을 말한다("데이터 소스와 저장소 사이에 위치한 ETL 서버가
> 폭증하는 데이터 양을 감당하지 못해…"). 제목이 잘못 붙은 것으로 보인다.

- **SPOF** — ETL 서버가 멈추면 적재 불가
- **확장성 부족** — 데이터는 10배인데 서버는 그대로
- **처리 지연** — 수시간~수일 대기
- Black Friday 시나리오: 평소 20배 트래픽에 ETL 서버 CPU 100%, 데이터 유실 또는 분석 지연

### ELT를 가능케 한 두 가지 변화

**1. 클라우드 객체 저장소 — 스토리지 비용 99% 하락**

1GB 저장 비용이 커피 한 잔 값도 안 되는 수준(몇십 원 미만)으로 떨어졌다. S3·GCS·Azure Blob.

> 엔지니어들의 의문: **"저장소가 이렇게 싼데, 굳이 비싼 인력을 써가며 데이터를 줄여서 넣을 필요가
> 있을까?"**

**2. MPP (Massively Parallel Processing)**

저장소가 싸져도 계산이 느리면 소용없다. 과거 단일 서버(SMP) → 현재 수백~수천 대 병렬 처리.

- **무한한 확장성** — 노드를 10대→100대→1000대로 순식간에 (Scale-Out)
- **속도** — ETL 서버 한 대가 10시간 걸린 변환을 수백 대가 나눠 10분에
- 대표: **Snowflake · BigQuery · Redshift**

### ELT의 구조

```
Extract → Load (가공 없이 원본 그대로 즉시 적재) → Transform (필요한 시점에 DW 내부에서)
```

- 철학: **"Load First, Think Later"**
- 이사 비유: 일단 모든 짐을 박스째 새 집에 옮겨놓고, 편안한 환경에서 정리한다.
  **"트럭은 밖에서 기다리는데 짐 하나하나 닦고 있을 시간은 없다."**
- **In-DB Processing** — 변환을 위해 데이터를 밖으로 꺼내지 않는다.
  SQL 중심(`CREATE TABLE AS SELECT`·`MERGE`), 네트워크 egress/ingress 생략, DW 옵티마이저가
  실행 계획 자동 최적화.

### ELT의 강점 — 재현 가능성

**ETL은 들어오는 순간 가공해버려 원본이 사라진다. ELT는 원본이 그대로 보존된다 —
파이프라인의 타임머신.**

- **원본 불변(immutable)** — 어떤 로직을 적용하든 원본은 변하지 않는다
- **로직 변경 → 즉시 재계산** — 데이터를 다시 부을 필요 없이 SQL만 수정
- **"지난달 지표 다시 뽑아주세요"에 당황하지 않는다**

### ETL vs ELT 비교표

| ETL | 비교 항목 | ELT |
|---|---|---|
| 별도 ETL 서버 | 변환 수행 위치 | **DW 내부** |
| 느림 | 적재 속도 | 매우 빠름 |
| 정제 데이터만 | 데이터 보존 | **원본 + 정제** |
| 낮음 | 유연성·재현성 | 높음 |

### 언제 무엇을 — 결정 기준

**ETL을 써야 할 때 — 규제.** 금융·의료에서는 보안이 생명이고,
**민감 정보(PII)가 원본 그대로 클라우드에 올라가는 것은 법적으로 금지되거나 매우 위험하다.**

- GDPR·HIPAA·신용정보법 준수
- PII 마스킹 또는 **복호화 불가능한 단방향 암호화**
- 최소 권한의 원칙 — ETL 단계에서 선별적으로 민감 정보를 제거하고 적재
- **반드시 적재하기 전(Before Load)에 안전하게 가공해야 한다**

**ELT를 써야 할 때 — 민첩성.** 스타트업·이커머스·게임처럼 분석의 민첩성이 생명인 곳.

- 새 소스를 연결하는 즉시 쿼리 가능
- **스키마 온 리드** — 저장할 때가 아니라 읽을 때 구조를 정의. JSON 로그처럼 구조가 자주 변하는
  데이터에 유리
- 원본 보존 → 나중에 새 분석 기법이나 AI 모델이 등장했을 때 과거 데이터에서 새 가치 창출
- **"일단 데이터 다 모아! 로그 하나도 버리지 마!"**

### 현대 ELT 스택 (강의 제시)

| 단계 | 도구 |
|---|---|
| 수집 (Extract & Load) | **Fivetran**(완전 관리형) · **Airbyte**(오픈소스) |
| 웨어하우스 | **Snowflake** · **BigQuery** · **Redshift** |
| 변환 (Transform) | **dbt** (SQL 기반 모델링) |
| 오케스트레이션 | **Apache Airflow** |

## 기존 페이지와의 대조

- **일치** — ELT를 고르는 실질적 이유가 "원본이 남는다"라는 것.
  [[ETL and ELT]]가 랜드스케이프 가이드에서 얻은 결론과 정확히 같다. Fivetran·Airbyte·dbt도 동일.
- **보강(큼)** — **왜 ETL이 먼저였나**(스토리지 가격), **무엇이 바뀌어 ELT가 가능해졌나**
  (비용 99% 하락 + MPP), ETL 서버의 SPOF·병목, Extract의 실제 난이도와 "소스에 부하 주지 말라"
  원칙, **ETL을 여전히 써야 하는 조건(규제·PII)**. 랜드스케이프 가이드는 ETL을 고를 이유를 다루지
  않았다.
- **추가** — Golden Record, GIGO, schema-on-read, In-DB Processing.
