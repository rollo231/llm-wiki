# Java 면접 3 빈출 질문

[[인프런 Java 면접 강의]] Section 3(GC)의 부록 PDF다. 부록이라는 것은 제목의 "[GC]"가 Section 3 주제와 같아서 한 추론이다.
[[Java 면접 2 빈출 질문]]과 형식이 같다. 질문은 6개이고, 질문마다 **빈도 별점(⭐1~3)과 짧은 답 하나**가 붙는다. 등급 루브릭은 없다.
슬라이드 쪽 [[Java 면접 3 GC]]는 알고리즘·세대·컬렉터를 다룬다. 이 자료는 **GC의 정의와 장단점, OOM, 메모리 영역의 역사**를 다룬다.

## 요약

| # | 질문 | 빈도 | 답의 요지 | 자세히 |
|---|---|---|---|---|
| 1 | GC란 무엇인가 | ⭐⭐⭐ | 동적으로 할당한 힙 메모리 가운데 "어떤 변수도 가리키지 않게 된" 영역을 해제하는 기능 | [[가비지 컬렉션]] |
| 2 | GC의 장단점 | ⭐⭐⭐ | 장점: 누수 · 이중 해제 · 해제된 메모리 접근 같은 수동 관리 에러를 예방한다. 단점: 해제 시점을 알기 어렵고, 검사와 해제가 오버헤드다 | [[가비지 컬렉션]] |
| 3 | OOM의 종류 | ⭐ | 대표적으로 `Java heap space`와 `GC overhead limit exceeded` | [[가비지 컬렉션]] |
| 4 | 두 OOM의 차이와 발생 상황 | ⭐ | heap space는 새 객체를 만들 수 없을 때, overhead는 GC 뒤 새로 확보한 메모리가 2% 미만일 때 난다. 필자의 실험: 빠르게 할당하면 heap space, 천천히 많이 할당하면 overhead | [[가비지 컬렉션]] |
| 5 | PermGen과 Metaspace의 차이 | ⭐ | PermGen은 Java 8 이전의 "힙 안 메서드 영역"으로 클래스·메서드 메타데이터와 정적 변수를 담았다. Metaspace는 메타데이터만 담는 "OS가 관리하는 네이티브 메모리"이고, 정적 변수만 힙으로 갔다 | [[JVM 메모리 구조]] |
| 6 | 정적 변수는 GC 대상인가 | ⭐ | primitive 정적 변수는 객체가 아니라 대상이 아니고, 정적 객체는 참조를 잃으면 대상이 된다 | [[JVM 메모리 구조]] |

## 핵심

- **별점이 높은 두 질문(Q1 · Q2)은 정의와 장단점이다.** Section 2 부록과 같은 모양이다. 면접관은 첫 질문으로 개념의 경계부터 본다.
  세부(OOM 종류, PermGen)는 별 하나다. *(위키의 관찰 — 별점의 기준은 자료에 없다)*
- **Q1의 정의가 이 자료에서 가장 위험하다.** "어떤 변수도 가리키지 않는다"는 참조 카운팅의 기준이다. 이렇게 답하면 "순환 참조는
  어떻게 되나"라는 꼬리 질문이 바로 온다. 슬라이드의 Q1 · Q1-2(GC Root)와 이어서 **도달 가능성**으로 답해야 한다.
  → [[레퍼런스 카운팅과 마크 앤 스윕]]
- **Q5 · Q6은 한 질문의 두 면이다.** "정적 변수는 어디 있나"와 "언제 회수되나"는 둘 다 JDK 7에서 static 필드가 힙의 `Class` 객체로
  옮겨진 일로 답한다. 슬라이드 Q1-2의 "메서드 영역의 static 변수"도 같은 곳에서 정정된다. *(위키의 연결)* → [[JVM 메모리 구조]]
- **Q4의 필자 실험은 1차 자료에 없는 관찰이다.** 공식 문서는 `GC overhead limit exceeded`가 "살아 있는 데이터가 힙에 겨우 들어갈 때"
  난다고 설명한다. 가르는 것은 할당 속도가 아니라 **live set이 힙 상한에 얼마나 붙어 있는지**와 컬렉터 종류다. → [[객체 수명과 메모리 상한]]

## 주의·결함

외부 검증 결과다(2026-09-27). 대조한 1차 자료: JLS SE 21 §12.7, JEP 122, JDK-6962931 · JDK-7017732 · JDK-6990754 · JDK-8212084,
Oracle GC Tuning Guide JDK 26, Troubleshooting Guide JDK 8 · 21.

| 질문 | 자료의 서술 | 판정 | 정정이 있는 곳 |
|---|---|---|---|
| Q1 | 쓰레기 = 어떤 변수도 가리키지 않게 된 영역 | 단서 필요 — HotSpot은 GC Root에서 **도달할 수 있는지**로 판단한다. 순환 참조도 루트에서 닿지 않으면 회수된다. GC는 힙만 치우지도 않는다. 클래스 언로드로 Metaspace의 메타데이터도 해제된다 | [[가비지 컬렉션]] |
| Q2 | 장점에 "메모리 누수 예방" | 단서 필요 — 해제를 잊는 누수는 막는다. 필요 없어진 참조를 계속 들고 있는 누수는 막지 못한다. Oracle 가이드가 Java의 누수를 바로 그렇게 정의한다 | [[가비지 컬렉션]] |
| Q2 | 단점 = 해제 시점 불명 · 오버헤드 | 단서 필요 — STW 멈춤, GC 스레드의 CPU, 힙 여유분만큼 늘어나는 메모리가 빠졌다 | [[가비지 컬렉션]] |
| Q3 | OOM 종류 = heap space · overhead | 단서 필요 — Oracle 가이드는 detail message 7종을 문서화한다(Metaspace · 배열 크기 · 네이티브 등) | [[가비지 컬렉션]] |
| Q4 | overhead = GC 뒤 확보한 메모리 2% 미만 | 단서 필요 — 조건이 반쪽이다. **GC에 시간의 98% 이상**을 쓰는 조건과 함께 성립해야 하고, 연속 5번이어야 한다. 원래 Parallel 컬렉터의 기능이다. G1은 **JDK 26**부터 구현했다(JDK-8212084) | [[가비지 컬렉션]] |
| Q4 | 빠른 할당 → heap space, 느린 할당 → overhead | 단서 필요 — 필자의 실험일 뿐이고 공식 설명과 기준이 다르다(위 핵심 절) | [[객체 수명과 메모리 상한]] |
| Q5 | PermGen에 정적 변수 | 단서 필요 — **JDK 6까지만** 맞다. JDK 7에서 intern 문자열과 static 필드는 힙으로, 심볼은 네이티브 메모리로 이미 옮겨졌다 | [[JVM 메모리 구조]] |
| Q5 | PermGen은 "힙 안"의 메서드 영역 | 단서 필요 — GC가 관리하는 한 세대였지만 `-XX:MaxPermSize`로 Java 힙(`-Xmx`)과 따로 제한됐다 *(JDK 6 문서 원문은 열지 못해 신뢰도 중간)* | [[JVM 메모리 구조]] |
| Q5 | Metaspace = "OS에서 관리하는" 네이티브 메모리 | 틀림 — OS가 아니라 **JVM이** 관리한다. `mmap`으로 받아 클래스 로더별 chunk로 나눈다. 기본 상한은 없다 | [[JVM 메모리 구조]] |
| Q5 | "정적 변수**만** 힙에 저장" | 틀림 — intern 문자열도 힙으로 갔다(JEP 122가 둘을 함께 적는다) | [[JVM 메모리 구조]] |
| Q6 | primitive 정적 변수는 GC 대상이 아니다 | 단서 필요 — primitive static 필드도 힙의 `Class` 객체 안에 있다. 따로 회수되지 않을 뿐, **클래스가 언로드될 때** 함께 사라진다 | [[JVM 메모리 구조]] |
| Q6 | 정적 객체는 참조를 잃으면 GC 대상 | 단서 필요 — 필드를 `null`이나 다른 값으로 바꿔야 대상이 된다. 그러지 않으면 클래스가 언로드될 때까지 산다. 부트스트랩 로더가 올린 클래스는 언로드되지 않는다(JLS §12.7). 정적 컬렉션이 누수의 전형인 이유다 | [[객체 수명과 메모리 상한]] |
