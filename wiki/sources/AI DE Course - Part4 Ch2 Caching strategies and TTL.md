## 출발점 — hit가 없으면 캐시는 손해다

| | 뜻 |
|---|---|
| **Cache Hit** | 요청한 데이터가 Redis에 존재 → 원본 조회 없이 즉시 반환 |
| **Cache Miss** | Redis에 없어 원본 저장소를 다시 조회 |

> ⭐ **miss가 많을 때의 문제 5가지:**
> - Redis 조회 비용이 **추가된다**
> - 원본 저장소도 **여전히** 조회한다
> - **전체 응답 경로가 길어진다**
> - DB 부하가 줄지 않는다
> - 캐시 메모리만 사용하고 성능 효과는 작다
>
> **캐시는 잘못 쓰면 "효과가 없는" 게 아니라 "손해"다.** 이 점을 명시하는 캐싱 자료가 의외로 드물다.

## 두 축

| 축 | 질문 | 전략 |
|---|---|---|
| **읽기 전략** | 데이터를 조회할 때 캐시를 어떻게 사용할 것인가 | Cache-Aside · Read-Through · **Refresh-Ahead** |
| **쓰기 전략** | 원본 데이터가 변경될 때 캐시를 어떻게 갱신·삭제할 것인가 | Write-Through · Write-Behind |

> ⚠️ **Refresh-Ahead는 목록에만 있고 본문에서 설명되지 않는다.** 무효화 절의 "읽기 지연을 줄이고
> 싶으면 갱신 또는 refresh-ahead" 한 줄이 전부다. (소단원 1의 **Prefetching**이 사실상 같은
> 아이디어인데 이름이 다르게 붙었다.)

## 읽기 전략

### Cache-Aside (Lazy Loading)

애플리케이션이 캐시를 먼저 조회 → 있으면 반환 → 없으면 원본 조회 후 캐시에 저장.

| 장점 | 단점 |
|---|---|
| 필요한 데이터만 캐시에 올라감 | **첫 요청은 항상 miss** |
| 구현이 비교적 단순 | 배포 직후나 Redis 재시작 직후 **cold cache** |
| 읽기 요청이 많은 시스템에 적합 | **동시에 같은 key가 miss되면 원본으로 요청이 몰릴 가능성** (thundering herd) |
| **캐시 장애 시 원본으로 우회하기 쉬움** | 원본 변경 시 무효화 전략이 별도로 필요 |

**예시 — 상품 상세 조회:**

```
1. GET product:detail:{product_id}
2. Redis hit → 상품 상세 정보 즉시 반환
3. Redis miss → DB 조회 → Redis에 TTL과 함께 저장 → 응답
```

예시 key `product:detail:10001`, TTL **5분 ~ 30분**.

> ⭐ **주의할 점 — 변경 주기가 다른 데이터를 한 key에 묶지 마라:**
> **"가격, 재고, 쿠폰 적용 여부처럼 실시간성이 높은 데이터는 같은 key에 섞어 넣지 않는 편이 안전.
> 변경 주기가 다른 데이터를 하나의 캐시 객체로 묶으면 TTL 설계가 어려워진다."**
>
> 이 조언이 이 소단원에서 가장 실무적이다. "상품 상세"라는 단일 객체 안에 초 단위로 바뀌는 재고와
> 며칠씩 안 바뀌는 설명이 함께 있으면 **TTL을 재고 기준(짧게)으로 잡을 수밖에 없고**, 그러면 설명
> 필드까지 초 단위로 다시 조회된다.

### Read-Through

캐시 **계층**이 miss 처리와 원본 조회를 감싼다. 애플리케이션은 캐시에만 요청한다.

| | Cache-Aside | Read-Through |
|---|---|---|
| miss 처리 주체 | **애플리케이션** | **캐시 계층** |

| 장점 | 단점 |
|---|---|
| 애플리케이션 코드가 단순 | 캐시 계층 구현이 복잡해짐 |
| **캐시 적재 로직 중앙화** | 원본 조회 로직이 캐시 계층에 들어감 |
| 여러 서비스가 같은 캐시 로딩 규칙 공유 용이 | **장애 시 추적 경로가 길어짐** |

## 쓰기 전략

### Write-Through

쓰기 시점에 캐시와 원본 저장소를 **함께** 갱신. 두 작업이 완료되면 응답.

| 장점 | 단점 |
|---|---|
| 쓰기 직후 캐시가 최신 상태에 가까움 | **쓰기 경로가 느려짐** |
| 읽기에서 stale data 가능성 감소 | **캐시와 DB 중 하나만 성공하면 보상 처리 필요** |
| 자주 읽히는 데이터라면 이후 read hit 안정적 | 자주 읽히지 않는 데이터까지 캐시에 저장될 수 있음 |
| | 쓰기 트래픽이 많으면 캐시 갱신 비용 증가 |

**예시 — 사용자 프로필:** 닉네임/이미지 변경 직후 바로 반영되어야 하고, 조회 트래픽이 쓰기보다 훨씬
많은 경우. `DB 업데이트 → Redis user:profile:{user_id} 갱신 → 응답`.

### Write-Behind (Write-Back)

먼저 캐시에 쓰고 사용자에게 빠르게 응답. **별도 worker가 변경 내용을 모아 원본에 비동기 반영.**

| 장점 | 단점 |
|---|---|
| 쓰기 응답 시간이 짧다 | ⚠️ **Redis 장애 시 DB에 반영되지 않은 데이터가 유실될 수 있다** |
| 짧은 시간에 많은 쓰기를 흡수 | 비동기 반영 실패에 대한 재처리 구조 필요 |
| 여러 변경을 묶어서 반영 가능 | 원본과 캐시 간 일시적 불일치 |
| | ⭐ **정산·결제·주문 같은 강한 정합성 데이터에는 위험** |

> ⚠️ **이 슬라이드가 [[AI DE Course - Part4 Ch1 CAP theorem and system limits]]와 충돌한다.**
> Ch1-3은 Redis를 **CP 시스템 / "금융 거래, 결제 시스템 등 데이터의 정확성이 생명인 경우에 적합"**
> 으로 분류했는데, 여기서는 **"결제 데이터에는 위험"** 이라고 말한다. **같은 파트, 65페이지 차이.**

## ⭐ 캐싱 무효화 전략

> **"캐시 무효화는 캐싱에서 가장 어려운 부분."**

| 방식 | 동작 | 특징 |
|---|---|---|
| **1. 삭제** | 원본 변경 후 관련 key를 삭제 → 다음 조회에서 miss 발생 후 재적재 | 구현 단순, 다음 조회에 miss 비용 |
| **2. 갱신** | 원본 변경 후 key를 새 값으로 갱신 | 쓰기 직후 읽기 최신성이 좋아짐 |
| **3. 짧은 TTL** | 명시적 삭제 없이 자연 만료 | 구현 단순, **stale data 허용이 필요** |

**선택 기준:**

- 최신성이 중요하면 → 삭제 또는 갱신
- 약간 오래된 데이터가 허용되면 → TTL 중심
- 쓰기 로직이 복잡하면 → 삭제 후 재적재
- 읽기 지연을 줄이고 싶으면 → 갱신 또는 refresh-ahead

> ⭐ **"캐시를 지우지 않으면 오래된 값을 줄 수 있고, 너무 자주 지우면 hit ratio가 떨어진다."**

## ⭐ TTL 설계 — 권장값 표

| 데이터 유형 | 권장 TTL | 근거 |
|---|---|---|
| **상품 가격** | 5초 ~ 30초 | 민감도 최상. 결제 직전 가격이 달라지면 안 되므로 아주 짧게 가져가되, 찰나의 반복 조회 부하는 막는 용도 |
| **상품 설명** | 10분 ~ 1시간 | 정적 데이터. **변경 시 캐시를 강제로 삭제(Evict)하는 전략과 병행하기 좋음** |
| **카테고리 목록** | 1시간 ~ 24시간 | 변동성 최저. **DB 조인이 많이 필요한 무거운 쿼리인 경우가 많아 길게 잡는 것이 유리** |
| **사용자 세션** | 30분 ~ 수 시간 | 활동성 기반. **조회할 때마다 TTL을 갱신하는 'Sliding Window' 전략이 필수** |
| **추천 결과** | 수초 ~ 수분 | 개인화 & 연산량. 클릭에 따라 계속 바뀌어야 하지만 추천 엔진 부하를 막기 위해 짧은 캐싱 |
| **랭킹 데이터** | 10초 ~ 1분 | 실시간성 체감. "순위가 바뀌고 있구나"를 느끼게 하면서도 실시간 집계 쿼리 폭주를 막는 선 |
| **실험 설정값** | 수 분 ~ 수십 분 | A/B 테스트 설정 등. 자주 안 바뀌지만 **잘못된 설정 시 긴급 수정이 필요하므로 너무 길지 않게** |

> ⭐ **표의 "근거" 열이 이 소단원의 진짜 가치다.** 숫자만 있으면 다른 도메인에 옮길 수 없는데,
> **"왜 이 값인가"** 가 붙어 있어서 판단 규칙으로 쓸 수 있다:
> - 민감도(가격) → 짧게 + 반복 조회 부하만 막기
> - 무거운 쿼리(카테고리) → 길게
> - 활동성(세션) → Sliding Window
> - **긴급 수정 가능성(실험 설정) → TTL 상한을 롤백 시간으로 잡기**
>
> 마지막 항목이 특히 좋다 — **TTL이 곧 "잘못된 설정이 살아있는 최대 시간"** 이라는 관점.

### TTL의 양면

| TTL이 짧을 때 | TTL이 길 때 |
|---|---|
| 데이터 신선도 ↑ | cache hit ↑ |
| cache miss ↑ | 원본 저장소 부하 ↓ |
| 원본 저장소 부하 ↑ | **오래된 데이터 제공 가능성 ↑** |

> **"좋은 TTL 설계는 성능과 신선도 사이의 타협."**

## 강의가 빠뜨린 것

**캐싱 실무의 3대 실패 모드 중 둘이 없다.**

- ⚠️ **Cache stampede / thundering herd 대응책이 없다.** Cache-Aside의 단점으로 *"동시에 같은 key가
  miss되면 원본으로 요청이 몰릴 가능성"* 을 언급하고 소단원 2에서 *"캐시 만료 시 원본 저장소 폭주"*
  를 위험으로 들지만, **대응(뮤텍스/single-flight, 확률적 조기 만료, TTL jitter)은 한 줄도 없다.**
- ⚠️ **TTL jitter가 없다.** 위 표대로 "카테고리 목록 1시간"을 일괄 적용하면 **같은 시각에 대량 만료**
  가 일어난다. 만료 시각을 흩뜨리는 것이 표준 대응인데 언급이 없다.
- ⚠️ **negative caching(없음을 캐싱하기)이 없다.** cache penetration — 존재하지 않는 key를 반복
  조회해 매번 DB를 때리는 패턴에 대한 대응이 빠져 있다.
