# Java 면접 5 객체지향 프로그래밍

[[인프런 Java 면접 강의]]의 Section 5. 주 질문 4개(캡슐화 · 상속 · 다형성 · 인터페이스와 추상 클래스)에 꼬리 질문이 하나나 둘씩 붙는다. 앞의 세 섹션(JVM·GC·동시성)은 런타임이 어떻게 도는지를 물었고, 이 섹션은 코드를 어떻게 설계하는지를 묻는다. 네 질문은 모두 변경에 얼마나 유연한지를 묻고, 답의 등급은 대개 결합도와 OCP를 말하는지로 갈린다.

## 요약

질문마다 Gold 답의 요지와, 자료의 "이유"가 짚은 아래 등급의 빈칸을 적는다.

### Q1. 캡슐화가 무엇이고, 왜 중요한가요? (p77–79)

- Gold: 데이터와 메서드를 묶고 접근 제어자로 외부 접근을 제한해 정보 은닉을 이룬다. 중요한 이유는 내부 구현이 바뀌어도 외부 코드가 영향을 받지 않기 때문이다. 예를 들어 내부의 ArrayList를 LinkedList로 바꿔도 외부는 공개 메서드만 쓴다.
- 등급을 가른 것: Bronze는 "묶는다"만 외웠고 정보 은닉을 말하지 않는다. Silver의 "객체 내부 보호"는 추상적이고, 실질적 이점(변경의 격리)이 없다.

#### Q1-1. getter/setter를 무분별하게 만들면 어떤 문제가 있나요? (p80–82)

- Gold: ① 내부 상태가 노출되어 캡슐화가 깨진다. ② setter로 외부가 상태를 마음대로 바꾸므로 객체가 수동적이 된다. 해결책은 `setBalance()` 대신 `deposit()`·`withdraw()` 같은 의미 있는 행동 메서드를 두는 것이다.
- 등급을 가른 것: Bronze의 "지저분해진다"는 막연하다. Silver는 캡슐화 위반까지만 말하고, 객체가 수동적이 된다는 점과 해결책이 없다.

### Q2. 상속이 무엇이고, 언제 사용하나요? (p83–85)

- Gold: 상속은 객체 사이의 관계를 만드는 것이고, 주로 다형성을 구현하려고 쓴다. 코드 재사용은 덤이다. is-a 관계가 분명하고 앞으로 변할 일이 거의 없을 때 쓴다.
- 등급을 가른 것: Bronze와 Silver는 "물려받는다", "코드 재사용"만 말하고 다형성과 타입 공유를 빠뜨렸다.

#### Q2-1. 상속의 단점은 무엇인가요? (p86–88)

- Gold: ① 하위 클래스가 상위 클래스의 구현에 강하게 결합되어, 상위의 변경이 하위로 번진다. ② 오버라이딩으로 기능을 확장하려면 상위의 내부 구현을 알아야 하므로 캡슐화가 깨진다.
- 등급을 가른 것: Bronze의 "복잡해진다"는 막연하고 구체적인 문제가 없다. (Silver 답은 없다.)

#### Q2-2. 상속과 조합(컴포지션)의 차이를 설명해주세요 (p89–91)

- Gold: 상속은 is-a 관계로 다형성을 구현한다. 조합은 has-a 관계로, 다른 객체를 필드로 두고 그 메서드를 쓸 뿐 다형성과는 관계가 없다. 조합은 결합도가 낮아 유연하므로, is-a가 분명하지 않으면 조합을 고른다.
- 등급을 가른 것: Bronze에는 "물려받는다 vs 포함한다"라는 표현만 있다. Silver는 결합도까지 말했지만, 다형성을 구현하는지 여부라는 근본적인 차이를 빠뜨렸다.

### Q3. 다형성이 무엇이고, 왜 필요한가요? (p92–94)

- Gold: 한 타입에 여러 종류의 객체를 대입할 수 있다는 것이다. 구현 방법은 오버로딩과 오버라이딩이다. 새 클래스를 추가해도 기존 코드를 고칠 필요가 없어서 OCP를 지킬 수 있다.
- 등급을 가른 것: Bronze는 사전적 정의("여러 형태")뿐이다. Silver는 예시(Animal에 Cat·Dog)까지 들었지만 OCP를 빠뜨렸다.
- ⚠️ 오버로딩은 자료 자신의 정의("한 타입에 여러 객체")를 구현하지 않는다([[다형성]]).

#### Q3-1. instanceof 키워드를 사용하면 어떤 문제가 있나요? (p95–97)

- Gold: ① 호출하는 쪽이 타입을 직접 확인하므로 다형성을 쓰는 의미가 없어진다. ② 타입이 늘 때마다 분기를 고쳐야 해서 OCP를 어긴다. ③ 런타임에 타입을 확인하는 성능 오버헤드가 있고, 상속 계층이 깊을수록 모든 부모 타입을 확인해야 해서 느려진다.
- 등급을 가른 것: Silver는 ①과 ②를 말했지만 OCP라는 이름과 런타임 성능을 빠뜨렸다.
- ⚠️ ③은 HotSpot 구현과 맞지 않는다(클래스 판정은 상수 시간이다). 최신 Java의 패턴 매칭도 이 주장과 반대 방향이다([[다형성]]).

### Q4. 인터페이스와 추상 클래스의 차이는 무엇인가요? (p98–100)

- Gold: ① 인터페이스는 상태를 가질 수 없고, 추상 클래스는 가질 수 있다. ② 인터페이스는 다중 구현이 되고, 추상 클래스는 단일 상속만 된다. ③ 인터페이스의 모든 메서드는 public이고, 추상 클래스는 접근 제어자를 자유롭게 쓴다.
- 등급을 가른 것: Silver는 구현 유무와 다중 구현을 말했지만 상태를 가질 수 있는지를 빠뜨렸다.
- ⚠️ ③은 Java 9부터 틀리다(private 인터페이스 메서드). "상태 없음"에도 상수라는 예외가 있다([[인터페이스와 추상 클래스]]).

#### Q4-1. 언제 인터페이스를 쓰고, 언제 추상 클래스를 쓰나요? (p101–103)

- Gold: 기본은 인터페이스 + default 메서드다. 다중 구현이 되고 상태가 없어 결합도가 낮다. 추상 클래스는 상태를 의미 있게 써야 할 때 쓴다. 하위 클래스들이 공통 필드를 쓰거나, 템플릿 메서드 패턴처럼 공통 로직을 상태와 함께 공유할 때다.
- 등급을 가른 것: Silver는 default 메서드와 "상태를 공유해야 하는 구체 상황"을 빠뜨렸다.
- Silver 답의 "인터페이스는 has-a, 추상 클래스는 is-a"는 이상한 구분인데, 이유 칸도 Gold도 이를 짚지 않고 그냥 넘어간다([[인터페이스와 추상 클래스]]).

## 핵심

- 네 질문의 채점 기준은 "변경이 어디까지 번지는가" 하나로 모인다. 캡슐화는 변경을 객체 안에 가두고, 상속은 변경을 하위 클래스로 번지게 하고, 조합은 그 번짐을 끊고, 다형성은 변경을 새 클래스 추가로 바꾼다. 이 정리는 위키의 관찰이다([[캡슐화]] · [[상속과 조합]] · [[다형성]]).
- "상속은 재사용보다 다형성을 위한 것"이라는 관점을 자료는 끝까지 유지한다. Q2와 Q2-2의 Gold가 모두 그렇게 말한다. 다만 이것은 하나의 관점이지 정의가 아니다([[상속과 조합]]).
- getter/setter 대신 행동 메서드를 두라는 답은 "Tell, Don't Ask"를 이름 없이 설명한 것이다([[캡슐화]]).
- 인터페이스를 기본으로 하고 상태가 필요할 때만 추상 클래스를 쓰라는 답은 Java 8의 default 메서드 이후 표준적인 답이다([[인터페이스와 추상 클래스]]).
- instanceof 비판은 패턴 매칭 instanceof(JDK 16)와 sealed 타입(JDK 17), switch 패턴 매칭(JDK 21)이 들어오기 전의 관점이다. 지금의 Java는 sealed 타입과 패턴 매칭으로 타입을 보고 분기하는 스타일을 공식 지원한다. 어느 쪽이 맞는지는 타입이 늘어나는 코드인지, 연산이 늘어나는 코드인지에 따라 달라진다([[다형성]]).

## 주의·결함

- ⚠️ 다형성의 구현 방법으로 오버로딩을 꼽은 것은 자료 자신의 정의와 모순된다(p94, [[다형성]]).
- ⚠️ "상속 계층이 깊을수록 instanceof가 느리다"는 틀렸다(p97, [[다형성]]).
- ⚠️ "인터페이스의 모든 메서드는 public"은 Java 9부터 틀리다(p100, [[인터페이스와 추상 클래스]]).
- 문서 안의 결함: Q1-1 Gold는 "세 가지 문제가 발생합니다"라고 해 놓고 두 가지만 든다(p82). 세 번째 자리에는 해결책이 온다.
- Q2-1은 Bronze만 있고 Silver가 없다. Q3-1·Q4·Q4-1은 Silver만 있고 Bronze가 없다. 질문마다 등급 예시가 다르다.
- Q3-1 Gold 둘째 항목의 "로직이 바뀜 때마다"는 "바뀔 때마다"의 오탈자다.
- 슬라이드는 OCP 말고 다른 SOLID 원칙(LSP 등)은 언급하지 않는다. 다섯 원칙은 같은 섹션의 부록 Q12에 있다([[Java 면접 5 빈출 질문]] · [[SOLID 원칙]]). 상속의 단점(Q2-1)은 LSP로 설명하면 더 탄탄해진다는 것은 위키의 관찰이다.
