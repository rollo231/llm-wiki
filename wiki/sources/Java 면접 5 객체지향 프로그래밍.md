# Java 면접 5 객체지향 프로그래밍

[[인프런 Java 면접 강의]]의 Section 5. 주 질문 4개(캡슐화 · 상속 · 다형성 · 인터페이스와 추상 클래스)에 꼬리 질문이 하나나 둘씩 붙는다. 앞의 세 섹션(JVM·GC·동시성)이 "런타임이 어떻게 도는가"였다면, 여기서는 "코드를 어떻게 설계하는가"를 묻는다. 네 질문을 관통하는 축은 **변경에 유연한가**이고, 답을 가르는 기준은 대개 결합도와 OCP다.

## 요약

질문마다 Gold 답의 요지와, 자료의 "이유"가 짚은 아래 등급의 빈칸을 적는다.

### Q1. 캡슐화가 무엇이고, 왜 중요한가요? (p77–79)

- **Gold** — 데이터와 메서드를 묶고 접근 제어자로 외부 접근을 제한해 **정보 은닉**을 달성한다. 중요한 이유는 내부 구현이 바뀌어도 외부 코드가 영향을 받지 않기 때문이다. 예: 내부의 ArrayList를 LinkedList로 바꿔도 외부는 공개 메서드만 쓴다.
- **등급을 가른 것** — Bronze는 "묶는다"만 외웠고 정보 은닉이 없다. Silver는 "객체 내부 보호"가 추상적이고 실질적 이점(변경의 격리)이 없다.

#### Q1-1. getter/setter를 무분별하게 만들면 어떤 문제가 있나요? (p80–82)

- **Gold** — ① 내부 상태가 노출되어 캡슐화가 깨진다. ② setter로 외부가 상태를 마음대로 바꾸므로 객체가 **수동적**이 된다. 해결책은 `setBalance()` 대신 `deposit()`·`withdraw()` 같은 의미 있는 행동 메서드다.
- **등급을 가른 것** — Bronze "지저분해진다"는 막연하다. Silver는 캡슐화 위반까지만 말하고 객체의 수동성과 해결책이 없다.

### Q2. 상속이 무엇이고, 언제 사용하나요? (p83–85)

- **Gold** — 상속은 객체 사이의 관계를 구축하는 것으로, **주로 다형성을 구현하기 위해** 쓴다. 코드 재사용은 부가적인 장점이다. is-a 관계가 명확하고 향후 변화가 거의 없을 때 쓴다.
- **등급을 가른 것** — Bronze·Silver는 "물려받는다"·"코드 재사용"만 말하고 다형성·타입 공유를 빠뜨렸다.

#### Q2-1. 상속의 단점은 무엇인가요? (p86–88)

- **Gold** — ① 하위 클래스가 상위 클래스 구현에 강하게 결합되어 상위의 변경이 하위에 번진다. ② 오버라이딩으로 기능을 확장하려면 상위의 내부 구현을 알아야 하므로 캡슐화가 깨진다.
- **등급을 가른 것** — Bronze "복잡해진다"는 막연하고 구체적 문제가 없다. (Silver 답은 없다.)

#### Q2-2. 상속과 조합(컴포지션)의 차이를 설명해주세요 (p89–91)

- **Gold** — 상속은 is-a로 다형성을 구현한다. 조합은 has-a로, 다른 객체를 필드로 두고 그 메서드를 쓸 뿐 다형성과는 관계가 없다. 조합이 결합도가 낮아 유연하므로 is-a가 명확하지 않으면 조합을 선호한다.
- **등급을 가른 것** — Bronze는 "물려받는다 vs 포함한다" 표현만 있다. Silver는 결합도까지 말했지만 **다형성 구현 여부**라는 본질적 차이를 빠뜨렸다.

### Q3. 다형성이 무엇이고, 왜 필요한가요? (p92–94)

- **Gold** — 하나의 타입에 여러 가지 객체를 대입할 수 있다는 것. 구현 방법은 오버로딩·오버라이딩. 새 클래스를 추가해도 기존 코드를 고칠 필요가 없어 **OCP**를 지킬 수 있다.
- **등급을 가른 것** — Bronze는 사전적 정의("여러 형태")뿐이다. Silver는 예시(Animal에 Cat·Dog)까지 들었지만 OCP를 빠뜨렸다.
- ⚠️ 오버로딩은 자료 자신의 정의("한 타입에 여러 객체")를 구현하지 않는다. → [[다형성]]

#### Q3-1. instanceof 키워드를 사용하면 어떤 문제가 있나요? (p95–97)

- **Gold** — ① 호출하는 쪽이 타입을 직접 확인하므로 다형성의 의미가 사라진다. ② 타입이 늘 때마다 분기를 고쳐야 해서 OCP를 위반한다. ③ 런타임 타입 확인의 성능 오버헤드가 있고, 상속 계층이 깊을수록 모든 부모 타입을 확인해야 해서 느려진다.
- **등급을 가른 것** — Silver는 ①·②를 말했지만 OCP라는 이름과 런타임 성능을 빠뜨렸다.
- ⚠️ ③은 HotSpot 구현과 어긋난다(클래스 판정은 상수 시간). 최신 Java의 패턴 매칭도 반대편에 있다. → [[다형성]]

### Q4. 인터페이스와 추상 클래스의 차이는 무엇인가요? (p98–100)

- **Gold** — ① 인터페이스는 상태를 가질 수 없고 추상 클래스는 가질 수 있다. ② 인터페이스는 다중 구현, 추상 클래스는 단일 상속. ③ 인터페이스의 모든 메서드는 public이고 추상 클래스는 접근 제어자가 자유롭다.
- **등급을 가른 것** — Silver는 구현 유무와 다중 구현을 말했지만 **상태 보유 여부**를 빠뜨렸다.
- ⚠️ ③은 Java 9부터 틀리다(private 인터페이스 메서드). "상태 없음"도 상수는 예외다. → [[인터페이스와 추상 클래스]]

#### Q4-1. 언제 인터페이스를 쓰고, 언제 추상 클래스를 쓰나요? (p101–103)

- **Gold** — 기본은 **인터페이스 + default 메서드**. 다중 구현이 되고 상태가 없어 결합도가 낮다. 추상 클래스는 상태를 유의미하게 써야 할 때 — 하위 클래스가 공통 필드를 쓰거나, 템플릿 메서드 패턴처럼 공통 로직을 상태와 함께 공유할 때.
- **등급을 가른 것** — Silver는 default 메서드와 "상태를 공유해야 하는 구체 상황"을 빠뜨렸다.
- Silver 답의 "인터페이스는 has-a, 추상 클래스는 is-a"는 이상한 구분인데, 이유 칸도 Gold도 이를 짚지 않고 조용히 버린다. → [[인터페이스와 추상 클래스]]

## 핵심

- **네 질문의 채점 기준은 하나다 — "변경이 어디까지 번지는가".** 캡슐화는 변경을 객체 안에 가두고, 상속은 변경을 하위로 번지게 하고, 조합은 그 번짐을 끊고, 다형성은 변경을 새 클래스 추가로 바꾼다. *(위키의 관찰)* → [[캡슐화]] · [[상속과 조합]] ·[[다형성]]
- **"상속은 재사용이 아니라 다형성을 위한 것"은 자료가 일관되게 미는 관점이다** — Q2·Q2-2의 Gold가 모두 그렇게 말한다. 한 관점이지 정의가 아니다. → [[상속과 조합]]
- **getter/setter 대신 행동 메서드** — "Tell, Don't Ask"를 이름 없이 설명한다. → [[캡슐화]]
- **인터페이스 선호 + 추상 클래스는 상태가 필요할 때만** — Java 8 default 메서드 이후의 표준적인 답이다. → [[인터페이스와 추상 클래스]]
- **instanceof 비판은 Java 16 이전의 관점이다** — 지금 Java는 sealed 타입과 패턴 매칭으로 "타입을 보고 분기하는" 스타일을 공식 지원한다. 어느 쪽이 맞는지는 "타입이 늘어나나, 연산이 늘어나나"로 갈린다. → [[다형성]]

## 주의·결함

- ⚠️ **다형성 구현 방법에 오버로딩을 꼽는 것은 자료의 정의와 모순된다**(p94). → [[다형성]]
- ⚠️ **"상속 계층이 깊을수록 instanceof가 느리다"는 틀리다**(p97). → [[다형성]]
- ⚠️ **"인터페이스의 모든 메서드는 public"은 Java 9부터 틀리다**(p100). → [[인터페이스와 추상 클래스]]
- **문서 안 결함** — Q1-1 Gold가 "세 가지 문제가 발생합니다"라고 해 놓고 두 가지만 든다(p82). 세 번째 자리에는 해결책이 온다.
- Q2-1은 Bronze만 있고 Silver가 없다. Q3-1·Q4·Q4-1은 Silver만 있고 Bronze가 없다. 등급 표본이 질문마다 다르다.
- Q3-1 Gold 둘째 항목의 "로직이 바뀜 때마다"는 오탈자다("바뀔 때마다").
- 자료는 OCP 외의 SOLID 원칙(LSP 등)을 부르지 않는다. 상속의 단점(Q2-1)은 LSP로 설명하면 더 단단하다. *(위키의 관찰)*
